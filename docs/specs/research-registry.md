# Spec: Research-experiment registry (runs that are not backtests)

**Status:** Draft  ·  **Issue:** #661  ·  **Related:** [charter](../charter.md) (stop criterion: an untracked run halts the phase; principle 2), [ADR 0005](../decisions/0005-objective-benchmark-stop-criteria.md) (integrity criterion; "no id, no run"), [ADR 0008](../decisions/0008-llm-role.md) (points 1 to 3: the registry records runs, it authorizes nothing), [backtest spec](backtest.md) reqs 8 to 12 (the trial registry this one sits beside; req 8 and the `trial_results` table amended by plan task T79b below), [strategy-lab spec](strategy-lab.md) (draft; also amends req 8 and `trials`; sequencing in req 9), [trial-registry note](../research/trial-registry.md), [research program](../ways-of-working/research-program.md) (§4 item 4 trial budgets, §6 `TP-` claims), [claims register](../research/claims.toml), [hypothesis backlog](../research/hypothesis-backlog.md) (B5, B8), [ML validation brief](../research/2026-10-03-ml-validation-methodology-brief.md) (§2 governance, §3 splits, §4 discipline, §8.1 E1, §10 the proposal this spec answers), [annotation protocol](../research/2026-10-03-disclosure-annotation-protocol.md) (§7 label storage, §10 step 6 the interim log), [prospective feature spec](../research/2026-10-03-prospective-semantic-feature-spec.md) (§3 version objects, §7 immutability), development-process domain rules 1 to 3

## Problem & why now

The store's registry (`hypotheses`, `trials`, `trial_results`, schema version 3) records one thing: a run of the backtest engine under a registered hypothesis. Every column assumes an equity curve: a cost level, a Sharpe, a rebalance row. The 2026-10-03 research program proposes runs that are not that: an annotation-agreement analysis (protocol §8), classifier benchmarks on dev, calibration and sealed test splits (brief §5), the E1 regression of revenue-growth deceleration on a disclosure label (brief §8.1), feature studies of rank ICs and quantile spreads (brief §9), robustness and drift probes (brief §5.8, prospective spec §8). None has a home. The protocol's answer is an "interim append-only log named on #618"; the brief's is "experiments that need registration wait". The charter's stop criterion does not distinguish: any untracked run halts the phase, and ADR 0005 says a run without an id must not happen. So before the first agreement run or regression, the registry has to exist, or the pilot stalls at protocol step 6 and B5 and E1 cannot start.

**Why a new spec rather than an amendment of the backtest spec.** The two registries share one principle (register, then run; append only; count everything; one holdout spend) and one store, but not one shape. A backtest trial is defined by an engine window and a frozen parameter set, and its result is a set of metrics with the deflated Sharpe inputs. A research run is defined by a kind, a dataset version, a split, a configuration and a primary metric, and its holdout is a sealed split or a family's holdout dates rather than its own window. Forcing both into `trials` would make every column nullable by kind, and the backtest spec is one owner run (T45b) from Shipped; an amendment that loosens its tables now would invite the drift it was written to stop. The backtest spec is amended in exactly one place, req 8's trial count and the `trial_results` table, by plan task T79b below, so that a research run on return data raises the family's N like any other look at the data.

**Why in the runtime store, not a separate research store** (the brief §10 recommends a separate one; open question 1 asks the owner to confirm). The family's N must be one query that cannot lose rows: a second database file can be missing, moved or stale, and a backtest that silently counted N without the research runs would be the exact failure ADR 0005's integrity criterion names. The registry rows are run metadata and code-computed statistics, not model outputs and not facts: nothing in them is read by the decision path, and req 13 makes that a test. The research **data** (label exports, feature records, model inference records, raw responses) stay outside the runtime store, in the research store the prospective spec §2 preconditions require, and the registry points at them by content hash (req 11). That keeps ADR 0008 option 4 intact: no model-produced value enters the store as a fact.

## Users & usage

- **The owner** writes an experiment file under `docs/experiments/`, merges it, runs `tradepartner experiment register <file>`, and runs the analysis command of the experiment's kind (each analysis is its own spec; this spec fixes what they must call). He reads the research view on the dashboard and records the verdict as a `TP-` claim (research program §6). Only the owner spends a protected window, amends a budget, or runs anything against the real store (CLAUDE.md rule 9); an agent cannot, because an agent never runs on the real store and every run on another store file is synthetic.
- **Agents** draft experiment files, propose claims, and run analyses only on fixture or temp-file stores (synthetic runs, excluded from every count, refused on the real store, as `backtest-runner` does today).
- **The annotation pilot** (protocol §10 step 6) registers the agreement analysis once and opens a run for every execution of the analysis script and every revision round. The interim log, if any run precedes this registry, is imported once (req 12).
- **The backtest** (results writer and backtest page) reads the family's research-run count when it computes N (req 9).
- **Tests** build fixture stores with the research tables and never touch the network.

## Definitions

- **Backtest trial**: as in the backtest spec: one engine run under a registered hypothesis, with a `TrialHandle`. Unchanged.
- **Treatment** and **outcome**: a treatment is a feature, a label, a system's output, a perturbation or an annotator's label; an outcome is a gold label, another annotator's label, an economic variable or a return.
- **Research experiment**: a registered design (one file, one registration) for a computation on non-fixture data that reads both a treatment and an outcome. **Any computation that reads both is a run**, whatever it prints: a regression, a benchmark score, an agreement statistic, a cross-tabulation of a feature against a label, a correlation table. A **run** is one execution of that design under a `RunHandle`: a success, a failure, a refusal, an abandoned execution and a rerun are each a run. A computation that reads treatments only or outcomes only (a corpus build, a sampling frame, a deterministic feature computation, class prevalence, a count of rows per stratum) is a **dataset build**, recorded as a dataset version (req 11), not a run; the moment it joins an outcome it is a run. A unit test on fixtures is neither.
- **Kind** ∈ `agreement` (annotator agreement and the protocol's gates), `benchmark` (a system scored against gold labels on a split; a scoring of the sealed test is a benchmark run on `split=test`), `robustness` (perturbation sets, name-definition binding, drift probes: label flips and probability shifts of a system against its own earlier outputs), `economic` (an economic variable regressed on features; stage 5), `return` (any run whose outcome is a return: rank IC, quantile spreads, event studies, ablations; stage 6). The set is a code constant pinned by a test; a new kind is a spec amendment. A classifier training with a hyperparameter grid is one `benchmark` run whose result records `n_configurations` (req 6). `kind = return` implies `touches_returns = true` (req 2 refuses the other combination).
- **Stage**: 2 to 7, the brief §2 gate the experiment belongs to. Stage 1 has no runs.
- **Confirmatory** run: its registration was frozen before the data that decide its primary metric could be read (req 7), it names a multiplicity family, and its treatment's provenance allows it. Everything else is **exploratory** and is registered and counted all the same.
- **Provenance** of the treatment ∈ `human` (annotator labels), `deterministic` (brief §6 features), `classical` (arms 2 to 4, trained on our labels), `model_historical` (a pretrained model's output on filings before its configuration freeze), `model_prospective` (prospective spec records), `pit_model` (a chronologically consistent model). Brief §7 fixes the weight of each; req 7 turns one line of it into a refusal.
- **Dataset**: a content-addressed export of research data outside the runtime store (labels, features, inference records, a frame), registered under a **name** with a version, its SHA-256, row count, **event span** (`event_start`, `event_end`: the earliest and latest source-event time in it, filing acceptance or session), its split assignment and which splits and periods are sealed (req 11). A run binds exactly one dataset version.
- **Split** ∈ `dev`, `cal`, `test`, `prospective`, `pilot`, `full`, `none`. `test` is always sealed; a dataset may seal other split names and **periods** (date ranges of source events, so the brief §3.1 secondary sealed test, `dev` issuers × test period, is sealed by period whatever its split label).
- **Data window**: the registration's `[window.start, window.end]`, dates. For `economic` and `return` runs it is also the as-of bound: no read with `t` later than `close(window.end)` (req 4). For every kind it bounds the bound dataset's event span.
- **Protected window**: (a) for a run that names a family, every `[holdout.start, holdout.end]` of a registered hypothesis in that family, read from `hypotheses`; (b) every sealed split and sealed period ever registered under the bound dataset's **name** (sealing persists across versions, req 11). Touching one is a **holdout spend** (req 5). A protected window is **already spent** when any backtest trial of the family (`trials.kind = holdout`), or any research run in the family, or any research run on that dataset name, has spent it (synthetic rows excluded).
- **Family**: one of `hypotheses.families`, the unit of N and of holdout spends, unchanged. Required when `touches_returns` is true; optional otherwise. Adding `filing_change`, `semantic` or `insider` is the same reviewed config change as today.
- **Multiplicity family**: the registration's `multiplicity.family_id`, the set of confirmatory comparisons adjusted together (Holm, fixed sequence, BH or none; brief §4.3), with its declared size. Distinct from a hypothesis family: one is about which Sharpes share an N, the other about which p-values share an adjustment.
- **Amendment chain**: the registrations of one slug, each pointing at the one it supersedes (req 2). Budgets, run counts and repeats are summed along the chain.
- **Synthetic** run: opened on a store whose file is not `settings.store.path` (tests, fixtures), excluded from every count and refused on the real store, by the same file-identity check `store.registry` uses.
- **Artifact**: the full output of a run (tables, figures, the report) written outside the repo by the analysis code; the result row stores its SHA-256 so the report cannot be swapped under its registered summary.

## Requirements

1. **Registry tables in the store.** Tables `research_registrations`, `research_datasets`, `research_runs`, `research_results`, `research_decisions` (schema in Data / interfaces), created by `store.schema` at the **next schema version** with an additive migration (the version row is appended; no fact table and no journal table changes; `trial_results` gains one nullable column, req 9). The draft strategy-lab spec also takes "the next schema version" with an additive migration (`trials.detail_level`, its `trial_results` columns): whichever plan lands first takes 9 and the other takes 10, each additive, and `n_research` sits beside whatever strategy-lab adds; neither plan edits the other's DDL. The tables are listed in `RESEARCH_TABLE_NAMES`, disjoint from `TABLE_NAMES` (the look-ahead harness never sees them), from `REGISTRY_TABLE_NAMES` and from the journal tables. **Every row carries `known_at`** (`db.utc_now()` at the write, tz-aware UTC, NOT NULL): the registration time, the run's open, the result's close, the decision's time. Imported rows keep the log's own time in `source_logged_at` and take the import time as `known_at` (req 12); nothing is ever back-stamped. **Append-only**: `store/research.py` exposes inserts and reads only (text check, as for `store/registry.py`); a run's outcome is its one `research_results` row, never an update of `research_runs`; a run with no result row lists as `unfinished`. Ids are `MAX + 1` inside the write transaction, as in the trial registry. Writing commands migrate an older store; the read-only page shows "research registry not initialised" instead.

2. **Pre-registration file and `experiment register`.** An experiment is a file `docs/experiments/<slug>.md` from `docs/templates/experiment.md` with one ```` ```toml experiment ```` block that names: `slug` (= file stem), `kind`, `stage`, `title`, `confirmatory`, `provenance`, `touches_returns`, `family` (required when `touches_returns`; from `hypotheses.families`), `claims` (a non-empty list of ids), `hypothesis_ref` (optional: a `docs/hypotheses` slug or a backlog id such as `B5`), `[dataset]` `name` and optional `sha256` pin, `[window]` `start`/`end`, `splits` (the splits a run may bind; `test` only when `confirmatory`), `[primary]` `metric`, `direction` (`greater`/`less`), `threshold` (optional; the decision rule), `ci_level` (default 0.95), `min_clusters` (the numeric floor under which a result is `underpowered`) and `inference` (the CI or test method in words, for example `issuer-cluster bootstrap, 2000 resamples, percentile`), `secondary` (a list of metric names; anything not listed is exploratory in every table), `comparison_set` (words), `[multiplicity]` `method` ∈ `holm`, `fixed_sequence`, `bh`, `none`, `family_id` and `family_size` (required unless `none`), `[budget]` `runs` (the maximum number of runs this slug allows across its amendment chain, failures and refusals included) and `configurations` (the maximum configurations evaluated across those runs), `stop_rule` (words: the sensitivity set and its tolerance, the revision rule; the numeric floor is `min_clusters`), `expected_effect` (words, with the prior at or below the brief §4.5 haircuts for return claims), `seed` (the published seed; an integer), and, on an amendment only, `amends_sha256`. The prose sections (rationale, prior-evidence disclosure: what of the window, the split or the outcome has already been seen) are hashed with the block: the registry stores `doc_sha256`, `params_json` (the canonical JSON of the block) and `params_sha256`; a changed file is a new registration, never a variant. **Registration refuses**: a file outside `research.experiments_dir`; a `slug` that differs from the file stem; a missing required key, an unknown key, a kind, stage, provenance, split, direction or method outside its set; `kind = return` with `touches_returns = false`; `touches_returns` without a family, or a family outside `hypotheses.families`; a claim id absent from the sibling `docs/research/claims.toml` or whose grade is `UNGRADED` on a confirmatory file (an ungraded claim never supports a confirmatory test, research program §2); `splits` containing `test` on an exploratory registration; `confirmatory = true` with `provenance = model_historical` (brief §7: such results are exploratory only; E1-M is confirmatory only on prospective data); `budget.runs < 1`; `min_clusters < 1`; **a slug that is already registered unless the block carries `amends_sha256` equal to the `params_sha256` of that slug's latest registration** (so a changed file cannot buy a fresh budget or a fresh look: every re-registration is an explicit amendment, and a stale one, pointing at an older version, is refused); `amends_sha256` on a slug not yet registered; a `family_id` that already exists under a different `method` or `family_size`. An **amendment** is registered as a new row pointing at the old (`amends_registration_id`), is listed on the page beside the runs already spent under the chain, and its budget change and reason are a `research_decisions` row of kind `budget_amend`. The old registration stays and opens no further runs. Run counts, configuration sums and protected-window spends are read along the whole chain (req 5, req 6).

3. **No handle, no run, and one reader.** `research.open_run(conn, slug, dataset_id, split, config, run_by, note, synthetic=False, flags, reasons) -> RunHandle` and `research.attach_run(conn, run_id) -> RunHandle` (an unfinished, non-synthetic-mismatched run on the same store file; a run with a result row is refused) are the only constructors of `RunHandle`, each committed in its own write chunk before any other work. Every analysis entry point in `src/tradepartner/research/` takes a `RunHandle` and raises before reading any data without one (ADR 0005, by construction, tested per analysis module as for `engine.run`). **`research.load_dataset(handle)` is the only function that resolves a registered export's path**: it reads the bound dataset row, verifies the export's SHA-256 against the row before the first byte is parsed, and returns the rows; no other module reads `DatasetRecord.path`, and nothing under `scripts/` imports `tradepartner.research` (both AST tests, req 13). The run row records the registration, the dataset version bound and its `sha256` at open, the split, `config_json` and `config_sha256` (the prospective spec §3 version ids that apply, the hyperparameter grid or values, the seed), `n_configurations_declared`, `code_version` and `code_dirty`, `store_max_ingested_at` for runs that read the runtime store, `run_by`, the synthetic flag and a note. A handle remembers its store file and refuses writes from another store, as `TrialHandle` does.

4. **Data window and as-of reads.** The handle is issued first. Then, before any data read: a bound dataset whose `[event_start, event_end]` is not inside the registration's `[window.start, window.end]`, or a requested as-of bound later than `close(window.end)`, is refused (`refused_window`). `economic` and `return` runs read market and company data only through the as-of API (`store.asof`, `store.master`, `universe.universe_as_of`) with an explicit `t` per observation, never later than `close(window.end)`, through short-lived read-only connections, exactly as the backtest's `StoreProvider` does, and never through an adapter. Each such analysis module ships a truncation-invariance test at the window end (a run to `window.end` equals the same run on a store truncated at `close(window.end)`), reviewed by `quant-auditor`; this spec does not write those modules (Out of scope), it binds them.

5. **Protected windows.** Before any data read, after the window check: a run whose window overlaps a protected window of its family, or that binds a sealed split or whose bound dataset's event span overlaps a sealed period of the dataset name, is refused (`refused_holdout`) unless the command carries `--spend-holdout --holdout-reason "<why>"`. With the flags, the run opens with `holdout_spent = true` and the reason, and a `research_decisions` row of kind `holdout_spend` records the window, split or period spent. **A spend is a repeat** (`holdout_repeat = true`, the page says so, `--holdout-repeat` additionally required) when the protected window is already spent in the Definitions sense: by any backtest `holdout` trial of the family, by any research run of the family, or by any research run on that dataset name, under any registration and any slug, synthetic rows excluded. A new slug, an amendment or a new dataset version therefore never buys an unflagged look. **The sealed test is scored once**: the first `split=test` run on a dataset name is the spend, every later one on that name is a repeat (brief §3.1, "a second look is a new, flagged entry"). A run on `split=test` with `confirmatory = false` cannot exist (refused at registration, req 2) and a split the registration's `splits` does not list is refused at open (`refused_split`). Holdout spends by research runs count in `family_holdout_spends`, so a later backtest in the family is marked `holdout_repeat` as backtest spec req 11 requires, and a backtest's spend marks a later research run. No flag skips the record; no environment variable moves a protected window, because protected windows are rows.

6. **Budgets.** A slug's `budget.runs` and `budget.configurations` are hard along its amendment chain: opening a run when the chain's run count (every run row, whatever its outcome, synthetic excluded) has reached the latest registration's `budget.runs`, or when the configurations declared at open would push the chain's sum of `n_configurations` over `budget.configurations`, is refused (`refused_budget`) with a row. The way past a budget is an amendment (req 2), which is visible with its reason. `n_configurations` is declared at open (`--configurations`, default 1) and recorded again at close as evaluated; a close that reports more than declared records `failed` with the message `configurations exceeded declaration`. The `stop_rule` text is not executed; the result's `verdict` (req 8) and the owner's `TP-` claim are where it is applied, and the page shows the text beside the runs so a reviewer can check it was. **Family budget** (research program §4 item 4 states a trial budget per hypothesis family): the research view shows, per hypothesis family, the sum of research runs and configurations over every slug naming that family, beside the family's backtest N, so the family's stated budget can be checked against what ran; the registry enforces the per-slug budget, the owner checks the family one.

7. **Confirmatory means pre-registered before the deciding data.** A registration is `confirmatory` only if its `known_at` precedes the **first** `known_at` of any dataset version registered under the bound dataset's name (re-hashing an export makes a new version, never an earlier name), **or** the run binds a sealed split or sealed period drawn under the seed named in the file; the run records which (`confirmatory_basis` ∈ `predates_dataset`, `sealed_split`). A `confirmatory` run that satisfies neither is refused (`refused_split`, message `dataset precedes registration`). Agreement runs are confirmatory on the locked label export only (protocol §10 step 5): a `confirmatory` agreement run bound to a dataset with `locked = false` is refused (`refused_split`, message `label export not locked`). Exploratory runs carry `confirmatory = false` on every row and in every table the page renders; the page never labels an exploratory result as a test of its claims.

8. **One result row per run.** `research.close_run(handle, outcome, message=None)` records `failed`, `refused_window`, `refused_holdout`, `refused_split`, `refused_budget` or `abandoned` with no statistics; `research.write_result(handle, ...)` records `ok` with `primary_value`, `primary_ci_low`, `primary_ci_high` (at the registered `ci_level`, one-sided where `inference` says so), `n_observations`, `n_clusters` (issuers, firms or event-months, the brief §3.4 effective size), `n_configurations`, `secondary_json` (the declared secondary metrics only; anything else is exploratory and goes under `exploratory_json`), `verdict`, `artifact_sha256` and `artifact_path` (outside the repo). **The verdict is computed by code from the interval, never the point estimate**: `underpowered` when `n_clusters < min_clusters`; otherwise, with a threshold, `pass` when the interval excludes the threshold on the registered side (`direction = less`: `primary_ci_high < threshold`; `greater`: `primary_ci_low > threshold`) and `fail` otherwise; `n/a` without a threshold. `write_result` records `failed` with `dataset changed during run` when the dataset's `sha256` at close differs from the one bound at open, and `failed` with `store changed during run` when `store_max_ingested_at` moved for a run that read the runtime store (backtest spec req 9); it returns rather than raises so the row survives the commit. A second result row for a run raises; `experiment abandon --run <id> --reason` appends an `abandoned` result to an unfinished run and is the only way to finish one from outside the analysis.

9. **The family bar: research runs on return data raise N, never V.** For a family, `research.family_run_count(conn, family)` returns Σ `n_configurations` over `ok`, non-synthetic runs with `touches_returns = true` and `holdout_spent = false` (exploratory included: an exploratory look at returns is a look; holdout-spending runs are spends, not in-sample looks, mirroring the backtest's in-sample-only N). The backtest's `results.write_results` adds it to N for the deflated Sharpe, stores it in the new nullable `trial_results.n_research` column (NULL on rows written before the migration), and contributes nothing to V (a regression has no Sharpe). **Backtest spec req 8 is amended** (T79b edits the spec and the code together): N = the `ok`, non-synthetic, `in_sample` backtest trials of the family at run time, this one included, reruns and sweep variants included (as the strategy-lab spec's req 3 restates it), **plus `family_run_count`**; V is unchanged by this spec and whatever the strategy-lab spec makes it. The backtest page recomputes "today's N" with today's count and shows the split (backtest trials, research runs). Runs with `touches_returns = false` leave N untouched: an agreement statistic or a classifier F1 is not a look at returns; `touches_returns` cannot be false on a `return` run (req 2), and an `economic` run's outcome is an economic variable by definition. Within a multiplicity family, the registry reports the number of `ok` confirmatory runs against `family_size`, so a Holm family that grew after the fact is visible; the adjustment itself is computed by the analysis code and stored in `secondary_json` (`p_adjusted`).

10. **Claims and hypotheses.** Every registration names at least one claim id that exists in `claims.toml` at registration time; the ids are stored. A verdict (`pass`, `fail` or `underpowered`) is recorded by the owner as a `TP-` claim naming the run ids, and every claim the registration named lists it under `bears_on` (research program §6); the registry does not write the claims file. `hypothesis_ref` is stored as given; when it names a registered hypothesis slug, the page links the two, and a later hypothesis file in that family must list the experiment's runs in its prior-evidence disclosure (backtest spec Data / interfaces, "prior-evidence disclosure"); `spec-critic` checks that on the hypothesis PR, the registry cannot.

11. **Datasets.** `tradepartner dataset register --name <name> --version <v> --path <file or directory> --event-start <date> --event-end <date> [--split-json <file>] [--sealed <split>...] [--sealed-period <start> <end>]... [--locked] [--seed <n>] [--note]` hashes the export (a directory is hashed as the sorted list of relative path, size and SHA-256 per file), records `n_rows` where the export is tabular, the event span as declared (the build script computes it; the registering command checks it against the export's event column where one is named in `--split-json`, and refuses a declared span the data exceed), the split assignment file's hash, the sealed splits and periods, `locked`, the seed, `code_version` and `known_at`. **Sealing persists under a name**: the sealed set of a new version must include every split name and period ever sealed under that name, else the registration is refused (`sealed set shrinks`); a version with the same `(name, sha256)` and the same sealed set returns the existing row; the same `(name, sha256)` with a larger sealed set is a new version (sealing more is allowed, unsealing never). The export's bytes live outside the repo and outside the runtime store (open question 2 names where); the registry stores the path as given and the hash, so a moved file is found by hash and a changed file is a new version. Label exports from the annotation tool are datasets with `locked = true` once protocol §10 step 5 ends.

12. **Interim log import, once.** If agreement runs happen before this registry ships, under the protocol's owner-approved interim log named on #618, `tradepartner experiment import-interim <log file> --registration <slug> --reason "<why>"` validates the whole file first and then appends one run row and one result row per log entry, with `imported_from_sha256` = the log's hash, `source_logged_at` = the entry's own time, `known_at` = the import time, `confirmatory = false` on every imported row (they predate their registration row by construction), and a `research_decisions` row of kind `import` carrying the log hash and the entry count. Imported runs bypass no rule: each is checked against the registration's window, protected windows and budget as if opened now, and an entry that would have been refused is recorded with that refusal as its outcome and the logged outcome in `message`; imported runs count toward the chain's budget and, when `touches_returns`, toward N. A log hash already imported is refused; the log file is not deleted by the tool. Nothing else may be imported: there is no generic import command.

13. **Records, never authorizes (ADR 0008).** The registry has no column whose value permits anything, and it refuses nothing on the grounds of model type: a registration whose `config_json` names a pretrained model is accepted and recorded, because an unrecorded run is worse than a recorded one, and ADR 0008 point 1 (no LLM SDK or client in the repo before Phase 5) is enforced where it already is, by the dependency and import tests, and arms 5 to 9 by the research-measurement-boundary ADR the brief §2 calls for, which does not exist yet. Isolation is a test, as ADR 0008 point 2: nothing under `src/tradepartner/` outside `tradepartner.research`, `tradepartner.store.research`, `tradepartner.store.schema` (the DDL), `tradepartner.store.registry` (`family_holdout_spends` reads research spends), `tradepartner.backtest.results` (N reads `family_run_count`), `tradepartner.cli` and `tradepartner.dashboard` imports `tradepartner.store.research` or names a `RESEARCH_TABLE_NAMES` table in its source; `tradepartner.research` imports nothing from `tradepartner.execution` and `tradepartner.execution` nothing from `tradepartner.research` or `tradepartner.store.research` (no path from a research result to an order); `tradepartner.research` imports no adapter; `DatasetRecord.path` is read only in `research.load_dataset`; nothing under `scripts/` imports `tradepartner.research` or `tradepartner.store.research`. The registry stores no model output and no free text from a filing: `config_json` holds version ids and settings, `secondary_json` holds numbers, `message` holds the registry's own text. No value from a registry row ever enters config or a fact table.

14. **CLI.** `tradepartner experiment register <file>`; `tradepartner experiment open <slug> --dataset <id> --split <split> --config <json file> [--configurations <n>, default 1] [--spend-holdout --holdout-reason] [--holdout-repeat] [--note]` prints the run id (exit 0; 2 on a refusal, with the refusal recorded); the analysis commands of later specs take `--run <id>`, obtain their handle through `attach_run` and so refuse an id with a result row; `tradepartner experiment abandon --run <id> --reason`; `tradepartner experiment import-interim` (req 12); `tradepartner experiments [--registration <slug>] [--family <f>] [--kind <k>] [--include-synthetic]` lists runs newest first with outcome, verdict, confirmatory, split, holdout flags and unfinished rows; `tradepartner dataset register` (req 11). No `--synthetic` flag exists; there is no edit, delete, unseal or reopen command; `--spend-holdout` without a non-blank reason, and `--holdout-repeat` without `--spend-holdout`, are refused before anything is written. Output passes the `cli_record` secret scrub.

15. **Page.** A read-only **research view** on the dashboard, inside the shell's single read-only connection: registrations with their block fields, budgets used against declared along the chain, amendments; per hypothesis family the research run and configuration sums beside the family's backtest N (req 6); runs newest first with outcome, verdict, confirmatory and its basis, provenance, split, holdout spent and repeat, synthetic hidden by default, failed, refused, abandoned, imported and unfinished rows visible with their message; datasets with sealed splits and periods and their spends; decisions. The backtest page's N shows the research count (req 9). "Research registry not initialised" on a store before the migration. No run button: runs are CLI only.

## Risks & domain checks

- **Look-ahead:** `economic` and `return` runs read only through `t`-parameterised as-of calls bounded by `close(window.end)`, through short-lived read-only connections (req 4); each analysis module ships a truncation-invariance test; a dataset's declared event span is checked against the registered window before any read, and against the export's event column at dataset registration; a prospective record's `known_at` is never earlier than the filing's acceptance (prospective spec §4.3, enforced where those records are written, outside this spec). The registry itself reads no market data.
- **Survivorship:** the as-of API returns delisted names and the universe as of `t`; the window check cannot see a dataset built from today's membership, so every dataset build is reviewed code (protocol §4.5) and `quant-auditor` reads the frame script; this spec records the frame's hash so a rebuilt frame is a new version.
- **Multiple testing:** every run is a row, failures and refusals included, by construction (no handle, no read; one reader for exports); return-touching runs raise the family's N by their configurations and never shrink V; budgets refuse the run past the declared count along the amendment chain and an amendment is a visible row with a reason; Holm families carry a declared size and the registry reports the realised count beside it; the sealed test is scored once per dataset name and every later look is flagged; exploratory results are labelled on every row and never promoted by a page.
- **Holdout:** a family's hypothesis holdouts and a dataset name's sealed splits and periods are protected windows, spent only with a logged owner reason, repeats flagged across slugs, amendments, dataset versions and the backtest's own spends; sealing never shrinks; no environment variable moves a protected window (they are rows).
- **Contamination:** `confirmatory` with `model_historical` provenance is refused at registration (brief §7); the page labels provenance on every run; a confirmatory run must predate the first version of its dataset name or bind a sealed split drawn under the registered seed.
- **Costs:** not modelled here; a `return` run that claims a tradable effect is a backtest hypothesis next, under the backtest spec's cost model.
- **Order path:** no code path from `tradepartner.research` or the research tables to `tradepartner.execution`, tested (req 13). The registry stores numbers and version ids, never a decision input.
- **Secrets:** none read; CLI output scrubbed. **LLM inputs:** none; the registry neither calls nor authorizes a model (req 13), and a run row naming a model is a record, not a permission.
- **Store locks:** registration, open and close are short write chunks; analysis reads use per-observation read-only connections or the dataset export, so a long run never holds the ingest job's lock. A research run during the paper-trading window's own run contends like a backtest does (accepted).
- **Owner-only steps:** the first real registration, every holdout spend, every budget amendment and the interim import need the owner's store; agents stay on fixtures.

## Open questions

1. **Runtime store or a separate research store for the registry.** This spec puts the registry tables in the runtime store so that N is one query that cannot lose rows, and keeps the research data outside it (Problem). The brief §10 recommended a separate research store for both. Options: (a) as specified; (b) registry and data both in a separate research DuckDB file, with the backtest reading N from it and refusing to run when that file is missing (a hard refusal, never a silent zero). Recommendation: (a).
2. **Where research data live** (label exports, feature records, inference records; prospective spec unresolved question 1, protocol §7). Options: (a) a directory under `data/research/` outside the repo, content-addressed, with the registry holding paths and hashes; (b) a second DuckDB file `data/research.duckdb` with the prospective spec's record tables. This spec needs only a path and a hash and works under either. Recommendation: (a) until the prospective-capture spec needs tables, which is after the boundary ADR.
3. **How a return-touching research run counts in N.** Options: (a) each evaluated configuration adds one (specified: a grid of 50 is 50 looks at returns); (b) each run adds one regardless of its grid; (c) only confirmatory runs count. Recommendation: (a); (c) would let exploratory screens off the hook, which is the garden of forking paths the brief §17 names.
4. **Exploratory runs on sealed splits.** Specified as impossible (refused at registration and at open). Alternative: allowed with a flag and a reason, as a holdout spend. Recommendation: keep it impossible; the brief §3.1 says sealed means sealed.
5. **Interim log.** Whether any agreement run will precede this registry. If the registry ships before protocol step 6, req 12 is dropped: `import_interim` from T77 and `experiment import-interim` from T79, and the protocol's interim log is never created. Recommendation: build the registry first and drop req 12.
6. **`verdict` computed by code from the interval.** Specified: `pass`/`fail`/`underpowered`/`n/a` from the registered threshold, `ci_level` and `min_clusters`. Alternative: no code verdict, the owner records the verdict in the `TP-` claim only. Recommendation: as specified, so the page can show a verdict that the claim must agree with; the claim stays the record of the decision.

Settled in this draft rather than asked (say so if you disagree): the sealed-test and holdout repeat rule is the strict one (once per dataset name or family, whatever the slug); only the owner's store ever holds a non-synthetic spend, which the file-identity check already gives; re-registering a slug is always an explicit amendment.
