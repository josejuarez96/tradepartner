# Spec: Research-experiment registry (runs that are not backtests)

**Status:** Accepted (owner, 2026-10-05, #931)  ·  **Issue:** #661  ·  **Amended:** 2026-10-03 (#671, spec-critic follow-ups from PR #668; no decision changed, the six open questions stand); 2026-10-03 (#728, open question 7 added for B3's spanning diagnostic); 2026-10-04 (#810, the owner's decisions on open questions 1 to 7 folded in: 1 to 4 and 6 as specified, 5 drops req 12 and every import path, 7 (d) makes a closed trial's `trial_equity` export an ordinary dataset version; no new scope)  ·  **Related:** [charter](../charter.md) (stop criterion: an untracked run halts the phase; principle 2), [ADR 0005](../decisions/0005-objective-benchmark-stop-criteria.md) (integrity criterion; "no id, no run"), [ADR 0008](../decisions/0008-llm-role.md) (points 1 to 3: the registry records runs, it authorizes nothing), [backtest spec](backtest.md) reqs 8 to 12 (the trial registry this one sits beside; req 8 and the `trial_results` table amended by plan task T83b below), [strategy-lab spec](strategy-lab.md) (draft; also amends req 8 and `trials`; sequencing in req 9), [trial-registry note](../research/trial-registry.md), [research program](../ways-of-working/research-program.md) (§4 item 4 trial budgets, §6 `TP-` claims), [claims register](../research/claims.toml), [hypothesis backlog](../research/hypothesis-backlog.md) (B5, B8), [ML validation brief](../research/2026-10-03-ml-validation-methodology-brief.md) (§2 governance, §3 splits, §4 discipline, §8.1 E1, §10 the proposal this spec answers), [annotation protocol](../research/2026-10-03-disclosure-annotation-protocol.md) (§7 label storage, §10 step 6 the interim log), [prospective feature spec](../research/2026-10-03-prospective-semantic-feature-spec.md) (§3 version objects, §7 immutability), development-process domain rules 1 to 3

## Problem & why now

The store's registry (`hypotheses`, `trials`, `trial_results`, schema version 3) records one thing: a run of the backtest engine under a registered hypothesis. Every column assumes an equity curve: a cost level, a Sharpe, a rebalance row. The 2026-10-03 research program proposes runs that are not that: an annotation-agreement analysis (protocol §8), classifier benchmarks on dev, calibration and sealed test splits (brief §5), the E1 regression of revenue-growth deceleration on a disclosure label (brief §8.1), feature studies of rank ICs and quantile spreads (brief §9), robustness and drift probes (brief §5.8, prospective spec §8). None has a home. The protocol's answer is an "interim append-only log named on #618"; the brief's is "experiments that need registration wait". The charter's stop criterion does not distinguish: any untracked run halts the phase, and ADR 0005 says a run without an id must not happen. So before the first agreement run or regression, the registry has to exist, or the pilot stalls at protocol step 6 and B5 and E1 cannot start.

**Why a new spec rather than an amendment of the backtest spec.** The two registries share one principle (register, then run; append only; count everything; one holdout spend) and one store, but not one shape. A backtest trial is defined by an engine window and a frozen parameter set, and its result is a set of metrics with the deflated Sharpe inputs. A research run is defined by a kind, a dataset version, a split, a configuration and a primary metric, and its holdout is a sealed split or a family's holdout dates rather than its own window. Forcing both into `trials` would make every column nullable by kind, and the backtest spec is one owner run (T45b) from Shipped; an amendment that loosens its tables now would invite the drift it was written to stop. The backtest spec is amended in exactly one place, req 8's trial count and the `trial_results` table, by plan task T83b below, so that a research run on return data raises the family's N like any other look at the data.

**Why in the runtime store, not a separate research store** (the brief §10 recommended a separate one; open question 1, confirmed as specified by the owner on 2026-10-04, #810). The family's N must be one query that cannot lose rows: a second database file can be missing, moved or stale, and a backtest that silently counted N without the research runs would be the exact failure ADR 0005's integrity criterion names. The registry rows are run metadata and code-computed statistics, not model outputs and not facts: nothing in them is read by the decision path, and req 13 makes that a test. The research **data** (label exports, feature records, model inference records, raw responses) stay outside the runtime store, in the research store the prospective spec §2 preconditions require (a content-addressed `data/research/` directory, open question 2 (a), #810), and the registry points at them by content hash (req 11). That keeps ADR 0008 option 4 intact: no model-produced value enters the store as a fact.

## Users & usage

- **The owner** writes an experiment file under `docs/experiments/`, merges it, runs `tradepartner experiment register <file>`, and runs the analysis command of the experiment's kind (each analysis is its own spec; this spec fixes what they must call). He reads the research view on the dashboard and records the verdict as a `TP-` claim (research program §6). Only the owner spends a protected window, amends a budget, or runs anything against the real store (CLAUDE.md rule 9); an agent cannot, because an agent never runs on the real store and every run on another store file is synthetic.
- **Agents** draft experiment files, propose claims, and run analyses only on fixture or temp-file stores (synthetic runs, excluded from every count, refused on the real store, as `backtest-runner` does today).
- **The annotation pilot** (protocol §10 step 6) registers the agreement analysis once and opens a run for every execution of the analysis script and every revision round. No run precedes the registry: it ships before protocol step 6, so the protocol's interim log is never created (open question 5, decided 2026-10-04, #810; req 12 dropped).
- **The backtest** (results writer and backtest page) reads the family's research-run count when it computes N (req 9).
- **Tests** build fixture stores with the research tables and never touch the network.

## Definitions

- **Backtest trial**: as in the backtest spec: one engine run under a registered hypothesis, with a `TrialHandle`. Unchanged.
- **Treatment** and **outcome**: a treatment is a feature, a label, a system's output, a perturbation or an annotator's label; an outcome is a gold label, another annotator's label, an economic variable or a return.
- **Research experiment**: a registered design (one file, one registration) for a computation on non-fixture data that reads both a treatment and an outcome. **Any computation that reads both is a run**, whatever it prints: a regression, a benchmark score, an agreement statistic, a cross-tabulation of a feature against a label, a correlation table. A **run** is one execution of that design under a `RunHandle`: a success, a failure, a refusal, an abandoned execution and a rerun are each a run. A computation that reads treatments only or outcomes only (a corpus build, a sampling frame, a deterministic feature computation, class prevalence, a count of rows per stratum) is a **dataset build**, recorded as a dataset version (req 11), not a run; the moment it joins an outcome it is a run. A unit test on fixtures is neither.
- **Kind** ∈ `agreement` (annotator agreement and the protocol's gates), `benchmark` (a system scored against gold labels on a split; a scoring of the sealed test is a benchmark run on `split=test`), `robustness` (perturbation sets, name-definition binding, drift probes: label flips and probability shifts of a system against its own earlier outputs), `economic` (an economic variable regressed on features; stage 5), `return` (any run whose outcome is a return: rank IC, quantile spreads, event studies, ablations; stage 6). The set is a code constant pinned by a test; a new kind is a spec amendment. A classifier training with a hyperparameter grid is one `benchmark` run whose result records `n_configurations` (req 6). `kind = return` implies `touches_returns = true` (req 2 refuses the other combination).
- **Stage**: 2 to 7, the brief §2 gate the experiment belongs to. Stage 1 has no runs.
- **Confirmatory** run: its registration was frozen before the data that decide its primary metric could be read (req 7), it names a multiplicity family, and its treatment's provenance allows it. Everything else is **exploratory** and is registered and counted all the same.
- **Provenance** of the treatment ∈ `human` (annotator labels), `deterministic` (brief §6 features), `classical` (arms 2 to 4, trained on our labels), `model_historical` (a pretrained model's output on filings before its configuration freeze), `model_prospective` (prospective spec records), `pit_model` (a chronologically consistent model). Brief §7 fixes the weight of each; req 7 turns one line of it into a refusal.
- **Dataset**: a content-addressed export of research data outside the runtime store (labels, features, inference records, a frame), registered under a **name** with a version, its SHA-256, row count, **event span** (`event_start`, `event_end`: the earliest and latest source-event time in it, filing acceptance or session), the same span per split, its split assignment and which splits and periods are sealed (req 11). A run binds exactly one dataset version.
- **Split** ∈ `dev`, `cal`, `test`, `prospective`, `pilot`, `full`, `none`. `test` is always sealed, and a sealed split always has a sealed period holding its rows (req 11); a dataset may seal other split names and **periods** (date ranges of source events, so the brief §3.1 secondary sealed test, `dev` issuers × test period, is sealed by period whatever its split label).
- **Data window**: the registration's `[window.start, window.end]`, dates. For `economic` and `return` runs it is also the as-of bound: no read with `t` later than `close(window.end)` (req 4). For every kind it bounds the bound dataset's event span.
- **Protected window**: (a) for a run that names a family, every `[holdout.start, holdout.end]` of a registered hypothesis in that family, read from `hypotheses`; (b) every sealed split and sealed period ever registered under the bound dataset's **name** (sealing persists across versions, req 11). Touching one is a **holdout spend** (req 5). A protected window is **already spent** when any backtest trial of the family (`trials.kind = holdout`), or any research run in the family, or any research run on that dataset name, has spent it (synthetic rows excluded).
- **Family**: one of `hypotheses.families`, the unit of N and of holdout spends, unchanged. Required when `touches_returns` is true; optional otherwise. Adding `filing_change`, `semantic` or `insider` is the same reviewed config change as today.
- **Multiplicity family**: the registration's `multiplicity.family_id`, the set of confirmatory comparisons adjusted together (Holm, fixed sequence, BH or none; brief §4.3), with its declared size. Distinct from a hypothesis family: one is about which Sharpes share an N, the other about which p-values share an adjustment.
- **Amendment chain**: the registrations of one slug, each pointing at the one it supersedes (req 2). Budgets, run counts and repeats are summed along the chain.
- **Synthetic** run: opened on a store whose file is not `settings.store.path` (tests, fixtures), excluded from every count and refused on the real store, by the same file-identity check `store.registry` uses.
- **Artifact**: the full output of a run (tables, figures, the report) written outside the repo by the analysis code; the result row stores its SHA-256 so the report cannot be swapped under its registered summary.

## Requirements

1. **Registry tables in the store.** Tables `research_registrations`, `research_datasets`, `research_runs`, `research_results`, `research_decisions` (schema in Data / interfaces), created by `store.schema` at the **next schema version** with an additive migration (the version row is appended; no fact table and no journal table changes; `trial_results` gains one nullable column, req 9). The draft strategy-lab spec also takes "the next schema version" with an additive migration (`trials.detail_level`, its `trial_results` columns): whichever plan lands first takes 9 and the other takes 10, each additive, and `n_research` sits beside whatever strategy-lab adds; neither plan edits the other's DDL. The tables are listed in `RESEARCH_TABLE_NAMES`, disjoint from `TABLE_NAMES` (the look-ahead harness never sees them), from `REGISTRY_TABLE_NAMES` and from the journal tables. **Every row carries `known_at`** (`db.utc_now()` at the write, tz-aware UTC, NOT NULL): the registration time, the run's open, the result's close, the decision's time. Nothing is ever back-stamped, and no row enters the registry by any path other than these writes (the interim-log import that would have carried a `source_logged_at` was dropped with req 12, #810). **Append-only**: `store/research.py` exposes inserts and reads only (text check, as for `store/registry.py`); a run's outcome is its one `research_results` row, never an update of `research_runs`; a run with no result row lists as `unfinished`. Ids are `MAX + 1` inside the write transaction, as in the trial registry. Writing commands migrate an older store; the read-only page shows "research registry not initialised" instead.

2. **Pre-registration file and `experiment register`.** An experiment is a file `docs/experiments/<slug>.md` from `docs/templates/experiment.md` with one ```` ```toml experiment ```` block that names: `slug` (= file stem), `kind`, `stage`, `title`, `confirmatory`, `provenance`, `touches_returns`, `family` (required when `touches_returns`; from `hypotheses.families`), `claims` (a non-empty list of ids), `hypothesis_ref` (optional: a `docs/hypotheses` slug or a backlog id such as `B5`), `[dataset]` `name` and optional `sha256` pin, `[window]` `start`/`end`, `splits` (the splits a run may bind; `test` only when `confirmatory`), `[primary]` `metric`, `direction` (`greater`/`less`), `threshold` (optional; the decision rule), `ci_level` (default 0.95), `min_clusters` (the numeric floor under which a result is `underpowered`) and `inference` (the CI or test method in words, for example `issuer-cluster bootstrap, 2000 resamples, percentile`), `secondary` (a list of metric names; anything not listed is exploratory in every table), `comparison_set` (words), `[multiplicity]` `method` ∈ `holm`, `fixed_sequence`, `bh`, `none`, `family_id` and `family_size` (required unless `none`), `[budget]` `runs` (the maximum number of runs this slug allows across its amendment chain, failures and refusals included) and `configurations` (the maximum configurations evaluated across those runs), `stop_rule` (words: the sensitivity set and its tolerance, the revision rule; the numeric floor is `min_clusters`), `expected_effect` (words, with the prior at or below the brief §4.5 haircuts for return claims), `seed` (the published seed; an integer), and, on an amendment only, `amends_sha256`. The prose sections (rationale, prior-evidence disclosure: what of the window, the split or the outcome has already been seen) are hashed with the block: the registry stores `doc_sha256`, `params_json` (the canonical JSON of the block) and `params_sha256`; a changed file is a new registration, never a variant. **Registration refuses**: a file outside `research.experiments_dir`; a `slug` that differs from the file stem; a missing required key, an unknown key, a kind, stage, provenance, split, direction or method outside its set; `kind = return` with `touches_returns = false`; `touches_returns` without a family, or a family outside `hypotheses.families`; a claim id absent from the sibling `docs/research/claims.toml` or whose grade is `UNGRADED` on a confirmatory file (an ungraded claim never supports a confirmatory test, research program §2); `splits` containing `test` on an exploratory registration; `confirmatory = true` with `provenance = model_historical` (brief §7: such results are exploratory only; E1-M is confirmatory only on prospective data); `budget.runs < 1`; `min_clusters < 1`; **a slug that is already registered unless the block carries `amends_sha256` equal to the `params_sha256` of that slug's latest registration** (so a changed file cannot buy a fresh budget or a fresh look: every re-registration is an explicit amendment, and a stale one, pointing at an older version, is refused); `amends_sha256` on a slug not yet registered; a `family_id` that already exists under a different `method` or `family_size`. An **amendment** is registered as a new row pointing at the old (`amends_registration_id`), is listed on the page beside the runs already spent under the chain, and its budget change and reason are a `research_decisions` row of kind `budget_amend`. The old registration stays and opens no further runs. Run counts, configuration sums and protected-window spends are read along the whole chain (req 5, req 6).

3. **No handle, no run, and one reader.** `research.open_run(conn, slug, dataset_id, split, config, run_by, note, synthetic=False, flags, reasons) -> RunHandle` and `research.attach_run(conn, run_id) -> RunHandle` (an unfinished run whose synthetic flag matches the store file it is attached on, by the file-identity check in Definitions, Synthetic: a synthetic run on the real store or a non-synthetic run on another file is refused, as is a run with a result row) are the only constructors of `RunHandle`, each committed in its own write chunk before any other work. Every analysis entry point in `src/tradepartner/research/` takes a `RunHandle` and raises before reading any data without one (ADR 0005, by construction, tested per analysis module as for `engine.run`). **`research.load_dataset(handle)` is the only function that resolves a registered export's path**: it reads the bound dataset row, verifies the export's SHA-256 and the split file's SHA-256 against the row before the first byte is parsed, and returns the bound split's rows only (`full` and `none`: every row), so a run never reads a split it did not bind; no other module reads `DatasetRecord.path`, and nothing under `scripts/` imports `tradepartner.research` (both AST tests, req 13). The run row records the registration, the dataset version bound and its `sha256` at open, the split, `config_json` and `config_sha256` (the prospective spec §3 version ids that apply, the hyperparameter grid or values, the seed), `n_configurations_declared`, `code_version` and `code_dirty`, `store_max_ingested_at` for runs that read the runtime store, `run_by`, the synthetic flag and a note. A handle remembers its store file and refuses writes from another store, as `TrialHandle` does.

4. **Data window and as-of reads.** The handle is issued first. Then, before any data read: a bound dataset whose `[event_start, event_end]` is not inside the registration's `[window.start, window.end]`, or a requested as-of bound later than `close(window.end)`, is refused (`refused_window`). `economic` and `return` runs read market and company data only through the as-of API (`store.asof`, `store.master`, `universe.universe_as_of`) with an explicit `t` per observation, never later than `close(window.end)`, through short-lived read-only connections, exactly as the backtest's `StoreProvider` does, and never through an adapter. Each such analysis module ships a truncation-invariance test at the window end (a run to `window.end` equals the same run on a store truncated at `close(window.end)`), reviewed by `quant-auditor`; this spec does not write those modules (Out of scope), it binds them.

5. **Protected windows.** Before any data read, after the window check: a run whose window overlaps a protected window of its family, or that binds a sealed split or whose **bound split's** event span (recorded per split at `dataset register`, req 11; `full` and `none` span every row) overlaps a sealed period of the dataset name, is refused (`refused_holdout`) unless the command carries `--spend-holdout --holdout-reason "<why>"`. So a `dev` run on a dataset whose `test` period is sealed opens without flags when its `dev` rows lie outside that period, and a former `test` row relabelled `dev` inside it still trips the check. With the flags, the run opens with `holdout_spent = true` and the reason, and a `research_decisions` row of kind `holdout_spend` records the window, split or period spent. **A spend is a repeat** (`holdout_repeat = true`, the page says so, `--holdout-repeat` additionally required) when the protected window is already spent in the Definitions sense: by any backtest `holdout` trial of the family, by any research run of the family, or by any research run on that dataset name, under any registration and any slug, synthetic rows excluded. A new slug, an amendment or a new dataset version therefore never buys an unflagged look. **The sealed test is scored once**: the first `split=test` run on a dataset name is the spend, every later one on that name is a repeat (brief §3.1, "a second look is a new, flagged entry"). A run on `split=test` with `confirmatory = false` cannot exist (refused at registration, req 2) and a split the registration's `splits` does not list is refused at open (`refused_split`). Holdout spends by research runs count in `family_holdout_spends`, so a later backtest in the family is marked `holdout_repeat` as backtest spec req 11 requires, and a backtest's spend marks a later research run. No flag skips the record; no environment variable moves a protected window, because protected windows are rows.

6. **Budgets.** A slug's `budget.runs` and `budget.configurations` are hard along its amendment chain: opening a run when the chain's run count (every run row, whatever its outcome, synthetic excluded) has reached the latest registration's `budget.runs`, or when the configurations declared at open would push the chain's sum of `n_configurations` over `budget.configurations`, is refused (`refused_budget`) with a row. The way past a budget is an amendment (req 2), which is visible with its reason. `n_configurations` is declared at open (`--configurations`, default 1) and recorded again at close as evaluated; a close that reports more than declared records `failed` with the message `configurations exceeded declaration`. The `stop_rule` text is not executed; the result's `verdict` (req 8) and the owner's `TP-` claim are where it is applied, and the page shows the text beside the runs so a reviewer can check it was. **Family budget** (research program §4 item 4 states a trial budget per hypothesis family): the research view shows, per hypothesis family, the sum of research runs and configurations over every slug naming that family, beside the family's backtest N, so the family's stated budget can be checked against what ran; the registry enforces the per-slug budget, the owner checks the family one.

7. **Confirmatory means pre-registered before the deciding data.** A registration is `confirmatory` only if its `known_at` precedes the **first** `known_at` of any dataset version registered under the bound dataset's name (re-hashing an export makes a new version, never an earlier name), **or** the run binds a sealed split or sealed period drawn under the seed named in the file; the run records which (`confirmatory_basis` ∈ `predates_dataset`, `sealed_split`). A `confirmatory` run that satisfies neither is refused (`refused_split`, message `dataset precedes registration`). Agreement runs are confirmatory on the locked label export only (protocol §10 step 5): a `confirmatory` agreement run bound to a dataset with `locked = false` is refused (`refused_split`, message `label export not locked`). Exploratory runs carry `confirmatory = false` on every row and in every table the page renders; the page never labels an exploratory result as a test of its claims.

8. **One result row per run.** `research.close_run(handle, outcome, message=None)` records `failed`, `refused_window`, `refused_holdout`, `refused_split`, `refused_budget` or `abandoned` with no statistics; `research.write_result(handle, ...)` records `ok` with `primary_value`, `primary_ci_low`, `primary_ci_high` (at the registered `ci_level`, one-sided where `inference` says so), `n_observations`, `n_clusters` (issuers, firms or event-months, the brief §3.4 effective size), `n_configurations`, `secondary_json` (the declared secondary metrics only; anything else is exploratory and goes under `exploratory_json`), `verdict`, `artifact_sha256` and `artifact_path` (outside the repo). **The verdict is computed by code from the interval, never the point estimate**: `underpowered` when `n_clusters < min_clusters`; otherwise, with a threshold, `pass` when the interval excludes the threshold on the registered side (`direction = less`: `primary_ci_high < threshold`; `greater`: `primary_ci_low > threshold`) and `fail` otherwise; `n/a` without a threshold. The verdict can be stricter than a protocol gate that reads the point estimate: protocol §8 G1 passes on α(J) ≥ 0.667 with the lower bound reported, while the agreement example's registry verdict is `pass` only when the bootstrap lower bound clears 0.667. That is intended, and there is no point-estimate option: the registry's `pass` is the interval standard; a gate on the point estimate is applied by the owner from `primary_value` and the per-cell secondary metrics and recorded in the `TP-` claim, which names the standard it applied (open question 6, decided as specified by the owner on 2026-10-04, #810: code computes the verdict, and its basis is the interval). `write_result` records `failed` with `dataset changed during run` when the dataset's `sha256` at close differs from the one bound at open, and `failed` with `store changed during run` when `store_max_ingested_at` moved for a run that read the runtime store (backtest spec req 9); it returns rather than raises so the row survives the commit. A second result row for a run raises; `experiment abandon --run <id> --reason` appends an `abandoned` result to an unfinished run and is the only way to finish one from outside the analysis.

9. **The family bar: research runs on return data raise N, never V.** For a family, `research.family_run_count(conn, family)` returns Σ `n_configurations` over `ok`, non-synthetic runs with `touches_returns = true` and `holdout_spent = false` (exploratory included: an exploratory look at returns is a look; holdout-spending runs are spends, not in-sample looks, mirroring the backtest's in-sample-only N). The backtest's `results.write_results` adds it to N for the deflated Sharpe, stores it in the new nullable `trial_results.n_research` column (NULL on rows written before the migration), and contributes nothing to V (a regression has no Sharpe). **Backtest spec req 8 is amended** (T83b edits the spec and the code together): N = the `ok`, non-synthetic, `in_sample` backtest trials of the family at run time, this one included, reruns and sweep variants included (as the strategy-lab spec's req 3 restates it), **plus `family_run_count`**; V is unchanged by this spec and whatever the strategy-lab spec makes it. The backtest page recomputes "today's N" with today's count and shows the split (backtest trials, research runs). Runs with `touches_returns = false` leave N untouched: an agreement statistic or a classifier F1 is not a look at returns; `touches_returns` cannot be false on a `return` run (req 2), and an `economic` run's outcome is an economic variable by definition. Within a multiplicity family, the registry reports the number of `ok` confirmatory runs against `family_size`, so a Holm family that grew after the fact is visible; the adjustment itself is computed by the analysis code and stored in `secondary_json` (`p_adjusted`).

10. **Claims and hypotheses.** Every registration names at least one claim id that exists in `claims.toml` at registration time; the ids are stored. A verdict (`pass`, `fail` or `underpowered`) is recorded by the owner as a `TP-` claim naming the run ids, and every claim the registration named lists it under `bears_on` (research program §6); the registry does not write the claims file. `hypothesis_ref` is stored as given; when it names a registered hypothesis slug, the page links the two, and a later hypothesis file in that family must list the experiment's runs in its prior-evidence disclosure (backtest spec Data / interfaces, "prior-evidence disclosure"); `spec-critic` checks that on the hypothesis PR, the registry cannot.

11. **Datasets.** `tradepartner dataset register --name <name> --version <v> --path <file or directory> --event-start <date> --event-end <date> [--event-column <name>] [--split-json <file>] [--sealed <split>...] [--sealed-period <start> <end>]... [--locked] [--seed <n>] [--note]` hashes the export (a directory is hashed as the sorted list of relative path, size and SHA-256 per file), records `n_rows` where the export is tabular, the event span as declared (the build script computes it; the registering command checks it against the export's event column where `--event-column` names one, and refuses a declared span the data exceed), the event column's name, the split assignment file's path and hash, the event span per split computed from `--event-column` and `--split-json` (`split_spans_json`; without a split file the one split `full` spans the declared span; `--split-json` without `--event-column` is refused, `split without event column`, since req 5 reads those spans), the sealed splits and periods, `locked`, the seed, `code_version` and `known_at`. **Sealing persists under a name**: the sealed set of a new version must include every split name and period ever sealed under that name, else the registration is refused (`sealed set shrinks`); a version with the same `(name, sha256, split_sha256)` and the same sealed set returns the existing row; the same export with a larger sealed set, or with a different `--split-json`, is a new version (sealing more is allowed, unsealing never; a relabelled split is a new assignment, never the old row). **A sealed split name protects rows by their label only**, so a later version that relabels former `test` rows as `dev` would leak them unless a period holds them: whenever a split is sealed, `--event-column` is required and every row of that split must fall inside a sealed period, else the registration is refused (`sealed split without period`). `test` rows in `--split-json` seal `test` whether or not `--sealed test` is passed (Definitions, Split), so the rule fires on them too. A directory export has no event column, so it cannot seal a split and `--sealed` on one is refused the same way: sealing is for tabular exports, by design. The brief §3 design is therefore covered by sealing the test *period* (the §3.1 secondary sealed test, `dev` issuers × test period, included), and a relabelling cannot reach rows a sealed period holds. The export's bytes live outside the repo and outside the runtime store, in a content-addressed directory under `data/research/` (open question 2, decided (a) by the owner on 2026-10-04, #810); the registry stores the path as given and the hash, so a moved file is found by hash and a changed file is a new version. **Amendment 2026-10-28 (#2440, owner goal "less code per useful experiment").** An in-repo, reusable **event-study runner** replaces the one-off out-of-repo probe script for experiments of the event-study shape (an event list, a held return after each event, a comparison against matched peers). It is an analysis module under `src/tradepartner/research/` and so is bound by req 3 (every entry point takes a `RunHandle`), req 4 (as-of reads, never later than `close(window.end)`, with a truncation-invariance test) and req 13; it is the "own spec" that Out of scope reserves for return tests, written here as an amendment because it adds no table and changes no registry rule. Why now: C1, C1b and C1c each cost a new probe script (`~/tradepartner-probes/c1lag/c1b_filing_delay.py` is 715 lines, `c1c_filing_delay.py` 824, about two thirds of C1c a copy of C1b), an experiment file, three reviewers and a manual run; the ranked idea queue (13D activist drift, insider buying next) makes such experiments routine, which is the condition the 2026-10-19 MVP usability report set for building a reusable runner. The sentence in earlier amendments and experiment files that "the script lives outside the repo" stays true for what is not runner-eligible.

*What is shared (the runner).* One module computes, from explicit inputs, everything the C1b probe computed after the event list existed:

- **Entry and exit.** The file's `entry` key is an enumerated choice, because the two rules differ on a filing accepted before the open: `next_open_after_instant` (the open of the first XNYS session whose open is strictly after `known_at`; the default for new files) and `next_session_after_date` (the open of the first session whose America/New_York date is later than the event's; C1b's rule, so C1b's file uses it). The exit for horizon `h` is the close of the `h`-th session counting the entry session as the first. Dividend-adjusted returns from the as-of API; the trading calendar, never weekdays. An event with no bar on the entry session is dropped and counted (`n_dropped_no_entry_bar_*`); an exit session past the last session the window allows drops it too (`n_dropped_horizon_*`). **A name with no bar at its exit session is not dropped (survivorship, non-negotiable 6):** it is held at its last bar's close, flagged `exited_early_h` and counted (`n_delisted_exits`), as C1b does; it carries no delisting return, which can flatter names delisted for cause, so the report states that next to `n_delisted_exits`.
- **Tradability filters.** A price floor on the raw close of the session before entry; a liquidity floor on the median raw dollar volume of the `volume_lookback` sessions before entry, with at least `min_volume_bars` bars present; a shares fact no older than `shares_stale_days`. Each is a `[study]` key, never a constant, and each drop is counted by group and reason (`n_dropped_price_floor_*`, `n_dropped_liquidity_*`, `n_dropped_no_mcap_*`, `n_dropped_no_beta_*`).
- **Size buckets.** Market cap at entry (shares from a named company-level fact times the raw close the session before entry). Two cells are declared separately: the **bucket cell**, the keys within which market cap is cut into `n_buckets` quantile buckets (`bucket_by`, a list of `quarter` and `stratum`; the runner derives the calendar quarter from `known_at` in America/New_York; C1b uses both), and the **peer cell**, the keys a peer must share beyond the bucket (`peer_by`, `stratum` for C1b). A bucket cell with fewer than `min_bucket_events` events is unbucketed and its events untraded, counted (`n_dropped_small_size_group_*`).
- **Fact reads (look-ahead control).** The default `facts_read = "event_known_at"` reads every fact (shares) through `facts_as_of` at the event's own `known_at`, the explicit `t` per observation that req 4 asks for, so a later restatement is never seen. `facts_read = "window_end"` reads once at `close(window.end)` and is a declared golden-compatibility mode: C1b used it and disclosed that `facts_as_of` returns the latest revision (its "single-cutoff reads, accepted" paragraph), a look-ahead the file must state again. Bars are read once at `close(window.end)` in both modes, never later.
- **Matched normal/peer selection.** For each event of a treated group, the events of the file's peer group in the same peer cell and size bucket whose entry session is within `peer_window` sessions of its own, the event itself and every event of the same issuer excluded; fewer than `min_peers` peers drops the event and counts it. The size-tight reading uses the `near_k` peers nearest in log market cap.
- **Beta adjustment.** A causal OLS beta on the benchmark security's daily returns over up to `beta_lookback` sessions ending the session before entry, at least `beta_min_bars` return pairs; the beta-adjusted return is the event return minus beta times the benchmark return over the same span.
- **The four readings** (raw, beta-adjusted, size-tight, size-tight beta-adjusted), each as the spread against the peer mean over each peer's own entry-to-exit span, plus the raw and benchmark-adjusted means and the beta and log-cap gaps against peers that C1b reports.
- **Cost and borrow lines.** Long net = spread minus two sides of `cost_bps`; short net = minus spread, minus two sides of cost, minus `borrow_bps` pro rata for `h/252` of a year; all lines come from the file. The matched-peer leg is taken as costless to trade and the report says so (C1b's "idealisation, stated").
- **Clustered statistics.** The mean, the cluster-robust (sum of within-cluster deviations, no small-sample correction) standard error and t of the event-level value, clustered by each of the file's `cluster_by` choices (event date, month, quarter), with the smaller t taken across the clusterings as C1b does; the primary's interval uses the first clustering the file names.
- **Effective n for overlapping holds.** Reported, never used to change a registered line: events `n`, clusters `c`, the Kish effective cluster count `(sum n_k)^2 / sum n_k^2` for each clustering, the mean and maximum number of holds open on one date, and the count of events whose hold overlaps an earlier hold of the same security (counted, not removed). The clustered t of a 60-session hold stays an upper bound, as C1b states.
- **Kill lines.** Evaluated exactly as pre-registered, from a declarative `[study.kill]` list in the file (reading set, metric `gross_spread_bp` or `net_bp`, floor, t floor, which t), with C1b's rules: a line fires if any listed reading fails it, and a statistic that cannot be computed (no events, an undefined t) counts as a kill. The runner reports the booleans and the numbers beside them and cannot change, add or select a line; a kill line the declaration cannot express makes the experiment ineligible for the runner (open question 3).

*What stays per experiment.*

- **The experiment file**, a new frozen `[study]` table inside the existing `toml experiment` block (so it is hashed with the file and cannot differ from what was registered): `horizons`, `groups` (treated groups and the peer group), the entry rule (`entry`, above), the filter, fact-read mode, bucket, peer, beta, cost, borrow and cluster values above, the shares fact name, the benchmark security, `[study.kill]`, and the metric names it fills for `[primary]` and `secondary`. **Amendment 2026-10-31 (#2723, owner decision after the candidate 5 audit, [#2689 comment 6548223852](https://github.com/josejuarez96/tradepartner/issues/2689#issuecomment-6548223852)): desk reads that read returns outside the backtester are disclosed exposure.** Candidate 5 ([desk read](../research/2026-10-31-cash-profitability-long-only-desk-read.md)) ran a probe script, `~/tradepartner-probes/cbl/probe.py`, read-only on the owner's store. It computed monthly returns of a profitability book over August 2020 to December 2023, the `profitability` family's in-sample months. No row records it: it has no `TrialHandle`, so it is not a backtest trial (backtest spec req 8), and no `RunHandle`, so it is not a research run (req 3). So `profitability`'s N (req 9) is two looks short: the launch that crashed inside the return loop and the launch that finished. The quant-auditor's PASS left the question open ("the run is not in the trial registry ... the owner's call"). The owner decided: such reads are recorded in the registry as **disclosed research exposure**. Each record carries the frozen kill-line link, the probe's SHA-256, the window, the data pin and the verdict, so N and the search tally count them. This amendment adds one table and one count. It changes no existing rule.

*Definitions.*

- **Desk read**: a computation, outside the backtest engine and outside a `RunHandle`, that reads a return series: prices, adjusted bars or published portfolio returns. A desk read that reads counts only, such as coverage, universe sizes or zero-fill shares, is not one. Candidate 5's coverage-only dry runs were not desk reads. A computation that reads returns under a `TrialHandle` or a `RunHandle` is a trial or a run, never an exposure.
- **Launch**: one execution of a probe script that reached its first return read. This holds whether the launch printed a statistic, crashed or was interrupted. A launch that failed before any return read is not a launch: candidate 5's launch 1 failed inside `uv`, before Python started. **One launch is one exposure record.** So candidate 5 has two records: launch 2, which crashed inside the return loop, and launch 3, which completed. This mirrors req 9 as amended by #1408, where a `failed` return run raises N because its returns may already have been examined.
- **Source** ∈ `store` (the probe read the runtime store or a copy of it) or `open_data` (a published return file read outside the store, such as the Chen–Zimmermann parquets). This is a code constant pinned by a test, like the other enumerations (Data / interfaces, Config keys).
- **Exposure record**: one row of the new table `research_exposures`. It is a record, never a trial, a run or a registration (below, "Never a tradable trial").

Each entry is `measured` (the write hashed a file passed with `--input`) or `declared` (a value the writer passes) | `store` needs a `store_max_ingested_at` entry; the write hashes every `--input` file itself |
| `n_configurations` | the number of distinct signal × construction × window cells whose returns the launch computed. A cost sensitivity of the same cell is not a configuration (one backtest trial evaluates every cost level, backtest spec req 1), and a comparator is not one either (candidate 5: 1 per launch; its SPY and equal-weight comparisons and the 2× cost stress are not counted) | integer ≥ 1 |
| `verdict` | ∈ `pass`, `fail`, `insufficient`, `incomplete` (a launch that crashed or stopped before the combine rule applied), copied from the desk read | in the set |
| `desk_read_path` | the repo note that reports the launch (`docs/research/...`) | relative path under `docs/research/` |
| `audit_url` | optional; the quant-auditor's comment | URL shape |
| `overlaps_holdout` | computed: whether `[window_start, window_end]` overlaps a registered hypothesis holdout of `family` (`hypotheses` rows; Definitions, Protected window (a)) | computed |
| `post_boundary` | computed: whether `window_end` is on or after the development boundary (`registry.boundary_date`, ADR 0016); FALSE when no boundary row exists | computed |
| `synthetic` | by file identity (Definitions, Synthetic), never passed | computed |
| `recorded_by`, `code_version`, `code_dirty`, `note`, `known_at` | as in req 3; `known_at` is `db.utc_now()` at the write | as for every research table |

The verdict is the desk read's, not the registry's. The probe's code computed the statistics and applied the frozen combine rule; the registry copies the label and stores no statistic. This differs on purpose from req 8, where the registry computes the verdict: the registry never sees a desk read's numbers.

*How a record is written.* `research.record_exposure(conn, ExposureInput, recorded_by) -> ExposureRecord` in `store/research.py` is the only writer (append-only, as req 1). It hashes the probe file, the kill-line copy and every `--input` file itself before it inserts anything. It does not trust a hash it is given, just as `load_dataset` checks an export before it parses a byte (req 3). The CLI is `tradepartner exposure record --candidate <ref> --source <store|open_data> [--family <f>] --kill-line-url <url> --kill-line-file <file> --kill-line-posted-at <ts> --probe <file> --probe-sha256 <hex> --read-at <ts> --window-start <date> --window-end <date> [--input <file>]... [--pin <name>=<value>]... --configurations <n> --verdict <v> --desk-read <path> [--audit-url <url>] [--note <text>]`. It prints the exposure id and exits 0, or exits 2 on a refusal with nothing written. Timestamps must carry an offset; a naive one is refused, and each is stored in UTC. There is no edit, delete or withdraw command (open question 6). A record that repeats an existing record's `(candidate_ref, probe_sha256, read_at)` returns the existing row and writes nothing, so a backfill run twice cannot raise N twice. The real-store write is an owner step; an agent may run it at his word, as with the registered runs (plan T341). Agents write only on fixture and temp-file stores, and those records are synthetic.

*No back-stamping.* `known_at` is the write time. `read_at` and `kill_line_posted_at` are declared facts about the past, stored beside it, never in its place. A record written today about a launch on 2026-10-31 has `known_at` today. A backtest result written in between keeps the N it stored (`trial_results` is never updated, backtest spec req 9), and only "today's N" on the backtest page moves (req 15). This is the same discipline as req 1's "nothing is ever back-stamped".

*How it enters N (req 9 extended).* `research.family_exposure_count(conn, family)` returns Σ `n_configurations` over non-synthetic records of `family` with `source = store`. `results.family_n_split` gains a third part, `exposures`, beside `trials` and `research`, and N = trials + research runs + exposures. `results.write_results` stores the part in a new nullable column `trial_results.n_exposure`, NULL on rows written before the migration, and adds nothing to V: a desk read stores no Sharpe. The backtest page's "today's N" shows the three parts. `open_data` records do not enter N (open question 1). The ladder ledger's rule stays for them: "not added to N mechanically", disclosed at rung 4 (L3). Under this rule candidate 5's two records raise `profitability`'s N by 2.

*How it enters the search tally.* The strategy-search limit ([hypothesis backlog](../research/hypothesis-backlog.md), "Strategy-search limit") counts candidates, not reads. The tally stays in the backlog note, kept by the orchestrator. The registry gives a check, not the count: `tradepartner exposures --candidates --since <date>` lists each distinct `candidate_ref` with its first `read_at` on or after the date, its records and its verdicts, `store` and `open_data` both. A candidate the note counts with no record is expected only when its rung-2 read computed no return series: B7 read published evidence, not a return series, so it has no record, and its registered event study will be ordinary research runs. A candidate with a record that the note does not count is a finding for the orchestrator.

*Never a tradable trial.* A record writes no row to `hypotheses`, `trials`, `trial_results`, `research_registrations` or `research_runs`. It issues no handle, cannot be bound by a run, and spends no holdout under req 5 (open question 2). Nothing reads `research_exposures` except `family_exposure_count`, the listings and the research view. Req 13's isolation test covers the new table name through `RESEARCH_TABLE_NAMES`, and its allowlist is unchanged. A record is evidence that a look happened, never evidence for promotion: a later hypothesis, sweep or experiment file for the same mechanism lists the record ids in its prior-evidence disclosure, as for runs (req 10), and that file is a new registration under the backtest or research rules with its own N.

*Going forward.* A desk read note that reports a launch cites its exposure ids. The quant-auditor's desk-read audit checks that every launch the note lists has one record, with the probe hash the audit reviewed. A new probe prints its own SHA-256, the store's `store_max_ingested_at` and each input's SHA-256 before its first return read, so the pin can be `measured` from its output. That is a probe convention, which the auditor reads; the registry cannot check it.

*Open questions (not guessed; the owner decides).*

1. **Do `open_data` records raise N?** As specified, no. The ladder ledger says open-data reads are not added to N mechanically, and the owner's decision named a probe "on the store". Against that: CBOperProf's 2020+ cut read the same calendar months as `profitability`'s in-sample window, from a different construction. Options: (a) as specified; (b) every return-reading record with a family raises N; (c) only an `open_data` record whose window overlaps the family's in-sample window raises N. Recommendation: (a). An open file's returns are not the store's book, and (b) or (c) would quietly retire the ladder ledger's rule; that rule should change in its own decision.
2. **Is a record that overlaps a protected window a holdout spend?** As specified, `overlaps_holdout` and `post_boundary` are recorded and shown, and the record still raises N. It does not enter `family_holdout_spends`, so a later holdout trial in the family is not marked `holdout_repeat` by it. Options: (a) as specified; (b) a `store` record with `overlaps_holdout` is a spend: `family_holdout_spends` unions it, and the write requires `--holdout-reason`, as req 5 does for runs. Recommendation: (b) for family holdouts, since a look at holdout months by any path is a look. For ADR 0016's exam interval, flag only: the exam can only reject, and the owner has already said such exposure is disclosed, not spent. No backfill row overlaps a family holdout today, so this blocks nothing in the backfill.
3. **One record per launch.** As specified, candidate 5 is two records and N +2. The alternative is one record per desk read, with N +1 and the launches in the note. Recommendation: per launch. It matches the failed-run rule (#1408) and the auditor's count ("both return exposures ... are counted").
4. **A launch whose script no longer exists.** Candidate 5's frozen file can be rebuilt byte for byte, but CBOperProf's first-run file cannot (a display-only edit overwrote it). Options: (a) refuse, and record only launches whose file hashes; (b) allow a backfill record with `probe_sha256` NULL and `probe_verified = false`, behind an explicit `--probe-unavailable --reason`, listed as unverified on the page; (c) record the surviving file's hash and say in `note` which launch it does not match. Recommendation: (b), limited to `open_data` records. A `store` record must hash, since it raises N and its evidence is the probe. If (b) is chosen, the table gains `probe_verified` (T355 adds it either way, always TRUE under (a)).
5. **Backfill before 2026-10-30.** B9, IRRX, Q1 (2026-10-19) and L-1 are open-data reads that the ladder ledger already holds, from before the search limit began. Recommendation: do not backfill them. They raise no N under open question 1 (a) and do not count toward the limit.
6. **Correcting a wrong record.** As specified, nothing withdraws a record, so an error over-counts N, the conservative side. The alternative is a `research_decisions` row of a new kind `exposure_withdraw` with a reason, which `family_exposure_count` respects. Recommendation: none in v1; a withdraw path is a way to shrink N.

## Risks & domain checks

- **Look-ahead:** `economic` and `return` runs read only through `t`-parameterised as-of calls bounded by `close(window.end)`, through short-lived read-only connections (req 4); each analysis module ships a truncation-invariance test; a dataset's declared event span is checked against the registered window before any read, and against the export's event column at dataset registration; a prospective record's `known_at` is never earlier than the filing's acceptance (prospective spec §4.3, enforced where those records are written, outside this spec). The registry itself reads no market data.
- **Survivorship:** the as-of API returns delisted names and the universe as of `t`; the window check cannot see a dataset built from today's membership, so every dataset build is reviewed code (protocol §4.5) and `quant-auditor` reads the frame script; this spec records the frame's hash so a rebuilt frame is a new version.
- **Multiple testing:** every run is a row, failures and refusals included, by construction (no handle, no read; one reader for exports); return-touching runs raise the family's N by their configurations and never shrink V; budgets refuse the run past the declared count along the amendment chain and an amendment is a visible row with a reason; Holm families carry a declared size and the registry reports the realised count beside it; the sealed test is scored once per dataset name and every later look is flagged; exploratory results are labelled on every row and never promoted by a page.
- **Holdout:** a family's hypothesis holdouts and a dataset name's sealed splits and periods are protected windows, spent only with a logged owner reason, repeats flagged across slugs, amendments, dataset versions and the backtest's own spends; sealing never shrinks; no environment variable moves a protected window (they are rows).
- **Contamination:** `confirmatory` with `model_historical` provenance is refused at registration (brief §7); the page labels provenance on every run; a confirmatory run must predate the first version of its dataset name or bind a sealed split drawn under the registered seed.
- **Costs:** not modelled here; a `return` run that claims a tradable effect is a backtest hypothesis next, under the backtest spec's cost model.
- **Order path:** no code path from `tradepartner.research` or the research tables to `tradepartner.execution`, tested (req 13). The registry stores numbers and version ids, never a decision input.
- **Secrets:** none read; CLI output scrubbed. **LLM inputs:** none; the registry neither calls nor authorizes a model (req 13), and a run row naming a model is a record, not a permission.
- **Store locks:** registration, open and close are short write chunks; analysis reads use per-observation read-only connections or the dataset export, so a long run never holds the ingest job's lock. A research run during the paper-trading window's own run contends like a backtest does (accepted).
- **Owner-only steps:** the first real registration, every holdout spend and every budget amendment need the owner's store (the interim import no longer exists, req 12); agents stay on fixtures.
