## Problem & why now

Phase 3 answers "how would the rule have done?". Phase 4 asks whether the system can run the rule **unattended, against a broker, without a human in the loop and without cheating itself**: orders placed by code through deterministic risk rules, every order reconciled against what the broker says, every decision journaled from signal to outcome, and a paper result compared to the backtest on the same dates under a rule fixed before the first order. This spec builds the risk-gated broker wrapper (ADR 0003 rule 7), the Alpaca paper adapter, the scheduled tracking run, the journal, the operations and override pages, the alerts, the wash-sale lot ledger and the command that checks the Phase 4 exit criteria. It is where charter principles 3, 5 and 6 (code places orders, rules before money, tune on process) and development-process rules 5, 7 and 8 become code with tests.

The paper vehicle is the registered H1 (long-only 12-1 momentum, top decile equal weight, monthly). ADR 0005 makes Phase 4 a test of process, not of returns: its exit criteria are four checks a command can run, and beating a benchmark is not one of them. Phase 4 may not start until the owner has signed off on H1's recorded survivorship gap (ADR 0003 rule 8, ADR 0009 point 3); `paper start` enforces that gate.

## Users & usage

- **The scheduler** runs `tradepartner paper run` once per XNYS session, starting before the open, after the previous session's `ingest` has completed (ADR 0005's machine assumption). On most sessions the run collects order outcomes, reconciles and marks, then exits. On a fill session it also plans, submits sells before the open, waits for them to finish after the open, then submits buys sized from the cash the sells raised. Nothing else in the system places orders.
- **The owner** runs `paper start` once (after the gap sign-off), reads the operations page most days, uses the override screen rarely and with a reason, engages or releases the kill switch (a release settles any order a crash left pending), records Alpaca paper responses once with paper keys for the fixtures, and runs `paper check` and `paper report` at the phase close. Only the owner holds keys, runs anything against the real store or the paper account, and releases the kill switch.
- **Phase 6** inherits the wrapper, the journal, the ledger and the pages unchanged; it swaps the adapter's endpoint, not the rules. Nothing in this spec runs against a live account.
- **Tests**, on every PR, run the wrapper against `FakeBroker` (told per order to accept, fill, partially fill, expire, reject, or vanish) and the Alpaca adapter against recorded, scrubbed responses with the network disabled.

## Definitions

- **Rebalance session** T_i, **fill session** F_i and **read time** close(T_i) are the backtest spec's definitions (`backtest.schedule`). **S** is the session a run executes on, from the calendar and the shared clock.
- **Paper window**: opened by `paper start` and closed by `paper stop`. Its first rebalance session T_0 is the first rebalance session **after** `paper start`, so it lies after H1's frozen `holdout.end` (the backtest spec reserves those sessions for tracking) and never touches the holdout. The window row **freezes** the exit thresholds and the comparison rule (req 14); runs and checks read the frozen values, never live `Settings`.
- **Tracking run**: one execution of `paper run` on session S. Its **kind** is `stop` when the window has a stop requested (req 14), else `rebalance` when S = F_i, `catch_up` when a rebalance is pending and S ≤ F_i + `paper.max_catch_up_sessions`, `mark` otherwise. A run holds an exclusive **run lock** (`fcntl.flock` on `<store.path>.paper.lock`, shared with `resume`, `reconcile` and `stop`) for its whole life; a second instance writes no run row, writes a `locked` alert with a null run id, and exits non-zero. It writes its `paper_runs` row **first** and its `paper_run_results` row last; a run without a result row is `unfinished` (the registry rule applied to paper: no row, no run), and only a lock holder may close an unfinished run as `crashed`, because a live run always holds the lock.
- **Plan trial**: every run that plans opens a registry trial of `kind=tracking` before its first provider read and closes it before submitting, so every engine read in Phase 4 sits under a trial id (ADR 0005 check 4). A plan trial is one referenced by a `paper_plans` row; it writes no metrics and never counts in N, V or holdout spends.
- **Tracking trial**: the backtest of the registered hypothesis over [T_0, last completed T] with `kind=tracking`, opened by `paper report`. Its `trial_weights` and monthly returns are what paper is compared against.
- **Plan** at T_i: the universe, signal, targets and reasons computed at read time close(T_i) by the engine's own plan function over `StoreProvider` with the frozen parameters: a pure function of rows with `known_at ≤ close(T_i)`. The plan records the store's `store_max_ingested_at` at plan time.
- **Decision**: one row per name in the plan's held-or-target set, made once per rebalance and journaled before any order: trade (side, planned notional or quantity), skip (with a reason) or override. A `catch_up` or same-session re-run **re-uses** the journaled decisions of the pending rebalance; it never re-plans. Every decision is in exactly one **state**, derived from the journal (`plan.decision_state`): **closed** (a `skip_*` or `dust` decision; an `override` with no side, which is every `keep_name` and an `exclude_name` of a name not held (nothing to sell, its weight left in cash), its state reason the override's kind (#450); or one whose latest `decision_events` row is `skipped` or `written_off`: nothing more is ordered for it in this rebalance); **in flight** (it has a non-terminal order); **settled** (its latest order is terminal and its **remainder** is below the trading minimum: `risk.min_order_notional`, or, when the decision's journaled `whole_share` flag is set (the name was not fractionable at decision time; read from the row, never from the live asset), one share at the reference price × (1 + `risk.whole_share_price_buffer`), that rounding residue never counting as a skip, except that a `whole_share` **full exit** (a plan full exit or a forced exit) settles only when less than one share remains or its notional is below `risk.min_order_notional`, so a last single share is sold rather than kept (#366 Q3); a fractionable full exit therefore stays open until less than `risk.min_order_notional` remains); otherwise **open** (never ordered, or its latest order terminal with a remainder still worth trading), which is what a re-run or catch-up trades, **for the remainder only** (req 3). A `left_universe` name is a `trade` decision (full exit) with that reason, never closed. **Remainders.** A quantity sell: submitted quantity minus filled quantity, adjusted by the splits with `ex_date` in (the order's session, S] known at close(S−1). A notional sell (a trim): its planned notional minus Σ(filled quantity × filled average price) over all its orders, converted to a quantity at the reference price, which is the quantity its next order sells (every sell order is by quantity, ADR 0010 amendment 2026-09-30), **capped** at the reconciled holding on S rounded down to `alpaca.quantity_decimals`, less the name's residue, less the unfilled quantity of the name's non-terminal own sells (each split-adjusted like a quantity sell's remainder, put on the `alpaca.quantity_decimals` grid, the nearest step only within `float` noise of one and otherwise the step **above**, so an off-grid estimate such as a 1-for-3 split's is never under-counted (#719), and summed exactly, the same sum the sell-sum rule in req 3 checks), never below zero (#518 and #605 owner decisions, 2026-10-02: after a price drop the converted remainder can exceed the holding, and an earlier sell can still be open; a capped trim no longer halts the batch as `limit_breach` on `sell_within_holding` or `sell_sum_within_holding`). The cap sizes the order only; the trim's remainder stays as defined, so what the cap leaves is sold by a later attempt once the open sell ends (an under-trim heals itself; a halt would not). The open sell does end: every order is a market DAY order (req 1), so it is terminal at the broker by its session's close, and the journal records that once its fills are in, within `risk.max_fill_lag_sessions` (req 8) (#719). A full exit's order is netted the same way (#647 item 5 owner decision, 2026-10-03): it sells the reconciled holding on S rounded down, less the residue for a plan or `window_stop` exit (none for `delisted` or `untargeted_receipt`), less the same open-sells sum, never below zero, so a full exit beside an earlier non-terminal own sell of the name sells the rest instead of halting the batch on `sell_sum_within_holding`. Its remainder stays a quantity sell's (its latest order's quantity minus fills), so a netted exit whose order fills is settled, and if the other open sell then expires unfilled the name is still held with no open decision (an under-sell, never a short). That heals by exit kind: a `delisted` holding on the next run (req 7 makes a new forced exit once no own sell is open); a plan full exit (`left_targets`, `left_universe`, `exclude_name`) or an `untargeted_receipt` (its settled exit spends the receipt) only at the next rebalance's `decisions_from`; a `window_stop` exit is never made beside an open own sell (req 14). A buy: its **target notional** minus Σ(filled quantity × filled average price) over all its orders, the target fixed at plan time as `planned_notional` × min(1, spendable-if-every-sell-fills / Σ planned buy notionals), spendable computed with `costs.buy_notional_after_costs` on cash before the sells plus every sell **the plan made** at the reference price (a forced exit that joins the sells phase for a name the plan did not decide, a spin-off receipt appearing after plan time, is not in the target: its proceeds are cash until the next rebalance), so the cost reserve is inside the target and never re-opens a buy. **A buy is re-attempted only if a sell of its rebalance was open or in flight at its previous attempt** (the only source of more cash); every `orders` row records `sells_in_flight_at_submit` for that purpose, so the rule is a pure function of the `orders` and `order_events` rows alone: a buy whose latest order is terminal with a remainder at or above the minimum is **written off** when that order was submitted with no sell of its rebalance open or in flight **and** the order has no `cancel_requested` or `cancel_failed` event with reason `halt` **and** its terminal event is not a `cancelled` with reason `not_received` (a halt or a crash is not a funding shortfall: the cash is still there, so such a buy stays open and the next in-window run after the resume retries it for its remainder, sized from cash); it stays open otherwise. The `decision_events` `written_off` row (with the unfunded remainder) records the derived state and is appended by the run step that first sees the terminal order (collection in steps 3 and 7b, or the halt path's read); an order that became terminal inside `paper resume` gets its row from the next run's step 3, which back-fills the row for any terminal buy that lacks it, before the `executed` test. A buys phase that runs when no sell of the rebalance is open or in flight is therefore the rebalance's **last** unless it is halted: whatever its orders leave unfilled is written off when they end, and every buy it deferred is written off at the end of the phase, whether the shortfall came from sells filling below the reference price, from a deferred first attempt or from anything else. A deferred buy has no order row, so its write-off exists only as that end-of-phase `decision_events` row; a crash before it is written leaves the buy open for the next last phase, which is harmless. A buy whose scaled attempt falls below `risk.min_order_notional` while its remainder is above it is **deferred** (open, no order, no skip row, not counted toward the skip cap) until a last phase writes it off; one whose target is below the minimum is `skip_below_minimum` (closed). Cash left when a rebalance is `executed` is the report's `unspent_cash`, and an `unspent_cash` alert fires when it exceeds the frozen `risk.max_unspent_cash_fraction` of equity. **Order**: one attempt on a decision; a decision may have several across sessions and attempts, each with its own id. **Rebalance state** is derived, never planned into existence: every rebalance session T_i of the **open window** (T_i ≥ its `first_rebalance_session`; rows are tied to the window through `run_id → paper_runs.window_id`) with F_i ≤ S and no `executed` or `missed` event in `rebalance_events` is **pending**, whether or not it was ever planned (so a month with no run on F_i, a stale F_i or a plan blocked by a lag is still pending and still lapses to `missed` on schedule); `executed` when it has at least one decision and no decision of it is open or in flight (a plan with zero decisions never executes, #366 Q6, req 7; forced-exit decisions carry no `rebalance_session` and never enter this test; the test runs after every collection step, before any lapse rule); `missed` when the catch-up window lapses (for any reason, the kill switch included) or a `LimitBreachError` or `SkipCapError` abandons it. The run kind, step 6 and the lapse rule all read this derived state. Only a run writes `rebalance_events` and `decision_events` rows (both keyed by `run_id`); `paper resume` writes neither and leaves the `executed` test and any `written_off` back-fill to the next run's step 3. **Chain**: signal → decision → order → {fill | expired | rejected | cancelled} → outcome (ADR 0005), one journal row per link.
- **Halt**: ADR 0007's minimum (no further `submit` in this run, the exception propagates, the fault is journaled with its type) plus req 4.
- **System fault**: any `SystemFaultError` (ADR 0007): `ClockError`, `ReconciliationError`, `RejectionCapError`, `SkipCapError`, `KillSwitchEngagedError`, `LimitBreachError`, `AcknowledgementTimeoutError`. Every one takes the halt path and engages the kill switch. `StaleDataError` is **not** a `SystemFaultError` subclass: it is a data fault that halts the run without engaging the switch (req 4).
- **Ledger**: the positions and cash the journal implies, never stored as truth. Positions are rebuilt from journaled fills and journaled broker adjustments (req 6), split-adjusted by `corporate_actions` rows with `known_at ≤ close(S−1)` and `ex_date ≤` the instant the quantity is stated for. Cash is the broker cash recorded on the window's last `ok` reconciliation, or `paper_windows.starting_cash` before the first one, plus the journaled fill and adjustment deltas since it, so per-fill rounding at the broker can drift by at most one run's fills. **Reconciliation** compares the ledger with the broker's `positions()`, `open_orders()` and `account()`.
- **Reference price** on S: the close(S−1) close from `prices_as_of(close(S−1))`, divided by the split ratios with `ex_date` in (S−1, S] known at close(S−1), so it is on the same split basis as quantities adjusted through S (#366 Q3). A buy's `target_notional` is fixed at plan time from the close(T_i) prices and is a notional, so no split basis applies to it.
- **Full exit**: a decision that sells the name's whole remaining holding (less its residue for a plan or `window_stop` exit), derived from existing `decisions` columns and never stored as a flag. It is a decision with `side = sell` and one of the following: `decision = forced_exit`, whatever its reason (`delisted`, `untargeted_receipt`, `window_stop`); `decision = trade` with `reason ∈ {left_targets, left_universe}` (the reasons `decisions_from` writes, req 3); or `decision = override`, which with a side is always an `exclude_name` sell (a `keep_name` override and an `exclude_name` of a name not held have no side and are closed, never a full exit). Every other sell is a **trim**. The code reads it through one pure function, `plan.is_full_exit(decision)`, which T54c adds. The wrapper sets `PhaseOrder.full_exit` from that function, and `decision_state` reads it; neither re-derives the rule. The per-order limit exemption, the whole-share minimum exemption and the phase-time `dust` rule (req 3 (c)) all apply to exactly this set (#366 Q1 and Q3). `decisions_from` writes `left_targets` for every held in-universe name with no target weight and `left_universe` for every held name outside the universe, and no other reason on a `trade` sell except null (a trim). `plan.is_full_exit` raises `ValueError` on a sell whose (decision, reason) pair is outside this table. A schema `CHECK` on `decisions.reason` holds these spellings from schema version 7 (#377).
- **`known_at` rule for the journal**: `known_at` is the shared clock's reading at the moment the system learned or decided the fact (a plan when it was computed, a fill when the run collected it, a reconciliation when it ran); the instant the fact refers to is a separate column (`rebalance_session`, `session`, the broker's `event_at` or `filled_at`). A broker timestamp is never a `known_at`; a broker timestamp later than the clock reading by more than `risk.max_broker_clock_skew_seconds` is a `ClockError`. Rows written on the halt path after a `ClockError` are stamped with `store.db.utc_now()` and flagged `clock_fault`.

*Amendment 2026-10-13 (#1627; the owner's direction of 2026-10-06 recorded on [#1626](https://github.com/josejuarez96/tradepartner/issues/1626); built by the paper plan; accepted by the owner's merge).* **Cash in lieu of a stock dividend's fractional share.** #1626 (T186-family, #1618's guard) stores an Alpaca stock dividend as a `corporate_actions` row of `action_type = "split"` with `ratio_or_amount` its rate (#127's example: SCCO 1.0085, a 0.85% stock dividend), so the ledger's quantity for a held position grows by `shares x ratio`, a **fractional** number. Alpaca credits only whole shares — `floor(shares x ratio)` — and pays the value of the remainder as a **non-trade cash activity** of `activity_type = CIL` (its `AccountActivityType.CIL`, "Cash in Lieu of Stock"), with its own id, a `date`, an `executed` status and a `net_amount`. Until now the unknown `CIL` type and the sub-share position difference halted the book as two mismatches, resolving a booked-and-settled corporate action "by hand" every time. The rule below reconciles it: **when the broker credits the whole shares and a matching cash-in-lieu activity the book reconciles clean, and anything short of that halts as any residual does.**

1. **The rule (requirement 6).** A held **stock dividend** — a stored `split` action with `1 < ratio_or_amount <= alpaca.stock_dividend_max_rate` and `ex_date <= S` — leaves the broker holding `floor(shares x ratio)` whole shares (the whole-share growth requirement 6 already explains, minus the fractional remainder) plus a `CIL` activity for that remainder. Reconciliation journals the remainder's removal and the `CIL` cash as **one** `adjustments` row of the new kind `cash_in_lieu`: `security_id` the issuer, `quantity` the removed fraction (negative), `cash` the broker's `net_amount`, `broker_activity_id` the `CIL` id (nullable, `UNIQUE`, so a broker fact is booked **once**, as `fee_cash` is), `origin` null, and `session` the `CIL` activity's own `date` — which is the ex-date when the broker posts the cash in lieu that day and otherwise the payable date inside item 3's window (never the reconciliation session). The row lands **inside the ledger at its own point in the replay** (`ledger.from_journal`): when the replay reaches it the issuer's exact `Fraction` position is rounded down to the whole shares then held, so a later split, a second stock dividend, or a fractional fill after it acts on the whole, never on the remainder, and a whole-share exit never strands the share the old end-of-replay snap left (4065 x 1.0077 = 4096.3005 floors to 4096, never 4095.9999999999995). `explained.booked` carries the row's cash difference and it is subtracted from `broker_cash - ledger.cash`, the same way a booked fee's is.

2. **The reference and the tolerance.** The expected cash is the removed fraction valued at the **post-ex** price: the **pre-ex** reference for the name — the raw close of its latest bar on or before `previous_session(ex_date)`, read explicitly for the ex-date and not for the reconciliation's session, so a `CIL` posted on the payable date divides the same pre-split close — **divided by the split's ratio, once**. The `CIL`'s `net_amount` must match that expected cash within a **relative** tolerance, the window's frozen `risk.cash_in_lieu_tolerance` (default **0.10**; the broker values cash in lieu on the ex-date, which the pre-ex reference overstates by about the drop the dividend implies, so a several-percent gap is normal and is not cash drift a book should halt on). A `CIL` on a name with **no bar** here — no reference — halts; a zero-cash `cash_in_lieu` is never booked.

3. **The date window.** The whole-share credit and the `CIL` may post on different sessions (Alpaca typically pays cash in lieu on the payable date), so a `CIL` is accepted from the ex-date through `ex_date + alpaca.cash_in_lieu_max_lag_sessions` XNYS sessions (default **10**), clamped by the reconciliation session. A `CIL` dated before the ex-date or after that window is unexplainable and halts.

4. **What halts.** An unexplained `CIL` — one on a name with no stock dividend that session (including one whose ex-date matches a stock dividend on a *different* held name), one dated outside the window, one whose `status` is not `executed`, one whose issuer has no reference price, one beside a broker quantity that is not `floor(ledger)` (the whole-share guard keeps rounding from masking a lost share), a second `CIL` id on one name in one read, or one beyond the tolerance — is a mismatch of kind `unexplained_activity` and halts the book, with nothing booked, exactly as requirement 6 and ADR 0010's 2026-10-12 amendment word it. A held position with no `CIL` activity at all halts as a `quantity` mismatch on the unbooked fractional share, as today. When an order is lagging or pending, a bookable `CIL` records `Allowed("deferred cash in lieu", ...)` and is journaled by the next `ok` reconciliation instead (the `fee_cash` precedent): its cash is still subtracted and the position still rounded, but its id is not journaled, so nothing is booked twice and nothing is missed.

5. **Data / interfaces, additive.** `adjustments.kind` gains `cash_in_lieu` and the schema counter moves to the next version (store/schema.py's "Schema versions" records it; the `kind` `CHECK` is widened by the migration the counter names, every row kept in insertion order and byte-identical, as version 25 widened it for `fee_cash`; `broker_activity_id` already exists). `reconcile.compare` keeps its signature; `Explanations` gains `stock_dividends` (`security_id -> (ex_date, last_acceptable_CIL_date, ratio)`), `stock_dividend_references` (`security_id -> the pre-ex close`) and — through the caller — the two new keys. `reconcile_run.frozen_risk` refuses any window whose `frozen_json` lacks a `RiskConfig` field, and `risk.cash_in_lieu_tolerance` is a frozen field, so **a window frozen before this version cannot reconcile until it is stopped (`paper stop`) and a new window `paper start`ed on the corrected store**; the two windows open at this merge (`main`, `daily`) are abandoned at today's sitting on the owner's word. `alpaca.cash_in_lieu_max_lag_sessions` is live (an `alpaca.` key, not frozen), so it reaches every window from the merge, and `alpaca.stock_dividend_max_rate` stays live (the #1618 guard that stores the row and the one that re-reads it must agree).

6. **Acceptance (testable).** On the fake broker a book holding a stock-dividend issuer over the ex-date reconciles with no halt when the broker credits `floor(shares x ratio)` shares and a matching cash in lieu; it halts when the cash in lieu is missing or wrong beyond the tolerance; an issuer with no stock dividend is unchanged. Each guard above has a test that fails if the guard is deleted: the ledger snap (a later split, a second stock dividend, a fractional fill after the row, and the exact-whole-share assertion), the whole-share check, the date window's both edges, the missing reference, the non-executed single-mismatch, the two-ids and in-base re-book cases, and the version-27 migration (which fails if the migration body is a no-op). the run submits nothing more for that decision, finishes its phases (**at most one such order per run**: a second acknowledgement timeout in the same run halts with `AcknowledgementTimeoutError` as today), and until it is settled the unresolved order is carried fail-closed on both sides: an unresolved **buy**'s unfilled notional counts in the buy reserve (req 3's reserve, ADR 0010 amendment 2026-10-01); an unresolved **sell**'s proceeds are **excluded** from the cash the buys phase sizes from, and its position **counts as still held** for `risk.max_gross_exposure` and `risk.max_position_weight`; after the longer poll the existing submit-window and clock check (req 3, req 7 step 6) runs again before any remaining submit; (b) req 4's invariant "a `pending` order exists only under an engaged switch" now reads "a `pending` order exists only under an engaged switch **or** as the one `pending_unresolved` order of a run that ended `ok`", and req 5's "while any order is `pending`, a reconciliation's status is `pending_unresolved`" covers it unchanged, so the end-of-run reconciliation is `pending_unresolved`, cash is not re-based, and one alert of kind `pending_unresolved` is raised; (c) req 7 step 3 gains, **before** collecting outcomes: "read back every `pending_unresolved` order by `client_order_id`; one the broker knows gets its acknowledgement, events and fills journaled as any order's are; one the broker does not know is `cancelled` with reason `not_received` (the existing verdict); **an order still unresolved after that read-back (a read failure, or a broker state the journal cannot map) is a `ReconciliationError` and halts** before step 4": there is no second-run tolerance; and while the switch is engaged, `paper resume` and `paper reconcile` settle a `pending_unresolved` order by the same read-back before any new submit is possible. ADR 0017 E.2 already allows a `pending_unresolved` reconciliation when the book's next one is `ok`.

3. **The four intents (ADR 0015 seam 2; settled).** An order's intent is the pair (`side`, `position_side`): buy-long `buy_to_open`, sell-long `sell_to_close`, sell-short `sell_to_open`, buy-short `buy_to_close`. `OrderRequest` carries `position_intent` explicitly on **every** order, longs included, so the broker never infers a short from an oversell. A long book's request differs from today's only by that field, and a recorded test pins it. **A short open is a whole-share `quantity` order**, never `notional` and never fractional (Alpaca, item 2): the planned short notional over the reference price, floored to a whole share. A short target below one share is `skip_below_one_share`. A cover is a whole-share quantity no larger than the reconciled short holding. `risk.small_account`'s notional rule (amendment 2026-10-18, item 8) applies to buys only.

4. **Phases (ADR 0010 point 2; ADR 0024 item 5's `orders.phase`; settled).** The two phases keep their names and their check order. The **sell phase** carries the reducing intents (`sell_to_close`, then `buy_to_close`) and the **buy phase** the opening intents (`sell_to_open`, then `buy_to_open`). Forced covers go in `exit`. `orders.phase` keeps `sell`, `buy` and `exit`, so no schema version is needed for it. A flip (long to short, or back) is a close in the sell phase and an open in the buy phase, so a name is never long and short at once, and gross exposure falls before it rises. Buys are sized from free cash under ADR 0010's restated cash rule, so they do not wait on short proceeds.

5. **The order id (ADR 0010 point 3, ADR 0015 seam 1; settled).** The id's side token is the intent's: `buy` and `sell` for the long intents (every long id is byte-identical to today's), `short` for `sell_to_open` and `cover` for `buy_to_close`. `next_attempt` is keyed by (`security_id`, token), so the attempt count of a name's long sells and its short opens on one session never mix. The longest id stays within `alpaca.client_order_id_max_length` (128), and a test pins the length.

6. **Borrow availability at submit (ADR 0021's two-flag rule; ADR 0023's allowlist; settled).** Each buy phase already reads `assets` per name. A `sell_to_open` is ordered only when that read says `shortable` **and** `easy_to_borrow` are both true (ADR 0021: one asset is ETB and not shortable). Otherwise the decision is skipped with **`skip_not_borrowable`**, counted in the run's skip cap, its weight left in cash. Its reference price must also be at least the window's frozen `portfolio.short_min_price` (else `skip_short_price`), the backtest's proxy floor. 1. **Inputs (req 6; T249).** `reconcile_run` reads `mergers_as_of(close(S−1))` and passes to `compare`, as `Explanations.mergers`, every **open** merger. A merger is identified by its Alpaca id, which every row items 2 to 5 journal for it names in `explanation_json`. It is open at S when its row has `effective_date ≤ S` and either (a) the ledger still holds its acquiree, long or short, or (b) the acquiree's removal is journaled and the merger is not yet closed (item 4). The removal is item 2's or item 5's row naming the id, or the ended-listing band's `corporate_action_cash` row for the acquiree, linked by the acquiree's `security_id` because it was journaled before the merger row was known. A merger stays open across `ok` reconciliations, whatever date the window's last `ok` reconciliation has. A merger whose window (item 4) had already ended when its row became known opens nothing under (b); under (a), a held acquiree, it is open as usual. **Conflicts.** Two rows with different ids for one acquiree and one `effective_date` (the data spec's `merger_conflict`) are never explained. The first reconciliation at which both rows are known, and either is open or has rows journaled, is a `merger_conflict` mismatch naming both ids, whichever row came first and whether or not the first already explained the removal. That halt happens once per pair: after the owner's resume, the pair is closed, neither row explains anything further, and the acquiree falls back to today's rules (the ended-listing band, or a halt). The owner reads the journaled rows of the first row before resuming. The map is acquiree `security_id` → (merger id, kind, acquirer `security_id` or none, `share_ratio`, `cash_per_share`, `effective_date`, `payable_date`, the cash journaled for it so far: its own rows by id, plus the band's removal row for the acquiree). The acquirer joins the names `reconcile_run` maps to broker symbols (`_symbols`) before the map is built, so a symbol the acquirer shares with the acquiree is an `unknown_symbol` mismatch and never a crash. A row known only after close(S−1) explains nothing at S (no look-ahead).
2. **A cash merger on a long (T249).** The broker no longer holds the acquiree. The due is held × `cash_per_share`. The removal is explained when the cash difference, after the reconciliation's other explanations, is between zero and the due plus the cash bound (`_cash_bound`, the 2026-10-12 rule). One `corporate_action_cash` row removes the held quantity and credits the cash difference; it names the merger id. Any of the due not yet paid comes later (item 4). When the merger row is known by this reconciliation, this rule applies to the name instead of the ended-listing band, because it is the tighter check. When only the delisting is known, the band explains the removal as it does today, and if the merger row becomes known later, the cash that band journaled counts toward the due.
3. **A cash merger on a short (T249; #1930).** This makes item 10's "explained at the store's merger rate with the sign reversed" concrete. The broker's short is gone and its cash fell. The due is −|held| × `cash_per_share`. One `corporate_action_cash` row closes the short (a positive quantity) and debits the cash difference, which must lie between the due and zero, each widened by the cash bound; the rest of the due works as in item 4. This is the one corporate action on a short that item 9 no longer treats as `short_external_change`; every other one still is.
4. **Cash that comes later, and when a merger closes (T249).** Alpaca may remove the position on the effective date and pay on the payable date. Item 2 journals the removal when it happens, with whatever cash has arrived, so the run trades normally and the ledger's position is right. A due has a sign (positive for a long, negative for a short), a lower bound in size (|held| × `cash_per_share`; zero for `stock`) and an upper bound in size (item 5 adds cash in lieu for the stock kinds; for `cash` the two are equal). At each later reconciliation while the merger is open, a cash difference, after the reconciliation's other explanations, that has the due's sign and whose size is at most the rest of the upper bound's size plus the cash bound, is journaled as a cash-only `corporate_action_cash` row naming the merger id: a credit for a long, a debit for a short. Payments in parts therefore add up. An `MA` or `CIL` activity on the acquiree's or the acquirer's symbol is placed against the merger and never against the stock-dividend rule (#1627). The merger's **window** runs through `payable_date` (or `effective_date` when that is null) plus `risk.reconcile_merger_lag_sessions` trading sessions. The merger **closes** at the first of these:
   - the journaled total's size is within the cash bound of the upper bound's size;
   - the first reconciliation after the merger's window ends has run.

   That last reconciliation is a `cash` mismatch, with a detail naming the merger, only when the journaled total's size is below the lower bound's size less the cash bound: cash never paid on a long, or a debit never taken on a short. The merger is closed either way, so after the owner's resume the next reconciliation does not raise it again. Until the cash arrives, the ledger's equity is short of it; the mark and the drawdown rule read that lower equity.
5. **A stock merger on a long, and the stock part of a stock-and-cash merger (T249b; #1762).** The broker no longer holds the acquiree and holds r more acquirer shares than the ledger. The change is explained when both hold:
   - held × `share_ratio` − 1 < r ≤ held × `share_ratio`, within the quantity tolerance (the broker may give whole shares plus cash in lieu, or a fraction);
   - the cash difference lies between zero and the due's upper bound: held × `cash_per_share` (zero for `stock`) plus (held × `share_ratio` − r) × the acquirer's reference price (Definitions > Reference price, close(S−1)) × (1 + `risk.whole_share_price_buffer`), widened by the cash bound.

   Two rows are journaled, both naming the merger id: a `corporate_action_cash` row removes the acquiree and credits the cash difference, and a new adjustment kind, **`merger_receipt`**, adds r acquirer shares. The due's lower bound is held × `cash_per_share` (zero for `stock`) and its upper bound is the band's top above. Cash still short of the lower bound, and cash in lieu that posts later up to the upper bound, work as in item 4. A `stock` merger whose cash in lieu never comes closes quietly at the end of its window; a `CIL` after that is unexplained and halts, as today. The acquirer's broker quantity is compared as one total: the ledger's own acquirer holding plus r. The receipt is an ordinary holding from then on: the next rebalance's plan keeps it when the acquirer is a target and sells it when it is not. No forced exit is added, because the receipt carries the acquiree's weight rather than a new position (open question 22). As in item 2, this rule applies instead of the ended-listing band for the stock kinds.
6. **A stock merger on a short is not explained.** How paper books one is not known (a short in the acquirer? a cash debit?), so it stays a `short_external_change` halt under item 9. So does a stock-and-cash merger on a short. A dated amendment adds a rule once a booking has been observed.
7. **What still halts:** a held acquiree whose only rows the data spec refuses (a stock row with no acquirer symbol, a same-symbol right or escrow row, or a stock-and-cash row with `acquiree_rate ≠ 1`; data-foundation open questions 42, 45 and 46); two rows for one acquiree and one `effective_date` (`merger_conflict`, item 1: once per pair); a removal that neither a merger row nor a delisting known at close(S−1) explains (data-foundation open question 41: the first run halts, and after the owner's resume the next reconciliation explains it once the row is known); cash above the due's upper bound; a total below the due's lower bound when the window ends, which halts once and closes the merger (an election or proration deal will do this); an acquirer with no broker symbol; an acquirer receipt outside the band.
8. **Unverified.** Nobody has recorded whether Alpaca **paper** books mergers at all, on which date, as which activity, or how it pays a fraction (Risks, "Corporate actions at a simulated broker"). If paper never books one, these rules never fire, and today's delisting rules handle the held acquiree. The evidence is the first real event's reconciliation row, read by the owner (open question 24).
9. **Data / interfaces (T249b).** `adjustments.kind` gains `merger_receipt`. The schema takes the next free version, and its migration widens the `kind` `CHECK`. The ledger applies a `merger_receipt` as it applies a `spinoff_receipt`: a positive quantity and no cash. `Explanations` gains `mergers` (T249). No other table changes.
10. **Config keys.** `risk.reconcile_merger_lag_sessions=5`, frozen at start. A window frozen before T249 reads it at this default.
11. **Acceptance (testable; T249 and T249b, on the fake broker and the fixture store with a stored `mergers` row).**
    - A long acquiree removed with cash equal to held × rate reconciles `ok`, journals one `corporate_action_cash` row naming the merger id, and closes the merger.
    - The same with cash above the due's upper bound halts on `cash`.
    - The removal with no cash yet reconciles `ok` and journals the removal; cash equal to the due arriving two `ok` reconciliations later journals one cash-only row and closes the merger; the due paid in two parts journals two cash-only rows and closes the merger.
    - A due not met by the last lag session halts on `cash` once, at the first reconciliation after the window; after the owner's resume, the next reconciliation is `ok` and does not raise the merger again.
    - A removal at S with neither the row nor a delisting known at close(S−1) halts; with the row known at close(S), the reconciliation after the owner's resume reconciles `ok` and journals once.
    - A long acquiree with a known delisting and no known merger row is explained by the ended-listing band, as today. When the row becomes known later inside its window, the band's proceeds count toward the due, and the rest of the cash arriving after it reconciles `ok` with one cash-only row. A row stored after its window, for a removal the band explained, opens no merger.
    - A removal that halted, its row stored after the merger's window: the resumed run reconciles `ok`, journals the removal once and closes the merger (a `cash` halt once if the total is short of the lower bound).
    - A short acquiree removed with cash debited held × rate reconciles `ok` and journals the closing row; the same with cash credited halts `short_external_change`.
    - A short closed with no debit reconciles `ok` and journals the closing row; the debit taken two `ok` reconciliations later journals one cash-only row and closes the merger; a debit never taken halts on `cash` once, at the first reconciliation after the window.
    - A long stock merger with r = floor(held × ratio) and no cash yet reconciles `ok` and journals the two rows; cash in lieu as a `CIL` activity one session later is placed against the due and journaled; the next rebalance's plan treats the acquirer as a held name; a holding of the acquirer from before the merger is counted in the comparison.
    - A receipt r one share below the band halts on `quantity`.
    - A short stock merger halts `short_external_change`.
    - Two conflicting rows known before the removal: the first reconciliation that knows both halts `merger_conflict` once; after the resume, the acquiree's removal falls back to the ended-listing band or a halt.
    - Row A explains the removal, row B for the same acquiree and `effective_date` becomes known later: the next reconciliation halts `merger_conflict` once, naming both ids; after the resume, later cash is not matched to A's terms.
    - The same pair stored in one run and in two runs gives the same reconciliation result.
    - With no merger row and no known delisting, each case halts as today.
12. **Out of scope:** a stock merger on a short; election and proration deals; any read of `mergers` in planning, risk or the backtest.

*Amendment 2026-10-20 (#1997, part (a) of #1983; the owner's decision "A" of 2026-10-20 on #1997; built in the same PR; accepted by the owner's merge).* A partial ingest can leave one universe candidate without its bar at the read session (below "T_i" is the rebalance session being planned, and "its bar" is the bar at close(T_i); at the window's first rebalance this is T_0) while SPY's bar is present, so req 7's staleness check passes. Universe rule 6 (`history`, reason `missing_bars`) then drops that name with no trace, and the plan quietly buys the next-ranked name instead (the scratch break test `test_missing_bar_for_a_candidate_does_not_silently_retarget`, #1983). This amendment makes the drop visible. It adds no halt.

1. **The exclusion (req 7 step 6; #1997).** After `engine.plan` returns the plan at close(T_i), `planning` asks the same provider, at the same read time, for the *no-bar candidates*: the securities the universe dropped by rule 6 with reason `missing_bars` whose **only** missing history session is T_i itself (every other session of the `universe.min_history_months` window has a bar known at the read time). A name missing T_i and any other history session is a plain history exclusion and is not recorded here, as a new listing is not. Only bars with `known_at` at or before the read time count, so a bar ingested later never hides the gap and the rule has no look-ahead. Each such name is written as one `signals` row, `reason = excluded_no_t0_bar` (score and rank null), for the plan's rebalance session, and the plan's `exclusions` carries the reason `no_t0_bar`. It is declared per family in `config.FAMILIES[*].exclusion_reasons` ([ADR 0014](../decisions/0014-strategies-as-registered-objects.md) point 3) for all four families, with no new count name. The name was never a universe member, so `Plan.n_universe`, `paper_plans.n_universe`, the universe-collapse check, the scores, the targets and every decision are exactly what they were; the signals journal gains rows beyond the members, the one place a `signals` row names a non-member. The partition check (`plan._signals`) allows this reason, and only this one, outside the members. A store whose ingest is whole writes none of these rows and every paper path is byte-identical.
2. **The alert (req 11; #1997).** The kind `missing_candidate_bar` joins req 11's list. When the plan has at least one no-bar candidate, the run writes **one** alert for the run (dedupe on (kind, run), session = the run's S) naming the rebalance session and every excluded name, after the plan is journaled and before any order. It is written only on the run that plans anew, not on a `reused` or `lagging` outcome.
3. **The run continues.** Unlike `stale_data`, which means a held name's or a benchmark's data is bad and halts the run (the `stale` result, no order, the switch untouched), this alert reports a *candidate* that is not in the plan: no held position is priced from it, the exclusion is on the record, and the plan over the remaining names is the one the strategy would have chosen had the candidate not existed. So the run neither halts nor engages the kill switch, and the rebalance is neither delayed nor `missed`. The owner sees the alert and the `excluded_no_t0_bar` rows and decides whether to re-ingest; a re-ingest changes nothing for a plan already journaled (req 7's reuse rule), and the next rebalance reads the repaired store. **A held name** with no bar at T_i: when T_i is the session before the run (S-1), req 6's mark step carries the position at its last close and writes `stale_mark` for at most the frozen `paper.max_stale_mark_sessions` (default 3) sessions, and fails the run when the key is 0 or the gap is longer (that failure comes before the plan and records nothing here). Within the limit the run goes on, rule 6 drops the held name from the universe, it is also recorded and alerted here, and this amendment does not change what the plan does with it: outside the universe it is sold whole (`left_universe`), as before. Whether a data gap should realize that sale is the owner's open question on [#2023](https://github.com/josejuarez96/tradepartner/issues/2023); until it is decided, the `stale_mark` and `missing_candidate_bar` alerts are the owner's warning that a sale is about to follow a bad bar. *(Decided 2026-10-20, owner, (b) hold: the held name is kept at its quantity for that rebalance, not sold; the amendment #2023 below, built by T253, supersedes this sentence's sale and item 5's "sold whole" clause.)*
4. **Config and schema.** No new key and no schema version: `signals.reason` already accepts any `excluded_<reason>`, and `alerts.kind` is unconstrained. `ALERT_KINDS` gains the kind; the H1 and twin fingerprints are untouched (the reason list is not a fingerprinted input).
5. **Acceptance (testable), added under "Tracking run and journal".** On the fixture store with TRNS's bar at T_i deleted and SPY's present, the run ends `ok`, journals a `signals` row `excluded_no_t0_bar` for TRNS, writes exactly one `missing_candidate_bar` alert naming it, writes no `stale_data` alert and engages no kill switch; TRNS is not bought; `paper_plans.n_universe` equals the member count; the same fixture with a whole ingest writes neither the row nor the alert; a name missing T_i and one earlier history session gets neither; a held name with no bar at S-1 fails the run at the marks when the frozen stale limit is 0, and with the limit at 3 is recorded, alerted and sold whole (pinned, #2023); a T_i bar whose `known_at` is after the run's cut is still a candidate (no look-ahead).
6. **Out of scope.** Halting on a no-bar candidate (the owner chose exclusion); backfilling the missing bar from the run; a threshold on how many candidates may be missing before the run stops (the universe-collapse check already halts a universe that shrinks past `paper.max_universe_drop_fraction`, and this exclusion does not move its input); a per-name reason for the other rule-6 drops; the backtest engine, whose runs read a complete store (the helper `engine.no_t0_bar_candidates` lives beside `Plan` but no backtest path calls it; the backtest spec's exclusion-reason line is unchanged: the registry declares the reason and the engine fills it empty).

*Amendment 2026-10-20 (#2006; the owner's decision of 2026-10-20 on #2006: build the per-book performance view now in Streamlit, not waiting for the [ADR 0018](../decisions/0018-end-user-web-app.md) app; from the day-in-the-life re-walk Part 2 of 2026-10-20, routine 2 (posted on #2006; Part 1: [docs/research/2026-10-19-owner-day-in-the-life.md](../research/2026-10-19-owner-day-in-the-life.md)); accepted by the owner's merge of this PR; built by the [plan](../plans/paper-trading.md)'s tasks T250 to T252).* The re-walk found no performance view of a paper book: `paper status --book` shows a position count and a value, and the operations page (req 12) shows positions, open orders, the day's signals and the kill-switch state, and no screen shows the equity curve, the day's gain or loss, or the book against SPY or its own backtest. The one place that computes the comparison, `paper report` (req 10), **opens a `kind=tracking` trial** and appends a `paper_reports` row, and it raises `NothingToCompareYet` until the window holds two rebalance sessions (#1923), so it is not a screen and must not be run to look. This amendment adds a **per-book performance card**, read-only, whose numbers code computes from the journal. It sits off the order path: no broker call, no order, no write, no trial.

1. **What the card shows (req 12's page, extended; T250, T251).** Per book, over the sessions the window has marked since it opened, four things, all computed by pure functions over journal rows and all sharing one base:
   - the **base**: the comparison base is the window's frozen `starting_equity` at the **base session B**, the latest session whose close falls at or before `paper_windows.started_at` (the `run.py` first-mark and `marks` as-of rule); B carries `starting_equity`, or `equity_at(B)` when the first mark is already B (the window opened after B's close);
   - the **equity curve**: the ledger equity at each marked session, the same `positions_daily` series the req 10 terms and the mark step read (`marks.equity_at`), one point per marked session plus the base point at B, the book in the accent colour (the design standard's hero chart);
   - the **daily P&L**: `equity(S) − equity(S−1)` per session, its own bar card on its own axis (design standard principle 4: a second measure is a second chart, never a dual axis);
   - **vs SPY total return**: SPY's dividend- and split-adjusted close (`store.asof.adjusted_prices_as_of` at the header's "as of" `known_at`, `include_dividends=True`, so the read is point-in-time; SPY resolves to a security id through `store.benchmarks.benchmark_security_ids`, never by ticker) rebased to the base value at B and selected at the equity series' sessions (extra benchmark sessions are ignored), a muted dashed line in the same hero chart (design standard principle 2: the benchmark is muted), so the comparison is total return against total return, never price-only;
   - **vs the book's backtest tracking**: the `trial_equity` series (the `series = 'strategy'` rows at the frozen base cost level) of the tracking trial the window's **latest `paper_reports` row** names (req 10; latest by `known_at` among `paper_reports_for(conn, window_id)`), rebased to the equity series' value at that trial's **own first session** (`equity_at(T_0)`, req 10's own base, not `starting_equity`), and drawn only over the sessions it covers, once a `paper_reports` row exists (item 3). The trial runs from T_0 to its last completed rebalance, so its line may start later and end earlier than the equity curve: the two spans need not align, and only the SPY series is held to the equity series' sessions.
   The **excess** over SPY is quoted in percentage points, `excess_t = 100 × (P_t / P_B − S_t / S_B)`, zero at B. Every value is a function of stored rows, computed by `execution.performance` (T250) through one read-only connection (T251, the `execution.ops` pattern); nothing is recomputed from live `Settings`, and the frozen `paper.*`, `risk.*` and `execution.fill_price` values come from the window's `frozen_json` as every other reader reads them (req 14). 2. **What the plan does with the weight (T253).** A kept name gets one decision: `skip_zero`, with no side, no reason and no order. Its `drifted_weight` is its weight at S, w_k = quantity × the reference price on S (its latest close at or before S-1, a stale mark when that is older) / equity. Its `target_weight` is the engine's, which is 0 because a kept name is not a member. That matches how the band journals a name it leaves alone, and it keeps req 10's target comparison (`report.compare_targets`) right for the kept name. The other names after a repaired gap are #2052, which predates this amendment. Against a tracking trial that also dropped the name (a permanent hole), both weights are 0 and no row is written. Against one that re-read a repaired bar, the name differs and is classed `late_data`, because the bar was ingested after the plan's `store_max_ingested_at`. A `target_weight` of w_k would instead be classed `bug` on a permanent hole. It is not a full exit (`is_full_exit` is false), and its quantity is unchanged. **The other names** (`equal` weighting, `long_only`) are planned as if each kept name were a name **inside the rebalance band**. A kept name keeps its current weight, and that weight comes off the budget the traded names share. Each traded name's effective weight is its **plan target t** (not `apply_rebalance_band`'s output, which is already scaled) times

   `min(1, max(0, 1 − W_K − H) / T)`

   - W_K = Σ w_k over the kept names;
   - H = Σ the current weights of the names held inside the band (0 when `strategy.rebalance_band = 0`);
   - T = Σ the plan targets of the traded names.

   A name is inside the band, as `apply_rebalance_band` classes it, when |t − its current weight| ≤ band × t. It then keeps its current weight. This is `apply_rebalance_band`'s own reconciliation with the kept names counted among the names held within the band. T253 computes it in one pure helper in `execution/plan.py` from (`plan.targets`, the drifted weights, band, the kept set), which returns H, T and the effective weights. With an empty kept set the helper returns exactly `apply_rebalance_band`'s output, and `backtest/portfolio.py` is not edited. At band 0 with full targets (T = 1) each target becomes t × (1 − W_K). What is left over stays cash. Everything else is today's rule, applied to these effective weights: `left_targets` exits, trims, notional buys, the minimums and dust, and the buy-side `target_notional` cash scaling. The other names' `target_weight` column stays the engine's `plan.targets` weight, as under the band. *Why this rule and not `keep_name`'s:* a `keep_name` override leaves the other targets at full weight. Their targets then sum to 1 on top of W_K. Only the buys shrink, pro rata by spendable cash, while trims stay sized for a larger book than the one held. The band rule is the one the engine and `decisions_from` already share, and it gives the book the strategy would hold with that slot occupied. *Hand case (the T253 test; zero costs, so planned and target notionals agree):* equity 100,000.00 and cash 0.00. A is kept, worth 10,000.00 (w = 0.10). B and C are worth 45,000.00 each. The plan targets B 0.5 and D 0.5, and C has left the targets. The scale is (1 − 0.10) / 1 = 0.9. The result: A `skip_zero` (target 0, drifted 0.10); B effective 0.45 against 0.45 held, so no order (the test asserts no B order and a delta under 0.01, not an exact `skip_zero`, since 0.5 × 0.9 may miss 0.45 by an ulp); C sold whole (`left_targets`, 45,000.00); D bought with a planned notional of 45,000.00. Today's plan would instead sell A whole (`left_universe`, 10,000.00), buy B for 5,000.00 and buy D for 50,000.00. Under **`hold`** weighting nothing changes. Paper refuses `weighting = "hold"` before planning today (#1832) and passes `hold=None`, so this is covered only by T253's direct `decisions_from` test: a live held name is already never re-weighted and never written `left_universe`, so it is `skip_zero` today. Under **`long_short`** the kept name keeps its signed weight, and the scaling runs per leg (open question 28). Paper planning passes no `side` until T235 wires it, so T253 builds `long_only`. Under `long_short` its helper raises `ValueError` on a non-empty kept set, which is unreachable today, and T235 builds open question 28's answer.

1. **The offer, and no ex-date lag bound (req 6; `execution/reconcile_run.py`).** `explanations_as_of` and `reconcile_now` build the `actions` frame with `live_actions_as_of(conn, cut)` at `cut = _cut(session)`, the close of the session before S (`session_close(previous_session(session))`; `_cut`), and pass it to `_explanations`. `_spinoffs` then keeps a `spinoff` row when `ex_date <= S` and `source_action_id` is not empty, and offers it keyed by child `security_id` to `(parent security_id, shares per parent share)`. The stamp is why. The Alpaca parser dates a spin-off at the close of the first session after its date-only `process_date` (`adapters/prices.py:announcement_date_known_at`, called by `adapters/alpaca_prices.py`'s spin-off parse), which can fall weeks after the ex-date, and the writer never lowers it below the close of the session before the ex-date (`adapters/prices.py:spinoff_known_at_floor`; `ingest.py:_add_actions`). So the row is offered from the first reconciliation whose cutoff is at or after its `known_at`, and an `ok` reconciliation that ran between the ex-date and the stamp does not hide it: the read is cut at the store's `known_at`, not at the base's session. 2. **The parent test (req 6; `execution/reconcile_run.py:_spinoffs`, `execution/reconcile.py:compare`).** A candidate row is offered only when the ledger held its parent on the session before the ex-date (`previous_session(ex_date)`), that holding is above the frozen `risk.reconcile_quantity_tolerance`, and it still equals the ledger's stated holding through S (the clock's New York date on a weekend `paper reconcile`; `_stated_through`) within that tolerance; a zero or short parent does not count. The stated holding is the one `compare` multiplies by the ratio (`due = expected[parent] × ratio`), so the bound uses the basis the distribution was earned in. A parent bought, sold or split between the ex-date's session and S fails the equality, so its row is not offered and the broker's child stays a mismatch (never a guess). `compare` explains the child only when it is new to the ledger (its stated holding within the tolerance of zero) and the broker's quantity is above the tolerance, at most the due plus the tolerance and less than one share below the due. It then journals one `spinoff_receipt` for the quantity the broker holds, with no cash.

3. **Until then, and after (req 6; req 7 step 7; `execution/reconcile_run.py:reconcile_now`).** Before a row is offered, the broker's child is a `broker_only_position` mismatch, or `unknown_symbol` when the store cannot map its ticker (`execution/reconcile.py:_position_mismatch`). A mismatch returns no adjustments (`Reconciliation` carries `adjustments` only when `status == OK`), so nothing is journaled, and the ledger's cash base stays the window's latest `ok` row (`_JournalState.base`): the halt holds the base back, so no child is explained twice. While an order is lagging or pending, `compare` lists an explained child as `Allowed` (`deferred spin-off receipt`) and journals nothing; the next `ok` reconciliation books it. The halt starts at the first reconciliation that sees the child, which can be a run's step 8 after its own trades; those trades are not undone. Once an `ok` reconciliation journals the `spinoff_receipt` at S (its `known_at` that reconciliation's stamp), the ledger holds the child, its stated holding is no longer within the tolerance of zero, and the same row cannot propose it again **while the ledger holds it**. After the receipt is sold, a new broker position in the same child inside the due band would read as another receipt; a broker does not re-book one distribution, so that is accepted as remote. The receipt is sold whole, reason `untargeted_receipt`, by `execution/exits.py:forced_exits` (through `_unspent_receipts`) unless the plan has taken the name in hand, as req 7 step 7 says.

It dedupes `client_order_id` against the broker (`get_order`) per the ABC docstring; maps master tickers to broker symbols through one function (class-share separators tested); paces requests at `alpaca.trading_requests_per_minute`; times out and retries per `alpaca.trading_request_timeout_seconds` and `alpaca.trading_max_retries`; maps every broker order status through one table (`new`, `accepted`, `pending_new`, `pending_cancel` → `ACCEPTED`; `partially_filled` → `ACCEPTED` with fills; `filled`, `expired`, `rejected`, `canceled`; **any status not in the table raises `SystemFaultError`**, never a guess); `cancel` is a **request** and returns nothing about the outcome, so the adapter never reports an order cancelled from the cancel call itself; contains no risk logic (ADR 0003 rule 7: the adapter imports nothing from `execution/`); and holds no secret in any exception text. Contract tests run on recorded, scrubbed responses (the Phase 2 recorder pattern) that the owner records once with paper keys. The recording task also answers, in the PR: the accepted fractional quantity precision; the `client_order_id` length limit; whether the paper `cash` reflects same-session sale proceeds (if it does not, the two-phase funding in req 3 invests nothing, and this spec is amended before the wrapper task starts); how cash is rounded per fill; whether the duplicate `client_order_id` check covers terminal orders and for how long (replay depends on it); whether a whole-position quantity sell below `risk.min_order_notional` is accepted; whether a fractional-quantity sell of a non-fractionable asset (a spin-off receipt, a name that lost the flag) is accepted (if it is not, the `whole_share` flag is set for such names at decision time so a full exit sells the whole-share floor and the sub-share residue is `dust`, held and reported; a name that loses the flag **after** its decision is not covered by that, so a refusal also means this spec is amended before the wrapper task starts, #395; the branch itself exists either way); how paper handles a split, a cash dividend, a spin-off and a cash merger on a held name (the #86 report says dividends are not simulated); whether the `Asset` object carries a CUSIP; how many current universe members are not fractionable; the endpoints behind `fills(since)`; and the documented request limit.
3. **Risk-gated wrapper.** `execution.RiskGatedBroker` is the **only** object that calls `Broker.submit` or `cancel` (AST check: no module outside `execution/` imports a `Broker` implementation, and nothing outside `execution/wrapper.py` calls `.submit(` or `.cancel(`). A run hands it the rebalance's journaled decisions and it executes them in **two phases on the same session**: (i) **sells**, submitted before the open; (ii) **buys**, submitted only after every sell of this run is terminal or `paper.sell_wait_seconds` has elapsed since the open (polling `get_order` every `paper.poll_interval_seconds`; buys may therefore land up to that long after the open, by design), sized from `account().cash` **after** the sells (never `buying_power`, so nothing is ever borrowed; a sell still open at the deadline stays in flight and its planned proceeds are not spent), less the **reserve** for our own open buys (ADR 0010 amendment 2026-10-01, #366 Q16): the unfilled notional of every own non-terminal buy from any session, a notional buy's submitted notional minus its journaled filled value and a quantity buy's unfilled quantity (split-adjusted like a remainder) × the reference price × (1 + `risk.whole_share_price_buffer`), in `Decimal` rounded up to the cent; every "cash" below in buy sizing and in the cash rule means max(0, `account().cash` − the reserve), and a reserve at or above cash defers every buy of the phase (written off in a last phase, Definitions). **Buy sizing:** spendable = `costs.buy_notional_after_costs(cash, per_side_bps, commissions, price)` with the reference price `prices_as_of(close(S−1))` (commissions are zero at Alpaca, so the price only matters for per-share commissions); scale = min(1, spendable / Σ over the phase's buys of their remainders) (a first attempt's remainder is its `target_notional`, Definitions: the target already carries the cost reserve, so the cost is deducted once); every buy's attempt = its remainder × scale, so the batch fits the cash the sells raised, every name is scaled alike, and a deferred buy is rescaled against the remaining buys, not against every planned one. A buy of a name whose listing ended at close(S−1) is skipped as `skip_delisted` before the scale is computed, so it takes no share of the cash and the other buys are not shrunk for it (#604). A non-fractionable name is bought by quantity = floor(scaled notional / (reference price × (1 + `risk.whole_share_price_buffer`))), submitted **after** the notional buys and only while the buffered notional plus its modelled cost fits the cash left; one that does not fit is **deferred** like a sub-minimum buy. The formula is pinned by a test. **Re-runs and catch-ups** trade only **open** decisions (Definitions): a first attempt is sized from the plan (a full exit resolved at submit time to the reconciled held quantity, minus the name's residue quantity (req 14) for a **plan** full exit (`left_targets`, `left_universe`, `exclude_name`) or a `window_stop` exit, **except a long-to-short flip's close** (a `left_targets` full exit of a name that also has a short-open trade, a journaled `trade` decision with `side` sell and `position_side` short, among the rebalance's decisions in any state, so the test is stable across re-runs; pinned by `tests/execution/test_phases_flip.py`, #1998), which sells the whole holding, residue included, like a `delisted` exit, so a name is never long and short at once (dated 2026-10-19, owner, #1959; it still nets the name's open sells, and a short open the planner skipped is no flip, so that close keeps its residue), and the **whole** holding for a `delisted` or `untargeted_receipt` forced exit; any other planned quantity adjusted by the splits with `ex_date` in (T_i, S] known at close(S−1), the plan's quantity already reflecting earlier ones; a notional buy scaled as above), and every later attempt is sized for the previous attempt's **remainder** (Definitions); a decision in flight is left to collection, a settled one is done; each attempt gets its own id (e). Every sell order is by **quantity** (ADR 0010 amendment 2026-09-30): a trim decision is notional, and each of its orders is a quantity sell of its remainder at the reference price, rounded down to `alpaca.quantity_decimals` (whole shares on whole-share names), so a gap-down open never sells more than the sell-sum rule checked. That quantity is first capped as Definitions > Remainders says (the holding rounded down, less the residue, less the name's open own sells), so a trim never halts the batch as `limit_breach` after a price drop or beside an earlier open sell; a full exit's quantity is netted of the open sells the same way (Definitions > Remainders, #647 item 5). A sell, trim or full exit, is **held** exactly when its capped quantity is a skip and its uncapped quantity is not (#647 items 5 and 7 owner decisions, 2026-10-03, superseding #605's open-sells-only hold): no order, no `decision_events` row, nothing counted toward the skip cap, the decision open for the next run, like a deferred buy; the wrapper logs one warning line per hold naming the decision, the security and the uncapped and capped quantities, and the buys phase never buys a held name (#719). For a trim, uncapped is its remainder with no cap at all (rounded down, floored for a whole-share trim), so a trim the holding cap alone binds (after a price drop, or with only the residue left) is held, like one the open sells bind. For a full exit, uncapped is the holding-and-residue cap without the open-sells subtraction, so only a skip the open sells cause is held, and a full exit that is `dust` even without open sells still closes as `dust`. A trim below `risk.min_order_notional` (or, for a whole-share trim, below one share) even uncapped is skipped as `skip_below_minimum` (`skip_below_one_share` for a whole-share trim), counted toward the cap, which closes it. A held trim whose holding cap keeps binding (only the residue is left) stays open, so its rebalance stays `pending` (and the open decision blocks a new forced exit of the name, req 7) until it lapses `missed` under `catch_up_lapsed` after `paper.max_catch_up_sessions` with a `missed_rebalance` alert: a broad price drop that caps several trims shows up as that alert days later, not as a `SkipCapError` halt (owner-accepted, #647). Within a phase, every sell is expressed as a quantity (a trim's remainder converted at the reference price, as its order is), the quantities for one name are summed (at most one sell per name per phase, so the sum is with the unfilled own sells), and the sum plus the **unfilled** quantity (submitted minus **journaled** filled quantity, split-adjusted, each put on the `alpaca.quantity_decimals` grid as Definitions > Remainders says and summed exactly) of the name's non-terminal own sells **from any session** must not exceed the reconciled holding (no path to a short). A skip decided at phase time (a whole-share buy that reaches the risk check at zero shares, which the sizing never produces since it defers such a buy (`skip_below_one_share`, counted toward the cap), a name no longer `tradable` (event reason `skip_untradable` for a buy or trim, but **`untradable`**, exempt from the cap like `dust`, for any `forced_exit`, so the name becomes a residue instead of a repeated skip; a name that merely lost `fractionable` switches to whole-share quantity orders instead for a buy or trim, while a full exit still sells the whole holding), a target notional below the minimum, a reused decision for a name whose listing ended after T_i, a full exit fallen below the minimum, or a whole-share **full exit** whose floor is zero such as a sub-share receipt, both phase-time `dust` and exempt from the cap; a sub-share whole-share **trim** stays `skip_below_one_share`) appends a `decision_events` `skipped` row with its reason, which closes the decision. Whether an order goes by whole shares is decided by the decision's journaled `whole_share` flag (a name that became `fractionable` after a `whole_share` decision stays whole-share), except that a **buy or trim** of a name no longer `fractionable` at phase time goes by whole shares, floored: a 9.5-share trim sells 9, and since the journaled flag is false its 0.5-share remainder is measured against `risk.min_order_notional` (Definitions > Decision): when it is worth at least that minimum at the reference price the trim stays **open** and the rebalance cannot reach `executed` on that run, and the next attempt floors the remainder to zero and closes it `skip_below_one_share`, which counts toward the skip cap; below the minimum it settles. A buy of such a name whose whole-share floor is zero is **deferred** by the sizing (`size_buys`: no order, no skip row, no cap count), like a sub-minimum buy, and written off under the Definitions rule. A **full exit** goes by the decision's flag alone: on a name that lost `fractionable` it sells its full-exit quantity on the decision's basis, fractional included, and never halts on `whole_shares` (owner, #395). Whether the broker accepts that fractional sell is req 2's open recording question. If it refuses it at `submit`, the exception halts the run (req 4's empty `submit` allowlist); if it accepts and later reports it `rejected`, the rejection counts toward `risk.max_rejections_per_run` like any other. Either way the decision stays open; if the recording shows a refusal, this spec is amended before the wrapper task starts (req 2). Open `forced_exit` decisions are re-attempted for their remainder by the first in-window run, in the sells phase on a fill session, and `plan.decisions_from` emits **no** decision for a name that has an open or in-flight `forced_exit` decision (the forced exit handles it). A `LimitBreachError` or `SkipCapError` abandons a rebalance only when the halted batch contained that rebalance's decisions; a forced-exits-only batch that halts leaves the pending rebalance as it was. Before the first `submit` of each phase it re-reads the derived kill-switch state and the unconsumed `engage_kill_switch` overrides, and if engaged submits nothing more and ends the run `skipped_kill_switch` (a run result, not a decision state; the open decisions stay open for the run after the release); a price check the wrapper makes before the first phase (the open-buy reserve's pre-check, which halts on an unpriced open quantity buy before any sell is submitted) runs only after one such read finds the switch clear, so an engaged switch never ends the batch in that halt: it ends `skipped_kill_switch`, or `ok` with nothing submitted when no decision is left to attempt (owner decision on #692); then (a) runs the ADR 0007 clock pre-check: well-formed; not earlier than the `finished_at` of the last `ok` ingestion run; not later than close(S) + `risk.clock_max_sessions_late` sessions; the wrapper and the adapter hold the same clock object; every later reading is monotonic, or `ClockError`; (b) builds and validates every `OrderRequest` of the phase (a `ValueError` here halts, ADR 0007 point 6); (c) checks the phase's batch against the limits, every one from config: per-name target weight ≤ `risk.max_position_weight`, and, for every name the phase buys, its held value after the phase ≤ `risk.max_position_weight` × equity (equity is the ledger equity at the reference prices at the phase start; held value is the ledger quantity at the phase start plus this phase's buy, at the reference price, with a whole-share buy at the buffered price) (names the phase does not buy are not checked, so drift alone never halts); at most one order per (name, side) in the phase; per-order notional ≤ `risk.max_order_notional_fraction` × equity for buys and trims, with full exits (every forced exit, `window_stop` included) exempt so a drifted name can always be exited (ADR 0010 amendment 2026-09-30); gross exposure after the batch ≤ `risk.max_gross_exposure` (no leverage); every sell quantity ≤ the reconciled held quantity, rounded **down** to `alpaca.quantity_decimals` (long-only, no shorts, ever); buys sized after the modelled cost (`costs.*`) within cash less the reserve, compared strictly with no tolerance, with notionals rounded down to the cent and the check computed in `Decimal` against the same `account().cash` reading used for sizing (sizing uses the same cost function in `Decimal`, `costs.commission_per_order` once per buy order, so a correctly sized batch always passes; a property test pins it) (`risk.reconcile_cash_tolerance` is a reconciliation key only); an order whose name the `assets` read lacks (`asset_missing`) or a whole-share order with a fractional quantity (`whole_shares`), both fail-closed; order count ≤ `risk.max_orders_per_run`; a **batch** that breaks one of these halts with `LimitBreachError` naming the rule before any submit. Per-name conditions **skip** the name instead of halting, each journaled with its reason: not `tradable` (`skip_untradable`); a non-`fractionable` symbol is bought or trimmed by **whole-share quantity** rounded down; a trim is skipped only when that rounds to zero (`skip_below_one_share`), while a sized buy that floors to zero is deferred (above); a full exit follows its decision's flag (above); a notional below `risk.min_order_notional` (`skip_below_minimum`; a plan full exit below it is `dust`, retried every fill session and not counted toward the cap — a `delisted` or `untargeted_receipt` forced exit's `dust` is never re-decided each session instead, req 7 (req 14 for a `window_stop`'s); a `whole_share` full exit is `dust` when less than one share remains or its notional is below `risk.min_order_notional`, #366 Q3); a name whose listing ended at close(S−1) (`skip_delisted`, handled by req 7's forced exits). Skips other than `dust` and `untradable` above `risk.max_skips_per_run` halt with `SkipCapError` before any submit and before any `decision_events` row of the phase is written, and the rebalance is abandoned `missed` with reason `skip_cap`: many skips are a fault in disguise. 4. **Halt path and rejections (ADR 0007).** The rejection allowlist is one frozen constant per `Broker` method, pinned by a test, and the per-candidate reasoning is: `submit`: **empty** (an adapter's "not tradable" and "not fractionable" are pre-checked in req 3(c), except the deliberate fractional full exit of a name that lost `fractionable` (req 3, #395), whose refusal halts like any other, so a rejection for them at submit means state changed mid-run; "insufficient buying power" means the ledger and the broker disagree; "market closed" is a scheduling fault); `cancel`: `{OrderNotOpenError}` (the order finished before the cancel: journaled `cancel_noop`, not a fault; `UnknownOrderError` on cancel halts, the journal and the broker disagree); `get_order`, `positions`, `fills`, `account`, `open_orders`, `assets`: **empty**. Every other exception, `SystemFaultError` first, halts. An asynchronous `rejected` status is not an exception: it is a terminal chain state counted against the **submitting** run; the run that observes the count exceed `risk.max_rejections_per_run`, or observes every order of a run rejected, halts with `RejectionCapError`. A `DuplicateClientOrderIdError` triggers `get_order`: identical fields adopt the order as a **replay** (journaled as such: the journal lost an attempt the broker kept); any difference or a failed fetch halts. **What a halt does here, in order:** appends the `kill_switch` `engaged` row (retrying the lock per `store.lock_retry_seconds`; if the write still fails, the alert is delivered through every non-store channel with kind `kill_switch_write_failed` (req 11 guarantees one is configured) and the process exits with a **distinct exit code reserved for a failed halt write**, never the 1 a crash exits with, so the plist and the runbook can tell a store failure from a crash; *owner decision 2026-10-01, #366 Q22 (ii); `wrapper.WRITE_FAILED_EXIT_CODE`, 3, landed with [#515](https://github.com/josejuarez96/tradepartner/issues/515)*); journals the fault; best-effort cancels this run's **acknowledged** non-terminal orders (a `pending` order, one with no broker-acknowledged event, is left alone for `paper resume`), journaling a **non-terminal** `cancel_requested` event with reason `halt` **before every cancel call, whatever its outcome**, followed by `cancel_noop` (the order had already finished) or `cancel_failed` (the halt stands) where the call says so (an order whose `cancel_requested` row cannot be written gets no cancel call and stays working at the broker after the halt, the engaged switch blocking any new order: accepted for paper, where the exposure is one DAY order on a paper account, *owner decision 2026-10-01, #366 Q24 (a)*; revisited at Phase 6 entry, where cancelling first and journaling afterwards would be an amendment of this rule); then reads each such order once through `get_order` and `fills` and journals its fills and, only if it is already done, its terminal event (a `get_order` error here is journaled `cancel_failed` and the halt stands; an order still `pending_cancel` stays in flight and is collected by the next run's step 3 or by `paper resume`, which is what makes a fill after the cancel request land in the ledger); writes **one** alert (req 11), with kind `reconciliation` for a `ReconciliationError`, `rejection_cap` for a `RejectionCapError`, `skip_cap` for a `SkipCapError`, or `halted` for any other fault, its message still carrying the fault's type (*owner decision 2026-10-03, #644, Option A*); writes the run's result row `halted`; re-raises. **Exception:** `StaleDataError` is a data fault, not a system fault in the ADR 0007 sense: it halts the run and alerts but does not engage the switch, because the next successful ingest cures it and the next run re-checks. **A `LimitBreachError` abandons the rebalance:** a `rebalance_events` row `missed` with reason `limit_breach` is written so a resume does not re-run the same breaching decisions every session. **Unknown state:** an order is `pending` while it has no broker-acknowledged event (`accepted`, `replay`, a fill or a terminal event), whatever `cancel_*` rows follow. A `pending` order, whether its `submit` raised or a crash left it, is settled only by `paper resume` (req 5), never by a run: `get_order` found → its events journaled from the broker's status; `UnknownOrderError` → terminal event `cancelled` with reason `not_received` (the broker dedupes by `client_order_id`, so an id it does not know was never received; the recording task confirms the dedupe covers terminal orders, and the reconciliation that follows catches a position the ledger lacks if it does not). The decision is then open again and the next run makes a new attempt. *Amended 2026-10-03, #571:* an **acknowledged** order the broker no longer knows (`get_order` raising `UnknownOrderError` at a collection, as after a paper-account reset at Alpaca) is a fault under the empty `get_order` allowlist, so every run halts at its collection and `paper resume`'s collection raises the same way; no collector can make it terminal, and the owner settles it with `paper settle` (req 17).
5. **Kill switch, persisted and derived.** An append-only `kill_switch` table holds `engaged` and `released` events with source (`owner`, `fault`, `drawdown`), fault type, reason, run id and, on release, the reconciliation id and the equity the drawdown peak resets to. The state is **derived**, and read before anything else a run or a resume does: engaged when the latest row is `engaged`, or when any **earlier** run (never the reading run itself) has a result row `halted`, `crashed` or `failed`, or no result row at all, with no `released` row after **both** that run's `started_at` and its `finished_at` (*amended 2026-10-01, #366 Q7 (a), the rule as #331 built it*: a release stamped at or before a faulted run's `finished_at` clears nothing, so a release clock running ahead of the run's cannot open the switch; and a run with no result row is cleared by no release at all: `paper resume` closes it as `crashed` first, which gives it the `finished_at` the rule reads); so a lost write or a crash cannot leave the switch open. Engaged by: any halt except `StaleDataError`; a crash (an unfinished run, through the derived state); the owner (`paper kill --reason`, or an `engage_kill_switch` override: a run or a phase boundary that finds an override with no `engaged` row citing its `override_id` appends one, so an override engages exactly once and a release ends it, req 3); the drawdown trigger, evaluated at the mark step: ledger equity below the window's peak (initially `paper_windows.starting_equity`; the peak resets at each release to the ledger equity at the last mark, recorded on the release row) by more than the frozen `risk.max_drawdown`, firing once per crossing. A reader that does not hold the run lock (the page, `paper status`) treats a run without a result row as unfinished only when the lock is free; while it is held, the reader shows "run in progress" instead of an engaged switch. While engaged, `paper run` still collects outcomes, reconciles and marks (read-only broker calls) but submits nothing and ends `skipped_kill_switch`; a pending rebalance stays pending and is traded after the release if the catch-up window still allows, else becomes `missed` with reason `kill_switch`. While any order is `pending`, a reconciliation's status is `pending_unresolved` whether or not a difference exists (so cash is never re-based over an unsettled order), and it reports differences on the order's symbol, and a cash difference up to Σ |notional| over the pending orders (a quantity order counted at quantity × reference price × (1 + `risk.whole_share_price_buffer`)), instead of halting, without re-basing cash (the switch is already engaged and the resume settles them), so the marks still run and other faults stay visible. Released **only** by the owner with `paper resume --reason`, which, in order: takes the run lock; journals its `resume_invocations` row; closes any unfinished run (`crashed`); **settles every `pending` order** (req 4); collects every non-terminal order; with `--accept-broker-fills` only, journals the residual synthetic fills for orders past the lag bound (req 8), and without it refuses while any such order exists; refuses while a run the release would clear (`halted`, `crashed` or `failed`) has a rejection-cap verdict (req 4), unless the owner passes `--accept-rejections`, which accepts only those verdicts, records them on a `resume_acceptances` row before reconciling, and lifts no other refusal (no run, schedule or config sets it); runs reconciliation; refuses unless it is `ok` (a `fills_lagging` reconciliation inside the bound refuses too, req 8, #366 Q21); and otherwise appends `released` carrying the `resume_id`. After a release, the next run continues the pending rebalance with new attempts for its open decisions: on the same session if the submit window allows, else as a catch-up. No config, flag or page can bypass an engaged switch. *Amended 2026-10-03, #571:* `paper settle` (req 17) is not a release and writes no `kill_switch` row; it runs only while the derived switch is engaged, and the resume that follows it needs everything above.
6. **Reconciliation and corporate actions.** Runs at the start of every tracking run (after collecting outcomes) and at the end, and on `paper reconcile`. It checks `account().account_id` against the window's; compares, per symbol, the ledger quantity adjusted through S with `positions()` within `risk.reconcile_quantity_tolerance`; ledger cash with `account().cash` within `risk.reconcile_cash_tolerance`; the journal's non-terminal orders with `open_orders()` (each side must explain the other; an own-prefix broker order with a `pending` journal row is a resume matter, req 4, not a foreign order; a position difference equal to an open order's collected `fills` is explained by those fills); and flags anything the journal cannot explain (a foreign-prefix order, a symbol never journaled). An `ok` reconciliation records the broker's cash, which re-bases the ledger's cash (Definitions). **Explanations**, all from rows with `known_at ≤ close(S−1)`: a quantity change equal to a split's ratio with `ex_date ≤ S`; a removed position for a name whose listing ended (delisting or cash merger), with the broker's cash change journaled as an `adjustments` row of kind `corporate_action_cash` and applied to the ledger; a new position in a name that a spin-off with `ex_date ≤ S` names as the child, journaled `spinoff_receipt` and sold whole by the next run as a forced exit (`untargeted_receipt`). *Owner decision 2026-10-01 (#366 Q18):* a child links to its parent through a `corporate_actions` row with `action_type = "spinoff"`, `security_id` = the child, `ratio_or_amount` = child shares per parent share and `source_action_id` = the parent's `security_id` (T64's convention, no dedicated column). No adapter stores spin-offs yet ([#473](https://github.com/josejuarez96/tradepartner/issues/473), after T48b's recording), so until then a spin-off child the broker books is unexplained and halts here for the owner to fix by hand, and until #473 cash in lieu of a fractional child share is not an explanation either: it halts as a `cash` mismatch and is resolved by hand too (#412). A cash dividend is **not** expected from paper (#86 S27); if the broker credits one anyway it is journaled `dividend_cash` and applied. Any residual is `ReconciliationError`: halt, kill switch, alert. *Owner decisions 2026-10-01:* (#366 Q22 (i)) a failing `paper reconcile` engages the switch and exits non-zero but writes **no alert**, because reconciliation alerts are run-scoped and the command has no run; the owner runs it by hand and reads the exit, so no session-scoped kind is added. (#366 Q23 (a)) Broker cash that arrives a session late halts for now: a delisted position the broker removes on one session and credits on a later one journals zero proceeds on the first and halts as a `cash` mismatch on the credit ([#411](https://github.com/josejuarez96/tradepartner/issues/411)), and a dividend credited after the reconciliation that covers its ex-date halts the same way (the store has no pay date); both are resolved by hand until T48b's recording shows how paper books them, and the rule is decided then. Every reconciliation writes a `reconciliations` row with its status and mismatches, so "reconciled since the last order" is a query.
7. **Tracking run.** `paper run` (the session is always the clock's; a non-session exits `mark`-less with a `no_session` result; with no open window, as before `paper start` or after `paper stop`, it exits `no_window` right after the lock, with no broker call, no `paper_runs` row and a `no_window` alert at most once per session, the dedupe key being (kind, `alerts.session`: the calendar session containing `at`, or the next session on a non-session day)). Sequence: (1) take the run lock; read the derived kill-switch state; write the `paper_runs` row; close any unfinished earlier run as `crashed`; (2) staleness: the last `ok` ingestion run must cover S−1 for `ingest.reference_symbol`, else `StaleDataError` before any broker call that needs the store's explanations (on a fill session the rebalance stays pending); (3) collect outcomes for every non-terminal journaled order (`accepted`, from any session; a `pending` one is a resume matter) via `get_order` and `fills(since)`, journaling fills and terminal events, and evaluate the rejection cap for their submitting runs; (4) reconcile; (5) mark: `positions_daily` for **every session since the last mark through S−1**, each from the ledger quantities adjusted through that session and `prices_as_of` at its close, with the `tradable` flag of each held name from this run's `assets` read (the journal source of "still untradable" in req 14), so a missed or halted run never leaves a month-end without a mark; then the drawdown check; (6) if S = F_i, or a rebalance is `pending` and S ≤ F_i + the frozen `paper.max_catch_up_sessions`: if neither decisions nor a `paper_plans` row exist for T_i (an empty committed plan is re-used, #366 Q6), open the plan trial, plan at close(T_i), apply the overrides naming T_i (req 9), build and journal the decisions and the `paper_plans` row (a name leaving the targets is sold whole by quantity; other trades are notional, target minus drifted ledger weight; names whose listing ended by close(S−1) are dropped as `skip_delisted`; `n_orders_below_min_at_live_capital` is computed once per plan for the same decisions at `paper.live_capital_reference`, no order), close the plan trial (*owner decision 2026-10-01, #366 Q6 (a)*: a plan with **zero** decisions writes its `paper_plans` row and closes its trial but never executes the rebalance, since `executed` needs at least one decision (Definitions): the rebalance stays `pending`, each catch-up run **re-uses** the empty plan (its `paper_plans` row makes `planning.plan_rebalance` answer `reused`; nothing is planned again, Definitions > Decision), and it lapses to `missed` on schedule, listed separately in req 10. Zero decisions occur only when the plan's held-or-target set is empty (no target weight and nothing held outside an open forced exit); a held name already at its target gets a closed `skip_zero` or `skip_below_minimum` decision, so a month in which H1 holds its targets exactly reaches `executed` through skips, not `missed` (the note on #366 Q6 predates T53b's `skip_zero`)); then, only if the **sells phase starts** inside the submit window [open(S) − `paper.submit_window_before_open_minutes`, open(S) + `paper.submit_window_after_open_minutes`], hand the **open** decisions to the wrapper (req 3); a fill session whose run is outside the window leaves the rebalance `pending` and trades nothing; (7) forced exits: on a fill session they join the **sells phase** of step 6 (their proceeds and the batch limits counted with it); on any other session they are a wrapper batch of their own inside the same submit window, else left for the next in-window run. A new forced-exit decision is never created for a name that already has an **open or in-flight** decision in the pending rebalance (that decision handles it), an open or in-flight `forced_exit` decision (re-attempted for its remainder instead), or a non-terminal own sell order from any session; nor for a name whose latest `forced_exit` (by `known_at`, then decision id) is settled, or closed by a `decision_events` `skipped` row with reason `dust`, while its holding is not above that exit's remainder (settled) or planned quantity (`dust`: for a `delisted` or `untargeted_receipt` exit the whole holding it was made for, before the whole-share floor; for a `window_stop`, its excess over the residue, floored when `whole_share`; not split-adjusted, so a split makes one more decision, closed `dust` in turn; never re-priced, so a price recovery does not reopen it before the window stop, while a settled remainder is re-derived each session and reopens once it reaches the minimum, except a `whole_share` full exit's remainder under one share): the remainder below the trading minimum is a `dust` residue, held and reported, never re-decided each session (*owner decision 2026-10-01, #505*; this block covers this step's `delisted` and `untargeted_receipt` exits only: a `stop` run still makes req 14's `window_stop` exit for such a name, closed `dust`, so the residue is counted and listed): a held name whose listing ended at close(S−1) and is still tradable is sold whole (`forced_exit`, reason `delisted`); a Form 25 **transfer** to another exchange does not end the listing (the name keeps trading there), so neither this forced exit nor step 6's `skip_delisted` applies to it; an untradable one gets the same `forced_exit` decision (reason `delisted`) closed at once by a `decision_events` `skipped` row with **event** reason `untradable`, is marked at its last close, and is re-evaluated on the next session; a `spinoff_receipt` is sold whole (reason `untargeted_receipt`); (7b) collect this run's own orders via `get_order` and `fills(since)` until each is terminal or `paper.accept_wait_seconds` has passed since the step began (an absolute deadline; an order still open then stays in flight for step 3 of the next run), journaling fills and terminal events, then write `rebalance_events` `executed` when no decision of T_i is open or in flight (the same test runs after step 3 on every run, before the lapse rule, so a fill collected late still executes the rebalance), and the `unspent_cash` alert when cash exceeds the frozen `risk.max_unspent_cash_fraction` of equity at that moment; (8) reconcile again; (9) write `paper_run_results` with status `ok`, `halted`, `stale`, `skipped_kill_switch`, `crashed` or `failed` (any other exception) and `invoked_by` (`scheduler` when `TRADEPARTNER_INVOKED_BY=scheduler` is set and stdin is not a TTY, else `tty`). A rebalance still `pending` after the frozen `paper.max_catch_up_sessions` gets a `rebalance_events` `missed` row and is not traded until T_{i+1}; its reason is `kill_switch` when the derived switch (req 5, from the window's `kill_switch` rows and run results) was engaged at **any instant** of the catch-up period, from open(F_i) to close(the boundary session): already engaged at open(F_i), or engaged by a row or a faulted run stamped inside that interval, whether or not a run happened on that session, so a switch released the session before the lapse still yields `kill_switch`; `catch_up_lapsed` otherwise: the reason names the cause (*owner decision 2026-10-01, #366 Q19 (b)*; `marks.lapses` reads the switch rows and the faulted runs of that interval, built by [#514](https://github.com/josejuarez96/tradepartner/issues/514)). A run that finds no `paper_runs` row for S−1 writes a `missed_run` alert.
8. **Journal chain (ADR 0005 check 2).** Append-only tables (below), every row with `known_at` and `ingested_at` per the Definitions rule, written through `store.journal` (inserts and reads only, like `store.registry`). Every collector (step 3, step 7b, the halt read, `paper resume`'s settlement) reads `fills(since)` account-wide with `since` = min(the latest `collected_through` across every `fill_cursors` row, the earliest `known_at` of the `pending` event of any non-terminal own order) − `paper.fill_read_overlap_seconds`, inclusive at equal timestamps, then appends a `fill_cursors` row keyed by its own invocation (a run id, or a resume invocation id that `paper resume` journals whether or not it releases) with the latest `filled_at` seen; it journals a fill only once (`fills.broker_fill_id` is unique and a collector's duplicate check and superseding step look up the id across **all** rows, superseded ones included, as an insert-or-ignore, so overlapping reads never double the ledger and never trip the constraint, and a fill that lags a later one is picked up on the next read because the window reaches back to the oldest open order); and it journals an order's terminal event **only once its journaled fills add up to the broker's `filled_quantity` within the frozen `risk.reconcile_quantity_tolerance`**; until then the order stays in flight, whatever `get_order` reports, so a status that arrives before its fill activity can never leave a terminal order without its position. An order is **`fills_lagging`** whenever it is non-terminal in the journal and `get_order`'s `filled_quantity` exceeds its journaled fills by more than the frozen `risk.reconcile_quantity_tolerance`, whatever its broker status (a finished order whose activity has not arrived, or a still-open partly filled one at a phase deadline). Reconciliation explains such an order's symbol quantity gap and a cash difference up to the unjournaled filled quantity × `filled_avg_price`, without re-basing and without halting, so a lagging fill feed never engages the switch; every reconciliation row, whatever its status, lists its lagging `client_order_id`s in `mismatches_json`; every reconciliation, `paper reconcile` included, first reads `get_order` for every **acknowledged** non-terminal order (never a `pending` one, which `paper resume` settles and which the reconciliation reports `pending_unresolved`) and passes those readings to `reconcile.compare` as its `lagging` input, so a finished order whose activity has not arrived is explained everywhere, not only after a run's collection step; but the lag is bounded: an order still `fills_lagging` at any **`paper run`** collection **at or after** `risk.max_fill_lag_sessions` sessions (validated ≥ 1) past the `known_at` of the first reconciliation row that listed it is a `ReconciliationError` (halt, switch, alert) the first time, and while the switch is already engaged the same condition is reported as a `mismatch` row without a new halt, so the run still marks; in `paper resume` the condition means refuse without the flag or synthetic fills with it, and **no plan is made while any order is `fills_lagging`** (a fill session so blocked leaves the rebalance `pending`, so a filled position can never be bought twice). The "reconciled holding" is always the **ledger** quantity (the conservative choice while a lag is open). A reconciliation's status is `mismatch` over `pending_unresolved` over `fills_lagging` over `ok`; `paper resume` **refuses** while any order is `fills_lagging`, inside the bound too (*amended 2026-10-01, #366 Q21 (a)*: a release accepts only an `ok` reconciliation, so the ledger's cash is never re-based over a fill the journal lacks; the owner waits for the feed, or, once the bound has passed and `get_order` reports the order finished, releases with `--accept-broker-fills`; the refusal is not a halt, and the switch stays as it was). **The way out when the feed never delivers a fill** is an owner decision, logged: `paper resume --accept-broker-fills --reason` journals, for each order past the bound **that `get_order` reports finished** (an order the broker still holds open is refused, since it may yet fill), a **synthetic fill for the residual only**: quantity = `get_order`'s `filled_quantity` − Σ journaled quantity, price = (`filled_quantity` × `filled_avg_price` − Σ journaled quantity × price) / that residual, `filled_at` = the order's `filled_at` from `get_order` (nullable on `Order`; close of the order's session when the broker gives none; `source = broker_status` rows are exempt from the broker-clock skew check), `source = broker_status` and `broker_fill_id = synthetic:<client_order_id>`, which completes the order without touching the fills already journaled (the implied residual price may fall outside the session's range or below zero when the broker rounded its average; it is stored as computed with `price_implied = true`, the `price > 0` check applies only to `broker_feed` rows, and `lots.rebuild` and the FIFO realised-P&L outcome merge an order's fills into one acquisition or disposal at the order's average price whenever any of its fills is `price_implied`, so no lot ever carries a wild or negative basis); a real fill for that order arriving later is journaled with `superseded_by` the synthetic one, and **every reader of `fills`** goes through one `store.journal` accessor that filters `superseded_by IS NULL` (the ledger, `lots.rebuild`, outcomes, the fill-timing term, the fill-completeness test, `plan.remainder` and `plan.decision_state`), so nothing is ever counted twice. Without the flag, a resume with an order past the bound is refused (not halted). *Amended 2026-10-03, #571:* the synthetic fill is the only way a fill that exists enters the ledger; when the broker's book shows no fill of the order (no fill in the stream, no position in the fill's direction), a synthetic fill would only make a position the broker lacks, and the owner settles the order without a fill with `paper settle` (req 17), which refuses while the book shows one. For every order: exactly one `orders` row (written before submit, with its `pending` event), one or more further `order_events` rows (`accepted` with the broker's order id, `replay`, fills, cancels) of which exactly one is terminal in `{filled, expired, rejected, cancelled}`, zero or more `fills` rows, and exactly one `outcomes` row, **due** at the first run after close(T_{i+1}) for an order of rebalance i (or after the exit session for a forced exit), whatever the order's terminal state: for a filled buy, the position's return from the order's average fill price over its filtered fills to the mark at close(T_{i+1}) and its contribution; for a filled sell, the realised P&L on the FIFO lots closed; for an expired, rejected or cancelled order, kind `not_executed` with the name's return over the same horizon (the cost of the miss); for a partially filled then expired order, both. Fills carry the broker's `filled_at` as `filled_at` and the collection time as `known_at`. `paper check` reports every order whose chain is incomplete once its outcome is due.
9. **Overrides (ADR 0005 check 3, ADR 0008).** The override page is the dashboard's **only write**: a form that appends an `overrides` row through a short-lived write connection (`store.db.open_for_write`, "store busy" when locked), with kind ∈ `{exclude_name, keep_name, engage_kill_switch}` (and `settle_order`, *added 2026-10-03, #571*, which only `paper settle` writes, req 17: the page never offers it and the shared writer refuses it), the rebalance session it applies to (or none for the kill switch), the name, and a reason whose trimmed length is at least `paper.min_override_reason_chars` (a `CHECK` on the trimmed length ≥ 1 in the schema; the frozen minimum in the form, the CLI and `paper check`). `exclude_name` drops the name from the targets and sells it if held, its weight staying in cash (not re-spread); `keep_name` keeps the name at its drifted weight (no trade) — on a name not held that weight is 0, so nothing is bought (`plan.decisions_from`, #470). An override is consumed by the run that plans T_i, which journals the decision as `override` with the override id (consumption is visible only through `decisions.override_id`; nothing is updated); the resulting order passes the wrapper like any other (ADR 0008 point 4). **Precedence and consumption** (`plan.decisions_from`, #470): a name with an open or in-flight `forced_exit` decision gets no decision at T_i at all (its forced exit handles it, req 3), and a name whose listing ended at close(S−1) gets `skip_delisted` instead; both are checked before any override, so an override on such a name is not applied and not consumed. An override naming a security that is neither held nor targeted at T_i gets no decision at all (`decisions_from` decides only the held-or-target set), so it is never consumed, with no record of why. `engage_kill_switch` takes effect at the next run or phase boundary, once (req 5). A month with an override is flagged `override` in the tracking comparison and listed separately (excluded from the maximum only under the amended rule, req 10); the target comparison reports overridden names as `override`, never as a bug. No memo panel exists in Phase 4; Phase 5 adds one additively and the form keeps working with none.
10. **Tracking comparison (ADR 0005 check 1), rule fixed before the first order.** `paper report` opens a `kind=tracking` trial over [T_0, last completed T] on the real store with the frozen parameters (the Phase 3 window rule is extended: a `tracking` window must start at or after the first rebalance session after `holdout.end`; `tracking` trials never count in N, V or holdout spends), then computes per month i: the **raw difference** = paper return (ledger equity at close(T_{i+1}) over close(T_i), from `positions_daily`) minus the trial's month return; the **dividend term** = Σ over names held on each ex-date in the month of amount × ledger quantity, over equity at close(T_i), from `corporate_actions` rows with `known_at ≤ close(T_{i+1})`, excluding any dividend the broker credited (`dividend_cash`, req 6), so nothing is counted twice (what the backtest reinvested and paper never received); the **fill-timing term** = [Σ over buys of (paper fill price − the frozen `execution.fill_price` bar price on the fill session) × filled quantity − Σ over sells of the same] over equity at close(T_i), so a buy that paid more or a sell that received less than the bar price makes the term **positive**, the amount by which execution timing lowered paper's return; the **residual** = raw + dividend term + fill-timing term (both terms add back what paper lost relative to the backtest for reasons the backtest cannot model); the **residue term**, printed beside them and never part of the residual: Σ over names with a residue at close(T_i) (the residue function evaluated on rows known at close(T_i)) of residue quantity × (close(T_{i+1}) split-adjusted to T_i − close(T_i)) over equity at close(T_i), what the residues paper is stuck with contributed; the **modelled cost per rebalance** = the trial's base-level `cost_paid` at T_i over its equity at close(T_i). The check applies `paper.tracking_k` × that month's modelled cost to the series the window's frozen `tracking_rule` names: `raw` (ADR 0005 as written: only months whose rebalance has a `missed` event are excluded from the maximum, listed separately) or `residual` (open question 4; it needs an ADR 0005 amendment merged before `paper start`, and that amendment is also where months with an override are excluded, since ADR 0005 as written excludes missed months only); months with `skip_*` decisions are listed with their skipped names (not excluded); all four series are printed every time. `paper report` appends a `paper_reports` row (window, trial, through session), which is what `paper check` reads. It also compares, per fill session, the decisions' targets with the trial's `trial_weights`: a difference is reported as `override` when the name was overridden, as `late_data` when any bar, action or filing for the name has `known_at ≤ close(T_i)` and `ingested_at` later than the plan's recorded `store_max_ingested_at` (the trial saw a row the plan could not; ADR 0003 rule 2 stamps late bars at the session close), and as `bug` otherwise (a look-ahead or determinism fault). Backtest conventions paper cannot copy are listed with each report: `stale_exit`, `missing_fill` on the backtest side, the exit at the last close, sells and buys at one price versus two phases, paper's `unspent_cash` (the cost reserve and any deferred buys the backtest never has), and the residues (`dust`, `untradable`, carried), through the residue term above.
11. **Alerts.** An `alerts` table (kind ∈ `{run_failed, halted, stale_data, kill_switch, kill_switch_write_failed, reconciliation, rejection_cap, skip_cap, missed_run, missed_rebalance, drawdown, unspent_cash, locked, no_window, lot_ledger, stale_mark, missing_candidate_bar}`, run id, message; `stale_mark` added 2026-10-18 by the owner's decision on #1763: a tradable held name with no S-1 bar was marked at its last close, run-scoped, one alert naming every such name and its gap, for at most the frozen `paper.max_stale_mark_sessions` (default 3; a window frozen before the key reads 0, the old failure) consecutive sessions, after which the run fails as before (reverses #892 within that bound); `missing_candidate_bar` added 2026-10-20 by the owner's decision on #1997 (see that amendment: a universe candidate with no bar at the rebalance session was excluded as `excluded_no_t0_bar`; run-scoped, one alert naming every such name; the run continues, unlike `stale_data`); `lot_ledger` added 2026-10-01 by the owner's answer to #366 Q5: the run's lot-ledger rebuild failed, which never fails the run) is the source of truth, written **before** the exception propagates. `kill_switch` is run-scoped: every run that ends `skipped_kill_switch` (at step 6 or from the wrapper's own read) writes one, naming the latest `engaged` row's source and reason and every derived cause, so one alert goes out per daily run while trading is paused (*owner decision 2026-10-03 on [#644](https://github.com/josejuarez96/tradepartner/issues/644), option 2; [#677](https://github.com/josejuarez96/tradepartner/issues/677)*). `lot_ledger` (#366 Q5 (a)) is run-scoped: the run's lot write (req 13, through `outcomes`' `on_lot_error`) raised `LotLedgerError`; the run goes on, since the ledger gates its own task and not the phase close, and the alert dedupes on (`lot_ledger`, run) like every run-scoped kind. The kind joined `alerts.ALERT_KINDS` with T63 (#519), which wires that write. Delivery channels from `alerts.channels`: `store` (always), `macos` (`osascript` notification), `email` (SMTP from `ALERT_SMTP_HOST`, `ALERT_SMTP_USER`, `ALERT_SMTP_PASSWORD`, `ALERT_EMAIL_TO`, and an optional sender `ALERT_EMAIL_FROM` that defaults to the login; spend stays $0). `alerts.channels` must hold `store` **and at least one non-store channel**, validated at config load, so `[store]` alone is refused and `kill_switch_write_failed` (req 4) always has a channel to reach (*owner decision 2026-10-01, #366 Q22 (iii), settles [#416](https://github.com/josejuarez96/tradepartner/issues/416); the validator landed with [#515](https://github.com/josejuarez96/tradepartner/issues/515)*). Each delivery attempt is an `alert_deliveries` row (channel, outcome, error); a failure never fails the run. One alert per (kind, run) for run-scoped kinds, with `alerts.session` = the run's S; `no_window` and `locked` have no run and dedupe on (kind, session). The operations page lists them.

13. **Wash-sale lot ledger (G7 scope for Phase 4).** Kept in Phase 4 on purpose: paper has no tax effect, but Phase 6 needs the ledger before its first taxable trade and paper fills are the only real fill stream to test it on before then. Pure `execution.lots` over journaled fills **and journaled adjustments** (below) writes `lots` (one per acquisition: account id and type, owner, `security_id`, broker symbol, nullable CUSIP from `assets`, trade date as UTC instant and exchange-local date, quantity, cost basis) and `disposals` (lots closed FIFO, trade date, quantity, proceeds, realised gain or loss before adjustment, tax year by trade date). For each loss disposal it scans acquisitions from `WASH_SALE_WINDOW_DAYS` before to after (a named constant from IRC §1091, not config, like `MONTHS_PER_YEAR`), across every account in the ledger, matches replacement shares to the loss in acquisition order with each replacement share absorbing one loss and losses processed in disposal order (G7 R11, R13), keeps same-day loss and gain blocks apart (R14), and writes `wash_sale_flags` with the matched lots, quantities and disallowed amount, re-scanning as later acquisitions arrive, including across December 31 (R15). The replacement rule is the **literal statute** (*owner decision 2026-10-01, #366 Q9 (a)*): every same-security acquisition inside the window counts, including the unsold rest of the lot being sold, another fill of the same order and an earlier losing lot, which some brokers do not count and which monthly rebalancing makes routine; it stands, pinned by tests, until Phase 6, when a tax adviser confirms or changes it before the first taxable trade (the flags feed nothing in Phase 4). **Adjustments** (*amended 2026-10-01, #366 Q4 (c)*): the ledger takes the window's journaled adjustments as the positions ledger does (Definitions > Ledger), so that a split, a spin-off receipt sold whole, a delisting or cash-merger removal and a carried residue sold whole no longer raise `LotLedgerError` for the rest of the window and hold back `realised_pnl` (req 8), which kept `paper stop` from reaching `closed`: a `corporate_actions` split with `ex_date ≤` the instant and `known_at ≤ close(S−1)` for a rebuild as of S (the `actions_as_of` view the positions ledger uses, no look-ahead) scales every open lot of the name (quantity by the ratio, per-share basis by its inverse, total basis and acquisition date unchanged); a `spinoff_receipt` opens a lot for the child on the adjustment's session; a `carried_residue` opens a lot at the carried quantity on its adjustment's `session` (the New York date of the previous window's `closed` stop row, as `paper start` journals it), split-adjusted from there as the positions ledger does (*owner, 2026-10-20, #516*); and a `corporate_action_cash` removal closes the name's open lots FIFO as a disposal at the journaled cash. A stock merger has no `adjustments` kind and stays unexplained: it halts at reconciliation (req 6) for the owner to resolve by hand, and the lot ledger does not cover it. Two choices go beyond the owner's answer and are **#516's proposals, which the owner confirms on its PR**: the spin-off child's lot carries the basis its `explanation_json` names and **zero** until [#473](https://github.com/josejuarez96/tradepartner/issues/473) stores spin-off terms (overstating the gain on its sale, never understating it); and the `carried_residue` lot carries **zero** basis with its adjustment's `session` (that same date) as its trade date (its real basis and holding period live in the previous window, below) and is **not** a replacement acquisition in the wash-sale scan, since nothing was bought. [#516](https://github.com/josejuarez96/tradepartner/issues/516) builds it and pins the cases; until it lands, `lots.rebuild` raises on each of them. Phase 4 holds one account (paper); the schema carries the account columns so Phase 6 can add others. Basis and holding-period carry-forward, broker 1099-B figures and the substantially-identical policy (G7 items 6 to 9 and 11) are Phase 6 (the policy's text and the 1099-B comparison task T90 are recorded in [ADR 0010](../decisions/0010-phase-4-risk-rules.md), amendment 2026-10-04, #658), and so is settling lots **across windows** (#366 Q4 (c)): today each window's rebuild stands alone and replaces the earlier windows' lots, and a `carried_residue` lot carries no basis or holding period from the window it came from; a ledger that spans windows per account is a Phase 6 entry item, before the first taxable trade. The ledger's acceptance criteria gate **its task**, not the phase close: `paper check` does not read it.
14. **Entry gate, start and stop.** `paper start --hypothesis <slug>` refuses unless `owner_decisions` holds a `gap_signoff` row referencing an `ok`, non-synthetic, `in_sample` trial of that hypothesis (ADR 0009 point 3); the hypothesis's frozen `holdout.end` is a completed month-end; `account()` succeeds on the paper endpoint; and the account is **flat** (no open orders and no position other than the latest closed window's listed residues, matched below). It appends a `paper_windows` row: hypothesis id, T_0, account id, starting cash and starting equity, code version, and `frozen_json`: the **entire `risk.*` section** plus `paper.tracking_k`, `paper.min_rebalances`, `paper.tracking_rule`, `paper.max_catch_up_sessions`, `paper.min_override_reason_chars` and `paper.max_stale_mark_sessions` (2026-10-18, #1763: absent from a window frozen before it, read as 0), and `execution.fill_price` (*amended 2026-10-01, #366 Q20 (a)*: req 10's fill-timing term reads "the frozen `execution.fill_price` bar", so the bar is frozen with the window, and T65b binds `paper report`'s price accessor from `frozen_json`, never from live `Settings`; the key joined the freeze with #526, whose amendment below names the refusal), canonicalised and hashed as the registry does for hypothesis parameters. *Amended 2026-10-02, #534 (owner's decision and wording, approved 2026-10-02):* `frozen_json` also holds `costs.per_side_bps`, `costs.commission_per_share` and `costs.commission_per_order` (`config.FROZEN_COSTS_KEYS`), the costs the wrapper sizes buys and checks the cash rule with; it must equal the hypothesis's registered value, which the tracking trial fills at, so `paper start` refuses (`execution_drift`) when the live value differs or the registration lacks the key. Runs, the wrapper, `paper report` and `paper check` read those values from the window, never from live `Settings`; changing a risk rule mid-window means `paper stop`, an ADR (development-process rule 7) and a new window. A second `paper start` while a window is open is refused. **Stopping** is the only legal way to a flat account (the owner never trades by hand, open question 9) and the liquidation is done by `paper run`, never by the stop command, so it has a run identity, the halt path and the switch derivation like any trade: `paper stop --reason` takes the run lock, refuses while the derived switch is engaged (unconsumed `engage_kill_switch` overrides of the window count as engaged), and appends a `paper_window_stops` row with `state = requested`. The **stop session** is the calendar session containing the `requested` row's `at`, or the next session when it is written on a non-session day; a month i is compared (req 10) only when T_{i+1} is strictly before the stop session, so no compared month contains liquidation. From then on every `paper run` on the window is of kind **`stop`**: it plans nothing, writes `missed` with reason `window_stop` for any pending rebalance, performs steps 1 to 5 as usual, applies req 7's forced-exit rules **unchanged** (every open `forced_exit` is re-attempted whatever its reason) and creates a `window_stop` exit only for a held name that has no open or in-flight `forced_exit` decision, no non-terminal own sell and no same-run `untradable` forced exit, for the held quantity **minus the name's residue quantity** (a name whose whole holding is its residue gets no exit), with the whole-share floor where flagged (a `forced_exit` decision with reason `window_stop`, `whole_share` from `assets`, reconciled before sizing, through the wrapper's sells phase inside the submit window), collects, reconciles and writes outcomes. **A residue is a quantity per name, defined by one pure function over the journal** (`plan.residue(security_id, adjustments, decisions, decision_events, positions_daily, ledger, actions_as_of, *, window_id, runs)`): the **carried** part is min(the window's `carried_residue` adjustment split-adjusted through S, the held quantity), except that a carried residue whose `carried_residue` row is marked `origin = untradable` counts only while the name's latest `positions_daily.tradable` flag is false; the **dust** part is the held quantity of a name whose **latest** decision in this window is a `window_stop` forced exit closed by a `decision_events` `skipped` row with reason `dust` (an old rebalance-time `dust` on a name since traded again counts for nothing); the **untradable** part is the held quantity of a name whose latest decision is a `forced_exit` (reason `window_stop`, `delisted` or `untargeted_receipt`) closed by a `skipped` row with reason `untradable`, counted only while the latest `positions_daily.tradable` flag (written at every mark from the `assets` read) is false, so each `stop` run re-creates the exit once the name trades again; the residue is their sum capped at the holding. A residue therefore shrinks or vanishes with the holding: a carried residue sold whole by a `delisted` forced exit, removed by a cash merger, or sold once an `untradable` name trades again leaves nothing behind, and a delisted name with no venue stays a listed `untradable` residue so the window can still close. **Flat apart from residues** means every held quantity is at most the name's residue quantity within the frozen tolerance, and `residues_json` lists only residues still held, each with its quantity and **origin** (`dust` or `untradable`; a carried residue keeps the origin it was carried with, and `untradable` wins when parts mix), which `paper start` copies into `adjustments.origin`. The outcome horizon of an order of the stopped window ends at the **earliest** of: the fill that makes the name flat apart from its residue; close(T_{i+1}); and, when neither has happened, the mark at close(S−1) of the first `stop` run on S whose step 3 finds the order terminal and the name flat apart from its residue (flatness is tested after step 7b, so a name flattened by a run's own fills is written by the next run); that run writes the row, so every outcome is computable by a run and `closed` is always reachable. A later `paper stop --reason` takes the run lock, refuses while the derived switch is engaged, runs a reconciliation and refuses unless it passes, and appends `state = closed` (carrying that reconciliation id) when the account is **flat apart from residues** (`dust`, `untradable` and carried residues alike, which the closed row lists with their quantities), every order of the window is terminal, and **every order of the window has its outcome row**; otherwise it says what is missing and refuses. **The ledger is per window**: `adjustments`, `reconciliations` and every `kill_switch` row carry a `window_id` (set from the open window whether a run, `paper start`, `paper stop`, `paper reconcile` or `paper resume` writes them), and the ledger, the cash re-base and the switch derivation filter on it; the ledger's cash is based on `paper_windows.starting_cash` (`account().cash` at start, recorded beside `starting_equity`, which seeds the drawdown peak), its positions come only from the window's fills and adjustments, and a residue from the previous window enters it only through the `carried_residue` adjustment `paper start` journals for each listed residue the broker still holds. `paper start` split-adjusts the listed residues by the splits known at start, requires the match in both directions (every broker position is a listed residue or a req 6 spin-off child of one, journaled `spinoff_receipt` in the new window and sold by its first run as an `untargeted_receipt` forced exit; and every listed residue is held or its removal is explained as in req 6, a delisting say) in symbol and in quantity within the frozen `risk.reconcile_quantity_tolerance`, and refuses otherwise. A carried residue is a **quantity**, not a name: the plan's sell decisions on its name trade the held quantity minus the residue (so shares bought on top of it are sold when the name leaves the targets), and the targets are untouched, so the paper-equals-backtest oracle and the target comparison are unaffected. `paper kill`, `paper resume`, `paper reconcile` and every override kind refuse with `no_window` when no window is open (an override always attaches to the open window). The kill-switch derivation is **per window**: it reads the rows tied to the open window (`run_id → paper_runs.window_id`; owner, drawdown and override rows carrying `window_id`), so a closed window's history never engages a new one. Every run checks `account().account_id` against the open window. **Abandoned windows** (amended 2026-10-01, T64b; open question 13, option (a)): after an `abandoned` window the account must be **strictly flat** at the next `paper start` (no position at all, residues or not; the abandoned row's list is the owner's record, never carried). The owner's **reset of the paper account at Alpaca** is the one approved way to reach that flat state; the owner never trades by hand (open question 9). `paper abandon` refuses (`open_orders`, writing nothing and cancelling nothing) while any order of the window has no terminal event in the journal, the same read `paper stop` makes; the owner cancels or waits, runs `paper resume` so the journal collects the order, then abandons (amended 2026-10-02, #542); an order no collector can make terminal is settled first by the owner, one `paper settle` per order (req 17, *2026-10-03, #571*), and `paper abandon` itself still cancels and settles nothing. Open question 13's "ADR-style note" is the `abandoned` row's `reason`, which the owner also writes on #247 (or its successor); `paper start` shows it.
15. **Exit-criteria command.** `tradepartner paper check` runs, on the real store, against the **latest** window's frozen values, open or closed (a closed window is checked through its last completed rebalance session before the stop session, so the owner can flatten the account at phase end and still produce the evidence; `paper report` targets the same window): (1) distinct rebalance sessions with an `executed` event whose writing run has `invoked_by=scheduler` ≥ `min_rebalances` (rebalances executed by a tty run, and fill-session runs that traded nothing, are listed, not counted); (2) the req 10 tracking check under the frozen rule, read from the trial of the window's latest `paper_reports` row, whose `through_session` must be the last completed rebalance session (else the check fails as `report stale`), over at least `min_rebalances` compared months that are not excluded; (3) no incomplete chain once due, and (*2026-10-03, #571, req 17*) no order with a **live** fill (`superseded_by` null, the rows every reader counts) whose `known_at` is after its terminal event's, whatever its outcome rows (a feed fill that arrives after req 8's synthetic fill is journaled superseded and is not one), a rule `paper stop`'s readiness read (req 14) applies as well; (4) no override whose trimmed reason is shorter than the frozen minimum (and, from Phase 3, no engine run without a trial: true by construction, including plan trials). Exit 0 only when all pass; each line names its query. `paper status` prints the operations-page numbers.
16. **CLI.** `tradepartner paper start|stop|run|reconcile|kill|resume|report|check|status|abandon|override|settle` (`abandon` and `override` added 2026-10-01, T64b: `paper abandon --reason` is owner-only, open question 13; `paper override` writes through the same function as the override page, req 9; `settle` added 2026-10-03, #571: `paper settle --order <client_order_id> --reason` is owner-only, req 17, its only other flag `--order`, exactly one). No flag selects a live endpoint, a session, a store path, or bypasses the kill switch or a limit (tests assert the parser has none); `--reason` is required by `stop`, `kill`, `abandon`, `settle`, `resume` (whose only other flag is `--accept-broker-fills`, req 8) and the override kinds; output contains no secret-shaped string. `paper run` is what the scheduler calls; the Phase 2 T22 runbook gains its plist, `TRADEPARTNER_INVOKED_BY`, and the pre-open start time.
17. **Owner settlement of an order the journal cannot close.** (*Added 2026-10-03, #571; owner decision of 2026-10-03 on #571: one owner-only override, gated on a fresh broker read, covering both cases below.*) Req 4 settles a `pending` order and req 8 a lagging one, both through `paper resume`, and #542 made `paper abandon` refuse while any order of the window has no terminal event. Two states satisfy neither: **(i)** an **acknowledged order the broker no longer knows**: `get_order` raises `UnknownOrderError` at every collection (a paper-account reset at Alpaca wipes the orders, the positions and the cash), which under req 4's empty `get_order` allowlist is a fault, so every run halts at its collection, `paper resume`'s collection raises the same way, and nothing ever journals the order terminal; **(ii)** an order **`fills_lagging` past `risk.max_fill_lag_sessions` whose fill the broker's book does not show** (`get_order` says finished with a `filled_quantity` the journal lacks, but no fill of it is in the stream and no position in the fill's direction exists) while `paper resume` is refused by a rejection-cap verdict: a refused resume writes no synthetic fill, `--accept-rejections` clears a collection verdict only once a `paper run` has judged it (a resume's collection moves no run cursor, so the same `rejected` events are judged again at every resume until a run's collection commits its cursor), and even then `--accept-broker-fills` would only turn the lag into a mismatch, since a synthetic fill of a fill the broker does not hold puts a position in the ledger the broker lacks, which every later reconciliation refuses. In both, the window can neither continue nor be abandoned, and in both the fill does not exist. The way out is **one owner-only override, `paper settle --order <client_order_id> --reason`**, which journals the named order terminal: an `order_events` row with status `cancelled` and reason **`owner_settled_unknown`**, **no fill**, and an `overrides` row of kind **`settle_order`** carrying the owner's reason and the order id. It is the journal's statement, made by the owner, that the order will never fill, on evidence the command reads itself and refuses without.
    **Gate, in order.** `paper settle` takes the run lock (`locked` while a run, a resume or another command holds it) and refuses, writing nothing and calling no broker method, when: no window is open (`no_window`); the id is not an order of the open window (`unknown_order`); the order already has a terminal event (`already_terminal`); the order is `pending` (`pending_order`: req 4's settlement belongs to `paper resume`, never to this command); the trimmed reason is shorter than the frozen `paper.min_override_reason_chars` (`reason`); or the derived kill switch is **not** engaged (`not_engaged`: the override is for a window that has stopped itself; while runs still collect nothing is stuck, the owner engages the switch with `paper kill --reason` first, and so no settlement ever runs beside a trading run). It then makes **one fresh, read-only read of the broker** (`account`, `get_order`, `open_orders`, `fills`, `positions`; `account().account_id` must be the window's, else `account_mismatch`, the check every run makes, req 14, so an empty book is never another account's) and refuses unless all three hold: **(1) no open order**: `get_order(client_order_id)` raises `UnknownOrderError` or reports a terminal status, and `open_orders()` does not list the id (else `broker_open`: the order may yet fill, and the owner cancels or waits; a non-terminal reading and a listing by `open_orders()` are each enough to refuse); **(2) no fill the journal lacks**: `fills(since)`, with `since` the `known_at` of the order's `pending` event minus `paper.fill_read_overlap_seconds`, holds no fill of the order whose `broker_fill_id` the journal lacks (else `unjournaled_fill`: a fill that exists enters the ledger through a collector or req 8's synthetic fill, never through a settlement); **(3) no unexplained position**: the order's name maps to a broker symbol (else `unexplained_position`: a name reconciliation cannot map, so its position cannot be read) and the broker's quantity in the order's name (zero when absent) does not exceed the ledger's (the window's filtered fills and adjustments, split-adjusted through S by the actions known at close(S−1), the view `reconcile.compare` takes) by more than the frozen `risk.reconcile_quantity_tolerance` **in the direction the order's fill would have moved it** (more of a buy's name, less of a sell's name; else `unexplained_position`), **except** when `get_order` raised `UnknownOrderError` and `positions()` holds no position in any name: the broker's book then has neither the order nor anything it could have traded, the fingerprint of a paper-account reset, and `paper abandon`'s final reconciliation lists the ledger's side of every difference, so nothing is hidden. A difference in the other direction is not this order's and is left to reconciliation, as today. Because the ledger omits the unjournaled fills of every other non-terminal order, two of them in one name could net out in the broker's quantity, so (3) also refuses (`other_open_order`) while another non-terminal order of the window trades the same `security_id` **and the broker still knows it** (a fresh `get_order` on it that does not raise `UnknownOrderError`): an order the broker has no record of holds no fill that could net, so two orders a reset wiped on one name settle one after the other and never refuse each other; under the reset exception the rule is not applied (an empty book nets nothing). A `get_order` reading whose `filled_quantity` exceeds the journaled fills (the lag of case (ii)) is not by itself a refusal: the fill stream and the position decide whether the fill exists. Any broker error other than `UnknownOrderError` from `get_order`, on the settled order or on another open order of the name, propagates and nothing is written.
    **What it writes.** One write transaction (`store.db.open_for_write`, the override page's pattern, "store busy" when locked past `store.lock_retry_seconds`), stamped by one clock reading taken **after** the broker reads, so both rows carry one `known_at` (= `ingested_at`) later than every reading they rest on: the `overrides` row (`kind = settle_order`, `client_order_id`, `security_id` the order's, `rebalance_session` the order's decision's (null for a forced exit's), `reason` the trimmed note), then the `order_events` row (`status = cancelled`, `reason = owner_settled_unknown`, `broker_order_id` from the journal's `accepted` event, `filled_quantity` and `filled_avg_price` null, `raw_json` the evidence: the override id, the account id, the `get_order` outcome (`unknown`, or the reading's status, `filled_quantity`, `filled_avg_price` and `filled_at`, the broker's instants in their own fields and never a `known_at`), the ids `open_orders()` returned, the broker's quantity in the name and the ledger's, the fill ids the stream returned, and the id and outcome of each other open order's `get_order`). The transaction re-reads the order's events and aborts (`already_terminal`) if a terminal event appeared since the gate. No `fills`, `reconciliations`, `kill_switch`, `paper_window_stops` or `decision_events` row, and no broker call that writes (`submit` and `cancel` stay the wrapper's; the AST check of req 3 holds). Exactly one order per invocation.
    **After it.** The order's chain is complete (req 8: exactly one terminal event; its outcome row is due as for any `cancelled` order: `not_executed`, plus `position_return` or `realised_pnl` for its journaled partial fills). Its decision is open for its remainder like any cancelled order's, and `plan.decision_state` protects it from the funding write-off as it does a `not_received` cancel (req 4), so a window that continues re-attempts it at the next in-window run; a window the owner abandons never runs again. The order is in no reconciliation's `lagging` or `pending` list any more and no longer refuses `paper abandon` (`open_orders`) or `paper resume`'s lag bound; `paper abandon` still cancels and settles nothing itself: one explicit `paper settle` per order (#542). The kill switch is untouched: the derived state is what it was, and only `paper resume --reason` releases it (req 5), which still needs an `ok` reconciliation; so in case (ii) the owner settles, lets the next `paper run` judge the rejection (its collection commits the run cursor and the verdict becomes one on a faulted run), then releases with `paper resume --accept-rejections --reason`; and in case (i) settles each order, then abandons, the abandon's final reconciliation listing the reset's differences. `plan.decisions_from` and the switch derivation ignore `settle_order` rows (a `decisions.override_id` never cites one, so no `override` decision exists and the month is not flagged `override`; the comparison treats the order as any `cancelled` one), and the target comparison is unaffected (targets are untouched); the row is on record for `paper check` (4), and the operations page shows the chain's `cancelled` (`owner_settled_unknown`) event as it shows any terminal event. A fill the feed delivers later for a settled order is journaled like any fill (fills are never dropped), and req 15 (3) gains the rule, with this amendment, that an order with a live fill journaled after its terminal event is an incomplete chain (a superseded feed fill after a synthetic one is not), which `paper stop`'s readiness read applies too; so a settlement can never silently absorb a real fill.
    **What the CLI and the page refuse.** `paper settle` takes exactly one `--order` and a required `--reason`; it has no `--all`, no pattern, no `--force`, no flag that skips the broker read or any refusal, and no flag that selects a window, a session, an endpoint or a store (req 16). The override page never offers `settle_order` (its kinds stay req 9's three; the page has no broker and the gate needs one), and `window.override`, the writer the page and `paper override` share, refuses the kind. `window.settle_order(settings, connect, broker, clock, client_order_id, reason)` is the one writer, called only by the CLI command: nothing in the scheduler, the T70b plist, `paper run`, the page or any LLM path reaches it (as for `abandon`, #542 item 5).

## Risks & domain checks

- **Look-ahead:** the plan is the engine's own function at `t = close(T_i)` over `StoreProvider` under a plan trial; the ledger, the mark and the reconciliation explanations use only rows known at close(S−1); the truncation test cuts the fact **and** journal tables; the tracking trial is the Phase 3 engine and inherits its invariance suites; nothing under `backtest/` can read the journal (text check); the paper-equals-backtest oracle catches a plan that drifts from the engine, and the `late_data` category keeps a late-ingested bar from being mistaken for one.
- **Point-in-time journal:** every link of a chain has its own `known_at` from the shared clock, with the broker's instants in their own columns and a skew bound (ADR 0007's "revisit if" on broker-sourced timestamps is answered: they never become a `known_at`); nothing is updated in place; a plan trial ties every engine read to a trial id.
- **Order path (development-process rules 5 and 7):** limits, the kill switch and the halt path are merged and tested before the first paper order, and every limit is frozen into the window so no environment variable can loosen one mid-phase; only the wrapper submits; the allowlist is empty with its per-candidate reasoning recorded; a phase is all-or-nothing against the batch limits and a breach abandons the rebalance rather than retrying it; ids are deterministic per attempt and per name, `orders` rows precede submits and every new attempt is sized for the remainder, so a crash, a halt or a partial fill can never double an order or open a short, and a pending attempt is settled by `paper resume` before anything trades again; one run at a time holds the lock; the kill-switch row is the first thing a halt writes, the state is derived from every earlier run's result, and it is re-read at each phase boundary, so a lost write, a crash or a kill during a run cannot be missed; a pending order the broker never received stops everything until `paper resume` settles it; buys are funded only by cash the sells raised, never by margin; an order no collector can settle is closed only by the owner, one order per command, after a fresh broker read that shows no open order, no fill and no position the settlement would hide, and the settlement never writes a fill, never cancels and never touches the switch (req 17); the adapter cannot reach a live endpoint (guarded key, separate paper keys); `safety-reviewer` runs on every Phase 4 PR touching `execution/`, `adapters/alpaca_broker.py`, `store/journal.py`, the override page or `.env.example`.
- **LLM inputs:** none (ADR 0008). The override form carries no memo and is never blocked by one.
- **Costs and fill realism:** paper fills at the NBBO after the open (#86), the frozen convention is the F_i close, and the two-phase execution means sells and buys fill at different times; ADR 0005's tolerance (`paper.tracking_k` × modelled cost, about 20 bp a month at H1's turnover and 15 bp) can be exceeded by fill timing alone, and paper never receives the dividends the backtest reinvests. Req 10 prints the raw difference with both terms every time, and the rule the phase is judged by is **frozen at `paper start`** (open question 4), so no criterion changes after results exist (ADR 0005 "Reversibility"). Paper does not simulate market impact or price improvement (#86 S27), so the paper stage measures the simulator, not live execution.
- **Backtest conventions paper cannot copy:** the list in req 10 (`stale_exit` and `missing_fill` on the backtest side, the exit at the last close, one fill price for sells and buys, `unspent_cash`, residues); each is listed in every report as a known source of difference.
- **Live sizing (H1 Q1 trigger):** at `paper.live_capital_reference` most H1 orders sit at the fractional minimum; `n_orders_below_min_at_live_capital` reports it per rebalance so Phase 6's ADR decides on evidence; the deferral itself is open question 11.
- **Survivorship:** the tracking trial records the gap per rebalance like any trial; forced exits follow the engine's last-close convention; a paper position in a name the broker removes must be explained by a known delisting or the run halts.
- **Corporate actions at a simulated broker:** how Alpaca paper applies splits, spin-offs and mergers is unverified; the recording task answers it before the adapter task closes, and the reconciliation explanations are written so a simulator that does nothing on a split still halts loudly rather than drifting.
- **Reconciliation drift:** split-adjusted comparison with frozen tolerances; the owner never trades in the paper account by hand (a foreign order is a fault by design, open question 9); the account id is checked every run.
- **Unattended machine:** a run that never starts cannot alert; the next run's `missed_run` alert and the page's stale chip are the detection; the submit window, ADR 0006's missed-rebalance rule and `paper.max_catch_up_sessions` bound how stale a traded plan can be; the plist is the T22 runbook's, extended.
- **Single writer:** the run opens write connections per chunk (journal writes, the plan trial) and read-only ones for reads; the override form's write retries per `store.lock_retry_seconds` and shows busy; the ingest job runs after the close, outside the run's window.
- **Secrets:** paper keys and SMTP credentials are `SecretStr`; scrub tests on fixtures and CLI output; no secret in any exception.
- **Spend:** Alpaca paper, `osascript` and SMTP cost nothing (ADR 0009 budget).
- **Alpaca facts unverified:** quantity precision, id length, same-session proceeds in `cash`, corporate-action handling, CUSIP on assets, non-fractionable share of the universe, whether a fractional sell of a name that lost `fractionable` after its decision is accepted (if not, a full exit of it halts at submit or counts as a rejection, and stays open, #395), the fills endpoint and the request limit are all recording-task questions (req 2); the adapter refuses to construct without the recorded precision, and an unmapped status halts.
- **Owner-only steps:** recording paper responses, `paper start`, `kill`/`resume` (a crash needs a resume, so an unattended month with a crash is a missed rebalance until the owner looks: alerted, and bounded by the catch-up window), the gap sign-off, ADR 0009's acceptance and the phase-close evidence need the owner's keys and machine.

32. **The bound: the row's stamp, or a lag key?** The rule above offers a child from the first reconciliation whose cutoff is at or after the row's `known_at`, however many sessions after the ex-date that is; a row that lands 40 sessions late is still the explanation. A row that never lands is a permanent halt unless a re-ingest lands it; a parent moved or split on or after the ex-date is a permanent halt with `paper abandon --reason` as the way out (item 4). Options: (a) as built, with no key: the halt is the bound, since a mismatch journals nothing and the base does not advance, so the book trades nothing after that reconciliation, and a late row is still the stored fact of the distribution (recommended: the rule exists because the stamp can be weeks after the ex-date — the close after `process_date`, data-foundation open question 18 — and a number would be an owner value that both turns some true late explanations into permanent halts and, being an `alpaca.*` live key, moves an open window's behaviour); (b) a live `alpaca.spinoff_max_lag_sessions` (mirroring `alpaca.cash_in_lieu_max_lag_sessions`), where a row whose ex-date is more than N XNYS sessions before the reconciliation session is not offered, so a very late row leaves the child a `broker_only_position` mismatch for the owner to resolve by hand.
