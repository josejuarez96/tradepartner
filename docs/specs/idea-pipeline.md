# Spec: the idea pipeline, the front half of the research loop

**Status:** Draft for the owner's review; revised 2026-11-02 after his reading of an outside review ("proceed", eight changes, folded in below)  ·  **Issue:** #2896  ·  **Date:** 2026-11-02  ·  **Related:** [research program](../ways-of-working/research-program.md) (the loop; stage 4a), [hypothesis backlog](../research/hypothesis-backlog.md) (the ladder ledger, the search limits), [ADR 0023](../decisions/0023-break-first-fast-books-paper-exam.md) (the kill ladder; the 2026-10-30 rung-1 cost rule), [research registry](research-registry.md) (`economic` and `return` runs, req 9, the 2026-10-31 exposure amendment), [strategy lab](strategy-lab.md) (the deflated Sharpe at the declared count), [strategy discovery 2026-10-19](../research/2026-10-19-strategy-discovery.md) (rung 2-O, rules L1 to L5), [Gate 0 reconciliation 2026-10-27](../research/2026-10-27-discovery-system-gate0.md), [retro 2026-11-01](../retros/2026-11-01-strategy-search-retro.md)

This document designs a process and its pilot. It proposes no strategy, builds nothing and reads no return. The owner reviews it and decides the items in [Decisions for the owner](#decisions-for-the-owner).

## Problem & why now

TradePartner can tell whether a candidate strategy is real: point-in-time data, honest backtests, a trial registry, frozen kill lines, paper books as forward exams. Nothing produces candidates. Every idea tested so far was picked in chat from whatever data was handy, almost all from published anomaly files in large liquid stocks, the most crowded pool there is. Six candidates under the first search limit, and B3, B9, C1 and the momentum variants before it, all failed ([retro](../retros/2026-11-01-strategy-search-retro.md) section 1), and each carried a prior near zero when it was picked (the [backlog](../research/hypothesis-backlog.md) says so of itself: "the priors are deliberately low"). The owner's goal is plain: start trading a profitable strategy. What he has been handed instead is lists of strategies with no process behind them, and a project that drifts into infrastructure between lists.

**The goal of the pipeline.** Supply the validator with candidates that each state why their return might persist (an inefficiency someone keeps losing to, or a risk premium someone pays to have borne) and whether TradePartner can capture it at its size and execution after cost, screened cheaply and counted honestly, so that the strict tests we already have are spent on ideas worth testing. The pipeline is the front half of the research loop: it ends where [research-program stage 4a](../ways-of-working/research-program.md#4a-feasibility-check-before-an-experiment-file) begins. It changes no rule of the back half.

**It starts as a pilot, not an operation.** Nothing is scheduled, scripted or held monthly until the pilot ([requirement 7](#7-the-pilot)) shows that cards improve selection over the chat-picked route. **What the pilot can and cannot show:** it cannot show that the pipeline finds a profitable strategy within three months; a profitable strategy is confirmed on paper, over weeks to months, and the pilot does not shorten that. It can show quickly whether the pipeline fails. It is **working** if at least one candidate reaches the strict tier that the old ad hoc route would not have picked. It is **failing** if none does, or if the admitted cards are of the two kinds already killed (a published slow anomaly in liquid names, or a fast signal at today's cost), the same two-part test the stop rule uses.

**What is tracked** (one table in the cards file, [Data / interfaces](#data--interfaces)), counts only, no minimum on any row. Zero admissions is an acceptable result; what is not acceptable is not knowing why:

| Measure | What it tells |
|---|---|
| Ideas reviewed, by source | The sources were mined, not remembered |
| Cards `rejected` (by question), `deferred`, `blocked` (by capability), `admit` | How harsh the filter is and where ideas die |
| Of the admitted: killable without a return read; forwarded to the strict tier; and, once an operation runs fast looks, killed by a fast look | Whether the cheap tests do the work |
| Strict-tier verdicts and the `TP-` claims written | Learning that stays learned |
| Agent-days spent on the pipeline | Effort, for the stop rule |
| The capability tally: admitted cards blocked, per missing capability, by distinct mechanism | What a build would unblock |

## Users & usage

- **The owner** reads one page at the end of the pilot (the table above, the tally, the one candidate selected for the strict tier, and the independent review's findings) and decides whether the pipeline becomes an operation. About 30 minutes, inside one of ADR 0023's weekly decision sittings, plus about a minute per exposure record written on the real store (an owner step under the 2026-10-31 amendment, or an agent at his word).
- **Agents** write the cards, run the independent review, and forward at most one survivor to the strict tier exactly as today (a kill line posted on the issue before any return is read).
- **The orchestrator** briefs the two pilot agents and the reviewer, keeps the table and the tally current by hand, and refuses any read that has no card.

## Requirements

### 1. Every idea enters as a card, from a named source

An idea exists in the pipeline only as a **card**: about twelve lines in a fixed shape ([Data / interfaces](#data--interfaces)), written before any return is read for it. A card has a source, a mechanism, an answer to each filter question, the capabilities it needs and a verdict. The owner's own ideas get the same card and the same filter; so do an agent's and an AI workflow's. A card is the ledger's unit: question 3's break-even arithmetic is a rung-1 number, so a card gets its [ladder ledger](../research/hypothesis-backlog.md#ladder-ledger) row (rule L1) when that question is answered, and every mining pass adds a batch row (rule L2) with the number of ideas reviewed and the number with verdict `admit` (L2's "admitted to rung 1"; a `blocked` card is not), so the denominator is visible.

### 2. Sources: own data and forced flows first, the literature as context

Mining means reading a finite, named body of material once, under a rule written before the reading, and writing a card for everything that passes the rule and a one-line reject for everything that does not. Nothing is "remembered"; nothing is "picked". Writing a card reads no return; the first return read, if any, is the card's fast look (requirement 4).

| Source | Body mined | Role in the first campaign |
|---|---|---|
| **B. Own data** | A **data-edge census** over the fields the store holds that most retail researchers do not: filing acceptance times (complete for every form once T324 lands; partial before it), first-vintage statement facts, Form 4 rows, 8-K items once `filing_events` is filled, delistings, corporate actions. For each field: "who had to do something after this fact became known, and could we act before they did?" The [store census](../research/2026-10-28-strategy-frontier-verified.md#census-re-derived) is the field list. *Illustrative only: "a 10-K accepted after the issuer's own usual date" was such a card (C1); it was tested and retired, which is what the process is for.* | **Pilot source.** One card per field × event pair that names why the return might persist; one-line rejects for the rest |
| **C. Market structure and forced flows** | A **flow calendar** of the scheduled or rule-bound trades of price-insensitive holders, read from the primary rule documents (index methodology papers, ETF prospectuses, fund mandate language, tax and settlement calendars, lock-up and dividend rules). *Illustrative only: an index reconstitution that forces buying of the names added on a known date.* | **Pilot source.** One card per flow: who must trade, on what date rule, how much, who is paid to take the other side today |
| **A. Literature** | The held Chen-Zimmermann catalogue (`SignalDoc.csv` and the two portfolio parquets, read locally since #2669, 2026-10-30) and the claims register. | **Context only, no catalogue-wide batch look.** A card from B or C names the related published mechanisms (question 5), takes its prior from them (question 3) and is marked redundant when one has already been tested here. The 2026-10-30 ranking stays [INCOMPLETE](../research/2026-10-30-strategy-first-ranking.md) |
| **D. The owner's knowledge** | What the owner reads, hears and notices, and our own post-mortems (B11: H1's holdout win was beta; B3's mega-cap shortfall; C1 run 2's benchmark error). | After the pilot, if it becomes an operation; his cards use the same filter |
| **E. Practitioner sources** | A fixed, dated list of practitioner feeds, read by hand with the Firecrawl CLI (development tooling, outside the charter's running-system budget; no scheduled job). | After the pilot, if it becomes an operation; each card `UNVERIFIED` until a graded source or our own read backs it |

**An honest word on B and C.** They are not obviously better than the published pool. EDGAR is public: every acceptance time and every as-filed fact we hold, a fund can hold too, and timing precision did not rescue B9's thin long leg. Known flow effects (index reconstitution, dividend dates) are published and have shrunk as they were arbitraged. The case for B and C is narrower: they are where a small, patient account is least disadvantaged, they produce cards that can often be killed without a return read, and nobody has mined them here with a written rule. The pilot tests that case; it does not assume it.

**Anti-fishing rules, one per source:**

1. **B.** The census reads counts and dates, never returns. A card with no published series takes rung 2-O (an `economic` run, `touches_returns = false`) before any return read.
2. **C.** The flow and its date rule are written from the rule document before any price is looked at; the test is one declared event window.
3. **A.** Used for mechanisms, priors and redundancy only. `SignalDoc.csv`'s `Return` and `T-Stat` columns are in-sample returns and are not read to pick cards. The 2020-and-later windows of the catalogue signals already read for XFIN and the composite (#2828, #2888) are **not clean confirmation data** for any later card on those mechanisms; a card naming one of them says so under question 5.
4. **D.** Same card, same filter, no shortcut. The owner's word admits a card; it does not answer a filter question for it.
5. **E.** The feed list is fixed and dated on the batch row; an item with no mechanism is a one-line reject; a vendor's return figure is never a kill or pass number.

### 3. The first-pass filter: the questions every card answers

A cheap, no-return screen. Answering takes about an hour. Every question is answered in one or two lines; an unanswered question is a `rejected` verdict, never a blank.

1. **Why might this return persist?** One of: an inefficiency someone keeps losing to (a forced or price-insensitive flow; a behaviour with a named reason it persists); a risk premium someone pays to have borne (named: what loss are we being paid to carry, and when does it arrive); a constraint on the natural holder (capacity, horizon, mandate, career). Two sources of return are allowed, not one: a premium is a reason as good as a loser. "The market under-reacts" alone is not an answer. Most of the candidates tested so far had none, which is the point.
2. **Can TradePartner capture it at its size and execution, after cost?** Capacity (does the trade exist at $100 to $100k without moving the price), holding period (does it fit a patient account, or does it need speed), execution (does it need an order type, bar or quote we do not have, which is question 6), and the cost arithmetic of question 3. The card need not show that a professional is absent; it must show that the return survives our cost at our size, which is the test that killed the past eight. Fitting the books' current shape is not by itself a reason to reject; needing scale or data we cannot get is.
3. **What does it cost at our size, and does the edge clear it with margin?** Holding period, one-sided turnover, round-trip cost for the names it trades, against the plausible gross effect after the publication haircut (QI-2, applied once; a post-2005 figure such as G2-S10 is already haircut). The arithmetic is [ADR 0023 rung 1](../decisions/0023-break-first-fast-books-paper-exam.md) (needed edge = 2 × one-sided turnover × cost per side) and stage 4a (d) (plausible effect above 60 bp round trip), unchanged. The cost per side is the figure measured for the card's liquidity band under the [2026-10-30 rung-1 rule](../decisions/0023-break-first-fast-books-paper-exam.md#amendment-2026-10-30-2667-one-rung-1-cost-rule) (arrival, equal-weighted, in band, rebalance days), with the figure against the open beside it as that rule requires. Today only one band is measured: names over $200M, **+8.8 bp per side against arrival** (the governing figure; the amendment makes arrival mandatory) **and +24.2 bp against the open on that band** ([fill-cost note](../research/2026-10-30-paper-fill-cost-arrival.md), rung-1 table, two rebalance days, paper simulator); both go on the card. Below $200M nothing is measured under the rule; the note's other +24.2 bp (all orders, all bands, against arrival) mixes bands and understates the cost of smaller names, so a card there writes `cost: unmeasured (<band>)`, and if its verdict turns on that cost it is `blocked: cost measurement (<band>)`, which the tally shows like any other missing capability. The margin the card must show above break-even is [decision D9](#decisions-for-the-owner).
4. **Is the data there, point-in-time?** The causal timestamp is held as `known_at`; the event count per year is known or countable without returns; delisted names in the window are covered; how long a history it needs (2016+ is held; older is bought). This is stage 4a (a), (b), (f), answered before an experiment file, not instead of 4a.
5. **What has already been tried?** The nearest retired, parked or deferred item, by mechanism, with its ledger row and exposure records, and the related published mechanisms from source A, and what is genuinely new. A second look at a killed mechanism is allowed and must say so (the [earnings-family design](../research/2026-11-02-earnings-event-family-design.md) is the model: "this is B9 again, with four changes, and must be disclosed as one"). A mechanism whose 2020-and-later catalogue window was read for XFIN or the composite says so here.
6. **Which capabilities does it need?** From a fixed vocabulary ([Data / interfaces](#data--interfaces)), each marked `held`, `self-imposed gap`, `charter (ADR)` or `external limit`. **The filter does not reject a card for a self-imposed gap.** Daily bars only, market DAY orders only, long-only in practice, a $200M liquidity floor: these are design choices we made, not facts about the broker. A card that needs one of those is verdict `blocked: <capability>` and feeds the tally. A capability the charter rules out (options, crypto, live shorts on the cash account, the $100 live cap) is `charter (ADR)`: the card is kept as `blocked` and the tally shows it, but only an ADR can unblock it. Genuinely external limits (price history starts 2016 unless bought; no futures at the broker) may reject. The card also records whether the **capabilities we hold suffice** for a first test, even if the trade itself would need more.
7. **Is a kill decidable?** The cheap screen of 4a (c): the effective number of independent events at which t reaches 1.0 at the plausible effect, n = (sd / effect)², with the effect and its dispersion taken from the published source or the register's claim, never from held returns. t = 1.0 is a screen, not evidence. Too few events is `deferred: power`, because a kill would say nothing.

**Admitted and the verdicts.** A card that answers questions 1 to 5 and 7 is **admitted**, whatever its capabilities. Its verdict is `admit` (every capability needed for a first test is held; goes to the fast tier) or `blocked: <capability>` (a good card waiting on a build or an ADR; counted in the tally). The other verdicts are `deferred: <reason>` (data or power; re-enters when the reason is removed) and `rejected: <question n>` (stays on file, one line, as part of the denominator). "Admitted" below means `admit` plus `blocked`. The card also records `killable without a return read: yes | no`, which the pilot reports. The owner may overrule any verdict; the overrule is written on the card.

### 4. The stages of evidence, and what each can establish

Every candidate moves through the same stages in order. The table says what each stage can and cannot show, so that nobody reads a screen as evidence.

| Stage | What is done | Can establish | Cannot establish | Counted as |
|---|---|---|---|---|
| 1 Economic mechanism | The card: why the return might persist, who or what pays it, at what cost to us | That the idea is coherent and worth a cheap test | Anything about returns; mechanism stories do not predict survival (CLZ, [discovery §B3](../research/2026-10-19-strategy-discovery.md#b3-what-mechanism-first-admission-buys-and-what-it-does-not)) | A card; a ledger row at question 3 |
| 2 Non-return test | Rung 2-O: the mechanism's fundamental or behavioural consequence on held facts, an `economic` run | That the stated mechanism is not false in our data | That the effect is priced or tradable | A registered run, no cost to N; **it is a test and carries multiple-testing risk**: every such run is a look, recorded on the card and carried forward under requirement 5 |
| 3 Feasibility and power screen | Stage 4a (a) to (f): timestamp, counts, power at t = 1.0, cost, matched benchmark, delisted coverage | Whether a kill would mean anything | Any effect; t = 1.0 is a screen, not evidence | The ledger's `feasibility` cell |
| 4 Exploratory return result | The fast look: one declared read, one number, pass or kill | A kill; or that the idea is worth a controlled test | A positive result of any kind; it is the first look at a return and is the most p-hackable step | An exposure record (open data or store), or a `return` run in N |
| 5 Controlled return experiment | The strict tier: a registered run or counted trial, frozen kill line, harsh settings, placebos, the deflated bar | A pre-registered pass or kill on development data | Out-of-sample performance; forty months can only kill | A trial or run in the family's N, the DSR at the declared count |
| 6 Forward exam | The paper book on the confirmation set (requirement 8), from the family's `holdout.start`, which is after its registration day (ADR 0016 point 4); the sessions between 2026-10-01 and `holdout.start` are the family's dead months (ADR 0016 point 2), read by no run of its own; a later backtest spend, if the owner allows one (ADR 0016 open question 2), covers the holdout months only | The strongest evidence we can produce before live | A guarantee; the exam's own kill rule decides | A trial; its outcome a `TP-` claim |

### 5. Two speeds, and the multiplicity rule that joins them

**The fast tier: one declared look, cheap.** An admitted card gets one read, declared on the card before it runs: the series or table, its construction, the window and the kill line, in one or two lines, posted where it gets a timestamp (an issue comment or a commit). The read computes one number and the card records pass or kill in five lines. No report and no issue thread beyond that comment. The ceremony that stays is the one the 2026-10-31 exposure amendment requires: **every launch that computes a return outside a handle is one `research_exposures` record per card** (`candidate_ref` holds one candidate; `source = open_data` for a published file, `store` for a store copy), with the kill-line URL and its hash, the probe path and SHA-256, `n_configurations`, `read_at`, the verdict, and `docs/research/idea-cards.md` as its `desk_read_path`. The exposure writer exists in `store/research.py`; until its CLI (research-registry plan T357) and backfill (T359) land, the record's fields are written on the card and recorded as the amendment's backfill section says. A fast look takes one of three forms, in cost order:

- **(a) on open data** (a published file, an open dataset): a ledger look (rule L1) and an `open_data` exposure record, which does not enter any family's N (the amendment's rule for `open_data`, its open question 1); window ending 2019-12 (rule L4). Under today's search-limit rule a rung-2 read on open data makes the card a counted candidate; see D2.
- **(b) on held facts without returns** (rung 2-O): an `economic` research run with `touches_returns = false`; a ledger look, no cost to N, no exposure record (it reads no return). It is still a look (stage 2 above).
- **(c) on store returns**: a registered `return` run, counted by configurations in the family's N ([research-registry req 9](research-registry.md)). A `return` run must name a family that exists in `hypotheses.families`, so (c) is open only to a card whose mechanism belongs to an existing family; adding a family is a strict-tier step. The fast tier reaches for (c) only when (a) and (b) cannot decide. A scratch read of store returns on a store copy outside a registered run, recorded only as exposure, is what the owner allowed on 2026-10-31; [decision D5](#decisions-for-the-owner) asks whether the fast tier is narrower than that. If he keeps it, such a read's window must end before its family's holdout, because under the amendment's decision 2 (b) a read that overlaps the holdout is a spend, and the fast tier may never spend one.

The fast tier can kill or forward. It can never promote, register a family, or spend a holdout. *Estimate: one survivor in five or worse.*

**The multiplicity rule.** A fast look is a test whatever its accounting, and so is a non-return test. The number of looks behind a candidate is carried forward and raises the bar at the strict tier:

- The card keeps a running count **k**: every look on the mechanism (its own and its relatives' under question 5) that is **not already in the family's N**: open-data fast looks, rung 2-O runs, open-data exposure records. Store `return` runs and `store` exposures are already in N (req 9 and the amendment's `family_exposure_count`) and are not counted again. The batch denominator of the pass that produced the card is stated beside k, not added to it (open question 1 asks whether it should be).
- The strict-tier file (hypothesis, sweep or experiment) states k and the denominator in its prior-evidence disclosure (rule L3) **and in its frozen kill line**.
- For a backtest trial, the file states that promotion is read at the deflated Sharpe computed with **N + k** trials, not N, with V floored at `min_sharpe_variance_annual` and against the family's high-water mark as strategy-lab req 4 reads it: the same arithmetic the lab uses to report "SR* at the declared count" ([strategy-lab spec](strategy-lab.md), Definitions and req 3) for variants declared but not yet run, applied by hand to k as a check beside req 4's code check. The registry's N is unchanged; the file states N + k and the resulting floor, and the quant-auditor checks it. This amends ledger rule L3's "promotion still uses the DSR at the family's high-water mark, unchanged" ([decision D11](#decisions-for-the-owner)).
- For a registered research run, the registry computes the verdict itself from the interval at the registered `ci_level` against `threshold` (research-registry req 8), so the correction must be in the registration, not beside it: the file registers a one-sided `ci_level` of (1 − α)^(1/(k+1)), that is 1 − α′ with α′ = 1 − (1 − α)^(1/(k+1)) (the Šidák form; α the single-test level, 0.05 today), with a one-sided `inference`, and writes the resulting floor in the kill line. That is the only form that reaches the verdict: a `[multiplicity]` block (Definitions, "Multiplicity family") only reports confirmatory runs against a declared size and puts `p_adjusted` in `secondary_json`; it never changes the verdict, so it may be filled in as a record but does not carry the correction.
- **Windows already seen are not clean.** The 2020-and-later catalogue windows read for XFIN and the composite (#2828, #2888), and B9's 2010-2024 read, are looks on months the strict tier would otherwise treat as fresh. A strict-tier file on any of those mechanisms counts them in k and says which months were seen.
- **What k cannot touch.** The forward data of requirement 8 (sessions from 2026-10-01) is read by no look at all, so the forward exam's evidence stands whatever k is. The correction above is for development-data verdicts; the exam needs none.

**The strict tier: unchanged otherwise.** A survivor goes where every candidate goes today: the stage 4a check recorded on its ledger row; a kill line frozen on its issue before any return is read; a registered run or a counted trial; ADR 0023 rungs 3 to 5 at the harsh settings; a `TP-` claim whatever the verdict; a forward paper exam for a root family with an unspent holdout. Nothing in this spec loosens the strict tier, and nothing lets the fast tier's number stand in for it.

**Two rules this spec touches but does not change now.** The ledger's **Upgrade path** ([backlog](../research/hypothesis-backlog.md#ladder-ledger): a batch over 20 ideas, or more than one item a month reaching rung 1, registers the rung-2 read as a `return` experiment in N once the family exists) overlaps the 2026-10-31 exposure amendment, which records the same open-data read as `open_data` exposure outside N; and the **search limit's counting rule** (a candidate counts at a rung-2 read or a registered event-study verdict) would count every open-data fast look as a candidate. Both are **deferred until the multiplicity rule above has been reviewed** (D2, D8): the review is the quant-auditor's read of the first strict-tier file that states k, reported on the pilot's page; the counting rule is not changed now. In the meantime: no catalogue-wide batch look runs; a pilot card's first test is non-return where it can be; and a card whose first test is a rung-2 read on open data counts as a candidate under today's rule, so the pilot takes at most one such read, and it is the selected card's. **The pilot trips the Upgrade path's second trigger** (8 to 12 cards answer question 3 in one month, so more than one item reaches rung 1), and the selected card's rung-2 read follows that path as written: if its family exists in `hypotheses.families`, the read is a registered `return` run counted in N (form (c)), not an open-data exposure; only if no family exists yet is it an `open_data` exposure counted in k, with that reason written on the card.

**What is new in the accounting, exactly.** Nothing in the registry, the exposure table or the DSR. Three practices: (i) a card is the unit of the ledger and carries the filter answers the ledger does not; (ii) the running count k and its use at the strict tier through the declared count and the kill line; (iii) the capability tally. Everything else (L1 to L5, 4a, req 9, the exposure amendment, the rung ladder, the deflated-Sharpe arithmetic) exists and is reused as written.

### 6. The capability tally drives the build order, not the reverse

The tally counts `blocked` admitted cards per missing capability, **by distinct mechanism** (two cards on one mechanism count once). The owner reads it. A capability earns a spec only when (i) it blocks several admitted cards of distinct mechanisms (the threshold is his, [decision D3](#decisions-for-the-owner)); (ii) at least one of those cards has passed a gate that did not need the capability: a fast look on open data, an `economic` rung 2-O read, or a graded claim in `claims.toml` (MIXED or better) for its mechanism, the third gate existing so that a card testable only with the capability (minute bars, intraday) can still earn a build; and (iii) the tally line carries a **rough cost comparison**: the build's size (S, M, L, in agent-days as the plan template sizes them) beside what abandoning those cards gives up (their count, their mechanisms, and whether any passed gate (ii)). No expected-value model: two numbers and a sentence, for the owner to weigh. A build that no admitted card is waiting on is infrastructure drift and does not start from this pipeline. A `charter (ADR)` capability earns an ADR draft the same way, not a spec.

### 7. The pilot

The pipeline starts as one manual campaign, not a monthly operation.

1. **Two agents, two sources.** One writes the data-edge census (source B); one identifies forced-flow mechanisms from primary rule documents (source C). Each works from a written rule, reads no return, and produces cards with every question answered: together **about 8 to 12 cards**, with the one-line rejects and the batch rows beside them. Source A is read only for questions 3 and 5.
2. **An independent review.** A third agent, briefed with the cards and not with the authors' reasoning, checks each card's assumptions: the persistence claim, the cost arithmetic against the rung-1 rule, the data claims against the store census, the capability list against the vocabulary, and question 5 against the ledger. Its findings go on the cards.
3. **Record two things per card:** whether it can be **killed without a return read** (a rung 2-O test or a feasibility fail), and whether the **capabilities we hold suffice** for its first test.
4. **Select at most one** card for the strict tier, by the filter's answers and the review, never by a return: **no fast look runs on any card before the selection**, and in the pilot only the selected card's first test runs. That test is non-return where one exists. It enters the strict tier as today (4a, frozen kill line, registered run), with k stated.
5. **Budget:** about six agent-days in all (two for each source pass, one for the review, one for the write-up and the selection), and the owner's 30 minutes. The pilot's page reports the table, the tally with its cost comparisons, the selected card, and the verdict under the working / failing test above.
6. **Nothing else until the verdict.** No scheduled passes, no scripts, no monthly sittings, no sources D and E, no research-program amendment, until the pilot shows the cards improve selection. If it does, the operation (one pass per source per month, a 30-minute sitting, the cards file folded at each sitting) is proposed in a short follow-up, not assumed here.

### 8. Forward data is the confirmation set; paper fills are the cost figure

**Forward data.** Every nightly ingest since the store went live under scheduled runs (bars for about 8,800 names, filings with their real acceptance-time `known_at`, Form 4 rows, statement facts, actions, the T-bill rate) is point-in-time as collected: each row was written the evening it became known. **No candidate-return read has touched it**: no card, no desk read of a candidate book and no backtest of a candidate. (Other reads have: the paper books' tracking trials, the fill-cost note and the 2026-11-02 replay read October sessions to measure execution cost, which is the exemption below.) Two limits, said plainly: a named data release can still rewrite rows in the set, since ADR 0016 point 7 protects only the sessions inside an open paper window; and the researchers live through these months, so the set is unread, not unseen. The pipeline treats it as the **confirmation set**: sealed from mining, from the filter, from every fast look and from every rung 2-O run; read only by the strict tier's forward exam (stage 6) under the family's own paper book. **Stated start: 2026-10-01**, the first session after the ADR 0016 point-8 exam window `[2024-01-01, 2026-09-30]`, whose months that record itself calls "not virgin". The owner confirms the first scheduled ingest's date from the Data health page, and if it is later than 2026-10-01 the start moves to it. The set grows by one session a night, unread, which is the main answer to the multiplicity concern of requirement 5: however many looks sit behind a candidate, the evidence that decides it was never exposed to any of them.

*What already seals it, and what is new.* ADR 0016 point 2: no in-sample run reads a session after the development boundary (2023-12-29), and the lab refuses such a window; stage 4a (b) likewise ends event counts at the boundary. Point 8: the months 2024-01 to 2026-09 are an exam for a single frozen finalist per family, never for development. Research-registry req 4 and 5: a research run's data window is an as-of bound and a protected window is refused without a holdout spend; the exposure amendment flags `post_boundary` on any desk read past the boundary. **New, and a convention rather than code:** none of those rules names 2026-10-01 or forbids a desk read on a store copy, an `economic` run or a card's census of what the store holds from touching sessions after 2026-09-30, because until now nothing but a paper book read them. The pipeline's rule is that **no card, mining pass, fast look or rung 2-O run reads a store row whose `known_at` or session is on or after 2026-10-01**. Event counts and power under stage 4a end at the development boundary, 2023-12-29, as 4a (b) already says; a census of which fields and forms the store holds (source B) may run to 2026-09-30 and no later. **One exemption:** execution-cost measurement (orders, fills and the fill-session prices read under the 2026-10-30 rung-1 rule) reads the sessions the books traded, because the cost figure is nothing else; it is not a candidate-return read. A read that breaks the rule is written on the card and the ledger as a look at the confirmation set, and the owner decides whether the card keeps its forward exam. Whether this becomes a registry refusal is open question 4, not pilot work.

**Paper fills.** The paper books' fills measure Alpaca's simulator, not the market: tiny orders filled at or near the print, no queue, no impact. They are **not an idea source**. Their one job in the pipeline is the cost figure every card uses in question 3, by liquidity band and by order timing (pre-open against the open; post-open against arrival), under the 2026-10-30 rung-1 rule, and the tally's `cost measurement` row says which bands a book has measured. When the live account exists, live fills recalibrate the figure band by band and the cards' question 3 is re-read at the new cost; until then every card's cost line carries the word "paper".

## Risks & domain checks

- **The market may hold nothing for us.** The honest prior from the register: post-2005 non-microcap anomalies earn about 0.07 %/month before costs (G2-S10); our measured cost is +8.8 to +24.2 bp per side depending on the measure and the band, and unmeasured below $200M. A good pipeline over that market produces honest zeros. That is why the pilot counts and does not require, and why the stop rule is about reaching the strict tier and effort spent, not about admissions.
- **B and C may be no better than the published pool.** Stated above: EDGAR is public and known flow effects have shrunk. If the pilot's cards all fail at question 2 or 3, that is the finding, and it is cheap.
- **"Why might this persist" is a story filter, not a return predictor.** Chen, Lopez-Lira and Zimmermann found that mechanism stories do not predict which predictors survive ([discovery report §B3](../research/2026-10-19-strategy-discovery.md#b3-what-mechanism-first-admission-buys-and-what-it-does-not)). The filter is used for what it does buy: fewer looks, a cheap kill, a clear failure. It is not evidence. The hard test is question 3's cost at our size.
- **The fast tier becomes mining.** Many cheap looks are how p-hacking happens. Mitigations: one declared read per card posted before the data is opened, the denominator on the batch row, the 2019-12 window, one exposure record per launch, the running count k carried into the strict tier's bar, no promotion from the fast tier, store returns only through a registered run (D5). Non-return tests are counted in k too. The residual risk is an agent reading a second series "to check"; the ledger's `looks` column and the exposure listing record it when it happens.
- **The tally pulls the project back into infrastructure.** The owner's complaint is drift into building. Mitigation: distinct mechanisms, a capability-free gate passed, and a written cost comparison before any build; the owner sets the threshold (D3). Capabilities blocking no admitted card are not built from here.
- **Forced-flow ideas are published too.** Index-rebalance and dividend-date effects are known and have shrunk. Questions 2 and 3 are where most of them should fail on the card: the flow may be real and still not pay our cost.
- **Forty months of store returns can only kill.** The development window is 2020-08 to 2023-12. Confirmation comes from paper (ADR 0023), which takes weeks for daily and weekly books and months for monthly ones. The pipeline cannot shorten that, and does not claim to.
- **Owner time.** Thirty minutes at the end of the pilot, one page.
- **Point-in-time and look-ahead.** The pipeline reads no store return outside a registered run (under D5), so it adds no look-ahead path. Fast looks on open data use windows ending 2019-12; nothing in the pipeline reads a session on or after 2026-10-01 (requirement 8). Cards record `known_at` fields by name.
- **The confirmation set is sealed by convention, not code.** Requirement 8's rule has no refusal behind it today; a careless count on a store copy could run to the latest session. Mitigation: every pilot read is listed on its card with its end date, the reviewer checks them, and a breach is recorded as a look. Whether to add a registry refusal is open question 4.
- **Secrets, orders, LLM inputs.** None touched. An AI workflow that proposes cards is a source like any other (batch row, card, filter); its output never reaches a run without the card and the declared read.

**The stop rule for the pipeline itself.** Two triggers, either one enough, read when the pilot's budget (about six agent-days) is spent or at the owner's sitting after it, whichever is first: **no candidate has reached the strict tier** (no card forwarded with a frozen kill line); or the one forwarded is a candidate the ad hoc route would have picked anyway (a published slow anomaly in liquid names, or a fast signal at today's cost). Either way the pipeline stops as designed, the pilot's page is the retro, and the question goes up a level: buy older data, change the market or instrument, or run the machine as a paper system only. An admission count is not a trigger; zero admissions with a clear reason is a result. If the pipeline becomes an operation, the same two triggers are re-read at an effort cap the operation proposal sets. The charter's six-month continue-or-stop criterion is not replaced by this; it is fed by it.
