# Spec: Data foundation (Phase 2)

**Status:** Draft  ·  **Issue:** #8  ·  **Related:** [ADR 0003](../decisions/0003-data-adapters-local-first.md), [ADR 0004](../decisions/0004-tooling-adopt-avoid.md), [ADR 0005](../decisions/0005-objective-benchmark-stop-criteria.md), [ADR 0006](../decisions/0006-universe-and-cadence.md), [roadmap Phase 2](../roadmap.md)

## Problem & why now

Nothing in Phases 3–6 can be trusted unless the data underneath answers one question correctly: *what was knowable at time T?* This spec builds that layer: a point-in-time store, a security master, a trading calendar, the adapters that feed them from free sources, a daily job, and the page that shows whether the data is healthy. It is the first code in the project.

## Users & usage

- **The owner**, once a day, glances at the data-health page. Once, at the start, the owner runs a recording script with their own keys to produce the scrubbed fixtures the tests use, and records the source-terms facts.
- **The scheduler**, once per trading day after the close, runs `tradepartner ingest`.
- **Phase 3 code** reads through the as-of API and never touches adapters directly.
- **Tests**, on every PR, run against the fixture universe with the network disabled.

## Definitions

- **T** is always a tz-aware UTC timestamp. A rebalance *date* maps to T = that session's close via the calendar. Never a bare date.
- **`known_at`** is when a fact became knowable to a market participant. **`ingested_at`** is when we stored it. `known_at ≤ ingested_at` always.
- **Revision**: a later value for the same key is a **new row** with its own `known_at`; rows are never updated in place. "Latest as of T" is the row with the greatest `known_at ≤ T`. One exception by design: `statement_facts` (amendment 2026-10-03, #660) holds the **first** vintage of each key only and never a later one, so it has no revisions to read; the amendment says why.
- **Provenance** on every row: `filing` (`known_at` = SEC acceptance timestamp), `bar` (session close), `action` (rule below), `snapshot` (current-only endpoint; `known_at` = fetch time), or `snapshot_static` (a snapshot attribute the config explicitly allows to apply before its fetch time, e.g. a company name or a pre-2019 exchange; counted and shown on the health page). A `snapshot_static` value is stored only in a row whose `known_at` is that snapshot's fetch time; only the row's `valid_from` may predate it, and as-of reads still see the row only once `known_at <= T` (#35).
- **Raw payload**: the bytes a source returns (JSON, SGML header text, or a downloaded filing file). Fetch functions return raw payloads; parsers turn raw payloads into records. Only parsers are unit-tested; fixtures are recorded raw payloads.

## Requirements

1. **Store.** A single DuckDB file, path from config. Every fact table has `known_at`, `ingested_at`, `source`, `provenance`. Prices raw OHLCV; corporate actions separate; adjusted series computed at read time as of T. Ingest holds the file read-write only while committing a chunk and releases it between chunks; every other process uses **short-lived `read_only=True`** connections and shows a "store busy" state when locked.
2. **Calendar.** Wrapper over `exchange_calendars` XNYS: is-session, next/previous session, open and close timestamps, last session of month, last *completed* session as of a timestamp, sessions in a calendar-month window, half-day detection. No weekday logic. The calendar-month window is exact: for `end_session` and `months`, it is every session `s` with `end_session − relativedelta(months=months) < s ≤ end_session`.
3. **Security master.** A `securities` row is created from the **earliest issuer filing per CIK** in EDGAR's filing index (`known_at` = that filing's acceptance; issuer form types from `master.issuer_forms`, so reporting owners filing Forms 3/4/5 and 13D/G never create rows). The index is scanned over **full history regardless of `--since`**, so `securities.known_at` is never too late. Companies therefore exist at historical T and delisted names exist at all. Ticker ranges, exchange, SIC, type and delisting come from filings where filings supply them and from `snapshot_static` attributes where they do not (pre-~2019 ticker and exchange); those count only from their fetch time, see open question 1. Keyed by `security_id`; adapters never resolve by bare ticker. Benchmarks (SPY, MTUM) are **seeded from config**, not derived from EDGAR (MTUM shares its trust's CIK with other funds).
4. **Delistings.** Forms **25 and 25-NSE** are both ingested as filing rows (`known_at` = acceptance) that name a class title and exchange. **Transfer status and listing end are never stored; they are derived at read time** from rows with `known_at ≤ T`: a listing's end is its last bar session known at T after the filing; the filing is a **transfer** at T only if a new listing row for the same security exists with `known_at ≤ T` and `valid_from` within `master.transfer_window_sessions` of the filing date. Between the filing and the new listing becoming known, the security is treated as delisted at T (conservative), and becomes a transfer once the new listing is known. `effective_on` is stored for reference (filing date + 10 days per Rule 12d2-2 unless stated) and is the anchor of req 11's *no bars after a listing's end* rule (amendment #822); it never sets a listing's end.
5. **Corporate actions.** `PriceSource.corporate_actions()` supplies splits and dividends. **First-seen** row: `known_at` = source announcement time if present, else the close of the session before ex-date. The announcement time is stored as `announced_at` (NULL when the source gives none), so the rule is checkable: `known_at == min(announced_at, proxy)` if set, else exactly the proxy; an earlier stamp without an announcement is look-ahead and refused (#83). A later announcement is capped at the proxy: raw bars from the ex-date on already reflect the action, and it is public before its ex-date. Revisions carry `announced_at` forward unchanged; it is never a filter for T. A source that gives only an announcement **date** is stamped at the close of the first session strictly after that date (the announcement may follow that day's close). **Any later row that differs** for the same action: `known_at = ingested_at`. Never back-dated on revision. An action's identity is (security, source action id) when the source gives a stable id, else (security, type, ex-date) (#108). So a **re-dated** action (same id, new ex-date) is a revision: the old ex-date applies until its `known_at`, the new one after, never both. A **cancelled** revision (`cancelled = TRUE`, stamped at `ingested_at`) withdraws the event from its `known_at` on. It also retires the old key of a re-date from a source with no id: ingest writes a cancel for the old key plus a **replacement** row for the new one, and the replacement is stamped `known_at = ingested_at` (it revises a known event, so it never takes a first-seen proxy stamp). The same applies when an event first stored without an id later arrives with one: cancel the id-less key, write the id row as a replacement. An id row may not share (security, type, ex-date) with a live id-less row. The store holds one row per identity per `known_at`. As-of reads take the latest revision per identity first, then apply the ex-date and cancel filters.
6. **`PriceSource`** (`bars`, `corporate_actions`) with **fixture** and **Alpaca** adapters. **`FilingSource`** (filing index, company facts, filing headers, cover pages, Form 25/25-NSE, companies snapshot) with **fixture** and **EDGAR** adapters. Real adapters = thin raw-fetch client (`httpx` for EDGAR JSON/SGML/files, `alpaca-py` for Alpaca) + pure parsers; `edgartools` (pinned, cache dir from config) is used only to parse downloaded cover-page iXBRL.
7. **`Broker` interface** and in-memory **fake broker** (submit, cancel, positions, fills; duplicate client order IDs rejected). No risk logic (Phase 4).
8. **As-of read API.** `prices_as_of`, `adjusted_prices_as_of(T, include_dividends=False)` (splits only by default; dividends for Phase 3 total return), `facts_as_of`, `securities_as_of`, `listings_as_of`, `universe_as_of`, `survivorship_gap`, and `statement_facts_as_of` (#660). All take tz-aware T and return only rows with `known_at ≤ T`, latest revision as of T (`statement_facts_as_of` has one row per key by construction, so "latest" and "first" coincide there). **Level rules** (ADR 0006 rules 4 and 8) use the **raw close at T** and adjust shares only for splits with **ex-date ≤ T**, regardless of when the split became known.
9. **Ingest.** `tradepartner ingest [--source alpaca|edgar|all] [--backfill --since DATE] [--dry-run]`. Per-source atomic chunks (one calendar month per source); a failure commits nothing from that chunk, earlier chunks stand; `--backfill` resumes from the last committed chunk. Idempotent for a completed session. Halts non-zero on stale or failed source, with only the `ingestion_runs` row written for that source. Retries on lock for `store.lock_retry_seconds`, then exits non-zero. Amendment #831 (holes): `--backfill --since DATE --source alpaca --fill-holes [--dry-run]` refetches, in the months the backfill for that `--since` has committed, each (security, month) whose security the code at the run counts as fetched in the month and that has no bar known at the run (a corrected listing end or a new listing row makes one; resume never revisits a committed month). The dry run lists them, fetches nothing and needs no Alpaca secret. The real run fetches only those names and the reference symbol, one month per chunk with req 10's staleness over the stored and fetched bars together and the existing write rules (a first-seen bar keeps the Provenance timing `known_at`, its session's close, and `ingested_at` is the fetch; absence withdraws nothing), and writes one run row per month fetched: mode `holes`, status `filled` (never `ok`, so never a fresh ingest), a cursor `holes;since=…;through=…` that resume ignores. Amendment #876: a hole is listed or fetched only when the store's price resolver at the run assigns the security some session of the month under a ticker that is an Alpaca symbol (otherwise no fetched bar can land on it); the others are counted per reason and not fetched. `--security ID[,ID…]` (repeatable) limits the holes to the named securities; a named id with no hole fetched is listed with the reason, not an error.
10. **Staleness** is source-level: expected latest session = calendar's last completed session at run time minus `ingest.settle_delay_minutes`; stale if the reference symbol has no bar for it, or more than `ingest.max_missing_share` of listed names are missing it. Amendment #784 (owner decision, 2026-10-04): listed names are the benchmarks and the common names on one of `universe.exchanges` (OTC is not one; the SIP feed has no OTC bars). A listed common name whose every listing span live in the chunk window (the month in backfill, the expected session in a daily run, where only the current listing is read) is `snapshot_static`, and that has no bar at all in that window, is reported (the run message gives their count and up to 10 names) and left out of both sides of the `max_missing_share` share; benchmarks, and names with any filing-based span in the window, count as before. Then (dark names, same amendment): any other listed name with no bar counts only if it had a bar in the previous chunk window (the previous calendar month in backfill, the previous session in a daily run; bars already in the store before this chunk, nothing later) or its first listing starts after that window; otherwise it is reported by cause the same way and not counted, so a name that goes dark counts once, in the chunk it disappears. Benchmarks always count, and when the store holds no bar at all in the previous window (the first chunk) every miss counts. What this gives up: before ~2019 almost every common name is `snapshot_static` (req 3), so in those backfill months the share check rests on the reference symbol, the benchmarks and the names with a bar or a filing-based span; a partial outage that returns no rows for static-only names, or for names already dark the chunk before, shows only in the message, and a month with no counted names has share 0. On an IEX-only feed (set by the owner in T3), `max_missing_share` and rule 6 thresholds are what the owner recorded, never silently relaxed.
11. **Health as code.** `tradepartner health [--check]` uses a pure `health.py` shared with the page: last successful ingest per source; coverage; gaps; survivorship gap and its three side categories; unclassifiable count; `snapshot_static` reliance count at the latest T; **delisted names count and list**; liquidity-rule and fill-price settings; integrity rules (non-null `known_at`; `known_at ≤ ingested_at`; bars only on sessions; no duplicate `(security_id, session, known_at)`; non-overlapping listings per security; no bars after a listing's end for delistings; guarded SIC default = charter). `--check` exits non-zero on any failure. Amendment #822 (owner decision, 2026-10-04): a delisted listing's end is its last bar (req 4), so *no bars after a listing's end* fails only a bar after `effective_on` that comes back after more than `master.transfer_window_sessions` missing sessions (XNYS sessions strictly between two bars, the first gap counted from the last bar on or before `effective_on`, or from `effective_on` when there is none), and every later bar up to the security's next listing on an exchange (a NONE or OTC row does not end the check); a line that keeps trading past `effective_on` without such a gap passes. A delisting that took effect before the store's first bar therefore fails its line's bars on purpose: the store cannot show the line kept trading. *Non-overlapping listings* tolerates rows of the same ticker with the same `valid_from`, whatever their exchange tag or class-title wording (filer noise, one line), and, when testing a late Form 25, does not count a next row on exchange NONE or OTC as a second line (suspension, OTC quote, then a late Form 25, the normal Nasdaq sequence): the filing is tested against the next row on an exchange instead. Same-start rows of different tickers still fail.
12. **Page.** Streamlit, rendering `health.py` output, read-only, with the busy state.
13. **Fixture universe** as CSV, seeded generator, content-equal regeneration. Required cases: delisting with truncated history (> N sessions before the Form 25 filing) and one within N; a **clean merger delisting** (last bar the session before filing; expected *not* missing); a **25-NSE**; a Form 25 on a **non-common class** (common survives); an **exchange transfer**, plus a probe T **between the Form 25 and the new listing's `known_at`** (expected: delisted at that T, transfer later); a **same-company ticker change**; a **ticker reused** by a different company; a **dual-class** company; a split; a split between a shares filing and T; a **split known before T with ex-date after T**; a **revised dividend**; a **split re-dated by source id**, a **split re-dated to an earlier ex-date with no source id** and a **cancelled dividend** (#108); a restated shares fact; a stale shares fact; an unclassifiable name; a `snapshot_static`-only pre-2019 listing; a holiday; a half day; SPY and MTUM as benchmarks with dividends. Generated CSVs are reviewed through the generator and excluded from the 400-line budget.
14. **Config** (pydantic settings). Every ADR 0006 threshold is a key with its default; `universe.exclude_sic_ranges` is guarded. `universe.liquidity_rule_enabled` defaulted to `false` and `execution.fill_price` to `close` until the owner's T3 research set them; T3 (#84, 2026-09-25) set `liquidity_rule_enabled=true` (SIP history gives consolidated volume) and kept `fill_price=close` ([research](../research/2026-09-25-free-data-terms.md)). Secrets only from `.env`.
15. **`data-validator` agent**: read-only, runs `health --check` and the suite on the owner's real store, reports; computes nothing itself.
16. **As-filed statement facts** (amendment 2026-10-03, #660). Revenue, cost of revenue, gross profit, total assets and operating cash flow as each issuer **first filed** them, keyed by CIK and the fact's own period, `known_at` = the filing's acceptance, one vintage per period for ever. The rules are under "Data / interfaces" > "Amendment 2026-10-03 (#660)".

## Acceptance criteria (testable)

Timing and store
- [ ] Every fact table row: tz-aware UTC `known_at`, `ingested_at`, `known_at ≤ ingested_at`, non-null `source`, `provenance` in the allowed set (schema test; `health --check` rule).
- [ ] A bar for session S has `known_at` = XNYS close of S (normal day and half day).
- [ ] A bar re-fetched with a different close becomes a second row with `known_at = ingested_at`; `prices_as_of` returns each in its interval.
- [ ] First-seen corporate action without an announcement time: `known_at` = close before ex-date; a **revised** dividend becomes a new row with `known_at = ingested_at`, and `adjusted_prices_as_of(T, include_dividends=True)` uses the old amount before that and the new after.
- [ ] Backfilled 2018 split in 2026: `adjusted_prices_as_of(2019-01-31 close)` adjusts 2017 prices.
- [ ] Split known before T with ex-date after T: `universe_as_of(T)` cap uses unadjusted shares and raw close; rule 4 uses the raw close.
- [ ] Restated shares fact: `facts_as_of(T)` returns the earlier value between the two `known_at`, the later after; facts carry `as_of_date` and `class_member`.

Look-ahead
- [ ] **Truncation invariance** for every as-of function including `universe_as_of` and `survivorship_gap`: f(T) on the full fixture store equals f(T) on a store truncated to `known_at ≤ T`, for probe timestamps placed **just before and just after every distinct `known_at`** in the fixture.
- [ ] The broken adapter's violations (early `known_at`; pre-adjusted prices; ticker-based resolution; `known_at > ingested_at`; back-dated revision) are each caught by a named check.
- [ ] A bare date passed as T raises.
- [ ] An autouse test fixture makes `socket.connect` raise; every test passes with it on.

Security master and universe
- [ ] Reused ticker: prices by `security_id` return only that company's rows. Same-company ticker change: one `security_id`, two listing ranges.
- [ ] Earliest-filing rule: a fixture company whose only filings are historical has a `securities` row with `known_at` = its first filing's acceptance; `securities_as_of` at a T before any filing returns nothing for it.
- [ ] `snapshot_static` attributes apply before fetch time only for the columns config allows; `health` reports the reliance count. `snapshot_static` values are never written into a row with an earlier `known_at`; as-of reads and the truncation harness give such rows no exemption, so before its `known_at` the row is invisible (#35).
- [ ] Delistings: 25 and 25-NSE both end the named listing; a Form 25 on a preferred class leaves the common listed; a transfer within the window keeps the security in `universe_as_of` on the new exchange once the new listing is known, and shows it delisted at a T before that; the delisted fixture name is absent from `universe_as_of` after its last session and present in `securities_as_of` with dates.
- [ ] `universe_as_of(T)`: rules 1–8 in ADR order; dual-class cap summed over classes, both listed classes admitted; split-adjusted cap; stale shares excluded; output records enabled rules and the fill-price setting.
- [ ] `universe.liquidity_rule_enabled=false` (when set; the default is `true` since T3): rule 5 skipped and recorded; `health` shows it.
- [ ] Each `universe.*` key overridden one at a time changes membership as expected; AST check: `universe.py` and `gap.py` contain no numeric literals other than 0, 1, -1.
- [ ] `survivorship_gap(T)` matches hand-computed count and size share per the formula; clean merger delisting is *not* missing; the three side categories are reported separately.

Adapters and fixtures
- [ ] EDGAR parsers on recorded payloads: filing-derived records have `known_at` = acceptance and `provenance = filing`; snapshot records `provenance = snapshot` with recorded fetch time; SGML header yields SIC; cover page yields title, symbol, exchange; 25 and 25-NSE yield class title and exchange.
- [ ] Alpaca parsers on recorded payloads: raw closes, `known_at` per timing rule, actions with the proxy rule, resolution through the master.
- [ ] Scrub test: no fixture contains a key-shaped string, an email pattern, or a `User-Agent`-shaped string (pattern-based; no `.env` needed).
- [ ] No `.env`: package imports and all tests pass.

Ingest
- [ ] Idempotent re-run for a completed session: no fact rows change; `rows_added = 0`.
- [ ] Staleness on holiday, weekend, pre-close, half day: expected latest session is the last completed one (four tests).
- [ ] Stale reference symbol: non-zero exit, `status = stale`, no fact rows changed for that source.
- [ ] #784: an OTC common name with no bar is not counted, and a NYSE or NASDAQ common name with no bar still is (daily and backfill).
- [ ] #784: a `snapshot_static`-only common name with no bar in the window gives `ok`, named and counted in the run message; the same gap on a name with a filing-based span in the window, or on a benchmark, is `stale`; a static-only name with some bars follows the existing rule.
- [ ] #784: a name with no bar in this chunk or the previous one is reported, not counted; a name with a bar in the previous chunk and none now counts; a name first listed in this chunk with no bar counts (daily and backfill).
- [ ] Mid-chunk failure: that chunk not committed, earlier chunks committed, `--backfill` resumes from `chunk_cursor`.
- [ ] Lock: with a short-lived reader that closes within `lock_retry_seconds`, ingest completes; with a writer that never closes, ingest exits non-zero after the retry window. The page shows "store busy" while a chunk commits.

Health and page
- [ ] `health --check` passes on the fixture store; fails naming the rule on an injected duplicate bar, overlapping listing, bar after a delisting end, or changed SIC default.
- [ ] Headless render shows every `health.py` metric, including delisted names and `snapshot_static` reliance.

Real-store evidence (close-out PR, not unit tests)
- [ ] `universe_as_of` at a month-end **inside the backfill window** on the owner's real store is non-empty and includes at least one name later delisted.
- [ ] Five consecutive scheduled `ingestion_runs` rows with `status = ok`.

Statement facts (amendment 2026-10-03, #660)
- [ ] Schema: `statement_facts` has the four common columns, `provenance = filing` only and UNIQUE `(cik, fact_name, period_end, period_days)`; a second row for a stored key raises; `period_start` is NULL exactly when `period_days = 0` (`health --check` rule).
- [ ] Switch: with `edgar.statement_facts_enabled = false` (the default) an ingest run calls no `statement_facts`, makes no request for it, writes no cache for it and adds no row; `backfill` is byte-for-byte the same code path as before on that setting.
- [ ] Parser on a constructed companyfacts payload: a 10-K carrying the fiscal year and two comparative years of `Revenues` yields three keys on their own `(period_start, period_end)`, the two comparatives flagged; an entry with a misleading `fy` and no `frame` still lands on its dates; a form outside `edgar.statement_forms` (taken from the submissions record, not the entry) is ignored; a non-`USD` unit is skipped and counted; a 10-K/A that is the first carrier of a key is its vintage with `form = 10-K/A`; an entry naming a dimension raises.
- [ ] Precedence and conflict: a filing carrying `Revenues` and `RevenueFromContractWithCustomerExcludingAssessedTax` with different values stores the first with its `xbrl_tag`; the same tag twice for one period with two values stores nothing for that key from that filing, counts one conflict and lists it, and the next filing's clean value is the vintage with `comparative` set by the Periods rule (TRUE from a prior-period column, FALSE from a 10-K/A of the same period); more than `edgar.min_failed_filings` conflicting accessions of one form do **not** fail the chunk and write nothing to `failed_filings.json`.
- [ ] Co-registrant filters: an accession FSN extracted under another CIK, and one whose cached cover page names another entity, contribute no statement rows to this CIK.
- [ ] Derived gross profit: no `GrossProfit`, stored `revenue` and `cost_of_revenue` vintages from one accession and period → one `derived` row equal to their difference with that filing's `known_at` and accession; components from two filings, or one withheld → no row; a filed `GrossProfit` that is the first carrier → `reported`, nothing derived; a `GrossProfit` filed after a derived vintage → counted restated, not stored, also when both filings arrive in one run (the derived row keeps the first filing's acceptance); an unstamped accession carrying `GrossProfit` for the key with `filed` on or before the components' filing's → nothing derived, `statement_held` counts the held entry once, and once stamped the earlier-accepted is the vintage; a conflict-withheld `GrossProfit` in the components' filing → nothing derived from it, and the key stays empty until a later filing carries it cleanly; a `GrossProfit` skipped as non-USD or malformed → the candidate stands; every `derived` row in the fixture store equals the difference of the two stored `revenue` and `cost_of_revenue` rows with its `cik`, `period_end`, `period_days` and `filing_accession`, both present (the `--check` rule, which also fails on a derived row with a component row missing).
- [ ] First vintage: a fixture issuer whose FY2018 revenue is restated in its FY2019 10-K: `statement_facts_as_of(T)` returns the FY2018 original at every T from the first acceptance on, including after the restating filing; the restated value is in no row; the run message counts `statement_restated = 1`; a re-run adds zero rows.
- [ ] `known_at` is the filing's acceptance from submissions: a fixture entry whose companyfacts `filed` date differs from its acceptance date (an after-hours filing) is visible from the acceptance instant and carries no trace of `filed`.
- [ ] Hold, unstampable and late: with the earlier carrier's accession absent from the stamps file, the key is not written and `statement_held` counts it, also when the two `filed` dates are equal; once stamped, that carrier is the vintage; an accession settled as unstampable holds nothing and its entries count on `statement_unstampable`. A record accepted before a stored vintage that arrives on a later run is not written, counted on `statement_vintage_late`, and `health` warns; `ingest --rebuild-statement-facts` then deletes and re-ingests the table in one transaction, after which the count is zero and the earlier carrier is the vintage, with the deleted count in the run row.
- [ ] Writes: a CIK's rows reach the store in one bulk insert per CIK (a test counts the statements), the tz validation runs once per frame, and a frame with a naive timestamp is refused before the insert.
- [ ] **No look-ahead**: truncation invariance for `statement_facts_as_of` with probes just before and just after every distinct `known_at` in the fixture (the T10 harness), including the join through `securities_as_of` (a CIK with no securities row at T returns nothing; a dual-class CIK's rows appear once per class); the broken adapter's statement fact stamped at its `period_end` close, and one stamped at midnight of `filed`, are each caught by a named check (the stamp precedes the filing's acceptance).
- [ ] `--bulk-from-cache`: with a zip present no request is made for the bulk file (the socket fixture proves it), the bulk path is taken whatever the stale-cache count, a CIK whose member holds its latest stamped cover-form accession makes no per-CIK request, and a file that does not open as a zip raises; without the flag the bulk file is requested as today, and stale statement caches count toward `edgar.bulk_stamp_threshold_ciks` as stale shares caches do, only while the switch is on (off, the count is unchanged).
- [ ] Real-store evidence (owner, plan T78; report-only, no threshold): the re-ingest's run-row counts and run time; zero bulk and per-CIK companyfacts requests for CIKs the zip holds; coverage at a month-end T inside the backfill window; one hand-checked issuer's FY revenue, cost of revenue, gross profit and total assets against its 10-K; `statement_vintage_late = 0`.
- [ ] Price-quality gate (#787): `traded_only=True` drops a zero-volume bar that `traded_only=False` keeps, and from the revision's `known_at` only. `price_jumps_as_of` lists an unexplained 3× move and its return. A stored split or dividend in (previous bar, session] explains its move. A split first known after T leaves the jump listed at T. The list equals the one over a store truncated at T at every probe (truncation invariance).
- [ ] Universe rule 6: a zero-volume bar in the window is `missing_bars`. An unaccepted jump in the window is `price_jump`. Accepting every listed jump of the name, or a window that no longer holds the jump, readmits it. A `price_jump` exclusion is not in the gap's `truncated_history`. Each new key has a membership case.
- [ ] `health` lists pending and accepted jumps without failing `--check`, and `--jumps-before` hides later ones. The backtest provider's marking and raw frames have no zero-volume bar.

## Out of scope

Signals, backtester, trial registry, cost model (Phase 3). Risk-gated broker wrapper, Alpaca paper adapter, alerts (Phase 4). Paid vendor (Phase 3 ADR). Intraday data. Fundamentals beyond shares outstanding, SIC and the five statement facts of the 2026-10-03 amendment (#660); within that amendment, also out of scope: IFRS statements (20-F/40-F filers), dimensioned (segment) facts, restated values as revision rows, and every derived series (a fourth quarter as FY minus nine months, trailing twelve months, calendarised periods), which are read-time computations for Phase 3. **Amendment 2026-10-03 (#660): as-filed statement facts.** The store gains the statement values the Phase 3 profitability claim needs (research brief B3, "slow liquid profitability-aware tilt": gross profits over total assets, the only SUPPORTED selection claim, [brief](../research/2026-10-03-quantitative-investing-research-brief.md); the [claims pilot](../research/2026-10-03-claims-pilot.md) HS-4 and its data table), stored as each issuer **first filed** them, so a signal at T sees exactly what a reader of the filing saw at T and nothing a later restatement, reclassification or comparative column added. Merging this amendment records owner decisions (a) to (e) below; the open questions stay open.

*Facts.* Five canonical names, each an ordered list of `taxonomy:tag` fallbacks in `edgar.statement_tags` (the defaults below; the order is the precedence within one filing):
- `revenue`: `us-gaap:Revenues`, `us-gaap:RevenueFromContractWithCustomerExcludingAssessedTax`, `us-gaap:SalesRevenueNet`, `us-gaap:RevenueFromContractWithCustomerIncludingAssessedTax`, `us-gaap:SalesRevenueGoodsNet`, `us-gaap:SalesRevenueServicesNet`;
- `cost_of_revenue`: `us-gaap:CostOfRevenue`, `us-gaap:CostOfGoodsAndServicesSold`, `us-gaap:CostOfGoodsSold`, `us-gaap:CostOfServices`;
- `gross_profit`: `us-gaap:GrossProfit`, derived when not filed (below);
- `total_assets`: `us-gaap:Assets`;
- `operating_cash_flow`: `us-gaap:NetCashProvidedByUsedInOperatingActivities`, `us-gaap:NetCashProvidedByUsedInOperatingActivitiesContinuingOperations`.

Why these (decision (a)): gross profits over assets needs `gross_profit` and `total_assets`; `revenue` and `cost_of_revenue` are its components (the derivation, and E1's revenue target); `operating_cash_flow` is included because cash-based operating profitability (Ball, Gerakos, Linnainmaa and Nikolaev, JFE 2016; not graded in the brief) is the one refinement of the profitability claim the signal work is likely to ask for next, and it costs nothing structurally: it is a duration fact exactly like `revenue`, stored as filed (a 10-Q's cash-flow statement is year-to-date, so its quarterly value is a read-time difference, which this amendment does not store). `us-gaap:InventoryNet` is **not** included (decision (b)): no SUPPORTED claim uses it (Novy-Marx's gross profitability does not), and for an issuer without inventory the absence of the tag and a value of zero mean different things, so a consumer could not tell "no inventory" from "not tagged" and any ratio built on it would be silently biased. Adding a name later is a config change plus one re-ingest (below). The lists are deliberately short: every tag on them is the concept itself, never a near relative (`CostOfGoodsAndServiceExcludingDepreciationDepletionAndAmortization` is a different concept and stays off the list).

*Table.* `statement_facts(cik, fact_name, xbrl_tag, period_start, period_end, period_days, value, unit, form, filing_accession, basis, comparative)` plus the four common columns, `provenance = filing` only. Keyed by **CIK**, not `security_id` (decision (c)): a statement is the issuer's, not a share class's (a dual-class company has one revenue), so no class mapping, no "unmatched" fact and no duplicate per class. ADR 0003 rule 3 is kept: the key is the master's own CIK column, never a ticker, and the read resolves through the master. `statement_facts_as_of(T, security_ids=None)` joins through the `securities` rows known at T and returns **one row per `(security_id, fact_name, period_end, period_days)`**, so a dual-class issuer's rows appear once per class (the shape every other as-of function has) and a CIK with no securities row at T is invisible at T. `period_start` is NULL and `period_days = 0` for an instant (`total_assets`); for a duration, `period_days = period_end − period_start` in days. **UNIQUE `(cik, fact_name, period_end, period_days)`** with no `known_at`: the schema itself enforces one vintage per period. Schema version bump with an additive migration (the table is new; no existing row changes).

*First vintage (decision (d)).* For each key the stored row is the value in the **earliest-accepted** filing (acceptance from submissions; the form is the submissions record's, never the companyfacts entry's `form`, and must be in `edgar.statement_forms`, default `10-K, 10-Q, 10-K/A, 10-Q/A, 10-KT, 10-QT`) that carries it. `known_at` is that filing's acceptance (submissions UTC; never companyfacts `filed`, FSN `accepted` or an SGML time, pitfall P12 of [#572](../research/2026-10-02-edgar-data-pitfalls.md)). A later filing carrying the same key, with an identical value (next year's comparative column) or a different one (a restatement, a reclassification, a 10-K/A), is **never stored**: no revision row, no in-place update. Differing later values are counted per run (`statement_restated`) so the owner can see how much restatement the rule hides; the Definitions' revision rule ("a later value for the same key is a new row") does not apply to this table, and that is the point of it. ADR 0003 rule 1 (every record carries `known_at` and `ingested_at`) holds unchanged; rule 4's fixture case "one restated fundamental (two `known_at` values for the same period)" stays met by `facts` (the restated shares case), and `statement_facts` cannot hold a revision by construction; no ADR is needed, because the table is rebuildable from the cached zip and nothing stored elsewhere changes. `form` is kept verbatim (`10-K/A`), so an amendment that is the first carrier of a key is visible as such. Within a run, a CIK's records are taken in acceptance order and a stored key skips. Two guards keep the result independent of the order runs see filings in: (i) a key is **held** (not written this run, counted `statement_held`) while an entry for it sits under an accession that has **no stamp record yet** (not in the CIK's stamps file) and a companyfacts `filed` date **earlier than or equal to** the stamped carrier's (`filed` orders, it never stamps; a same-day tie holds); an accession the stamps file has settled as **unstampable** (`accepted_at` None, the adapter's cached-unstampable case) never holds anything: its entries are absent, counted on `statement_unstampable`; (ii) a record accepted earlier than a stored vintage that surfaces on a later run (a stamp that arrived late, or a tag added to the list after the key was stored from a later filing) is not written and is counted (`statement_vintage_late`); `health` warns while it is non-zero. The remedy is `tradepartner ingest --source edgar --rebuild-statement-facts` (with `--bulk-from-cache`): in the run's one transaction it deletes every `statement_facts` row and re-ingests the table from the cached payloads, and the run row records the row counts before and after; never a back-dated row, never a partial fix. A rebuild changes what a past as-of read of this table returned, so a trial logged before it is reproducible only from its own export (the Phase 3 registry's concern, not this table's); T78 states the count before the first rebuild, if one is needed.

*Within one filing.* Tag precedence: the first name in the fallback list that the filing carries for the period wins and is recorded in `xbrl_tag`; two listed tags with different values for one period are different concepts, not a conflict. **Conflict** (pitfall P13): the same tag, period and unit with two different values in one filing withholds that (accession, fact, period) key from that filing: counted (`statement_conflicts`) and listed by the adapter on `statement_conflict_keys`, a plain attribute (accession, fact, period, the values), for the run message and T78's report, **never** recorded in `failed_filings.json` and never counted by T11h's per-document share or its cross-day (error class, base form) pair rule, which would otherwise halt every EDGAR run once five 10-K accessions had conflicted (a conflict is a property of the filing, not a fetch failure, and no number of them is a reason to stop ingesting); identical duplicates collapse to one; a withheld key's vintage is then whichever later filing carries it cleanly, with `comparative` set by the Periods rule as for any row (TRUE when it came from a prior-period column, FALSE for a 10-K/A of the same period). Only the units in `edgar.statement_units` (default `USD`) are read; a filing whose only unit for a tag is another currency is counted (`statement_non_usd`) and skipped. Only undimensioned facts: the companyfacts API carries no segment facts by construction, so an entry that names one is schema drift (pitfall P9) and the parser raises, which fails the chunk on purpose, as every other drift does.

*Derived gross profit (decision (e)).* The parser never derives; the **ingest** does, inside the first-vintage pass: a filing whose `revenue` and `cost_of_revenue` for a period are the **stored** vintages of both keys (stored on an earlier run, or being stored from this filing), in one unit, and which carries no `GrossProfit` for that period in a read unit (an entry skipped as non-USD or malformed is no value for the key, exactly as a skipped component is, so it does not count as carried), contributes a **derived candidate** for the `gross_profit` key, `revenue − cost_of_revenue`, taken at that filing's turn in the CIK's acceptance order, after the filing's reported keys, as the filing's own entry: if the key is still unstored then, the row is stored with `basis = derived`, `xbrl_tag` = the two source tags joined by `-`, that accession, and its acceptance as `known_at` (no knowledge beyond the filing's own); a stored key skips the candidate as it skips any entry. Every filed row carries `basis = reported`. Ordering the candidate by its filing's acceptance is what makes the vintage the same whether the filings arrived in one run or several: the first load sees a 10-K without gross profit and next year's 10-K carrying it as a comparative in one pass, and still stores the derived row at the first 10-K's acceptance and counts the comparative as restated (a derivation run at the end of the CIK's pass would store the later filed value instead, which is why it runs at the filing's turn). When the two components' vintages come from different filings, or one is withheld, nothing is derived (a consumer may subtract at read time). A filed `gross_profit` whose filing is the earliest carrier always wins; a derived row, once stored, is the key's vintage like any other, so a `gross_profit` filed later is counted as restated, not stored (the first filing had no gross profit, and the derived value is what its reader could compute). Two cases withhold the candidate. **Held key:** guard (i) applies to the candidate as to any carrier: while an accession with no stamp record (its records reach the ingest with `accepted_at = None` and their `filed`) carries `GrossProfit` for the key with a `filed` date earlier than or equal to the components' filing's, the key is held and nothing is derived for it this run, however complete the components (`statement_held` counts the held entry once; the withheld candidate adds nothing), since a derived row would take the key and the held filed value, once stamped, would be counted as restated and lost; once the stamp arrives, the earlier-accepted of the two is the vintage, the filed value as `reported` or the derived row. **Conflict in the same filing:** a `GrossProfit` withheld by conflict in the components' own filing (on the adapter's `statement_conflict_keys` list, which the ingest reads by accession, fact and period; a source without the attribute has none) withholds the candidate too: that filing's gross profit is ambiguous, so nothing is derived from it; and because the components' vintages are that filing's and no other accession can share them, only a later filing's clean `GrossProfit` can fill the key (`reported`, `comparative` by the Periods rule), and if none ever comes the key stays empty, visible through the run's `statement_conflicts` count, and a consumer may subtract at read time. Every derived row therefore equals the difference of the two stored `revenue` and `cost_of_revenue` rows with its `cik`, `period_end`, `period_days` and `filing_accession`, both present, and `health --check` recomputes exactly that (a derived row with either component row missing fails it), which cannot fail on correct data. The flag is on the row because a consumer may want to exclude derived values (a filer that reports no gross profit is often one whose cost line is not a cost of goods).

*Periods.* The key is the fact's own `(period_start, period_end)` from the entry, never `fy`/`fp` (a comparative column in a 10-K carries the filing's `fy`/`fp`, not its own) and never `frame` (SEC assigns it to one entry per calendar frame, usually the latest filing's, so a first vintage often has none). Every as-filed duration is stored as filed: a quarter, a half-year or nine-month year-to-date, a fiscal year, a stub after a fiscal-year change; `period_days` tells them apart and consumers filter on it. **No fourth quarter (FY minus nine months), no trailing twelve months, no calendarisation** at ingest: each is a read-time computation whose `known_at` is its latest component's, Phase 3's to write against this table. `comparative = TRUE` when the row's `period_end` is earlier than the latest `period_end` the same filing carries for the same fact and `period_days` (the value came from a prior-period column). An entry whose period ends after the filing's acceptance date (New York), starts after it ends, or whose value is not finite is withheld and counted (`statement_malformed`); the shares path's end-date cap is not applied, because here the date is the key and a moved date would be a different period.

*Source and re-ingest.* The whole path is behind **`edgar.statement_facts_enabled`, default `false`**: while it is off the ingest never calls `statement_facts`, the adapter makes no request and writes no cache for it, and the backfill, which runs the same `_ingest_filings`, is unchanged; T78 turns it on for the owner's store and flips the default in the same PR once the real-store run has passed. Values come from the companyfacts payloads the shares already use (`{}` and keyless members as #566 and #599), read once per CIK per run (one zip member read serves both the shares and the statement caches) and parsed into a cache beside the shares one (`statement_facts/v<N>/<cik>.json`, keyed by the CIK's latest stamped cover-form accession and the configured tags, so a new filing or a new tag re-parses that CIK). The cache holds the CIK's parsed entries **unstamped, and its conflict entries with them**, so a cache read restores `statement_conflict_keys` exactly as a parse sets it (else a run served from the cache would derive the candidate a conflict withheld, and a re-run would add a row), and every entry is stamped at read time from the stamps file, as the shares are, so a stamp that arrives later with no new cover-form filing is applied on the next read without a re-parse. **Which counts a cache read restores:** a cross-run fetch-pass cache hit (the CIK's cache key unchanged since it was last parsed) sets `statement_conflicts` for that CIK from the cached conflict entries, exactly as a parse would, because the cache carries those entries; it also sets `statement_unstampable` correctly, because stamping (and so settling an accession as unstampable) happens at read time from the stamps file on every read, cache hit or not, never baked into the cache at parse time. It does **not** set `statement_non_usd`, `statement_malformed` or `statement_none` for that CIK: the cache holds only parsed entries and conflict entries, never the parse-time skip counts, and it cannot tell "no tags filed" apart from "every candidate entry skipped, filtered or non-USD" once both look like zero cached entries. Those three counts come from a parse only; a CIK whose fetch-pass read is a cache hit contributes zero to each of them for that run, whatever it contributed when the entries were first parsed. The two filters `_company_facts` applies are carried over unchanged: an accession FSN extracted under another CIK and absent from this CIK's FSN cache (a co-registrant's combined filing), and an accession whose cached cover page names another entity, contribute nothing, so a REIT's operating partnership never stores the parent's revenue as its own. Statement facts are full history every run, as the shares are (`--since` does not limit them). `statement_facts(cik)` is asked once per CIK in the run's **fetch pass** (req 1, #173: every filing question before the write lock), so each CIK's payload read, parse and cache write happens with no store connection open and the adapter's `statement_*` counts and its `statement_conflict_keys` list are plain attributes set then, as the shares path's are, and the counts are taken from this fetch pass only. The statement cache is written for every CIK the pass answered (a member that trails the CIK's latest filing included, keyed by the accession the payload reached so the next run's key mismatches and re-parses it), because under the lock the write phase asks the adapter for one CIK at a time and that call is a **cache-file read, never a request** and never an in-memory memo of the records (the first load's 10^7 records would not fit the way the shares' memo does); that per-CIK read restores `statement_conflict_keys` for the ingest to consult but does not re-run the counting, so the write phase never adds to the run row's `statement_*` counts. Which source the bytes come from: today the bulk zip is used only when the count of stale **shares** caches crosses `edgar.bulk_stamp_threshold_ciks`; that count includes stale statement caches **only while the switch is on** (off, the decision is exactly today's, so the backfill never downloads the bulk zip on their account), and **`--bulk-from-cache`** forces the bulk path outright: `bulk_company_facts` returns `edgar.cache_dir/bulk/companyfacts.zip` as it stands, provided it opens as a zip, without a request, and every CIK whose zip member holds its latest stamped cover-form accession is served from it with no per-CIK request; only a CIK the zip lacks or whose member trails its latest filing goes to the per-CIK API, counted as today. The flag is off by default, and without it the nightly zip is re-downloaded as today. The flag changes where bytes come from, never a `known_at`: every stamp still comes from submissions. The first load on an existing store is therefore one ordinary `tradepartner ingest --source edgar --bulk-from-cache` run with the switch on.

*Ingest.* The fetch pass (the `_build_filings` pass that `_prefetch` freezes, req 1; both its callers run it) asks `statement_facts(cik)` for every issuer CIK before the lock and has the adapter fill each CIK's parsed statement cache; the proxy records only **which CIKs were filled**, never the records (the `_Recorded` memo would otherwise hold the first load's 10^7 records in Python). Inside the transaction the write phase asks the adapter for one CIK at a time, a cache-file read that makes no request (a CIK the pass did not fill raises, as any unanswered question does), and drops that CIK's records after its insert, so the lock is held only while writing and Python holds one CIK at a time. That read restores `statement_conflict_keys` for the derived-candidate rule below but does not re-trigger the adapter's own `statement_conflicts`, `statement_non_usd`, `statement_malformed`, `statement_unstampable` and `statement_none` counts, which the adapter sets once, from the fetch pass only (the run row's remaining counts below — `statement_held`, `statement_restated`, `statement_vintage_late` and `statement_derived` — are the ingest's own, computed here as this same write phase processes each CIK's rows). Per CIK: records in acceptance order, the held and late rules above, insert-or-skip against the keys the store holds for that CIK, with the derived candidate taken at its filing's turn (above). The rows are written **per CIK inside the run's one transaction** through a bulk insert (one frame per CIK registered with DuckDB and inserted in one statement, the tz check done once per frame, never `insert_row` per row), so Python holds one CIK's rows at a time (about 10^3) and the transaction holds the rest (about 10^6 vintages on the first load, 10^7 records read); the commit is the run's, as today. Idempotent: a re-run adds zero rows. The run row counts: added, `statement_held`, `statement_unstampable`, `statement_vintage_late`, `statement_conflicts`, `statement_restated`, `statement_non_usd`, `statement_malformed`, `statement_derived`, and `statement_none` (CIKs with a companyfacts payload and none of the tags, IFRS-only filers included); with `--rebuild-statement-facts`, also the row count deleted.

*Health.* `health.py` and the page report, at the latest T: the share of `universe_as_of(T)` names whose issuer has a `revenue` and a `total_assets` row known at T with `period_end` within `universe.max_shares_age_days` of T (the same freshness bound as rule 7, no new threshold); the derived share of `gross_profit` rows; the last run's counts above, with a warning while `statement_vintage_late > 0`; the switch's state. Coverage is reported, not thresholded: no rule reads it. **This bound is not any hypothesis's own.** A signal in the `profitability` backtest family (amendment 2026-10-03, #720) reads with its own `profitability.max_fact_age_days` (B3's default 548, 18 months, wider than `universe.max_shares_age_days`'s 400), so this page's coverage share under-reports how much a profitability signal can actually use each February to June, when a filer's prior-year row is between 400 and 548 days old and `universe.max_shares_age_days` has already called it stale. Kept as is, with this note, rather than taking the wider bound, both, or a per-family bound: this page answers one question, "is the shares/facts pipeline healthy", with rule 7's bound, the one every consumer shares; it does not answer "how much can each registered signal use", which varies per hypothesis and belongs in that hypothesis's own file. Rule 7's bound is **not claimed to be right for annual facts** (the amendment itself calls it "wrong for annual facts", "Config keys" above): the coverage share dips every February to June by the filing calendar, not a pipeline fault, so a reader should compare like months, and T78's evidence month-end is better chosen outside that window for the same reason (#728). Integrity rules for `--check`: the four common-column rules; `period_start` NULL exactly when `period_days = 0`, else `period_days = period_end − period_start`; every `derived` row equals the difference of the two stored `revenue` and `cost_of_revenue` rows with its `cik`, `period_end`, `period_days` and `filing_accession`, both present (a missing component row fails the rule); `basis` in `{reported, derived}`.

**Survivorship gap** at T: let W = the sessions in (previous rebalance session, T]. L = common, non-benchmark listings active at **any** session in W (known at T). M = names in L still listed at T with no bar at T, plus names in L delisted (not transferred) inside W whose last bar is more than `gap.missing_tail_sessions` before the **last session before the Form 25 filing**. Count share = |M|/|L|. Size share = Σ(shares × last known raw close) over M / Σ over L; names with no close ever contribute zero and are counted. Side categories, reported separately and not in M: `unclassifiable`, `truncated_history` (rule 6), `stale_shares` (rule 7).

**Amendment 2026-10-04 (#735): price-to-security resolution.** A price source keyed by symbol (Alpaca) maps each `(ticker, session)` to a `security_id` only through the master's `listings` rows known at the run (`ListingResolver`). This mapping through the master is the sanctioned form of req 3's "never resolve by bare ticker". A row that maps to nothing is dropped and counted, never guessed. *Terms.* A security's **span** of a ticker runs from a listing's `valid_from` until that security's next listing with a different ticker (exclusive; open while there is none). Consecutive rows with one ticker, such as a second exchange, are one span. A span is **contested** when a later span of the ticker belongs to another security that traded under a different ticker before (a rename into it: Roundhill's `META` ETF, then Facebook's `FB` -> `META`). Alpaca serves a renamed company's history under the new symbol (#104), so the contested span's rows are not assigned. The rules (owner-approved on #735):

1. **Only equity classes hold tickers.**
   - A row is left out when its ticker field names no ticker. That means `PLACEHOLDER_TICKERS` in `adapters/alpaca_prices.py` (`''`, `N/A`, `NA`, `None`, `Not applicable`, `Trading Symbol`), compared case-insensitively after trimming spaces, quotes and brackets at both ends, or any field with no letter (`-`, `0`). The words in `PLACEHOLDER_WORDS` (`true`, `false`, `yes`, `no`) count only when not in capitals, so TrueCar's `TRUE` resolves. `NA` stays on the list although Nano Labs trades as `NA`: other filers write it for "not applicable", and a later such row would take Nano Labs' bars. Nano Labs is therefore left out and counted.
   - A row is also left out when its class is not equity, read from the row's own `class_title` by `store.classify.listing_kind`. The rule runs on the title's head: up to the first comma, less a trailing "included as part of the units" clause, and less a shareholder-rights plan attached to a common class, as in "Common Shares (including Rights under Shareholder Rights Plan)". The kinds, in order:
     - `coupon`: a `%` in the head, or anywhere in a title whose head is not a common class.
     - `preferred`, `debt` (notes, debentures, bonds), `warrant`, `right`: the head names the word.
     - `preferred`: a depositary *share* that is not American or Global, so a foreign issuer's ADS titled only "Depositary Shares" is left out too.
     - `unit`: a unit, unless common or depositary units or partner interests (MLP units).
     - A row with no title (`None` or blank: a snapshot) takes the ticker-suffix rule of classification rule 7.
   - Everything else is equity, including ADSs and unrecognised share titles. This is wider than the universe's `security_types` on purpose, since the universe filters again.
   - The rule applies **per span**: a span with any non-equity row is left out whole.
   - A left-out row still ends its security's previous span. A non-equity span holds no ticker but still **shadows** another company's span that started on or before it, from its own start and while it lasts: the ticker resolves to nothing there rather than going back to the older company. Spans of the same company are not shadowed, so a company's notes listed under its common ticker never take the ticker or hide the common, whatever their start. Placeholder spans shadow nothing.
2. **One security, two tickers on one day** (two different tickers on equity rows of one day). If one of them is the ticker of the security's row just before that day (an equity row), the other rows of that day are a typo and are dropped: the security keeps its ticker (#819; FutureFuel listing Ford's `F` beside its own `FF` keeps `FF` and leaves `F` to Ford). Otherwise the security holds neither ticker, nor any later one, from that day. Its rows are not assigned, and the tickers resolve as if it had never listed them. Placeholder and non-equity rows do not count toward the pair.
3. **One company, two classes, one ticker (silent takeover).** Within one CIK (ids `<cik>` and `<cik>:<class>`), the class that held a ticker first keeps it. A span of another class of the company that starts while the first class holds the ticker never holds it, not even after the first class moves on: a Class B listed under the Class A's ticker never takes the Class A's prices. Such a span shadows other companies like a left-out span (rule 1). Across companies the most recent span still wins (ticker reuse).
4. **Same-start ambiguity.** Two securities' spans of one ticker starting on the same day are **ambiguous**: the ticker resolves to nothing while they are the latest, like a contested span, and the run continues.
5. **Counted.** Every alpaca run row's message carries the resolver's counts: placeholder-ticker listings, the rows of non-equity spans by kind, same-day-pair listings and securities, later-class, ambiguous and contested spans, and the co-registrant and disputed claims of rule 6 (held until the holder leaves). It also carries the bar and action rows of the chunk that resolved to nothing.
6. **Registrant check (#793).** The ticker belongs to the registrant whose equity trades under it. Across companies, a span that starts while another company's span of the ticker holds it (the *holder*: an assigned span under rules 1-4) is a **claim**, unless the holder **left** on or before the claimant's start. The evidence is read from the store as known at the run:
   - A holder *left* on the earliest of two days. One is the `effective_on` (else the day after `end_session`) of a listing of the holder's own security that `listing_ends_as_of` calls `delisted`, on or after the holder's span start, with an equity class by `listing_kind` (a transfer is not leaving, nor is a preferred or note class). The other is the day after its company's last cover-page `shares_outstanding` filing (UTC day of `known_at`), once more than `alpaca.registrant_quiet_days` (default 180) have passed by the run with none. Since 2022 a company's share-count filings are 91 days apart at the median and 168 at the 99th percentile, so 180 days marks a missed filing. The leaving day depends only on the holder's own filings and the run's day, never on which of the two companies filed last.
   - A claim is a **co-registrant** claim if the holder has not left at all and both companies reported one share count for one date no more than `alpaca.registrant_quiet_days` before the claimant's start, or later. That is the combined filing behind the claimant's listing, as with AEP Texas or a REIT's operating partnership citing the parent's stock; on the 2026-10-04 store the shared date is 0-30 days before the start. The holder keeps the ticker. The claimant never holds it, not even after the holder's span ends, and shadows nothing.
   - Any other claim is **disputed**. The ticker resolves to nothing from the claimant's start until the earlier of the claimant's own span end and the *wait's end*: the earlier of the holder's span end (any next listing row of the holder's security, rule 1 included) and its leaving. From the wait's end the claimant holds the ticker as an ordinary span, unless another security's span of the ticker starts that same day (no rule-4 tie). With several holders the claim waits for the last of them. Examples: MG&E citing MGE Energy's `MGEE`, where nothing in the store shows which equity trades, and an early successor listing in the window before its predecessor goes quiet.
   - A holder whose common was delisted or that went quiet before the claimant's start loses the ticker to the newer span as before. So a holding-company successor (Xerox Holdings 2019, NorthWestern Energy Group 2023) takes it from its first listing, while a reorganization younger than the quiet bound, with no delisted listing, is disputed until its predecessor goes quiet.
   - With no evidence on the holder (no share count and no delisted listing), the newer span wins as under rules 1-4.
   - Known limits, both falling back to newer-wins or holder-keeps (#799). `listing_ends_as_of` cannot tell a secondary exchange's Form 25 from leaving, so such a holder counts as left. In a holding-company reorganization with no Form 25, where the predecessor keeps filing and cites the successor's share count, the predecessor would keep the ticker as a co-registrant. Neither occurs on the 2026-10-04 store, where all five co-registrant verdicts are a subsidiary or operating partnership.
   - Accepted, counted cost: a claim whose holder renamed but whose new ticker is missing from the master stays disputed while that holder files. On the 2026-10-04 store that is five new SPACs (ACAC, CLBR, GIG, GPAC, KCAC); #799 tracks the missing rows.
7. **A span ends at its own delisting (#819).** A span ends on the `effective_on` (else the day after `end_session`; never before the day after the Form 25's acceptance) of a listing of its security under its ticker that `listing_ends_as_of` calls `delisted`, with an equity class, when that listing is the span's last row. If the span still holds the ticker after rules 3 and 6, the ticker resolves to nothing from that day until another span starts: it never falls back to another company's span that the ended span had superseded, while a span that started after the ended one (a successor listed before the old common's Form 25 took effect) keeps it. A span that never held the ticker (later-class, co-registrant) shadows nothing by ending. A reused ticker therefore never prices a delisted security (Eagle Bulk carrying another equity's `EGLE` from 2025). A delisted listing followed by a row of the same ticker for the same security (a cover page filed years after an old Form 25, as for Citigroup's `C`; a relisting; a transfer outside the window; a reorganized security's new row, #820) does not end the span: the security went on trading under it, and its bars before that row stay assigned. Not done, for want of evidence that tells a 1:1 successor from a reuse: a predecessor keeping a successor CIK's bars until the successor's own listing (BG, FERG, NWE, ZYME, MTAL). Those sessions are unassigned. Known limit, as for rule 6: `listing_ends_as_of` cannot tell a secondary exchange's Form 25 from leaving, so when the secondary listing is the span's last row the span ends while the security still trades (none on the 2026-10-04 store). The run row counts the ended spans, the spans kept through a delisting by a later row of the ticker, and the dropped typo rows.

*Repair (#819).* `tradepartner repair-resolution [--dry-run]` deletes every Alpaca bar and action, all revisions, whose key the resolver built at the run does not assign (a bar's session, an action's session before its ex-date), in one write transaction, and records an `ingestion_runs` row (source `alpaca`, mode `repair`, status `repaired`, never `ok`). A real run takes the dry run's bar and action row counts (`--expect-bar-rows`, `--expect-action-rows`) and deletes nothing on any other count; both list every security found with its counts. Deleting is the remedy, not a revision row: such a row was never its security's fact, so no `known_at` makes it right, and a revision would leave it visible before the repair. As with the `statement_facts` rebuild, past as-of reads change; a trial logged before the repair is reproducible only from its own export. Bars the corrected rules newly assign come only from a backfill with a new `--since`.

*Look-ahead.* The resolver is a key mapping built from every listing known at the run, not at each session, so a backfill maps 2016 bars with listings filed later; rule 6 likewise reads the share counts and listing ends known at the run, and the run's day. The bars' own `known_at` is unchanged. Rules 2-4 and the shadowing act only from the triggering span's start; rule 7 only from the effective day, after the Form 25's acceptance, except that a later row of the ticker keeps sessions before its own `valid_from`. Three rules can change an earlier session's mapping: a contested span, a span made non-equity by a later row of the same ticker (rule 1, per span), and rule 6, whose verdict depends on filings after the claimant's start. The first two normally make the session *unassigned*. Under rule 6 a claimant gains sessions only from the holder's leaving day on, never before it. A holder's leaving after the claimant's start ends a co-registrant verdict, so its sessions from the claimant's start become disputed (unassigned). A span re-started at a claim's end can newly contest an older span (or tie with one, rule 4). A holder that goes quiet after a run hands the sessions after its last filing to the claimant at a later run. A holder's fresh filing after a quiet spell turns the claim back into a wait. In one edge, a span removed by the first two stops making a sibling class later-class (rule 3) or stops contesting an older span, and a rule-6 claim stops contesting one; that other span then resolves. Which names have prices at an early T can therefore depend on later filings. This is an accepted deviation, bounded and visible through the run-row counts.

**Amendment 2026-10-04 (#787): price-quality gate.** Before about 2019 a listing is `snapshot_static` (today's ticker back-dated), and a price source keyed by symbol can serve another equity's bars under it: a flat price on zero volume, then a one-day move of +1,216% (BTU) or +12,900% (SD) that 12-1 momentum would rank first. The gate acts at read time, so nothing is re-ingested.

*(1) A zero-volume bar is missing, not a price.* `prices_as_of` and `adjusted_prices_as_of` take `traded_only` (default `false`). With `true`, a bar whose latest revision known at T has volume 0 is left out; adjustment factors still use every stored bar, and a later revision with volume brings the bar back. `universe_as_of` reads with it, so such a bar is no close for rules 4 and 8, no dollar volume for rule 5, and a missing bar for rule 6. The backtest provider reads its frames with it (backtest spec req 1). The survivorship gap still reads every stored bar, unchanged: it measures whether the source served bars at all, and #801 weighs applying the gate there. Execution's own reads are also unchanged.

*(2) An unexplained jump is reviewed.* `price_jumps_as_of(T, ids=None, settings)` lists, per security, each traded bar known at T where:
- its raw close over the previous traded bar's close is above `universe.max_jump_ratio` (2.5) or below `universe.min_jump_ratio` (0.4); and
- the splits and dividends known at T, with an ex-date after the previous bar and on or before this one, do not bring `(close + dividends) × split ratios / previous close` back inside those bounds.

`accepted` is true when `universe.accepted_price_jumps` names the jump as `"<security_id>@<session>"`.

ADR 0006 rule 6 also fails a name with an unaccepted jump on a session in its `min_history_months` window, with reason `price_jump`. That is the issue's "for that span": once the jump leaves the window, or the owner accepts it, the name is judged on its bars again. `price_jump` is not a missing-data reason, so the gap's truncated-history category does not count it.

The gate removes names from selection only:
- **Held names stay marked through a jump.** Hiding a real crash from a held name would flatter results, so a held name is marked on its bars.
- **The signal's coverage depends on the window.** A signal whose lookback is longer than `universe.min_history_months` can read across a jump once the name is readmitted. 12-1 momentum, with 12 months for both, is covered; a longer lookback is not.
- **Exclusions are not counted per rebalance.** The universe's exclusions name them, and the owner empties the review list before registering.

`health` lists every jump known at T, accepted or not, as the owner's review list. It is not an integrity rule. `--jumps-before DATE` lists only jumps before a hypothesis's `holdout.start`.

*Frozen parameters.* The three keys sit in `universe.*`, so a hypothesis freezes them (backtest spec req 10). Three consequences follow:
- Every hypothesis registered before this change must be registered again.
- An acceptance made after registration does not reach that hypothesis. Accepting later means a new hypothesis.
- A jump is accepted on data validity alone: do the bars belong to this issuer's own trading? Never on backtest results or on what the name returned afterwards.

`traded_only=True` is code, not a parameter, so a trial carries it only through its code version.

*Point in time.* The list at T reads only rows known at T, so a split first known after T leaves its jump on the list at T. A later zero-volume revision of a bar that a held position was marked at is a retracted mark, and that backtest step fails (backtest req 2's valuation rule); it is never silently re-marked.

A `snapshot_static` span trusted only from its first continuous traded bar (the AA case) is #797.

**Amendment 2026-10-04 (#845): shares plausibility.** Filers sometimes tag `EntityCommonStockSharesOutstanding` at the wrong scale: ×1,000 or ×1,000,000 ([research #174](../research/2026-09-25-cover-page-facts-at-scale.md) F22). AJG, SKY, VCEL and CCRN then ranked among the largest companies at some rebalances. The check runs at read time, and nothing is re-ingested (owner decision (A) on #845).

*The check.* `universe.shares_as_of(T, ids, settings)` walks each security's shares facts known at T in `as_of_date` order. Each fact gets the value rule 7 would read for its date, and a date with two class rows is skipped.
- The first fact is accepted. A value of zero or less is never a share count: it is always rejected, is never a baseline and cannot be accepted.
- Each later fact is compared with the **last accepted** fact, moved by every split known at T with an ex-date after that fact's `as_of_date` and on or before this one's.
- A fact is out of line when that ratio is above `universe.max_shares_ratio` (100) or below its inverse. An out-of-line fact is rejected unless `universe.accepted_shares_facts` names it as `"<security_id>@<as_of_date>"`. An accepted fact becomes the new baseline.

Comparing with the last *accepted* fact, not the previous one, also rejects a second bad quarter in a row (AJG 2020-03 and 2020-06).

*Use.* Rules 7 and 8 use the last accepted fact. Its age is judged by `universe.max_shares_age_days`, so a run of rejections ends in `stale_shares`, which is missing data that the gap counts. `Universe.shares_fallbacks` lists, per rebalance, each class whose latest fact was rejected and the fact used instead. The survivorship gap's size share reads the same selection.

*Review.* `health` lists every out-of-line fact known at T, accepted or not, as the owner's review list (`shares_outliers`). `--jumps-before DATE` keeps only facts dated before DATE. As with the jump list, the keys sit in `universe.*`:
- A hypothesis freezes them, so every hypothesis registered before this change must be registered again.
- A fact is accepted on data validity alone, never on results.

*Point in time.* Only facts and splits known at T are read. A correcting filing known after T never changes the pick at T, and a split first known after T leaves a split-explained move rejected until it is known.

*Accepted risk.* A genuine move of more than 100× in reported shares is rejected until the owner accepts it, for at most `max_shares_age_days`. Such moves are rare: a large reverse split is explained by its split action, and only a de-SPAC or a huge issuance would trigger it. A switch between an undimensioned total and a class row on consecutive dates is compared as is.

*When the first fact is the bad one* (possibly WMG), there is nothing earlier to compare with. The first fact becomes the baseline, and the correct later facts show on the review list as out of line. The owner then accepts the **first correct fact** in `universe.accepted_shares_facts`. Each later fact is compared with it, so one entry repairs the series.

## Risks & domain checks

- **Look-ahead:** adapters stamp `known_at`; the as-of API filters; truncation invariance with probes around every `known_at` proves agreement; the broken adapter proves each check has teeth; revisions are never back-dated.
- **Survivorship:** securities exist from their first filing, so delisted names are in the denominator; the gap is bounded and shown; it gates the holdout in Phase 3.
- **Adjusted-price rewrites:** raw storage plus read-time adjustment; revised actions get `ingested_at`.
- **Level-rule timing:** raw close at T and ex-date ≤ T, so a known-but-future split cannot distort cap or the price floor.
- **Ticker reuse and class confusion:** master keyed by `security_id`; delistings matched by class title and exchange; price rows mapped to securities by the #735 resolver rules (equity classes only, same-day pairs and same-start ties unassigned, a later class of one company never takes a ticker its sibling holds) and the #793 registrant check (a co-registrant or unproven claim never takes a live holder's ticker), every unassigned row counted on the run row.
- **Secrets:** pydantic settings; scrub test; fixtures pattern-checked.
- **Terms and opens:** the owner's T3 research resolves Alpaca terms, auction vs IEX open, fractional-at-open behavior, actions depth, history depth, assets-endpoint reuse, EDGAR rate limit and User-Agent, backfill runtime; it sets `liquidity_rule_enabled`, `execution.fill_price`, `max_missing_share`.
- **Single writer:** chunked commits release the lock; readers are short-lived; page has a busy state.
- **Statement facts (#660):** the look-ahead a fundamentals signal usually carries is a *restated* number standing in for the as-filed one; the first-vintage UNIQUE makes that impossible at the schema, and the hold and late counts make the one order-of-arrival hole visible instead of silent. The data-quality risk is heterogeneity: a tag list that is too short loses coverage (counted on `statement_none`), one that is too long mixes concepts, so the lists are config and every row names its `xbrl_tag`. Volume: about 10^7 records across the universe, so the ingest streams and bulk-inserts per CIK; T78 records the run time. Rollout: the switch is off until T78, so no merged task changes the backfill.
- **Costs:** none. **Order path:** fake broker only. **LLM inputs:** none.
