# 0015. Expansion seams: what to open before Phase 4, what to defer

**Status:** Accepted (2026-10-08, by the owner's merge of PR #1253; header set by #1258)  ·  **Date:** 2026-10-08  ·  **Issue:** #1252  ·  **Supersedes:** [ADR 0010](0010-phase-4-risk-rules.md) point 3, the id format only (the book token, seam 1)  ·  **Amends:** ADR 0010 point 1 with two structural refusals (`refused_position_side`, `refused_order_shape`; on breach the batch halts with `LimitBreachError`, as every structural rule there does), under its point 5  ·  **Related:** [charter](../charter.md) (Scope), [roadmap](../roadmap.md), [ADR 0003](0003-data-adapters-local-first.md) (adapters, point-in-time rules), [ADR 0005](0005-objective-benchmark-stop-criteria.md), [ADR 0006](0006-universe-and-cadence.md), [ADR 0009](0009-price-vendor.md), [ADR 0012](0012-cadence-as-a-hypothesis-parameter.md), [ADR 0014](0014-strategies-as-registered-objects.md) (the strategy seam), [paper-trading plan](../plans/paper-trading.md) (T48b, T48c, T71)

## Context

In plain words: the system was built narrow on purpose. The charter's Scope line says long-only US equities, daily or slower, no leverage, no options. The code says the same in about forty places: two order sides, a `securities` table where every row is an issuer's share, prices keyed by session date, a paper journal that runs at most once per session, one open paper window that owns the whole account. ADR 0014 fixed the one-strategy side of this (a strategy is now a registry entry). The rest is still narrow.

The owner's long-term goal, stated 2026-10-08, is wider: swing trading and day trading, and possibly options, futures and long/short spreads. He has not asked for any of those now. He asked, before Phase 4's paper path writes real journal rows and before Alpaca's order history exists for this account, which of the narrow assumptions will be expensive to undo later, so they can be undone cheaply now, and which can wait.

Two reports answer that, both in the owner's local research library (`tradepartner-probes/research-library/expansion/`, not in this repo because the repo is public):

- **The code audit** (2026-10-07, three full sweeps finished 2026-10-08). It maps every long-only, shares-only, daily-only and one-book assumption to a `file:line`, prices each at S/M/L, and ranks them by how much more they cost after Phase 4 than before. Its headline: three items (the book identity, the position side, the order shape) are a column or a field now and a migration with backfills later, because they live in journal tables that will hold real rows (`orders`, `lots`, `positions_daily`, `paper_windows`) or in a string that becomes Alpaca-side history (`client_order_id`). Three more (the explicit cadence, the frozen-key rule, the instrument-id rule) cost about the same whenever they are done and are taken now because each is nearly free and fixes a latent defect or a meaning that later tables would otherwise inherit. Everything else is pure logic, or needs data and a strategy that do not exist, and waits.
- **The prior-art report** (2026-10-07; LEAN, NautilusTrader, Zipline, vectorbt, backtrader, evidence-graded). The two event-driven multi-asset engines share one small set of abstractions: an instrument object with type, multiplier, tick and lot size, expiry and underlying; a signed position per instrument; an account and buying-power model separate from the position; orders with legs; one clock that releases every bar at its close. The report also records what every engine documents against itself: backtest-live parity is weaker than the slogan, shorting defaults are optimistic, no engine rolls a futures position for you, and no Tier 1 source addresses survivorship in options and futures data at all.

Three forces shape the decision:

1. **Phase 4 is the deadline.** T48b (the owner's recording of paper responses) and T48c (the Alpaca broker adapter) are unwritten. Until T71 runs `paper start`, the journal tables hold fixture rows only, so a column is a `CREATE TABLE` edit and a re-pinned test. After, it is a schema version with a table rebuild, and the `client_order_id` format of orders already at the broker is history.
2. **The owner's "validate before building" rule.** He has flagged overbuilding before: the one-strategy engine that pigeonholed us was itself built to a plan. A multi-asset redesign now, for strategies that do not exist and data (intraday bars, options chains) the store does not hold, would be the same mistake in the other direction. The same rule cuts the "now" list: a column or a key is opened only where a later change would be a migration, not where the frozen-key table already makes a late key free.
3. **The integrity rules do not bend.** H1's registration, fingerprint and trials are frozen (strategy-lab spec, "Frozen-key defaults": a new frozen key enters `FROZEN_KEY_DEFAULTS` at the default that reproduces the old behaviour, and no stored fingerprint moves). ADR 0010's "no shorts, ever" holds by construction in the wrapper. Both stay true after this record.

## Options considered

1. **Do nothing now; open each seam when its capability is built.** Pro: zero work before Phase 4, no risk of building for a future that never comes, every change arrives with the strategy that needs it and a test that uses it. Con: the three journal items become rebuild migrations on tables holding six months of real paper rows, with the paper window open (each a `safety-reviewer` task that rebuilds a journal table in one transaction, as versions 5 to 8 did); the `client_order_id` format is fixed for every order already at Alpaca; and T48c's response mapping, once recorded against (T48b) and tested, is edited a second time when the shape grows. The audit prices the difference at roughly M now against L later for the book identity and S-M now against M-L later for sides and legs. (The audit's top-ranked seam, the journal clock, is priced the same way; it is deferred below, with the reason.)
2. **Open the seams now: cheap, behaviour-preserving schema and interface changes, no new trading capability** (this record). Pro: every change is a column with a default, a read-side field with a default, an explicit argument where a default argument was, or a written rule; today's backtest results are byte-identical and every pin test says so; no new code path can place a short, a limit order or an option, because the request type does not change and the wrapper refuses, by name, what it refuses today. Con: columns nothing writes and fields nothing reads are a small permanent tax on readers of the schema and the broker protocol; a reserved shape can still be wrong when the real capability arrives (the prior art disagrees on, for instance, legs-as-order versus spread-as-instrument), so some of what is reserved may be superseded; the work displaces about a week of Phase 4 build time.
3. **Full multi-asset redesign now: an `instruments` model, signed positions, a margin account model, a bars table with a bar-interval clock, legs, a new backtest valuation.** Pro: the prior art's shape, done once, with no reserved-but-empty columns. Con: this is the overbuilding the owner warned against, in the largest possible form: the backtester's representation (unsigned dollar positions marked close to close on a date grid: `backtest/valuation.py`, `fills.py`, `engine._step`) would be rewritten for shorts, futures and intraday at once, with no strategy, no data and no holdout to test any of it against; it delays Phase 4 by months; it would touch H1's engine path during the six-month paper window; and the prior art's own caveats (optimistic shorting, unknown intrabar paths, no survivorship story for derivatives data) say the honest version of each capability needs its own research and its own ADR, not a shared rewrite.

## Decision

We will take option 2, in two separate decisions.

### A. Charter direction (a note, not a scope change)

The project's long-term goal now includes swing trading and day trading of US equities, and possibly options, futures and long/short spreads. **The charter's Scope line does not change here.** It changes only through a later ADR, one per capability, at the moment that capability is actually built and its data, risk rules, costs and tax treatment are specified; until then the system stays long-only, daily or slower, unleveraged, with no options, and ADR 0010's rules stand as written. This record is cited from the charter as the direction note so that a reader of the Scope line knows the narrowness is a current state and not the goal. Nothing in part B gives the system a new trading capability.

### B. Seams to open now

Every seam below follows the same rules: the change is additive (a nullable or defaulted column, a defaulted read-side field, an explicit argument, a written rule); nothing in `src/` writes a non-default value; `OrderRequest` does not change, so no new order kind can be sent; the risk wrapper's refusals grow, never shrink; and **the invariant** is that `H1_FINGERPRINT` and `TWIN_FINGERPRINT` (`tests/backtest/test_frozen_defaults.py`) and the Phase 3 reference metrics (`tests/backtest/test_metrics.py`) are unchanged, asserted by the tests each task names. The paper journal has no real rows yet, so its invariant is weaker and stated per seam: fixture pins are re-pinned in the same PR, and T48b's recordings are unaffected (ids are opaque to the adapter, and the fields below are ones Alpaca already returns).

1. **Book identity, including the `client_order_id` token.** *What:* a `book_id VARCHAR NOT NULL` on `paper_windows`, `decisions`, `orders`, `positions_daily`, `lots`, `disposals`, `adjustments` and `reconciliations`, frozen on the window with its other frozen values, written through from the window to every row the run creates; the id format (`execution/ids.py`, ADR 0010 point 3, which this record supersedes on that one point) becomes `{prefix}-{book}-{session}-{security_id}-{side}-{attempt}`, the book token matching `^[A-Za-z0-9]+$` (no `-`, because `security_id` contains one, `master.py:737`, and the prefix pattern `^\S+$` allows one, `config.py:1302`; so prefix and book parse from the left), and the whole id checked against `alpaca.client_order_id_max_length` once T48b sets it. **The rules do not relax:** `open_window` still fails closed on more than one open window per journal (`store/journal.py:924`), `paper start` still requires a flat account (`execution/window.py`), and reconciliation still compares the whole account to the one book. A second book is, for now, a second Alpaca paper account with its own store and key pair (a second checkout); sharing one store or one account is the multi-book ADR below. *Why now:* the id becomes Alpaca-side history on the first submit; ids without a token belong to the only book that will have existed, so the token is cheap insurance for attributing an order found at the broker to a book from the id alone (the reconciliation's "unknown order" case) once a second book shares the account, not a one-way door for H1's orders. *Prior art:* Nautilus NETTING keys a position on (instrument, strategy); vectorbt groups columns that share cash (`group_by`, `cash_sharing`); both make the book a first-class key rather than something inferred. *Invariant:* no journal rows exist; the id derivation's pins are re-pinned once in the same PR; nothing in the backtester reads it. If T48b records before this lands, its recorded ids stay as recorded (the adapter tests treat them as opaque strings). *(Amended 2026-10-09, [ADR 0017](0017-fast-paper-and-machine-readiness-gate.md) part B: a second book is a second Alpaca paper account with its own key pair in the same store and journal, not a second checkout; `open_window` fails closed per book, `paper start` requires the book's account flat, and reconciliation compares the book's account to the book. One account is one book, so the rules keep their meaning.)*
2. **Position side on lots, disposals and positions, and intent on orders.** *What:* `position_side VARCHAR NOT NULL DEFAULT 'long'` (CHECK in `long`, `short`) on `lots`, `disposals`, `positions_daily`, `decisions` and `orders`; `SIDES` (`store/schema.py:1098`) stays `buy`/`sell`, so an order's intent is the pair (`side`, `position_side`): buy-long opens, sell-long closes, sell-short opens, buy-short closes, the four intents Alpaca's `position_intent` spells `buy_to_open` and so on. `orders.phase` stays `sell`, `buy`, `exit`; a cover phase and its ordering are the shorting ADR's. Quantities stay unsigned (the "side on the order" design, which the audit found already short-tolerant in `fills`, `FakeBroker` and `Broker.Position`). The wrapper and `risk.py` refuse any `short` row by name (`refused_position_side`, structural, the batch halts), so ADR 0010's "no shorts, ever" is now a pinned refusal as well as a structural fact. The id's side token and `next_attempt`'s key (`security_id`, `side`) do not change here; the shorting ADR extends both before any short order exists. *Why now:* every row written before the shorting ADR is long by construction, so the value is never in doubt; the cost is that the CHECK constraints are generated from enums and DuckDB cannot alter one in place, so adding the column is a CREATE edit now and a rebuild of five tables with real rows later (`lots` and `disposals` outlive every window). *Prior art:* every engine in the report carries a signed position (Nautilus `signed_qty` with an explicit NETTING-versus-HEDGING choice, Zipline `Position.amount`, backtrader); we keep the sign as a column next to an unsigned quantity because the journal's quantities are unsigned by design. *Invariant:* every row the paper path writes today reads `long`, which the fixture tests pin; the backtester's `_Book` is untouched.
3. **Order and broker shape, before T48c: read side only.** *What:* `OrderRequest` (`adapters/broker.py`) is unchanged, so the adapter has no path that sends anything but today's market day order. `Order` gains `order_type`, `time_in_force`, `limit_price`, `stop_price`, `asset_class`, `order_class` and `legs` (Alpaca's `type`, `time_in_force`, `limit_price`, `stop_price`, `asset_class`, `order_class`, `legs`); the `orders` DDL gains `order_type` (default `market`), `time_in_force` (`day`), `limit_price` and `stop_price` (`NULL`), `asset_class` (`us_equity`), `order_class` (`simple`), `multiplier` (`1`, derived: Alpaca has no such field for equities) and `parent_order_id` (`NULL`, reserved); `Fill` gains `fee: float | None` (derived from Alpaca's account activities, not a field of the fill; `None` until an adapter fetches it); `Account` gains `short_market_value`, `maintenance_margin` and `daytrade_count` (Alpaca's names; `None` on the fake); `Asset` gains `shortable`, `easy_to_borrow` and `marginable` (Alpaca's names). `FakeBroker` carries them through at the defaults. The wrapper refuses, by name, any `Order` the broker returns or any journal row that is not a market, day, `us_equity`, `simple`, multiplier-1 order (`refused_order_shape`, structural, the batch halts), so an order of another kind on the account, however it got there, halts rather than reconciles. *Why now:* T48c maps the response once, against T48b's recordings, which already carry these fields; a read-side field added after T48c is a second adapter edit under `safety-reviewer` and a rebuild of `orders` with real rows in it. *Prior art:* LEAN `SymbolProperties.ContractMultiplier` and per-asset-class fee models; Nautilus instruments with `multiplier` and `margin_init`; LEAN `PatternDayTradingMarginModel`; LEAN combo orders (a parent with `Leg`s) is the shape `parent_order_id` reserves, and if the spread-as-instrument shape (Nautilus) wins later, the column stays `NULL` and costs nothing. *Invariant:* every request the wrapper builds today is unchanged field for field; every response a recorded test compares against maps to the same values plus the new fields at the values Alpaca recorded.
4. **Cadence passed explicitly through the paper path.** *What:* `execution/planning.py`, `plan.py`, `marks.py`, `run.py`, `outcomes.py`, `check.py`, `report.py` and `window.py` take the cadence from the window's frozen `schedule.rebalance_cadence` instead of a default argument or a bare `last_session_of_month` call (the audit lists the lines); `backtest/holdout.first_tracking_session` takes the cadence too (today month-end only, a latent bug at `week_end` and `daily`). The gate stays: `paper start` refuses anything but `month_end` (`_PAPER_CADENCE`, `window.py:273`, ADR 0012, strategy-lab spec req 11). *Why now:* it costs the same whenever it is done, and is taken now because it fixes the latent bug, because the default arguments multiply with every call site Phase 4 adds, and because swing cadences (`week_end`, `daily`) are the first expansion the owner named and ADR 0012 already makes them registrable in the backtest, so the only thing that stops a paper run at them is a hard-coded month end in ten functions. *Prior art:* Zipline `schedule_function(date_rules, time_rules)` and LEAN `DateRules`/`TimeRules` make the schedule an explicit object handed to the run, never a default inside it. *Invariant:* H1's window reads `month_end` through `frozen_values`, every call site passes it, and the pinned paper outputs on the fixture store are identical.
5. **The frozen-key rule for expansion keys, and the fingerprint answer.** *What:* no key is added now. The rule, decided here so that no later ADR has to argue it: when the shorting, intraday or derivatives ADR opens a capability, its keys enter `FROZEN_KEY_DEFAULTS` (`backtest/frozen.py:36`) at today's values (`portfolio.side = "long_only"` and `portfolio.gross_exposure = 1.0` in a new frozen section `portfolio`, the construction keys staying in each family's own section per ADR 0014; `schedule.bar_interval = "1d"`; `universe.asset_class = "us_equity"`, beside the existing `universe.security_types`, which selects within the class). **The fingerprint question, answered by the spec's own rule:** a key at its table default is left out of the canonical set and the fingerprint (`frozen.canonical_frozen_set`), so H1 and every pre-lab registration keep their hash whenever such a key lands; set to a non-default value, the key is in the fingerprint, so a long/short or intraday variant of a hypothesis is a different hypothesis identity, counted in the family's N, which is what charter principle 2 requires. `Cadence` (`config.py:718`) and `PERIODS_PER_YEAR` (`backtest/schedule.py:40`) are widened by the intraday ADR. *Why now (and why no key now):* the table is append-only and immutable and overlays a default for every registration that lacks a key, so a late key is free; adding four keys that no validator could accept at any other value would be a reservation for runs no code can produce, which the owner's rule forbids. The one code change is a bug: `engine.py:456,466` (`if value > 0`) silently drops a negative position value; a negative value raises, a zero value is still dropped, both pinned. *Prior art:* LEAN's per-security leverage and `Resolution`, Zipline's `data_frequency` and `set_long_only`, as explicit run parameters. *Invariant:* `H1_FINGERPRINT`, `TWIN_FINGERPRINT` and the reference metrics are asserted unchanged; `trial_*` rows are untouched.
6. **A reserved instrument id and type.** *What:* no new table and no DDL change to `securities`. Two rules, written into the data-foundation spec and `store/master.py`'s docstring: (a) every `security_id` column in the journal and the backtest is, from now on, read as an *instrument id*, and for a share the instrument id equals the security id, so today's rows need no change; (b) a future `instruments` table (type, multiplier, expiry, strike, right, `underlying_security_id`) issues ids in the same namespace with a type prefix, as `BENCH:` already does for benchmarks (`master.py:813`, the in-house precedent), and `securities` stays the equity master; the master's own id derivation (`primary_security_id` and the `{base}-{n}` class ids) can never produce a prefixed id, which a test pins. The `asset_class` column from seam 3 is the only type marker stored today. *Why now:* nearly free, and the audit's fourth-ranked seam is L either way, but its foreign keys spread with every journal table; fixing the id's meaning now means no re-keying later, while an `instruments` table built today, with nothing to put in it, would be exactly the overbuilding option 3 describes. *Prior art:* LEAN's `Symbol` with a `SecurityType` and `Underlying`; Nautilus's 21 instrument types behind one instrument interface. *Invariant:* no bytes change.

## Consequences

- Good: the three changes that would cost a rebuild migration during the paper window cost a column or a read-side field now; the `client_order_id` carries a book from the first order Alpaca ever sees; the request type is unchanged and the wrapper's refusals are pinned by name, so the new columns and fields cannot be used by accident; the latent cadence bug and the silent negative-value drop are fixed; the owner's direction is on record without moving the Scope line; every deferred capability has a named trigger, so none is built speculatively, and the frozen-key rule means a late key is free.
- Bad / accepted risks: reserved columns and fields that nothing writes are a small tax on every reader of the schema and the broker protocol until they are used, and a reserved shape may be superseded (legs as an order versus the spread as an instrument), in which case one nullable column stays null; about a week of agent time moves ahead of Phase 4's remaining build (T48c, T67, T71), though no task on the critical path waits on this record except through `broker.py` (TE3a before T48c); one journal schema version lands before `paper start` (TE0, `safety-reviewer`); ADR 0010 is superseded on one point and amended on another, which its point 5 requires and which TE1 notes on ADR 0010 itself.
- Reversibility: cheap for every seam. Columns with defaults and nullable fields can stay unused forever; the explicit cadence argument is a signature; the rules of seams 5 and 6 are text and one guard each. The id format is history for any order already submitted, but ids without a token map to the only book that existed, so landing the token after T71 would cost attribution convenience, not correctness; it lands before T71 because that is when it is free.
- Revisit if: the owner registers the first long/short, intraday or derivatives hypothesis (that capability's ADR, which may supersede the shape reserved here); T48b's recorded `client_order_id` length limit cannot fit the book token (shorten the token, never the attempt or security id); a reviewer finds a reserved column or field being written with a non-default value anywhere in `src/` before its ADR (that is a defect); Phase 4's retro finds the reserved shape cost more reading time than it saved; or the owner decides that part A's direction has changed.
