# 0015. Expansion seams: what to open before Phase 4, what to defer

**Status:** Proposed  ·  **Date:** 2026-10-08  ·  **Issue:** #1252  ·  **Related:** [charter](../charter.md) (Scope), [roadmap](../roadmap.md), [ADR 0003](0003-data-adapters-local-first.md) (adapters, point-in-time rules), [ADR 0005](0005-objective-benchmark-stop-criteria.md), [ADR 0006](0006-universe-and-cadence.md), [ADR 0009](0009-price-vendor.md), [ADR 0010](0010-phase-4-risk-rules.md) (long-only risk rules), [ADR 0012](0012-cadence-as-a-hypothesis-parameter.md), [ADR 0014](0014-strategies-as-registered-objects.md) (the strategy seam), [paper-trading plan](../plans/paper-trading.md) (T48b, T48c, T71)

## Context

In plain words: the system was built narrow on purpose. The charter's Scope line says long-only US equities, daily or slower, no leverage, no options. The code says the same in about forty places: two order sides, a `securities` table where every row is an issuer's share, prices keyed by session date, a paper journal that runs at most once per session, one open paper window that owns the whole account. ADR 0014 fixed the one-strategy side of this (a strategy is now a registry entry). The rest is still narrow.

The owner's long-term goal, stated 2026-10-08, is wider: swing trading and day trading, and possibly options, futures and long/short spreads. He has not asked for any of those now. He asked, before Phase 4's paper path writes real journal rows and before Alpaca's order history exists for this account, which of the narrow assumptions will be expensive to undo later, so they can be undone cheaply now, and which can wait.

Two reports answer that, both in the owner's local research library (`tradepartner-probes/research-library/expansion/`, not in this repo because the repo is public):

- **The code audit** (2026-10-07, three full sweeps finished 2026-10-08). It maps every long-only, shares-only, daily-only and one-book assumption to a `file:line`, prices each at S/M/L, and ranks them by how much more they cost after Phase 4 than before. Its headline: six items are cheap now and a migration with backfills later, because they live in journal tables that will hold real rows (`orders`, `lots`, `positions_daily`, `paper_windows`) or in a string that becomes Alpaca-side history (`client_order_id`). Everything else is pure logic that costs about the same whenever it is done.
- **The prior-art report** (2026-10-07; LEAN, NautilusTrader, Zipline, vectorbt, backtrader, evidence-graded). The two event-driven multi-asset engines share one small set of abstractions: an instrument object with type, multiplier, tick and lot size, expiry and underlying; a signed position per instrument; an account and buying-power model separate from the position; orders with legs; one clock that releases every bar at its close. The report also records what every engine documents against itself: backtest-live parity is weaker than the slogan, shorting defaults are optimistic, no engine rolls a futures position for you, and no Tier 1 source addresses survivorship in options and futures data at all.

Three forces shape the decision:

1. **Phase 4 is the deadline.** T48b (the owner's recording of paper responses) and T48c (the Alpaca broker adapter) are unwritten. Until T71 runs `paper start`, the journal tables hold fixture rows only, so a column is a `CREATE TABLE` edit and a re-pinned test. After, it is a schema version with a backfill across about twelve tables, and the `client_order_id` format can never change for orders already at the broker.
2. **The owner's "validate before building" rule.** He has flagged overbuilding before: the one-strategy engine that pigeonholed us was itself built to a plan. A multi-asset redesign now, for strategies that do not exist and data (intraday bars, options chains) the store does not hold, would be the same mistake in the other direction.
3. **The integrity rules do not bend.** H1's registration, fingerprint and trials are frozen (strategy-lab spec, "Frozen-key defaults": a new frozen key enters `FROZEN_KEY_DEFAULTS` at the default that reproduces the old behaviour, and no stored fingerprint moves). ADR 0010's "no shorts, ever" holds by construction in the wrapper. Both stay true after this record.

## Options considered

1. **Do nothing now; open each seam when its capability is built.** Pro: zero work before Phase 4, no risk of building for a future that never comes, every change arrives with the strategy that needs it and a test that uses it. Con: the audit's six "now" items become backfill migrations on tables holding six months of real paper rows, with the paper window open (each a `safety-reviewer` task that rebuilds a journal table in one transaction, as versions 5 to 8 did); the `client_order_id` format is fixed the day the first paper order reaches Alpaca, so a book token can never be added to that history; and T48c's `OrderRequest`, once recorded against (T48b) and tested, is re-recorded when its shape changes. The audit prices the difference at roughly M now against L later for the journal clock and the book identity, S now against M-L later for sides and legs.
2. **Open the seams now: cheap, behaviour-preserving schema and interface changes, no new trading capability** (this record). Pro: every change is a column with a default, a field with a default, a frozen key at its today-preserving default, or an explicit argument where a default argument was; today's backtest results are byte-identical and every pin test says so; no new code path can place a short, a limit order or an option, because the wrapper refuses what it refuses today by name. Con: columns nothing writes and fields nothing reads are a small permanent tax on readers of the schema and the broker protocol; a reserved shape can still be wrong when the real capability arrives (the prior art disagrees on, for instance, legs-as-order versus spread-as-instrument), so some of what is reserved may be superseded; the work displaces about a week of Phase 4 build time.
3. **Full multi-asset redesign now: an `instruments` model, signed positions, a margin account model, a bars table with a bar-interval clock, legs, a new backtest valuation.** Pro: the prior art's shape, done once, with no reserved-but-empty columns. Con: this is the overbuilding the owner warned against, in the largest possible form: the backtester's representation (unsigned dollar positions marked close to close on a date grid: `backtest/valuation.py`, `fills.py`, `engine._step`) would be rewritten for shorts, futures and intraday at once, with no strategy, no data and no holdout to test any of it against; it delays Phase 4 by months; it would touch H1's engine path during the six-month paper window; and the prior art's own caveats (optimistic shorting, unknown intrabar paths, no survivorship story for derivatives data) say the honest version of each capability needs its own research and its own ADR, not a shared rewrite.

## Decision

We will take option 2, in two separate decisions.

### A. Charter direction (a note, not a scope change)

The project's long-term goal now includes swing trading and day trading of US equities, and possibly options, futures and long/short spreads. **The charter's Scope line does not change here.** It changes only through a later ADR, one per capability, at the moment that capability is actually built and its data, risk rules, costs and tax treatment are specified; until then the system stays long-only, daily or slower, unleveraged, with no options, and ADR 0010's rules stand as written. This record is cited from the charter as the direction note so that a reader of the Scope line knows the narrowness is a current state and not the goal. Nothing in part B gives the system a new trading capability.

### B. Seams to open now

Every seam below follows the same rules: the change is additive (a nullable or defaulted column, a defaulted field, an appended frozen key, an explicit argument); nothing in `src/` writes a non-default value; the risk wrapper's refusals grow, never shrink; and **the invariant** is that `H1_FINGERPRINT` and `TWIN_FINGERPRINT` (`tests/backtest/test_frozen_defaults.py`) and every pinned trial metric are unchanged, asserted by the tests each task names. The paper journal has no real rows yet, so its invariant is weaker and stated per seam: fixture pins are re-pinned in the same PR, and T48b's recordings are unaffected (ids and fields are opaque to the broker).

1. **Book identity, including the `client_order_id` token.** *What:* a `book_id VARCHAR NOT NULL` on `paper_windows`, `decisions`, `orders`, `positions_daily`, `lots`, `disposals`, `adjustments` and `reconciliations`, frozen on the window with its other frozen values, written through from the window to every row the run creates; the id format (`execution/ids.py`, ADR 0010 point 3) becomes `{prefix}-{book}-{session}-{security_id}-{side}-{attempt}`, the book token validated like the prefix (non-empty, no whitespace) and the whole id checked against `alpaca.client_order_id_max_length` once T48b sets it. **The rules do not relax:** `open_window` still fails closed on more than one open window (`store/journal.py:924`), `paper start` still requires a flat account (`execution/window.py`), and reconciliation still compares the whole account to the one book. A second book is a second Alpaca paper account for now (Alpaca allows several), which is zero code; sharing an account is the multi-book ADR below. *Why now:* the id becomes Alpaca-side history on the first submit and can never be backfilled; without a token, an order found at the broker that the journal does not know (the reconciliation's "unknown order" case) cannot be attributed to a book from the id alone, and the single-window rule can never be relaxed on that account. *Prior art:* Nautilus keys a position on (instrument, strategy) in its NETTING mode and LEAN's Algorithm Framework carries the source of an insight through to the order; both make the book a first-class key rather than something inferred. *Invariant:* no journal rows exist; the id derivation's pins are re-pinned once in the same PR; nothing in the backtester reads it.
2. **Position side on lots, disposals and positions, and intent on orders.** *What:* `position_side VARCHAR NOT NULL DEFAULT 'long'` (CHECK in `long`, `short`) on `lots`, `disposals`, `positions_daily`, `decisions` and `orders`; `SIDES` (`store/schema.py:1098`) stays `buy`/`sell`, so an order's intent is the pair (`side`, `position_side`): buy-long opens, sell-long closes, sell-short opens, buy-short closes, the four Alpaca and options brokers spell `buy_to_open` and so on. Quantities stay unsigned (the "side on the order" design, which the audit found already short-tolerant in `fills`, `FakeBroker` and `Broker.Position`). The wrapper and `risk.py` refuse any `short` row by name (`refused_position_side`), so ADR 0010's "no shorts, ever" is now a pinned refusal as well as a structural fact. The id's side token and `next_attempt`'s key (`security_id`, `side`) do not change here; the shorting ADR extends both before any short order exists. *Why now:* a lot row written without a side cannot be fixed later (the tax ledger is per account and outlives every window), and the CHECK constraints are generated from enums, so widening is a CREATE edit now and a table rebuild later. *Prior art:* every engine in the report carries a signed position (Nautilus `signed_qty` with an explicit NETTING-versus-HEDGING choice, Zipline `Position.amount`, backtrader); we keep the sign as a column next to an unsigned quantity because the journal's quantities are unsigned by design. *Invariant:* every row the paper path writes today reads `long`, which the fixture tests pin; the backtester's `_Book` is untouched.
3. **Order and broker shape, before T48c.** *What:* `OrderRequest` and `Order` (`adapters/broker.py`) gain `order_type` (`market`), `time_in_force` (`day`), `limit_price` and `stop_price` (`None`), `asset_class` (`us_equity`), `multiplier` (`1`), `parent_order_id` and `leg_index` (`None`); the `orders` DDL gains the same columns with the same defaults; `Fill` gains `fee` (`0.0`); `Account` gains `margin_used`, `short_market_value` and `daytrade_count` (`None`, for the PDT rule); `Asset` gains `shortable`, `easy_to_borrow` and `multiplier`. `FakeBroker` carries them through. The wrapper refuses, by name, any request that is not a market, day, `us_equity`, multiplier-1, single-leg order (`refused_order_shape`), so no new order kind can reach a broker. *Why now:* T48c maps the request and the response once, against T48b's recordings; a field added after T48c is a re-recording, a second adapter edit under `safety-reviewer`, and a rebuild of `orders` and `order_events` with real rows in them. Alpaca already returns every one of these fields, so the recordings need no change. *Prior art:* LEAN `SymbolProperties.ContractMultiplier` and per-asset-class fee models; Nautilus instruments with `multiplier` and `margin_init`; LEAN `PatternDayTradingMarginModel`; combo orders as a parent with `Leg`s (LEAN) is the shape reserved by `parent_order_id`/`leg_index`, and if the spread-as-instrument shape (Nautilus) wins later, the two columns stay `NULL` and cost nothing. *Invariant:* every request the wrapper builds today has the default values; the request a recorded test compares against is unchanged field for field.
4. **Cadence passed explicitly through the paper path.** *What:* `execution/planning.py`, `plan.py`, `marks.py`, `run.py`, `outcomes.py`, `check.py`, `report.py` and `window.py` take the cadence from the window's frozen `schedule.rebalance_cadence` instead of a default argument or a bare `last_session_of_month` call (the audit lists the lines); `backtest/holdout.first_tracking_session` takes the cadence too (today month-end only, a latent bug at `week_end` and `daily`). The gate stays: `paper start` refuses anything but `month_end` (`_PAPER_CADENCE`, ADR 0012, strategy-lab spec req 11). *Why now:* the default arguments multiply with every call site Phase 4 adds, and the `through_session` and `rebalance_session` semantics in the journal are read by the report and the tracking comparison; swing cadences (`week_end`, `daily`) are the first expansion the owner named, and ADR 0012 already makes them registrable in the backtest, so the only thing that stops a paper run at them is a hard-coded month end in ten functions. *Prior art:* Zipline `schedule_function(date_rules, time_rules)` and LEAN `DateRules`/`TimeRules` make the schedule an explicit object handed to the run, never a default inside it. *Invariant:* H1's window reads `month_end` through `frozen_values`, every call site passes it, and the pinned paper outputs on the fixture store are identical.
5. **Frozen keys for side and exposure, bar interval and instrument class, at today's values.** *What:* four appended `FROZEN_KEY_DEFAULTS` entries (`backtest/frozen.py:36`): `portfolio.side = "long_only"` and `portfolio.gross_exposure = 1.0` (a new frozen section `portfolio`; the construction keys `top_fraction` and `weighting` stay in each family's own section per ADR 0014), `schedule.bar_interval = "1d"` and `universe.asset_class = "us_equity"`. Each key's validator accepts only today's value until the ADR that opens it (ADR 0014's "no signed weights in the type until an ADR allows them" is unchanged). `Cadence` (`config.py:718`) and `PERIODS_PER_YEAR` (`backtest/schedule.py:40`) are not widened here; an intraday cadence is the intraday ADR's. And `engine.py:456,466` (`if value > 0`, which silently drops a negative position value) raises instead. **The fingerprint question, answered by the spec's own rule:** a key at its table default is left out of the canonical set and the fingerprint (`frozen.canonical_frozen_set`), so H1 and every pre-lab registration keep their hash; set to a non-default value, the key is in the fingerprint, so a long/short or intraday variant of a hypothesis is a different hypothesis identity, counted in the family's N, which is what charter principle 2 requires. *Why now:* the table is append-only and immutable, so the keys cost the same whenever they land, but their absence is what lets a future run claim to be "H1 at daily bars" under H1's hash; naming them now also fixes where exposure and interval live before the lab's sweeps (T107 onward) start writing variant rows that read the frozen set. *Prior art:* LEAN's per-security leverage and `Resolution`, Zipline's `data_frequency` and `set_long_only`, as explicit run parameters. *Invariant:* `H1_FINGERPRINT` and `TWIN_FINGERPRINT` are asserted unchanged; `trial_*` rows are untouched.
6. **A reserved instrument id and type.** *What:* no new table and no DDL change to `securities`. Two rules, written into the data-foundation spec and the schema module's docstring: (a) every `security_id` column in the journal and the backtest is, from now on, read as an *instrument id*, and for a share the instrument id equals the security id, so today's rows need no change; (b) a future `instruments` table (type, multiplier, expiry, strike, right, `underlying_security_id`) issues ids in the same namespace with a type prefix that cannot collide with the master's EDGAR-derived ids (`store/master.py`), and `securities` stays the equity master. The `asset_class` column from seam 3 is the only type marker stored today. *Why now:* the audit's fourth-ranked seam is L either way, but its foreign keys spread with every journal table; fixing the id's meaning now means no re-keying later, while an `instruments` table built today, with nothing to put in it, would be exactly the overbuilding option 3 describes. *Prior art:* LEAN's `Symbol` with a `SecurityType` and `Underlying`, Nautilus's 21 instrument classes sharing one `InstrumentId` space. *Invariant:* no bytes change; the rule is a test that the namespace prefix is reserved (`master.primary_security_id` can never produce it).

### C. Deferred, each with its trigger and its own ADR

| Capability | Trigger | What its ADR must settle |
|---|---|---|
| **Shorting and margin** (signed exposure in the backtester, `_close_fifo` for short lots, net/gross and borrow keys in `RiskConfig`, negative dividend due in `reconcile.py:329`) | A registered long/short hypothesis the owner wants to run, and a research report on borrow cost and availability (the prior art: LEAN's default is unlimited free shorting, which is the optimistic case) | Account type (ADR 0010 point 1 sizes within `cash`; the charter's cash-account decision on #813), the margin model, borrow fees in `CostsConfig`, the side token in the id, `next_attempt`'s key |
| **Stop exits** (stop-loss, take-profit; none exist, `execution/exits.py`) | A swing hypothesis whose rule needs one | The intrabar path: the prior art calls same-bar stop-versus-target resolution a heuristic; the backtest must fill pessimistically and say so |
| **Intraday bars** | A day- or swing-trading hypothesis at a sub-daily interval, and a data source with honest bar-close timestamps and corporate-action handling | A new `bars(instrument_id, interval, bar_start, ..., known_at = bar end)` table and adapter, **never an alteration of `prices_daily`**; `known_at` at the bar's close (ADR 0003 rule 2 carries over); a `Cadence` value and `PERIODS_PER_YEAR` entry; the submit-window and lag keys in sessions become instants |
| **Other calendars** (CME and other venues) | The first non-XNYS instrument | `calendar.py` gains a venue argument; every session function stays date-based for XNYS |
| **Options and futures data** | An options or futures hypothesis, after a research report on point-in-time coverage: the prior art found no Tier 1 source on survivorship in derivatives data, so this is a known unknown, not a build task | Vendor, budget (ADR 0009's $0 stands until then), the `instruments` table, exercise and assignment, multiplier-aware notional in planning and marks |
| **Roll** (continuous view versus the dated contract) | The first futures hypothesis | The back-adjustment mode (ratio, additive, none) as a frozen key; the position stays in the dated contract and the strategy rolls it, as every engine in the report does |
| **Tax logic for shorts and derivatives** (short-sale holding periods, Section 1256, straddles, wash sales across instruments) | Live trading on such an instrument (Phase 6 or later) | The lot ledger's rules per instrument type; nothing before live money |
| **Multi-book aggregation** (two books on one account; `_Book`, `results.SERIES` and `trial_*` keyed by book in the backtester) | A second paper book the owner wants on the same account, or a portfolio-level report across books | Sleeve accounting on one account's cash, reconciliation per book, the single-open-window rule, aggregation in the backtester (L either way, per the audit) |

## Consequences

- Good: the six changes that would cost a migration with backfills during the paper window cost a column, a field, a frozen entry or an argument now; the `client_order_id` carries a book from the first order Alpaca ever sees; the risk wrapper's refusals are pinned by name, so the new columns and fields cannot be used by accident; the owner's direction is on record without moving the Scope line; every deferred capability has a named trigger, so none is built speculatively.
- Bad / accepted risks: reserved columns and fields that nothing writes are a small tax on every reader of the schema and the broker protocol until they are used, and a reserved shape may be superseded (legs as an order versus the spread as an instrument), in which case two nullable columns stay null; about a week of agent time moves ahead of Phase 4's remaining build (T48c, T67, T71), though no task on the critical path waits on this record except through `broker.py` (seam 3 before T48c); one journal schema version lands before `paper start` (seams 1 to 3 in one migration, `safety-reviewer`); the `portfolio` section is a new frozen section, which the lab's sweep axes and `FROZEN_SECTIONS` tests must learn.
- Reversibility: cheap for every seam. Columns with defaults and nullable fields can stay unused forever; the frozen entries cannot be removed (the table is append-only), but at their defaults they change no hash; the explicit cadence argument is a signature. The one-way part is the id format: once a paper order is submitted, the format with the book token is history, which is why the token lands before T71 and not after.
- Revisit if: the owner registers the first long/short, intraday or derivatives hypothesis (that capability's ADR, which may supersede the shape reserved here); T48b's recorded `client_order_id` length limit cannot fit the book token (shorten the token, never the attempt or security id); a reviewer finds a reserved column or field being written with a non-default value anywhere in `src/` before its ADR (that is a defect); Phase 4's retro finds the reserved shape cost more reading time than it saved; or the owner decides that part A's direction has changed.
