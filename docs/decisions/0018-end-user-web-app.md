# 0018. The end-user app: a local read API and a web front end, replacing Streamlit page by page

**Status:** Proposed  ·  **Date:** 2026-10-09  ·  **Issue:** #1410  ·  **Supersedes:** [ADR 0011](0011-dashboard-technology.md)'s "no separate API" rule (its page-purity rule, point 1, stays and is what makes this change cheap)  ·  **Related:** [charter](../charter.md) (Interface, Constraints), [roadmap](../roadmap.md) ("User experience"), [ADR 0001](0001-python-uv-toolchain.md) (toolchain), [ADR 0008](0008-llm-role.md) (LLM output never reaches orders), [ADR 0015](0015-expansion-seams.md) (seams), [ADR 0017](0017-fast-paper-and-machine-readiness-gate.md) (books), [design standard](../design/dashboard.md), [paper spec](../specs/paper-trading.md) reqs 9, 12, 15 and 16, [paper plan](../plans/paper-trading.md) T156 and T163

**Numbering note.** This record takes 0018. The Phase 6 ADR (paper plan T163, "`0018-<slug>.md` or the next free number") takes **0019**, the number after this one.

## Context

In plain words: the owner wants an app he can use, at his desk and on his phone, that answers four questions. How am I doing, overall and per book, against a benchmark. What is each book holding and doing, and why. Is anything wrong or waiting on me. And can I stop or resume a book safely. He decided on 2026-10-09 that the answer is a proper web front end over a small local API ("option B"), replacing the Streamlit pages over time. Restyling Streamlit ("option A") was rejected: the polish he wants (a refined dark terminal look, crisp financial charts, dense but clean tables) and phone use are what ADR 0011 listed as the things Streamlit cannot draw and the reason it was bound to localhost. He is designing the UI himself, in his own window, on a `spike/design-ui` branch with sample data; this record has to choose a stack that design ports to without a rewrite.

What exists today. Six Streamlit pages in `src/tradepartner/dashboard/` (data health, backtest, trials, research, operations, override) under the [design standard](../design/dashboard.md), with 159 headless-render tests. ADR 0011 made every page a pure function of a read-only connection; the operations page draws `execution.ops.page_data(conn, settings, book)` and `ops.book_summaries`, which `paper status` prints too; `paper report` is `execution.report.report`, `paper check` is `execution.check.check`, the alerts, runs, orders, fills, marks and reconciliations are `store.journal` readers; since ADR 0017 (T156) every one of them takes a book. So the numbers already live outside the renderer. That was ADR 0011's reversibility clause, and this record cashes it.

Three constraints shape the design. The store is DuckDB, single-writer: a read connection held by another process blocks the paper run's write chunks for `store.lock_retry_seconds` and then fails them (ADR 0011, Consequences), so a web server that holds connections is a hazard to the run. The paper run lock is per book and non-blocking (`execution.lock`): `paper kill` takes none, `paper resume` takes it and is refused at once while a run holds it. And the charter's constraints stand: local, personal, secrets only in `.env`, LLM output never reaches an order, the dashboard's only writes are logged owner actions with a reason. The repo is public, so nothing in it may carry a credential, a tailnet name or the owner's login.

Prior art, read before deciding (owner rule). **freqtrade + FreqUI**: the bot serves a REST API with FastAPI and uvicorn (`freqtrade/rpc/api_server/webserver.py`), listening on `127.0.0.1:8080` by default with the doc's warning "we strongly recommend to not expose this API to the internet"; auth is a username and password plus JWT for the SPA; FreqUI is a separate Vue 3 + TypeScript + Vite + pnpm repo (`packageManager: pnpm@…` pinned, ECharts for charts, GPL-3.0) whose built bundle the bot downloads with `freqtrade install-ui` into `api_server/ui/installed/` and serves as static files **on the same port** as the API, so one origin and no CORS in the common case. **Ghostfolio**: TypeScript end to end (NestJS, Angular, Prisma, Postgres, Redis, an Nx monorepo, Docker, AGPL-3.0), a multi-user SaaS shape; it shows what a full second stack costs and is the shape to avoid for one person with a Python core. **rotki**: a local-first, privacy-first portfolio tracker with a Python backend serving a REST API on localhost and a Vue + TypeScript frontend in a `frontend/` directory of the same monorepo, packaged with Electron (AGPL-3.0); the closest shape to ours, minus Electron. Hummingbot's dashboard went the other way (Streamlit over a FastAPI "backend-api") and is the option A we rejected. The pattern across the three that fit: Python owns the numbers and serves JSON on loopback; the UI is a TypeScript SPA in its own directory with its own lockfile, built to static files the Python server serves; auth is the network boundary plus one identity check.

## Options considered

Each numbered decision below lists its options; the summary of the rejected shapes is here.

1. **Restyle Streamlit (option A).** Pro: no new toolchain, the tests carry over. Con: no phone use without opening Streamlit's websocket to the network, which ADR 0011 refused for a reason that still holds (no identity check on it); interactions stay script re-runs; the look is Streamlit's. Rejected by the owner on 2026-10-09.
2. **A local read API plus a web front end (option B, this record).** Pro: any screen the owner designs can be built; one JSON contract serves the desk and the phone; the numbers stay in `execution` and `store`, computed once (ADR 0011 point 1 already made that so); the network boundary becomes explicit and testable. Con: a second language and toolchain beside uv (bounded below), a serialisation layer, a server process that must never hold the store.
3. **A desktop or native app** (Electron like rotki, SwiftUI for the phone). Con: two more toolchains and app distribution for one user; a browser over the tailnet gives the phone the same screens for free. Rejected.
4. **A hosted or cloud front end.** Con: the store and the keys leave the Mac; the charter says local and personal. Rejected without an option number.

## Decision

We will build the end-user app as **one local Python process serving a read API and a built web front end on one loopback port**, reachable from the owner's phone only through his own Tailscale network, writing nothing to the store except a book stop and a book resume through the CLI's own code paths, and retire the Streamlit pages one by one as each screen reaches parity.

### 1. The API: FastAPI, in this repo, over the CLI's read functions

**Options.** (a) **FastAPI + uvicorn** in `src/tradepartner/webapp/` (freqtrade's choice): pydantic models, which the project already uses for `Settings`, generate the OpenAPI document the front end's types are built from; async where it helps, sync handlers in a threadpool where the readers are sync. (b) Flask or Litestar: no reason to prefer either over the one whose schema tooling we already depend on. (c) A GraphQL API: one endpoint, flexible queries, but the screens are known and few, and a flexible query over a single-writer store is a way to hold connections long. (d) No API, the SPA reads the DuckDB file through a WASM build in the browser: no second process, but it would ship the whole store to the phone, cannot hold a read lock politely, and leaves no place for the two writes. **Recommended: (a).**

**Rules.**
- The API is the package `tradepartner.webapp` (`api.py` routes, `models.py` response models, `serve.py` the server), started by `tradepartner web` (a `cli.py` command, so `safety-reviewer` reviews it like every command). One uvicorn worker. The command binds `127.0.0.1` on `webapp.port` (config, default 8788) and **refuses any other bind address**, the way `render_app` refuses a non-localhost Streamlit (ADR 0011 point 3).
- **Every read goes through the functions the CLI uses**: `execution.ops.book_summaries` and `page_data`, `execution.report.report`, `execution.check.check`, `execution.marks.equity_at` over `store.journal.positions_daily_for`, `store.journal`'s readers (`runs_for`, `orders_for`, `fills_for`, `alerts_for`, `plans_for`, `reconciliations_for`, `kill_switch_events_for`), `store.registry` for the strategies, `store.benchmarks` for the benchmark ids. **No SQL string in `tradepartner.webapp`**, pinned by an AST test like the `RiskGatedBroker` one (spec req 3): a number the API needs and no reader provides is a new pure function in `execution` or `store`, with its own test, never a query in a route.
- **The store is opened read-only, per request, inside the handler, and closed before the response is serialised.** `store.db.open_read_only(settings)` is the only way the API touches the store; it is never opened at startup, never cached, never held across a request. Every per-row read is capped by `dashboard.page_row_limit` (renamed `webapp.row_limit` when the last Streamlit page goes; one key, two names until then) and every capped response says `capped: true`. `StoreLockedError` (a write chunk holds the file, or a resume is running in this process) is HTTP 503 `store_busy` with `Retry-After`, the screen's "store busy" chip; it is never retried inside the handler, because a retry is a held lock by another name.
- **Resources, in user terms**, under `/api/v1`, all `GET`:

  | Resource | Answers | Reader behind it | Shape (the contract, not the code) |
  |---|---|---|---|
  | `/books` | which books exist and how each is doing | `ops.book_summaries` | list of `book`: `book_id`, `window` (`id`, `hypothesis`, `cadence`, `opened_on`, `state` open/stopped/abandoned), `positions_count`, `open_orders_count`, `switch` (`state`, `causes[]`, `run_in_progress`), `last_run` (`session`, `status`), `next_rebalance_session` |
  | `/books/{book}` | what this book is holding and doing now | `ops.page_data` | the operations page's `OpsData` as JSON: `as_of`, `last_updated`, `stale`, `positions_count`, `positions_value`, `open_orders_count`, `targets_count`, `switch`, `ranking[]` (`security_id`, `ticker`, `score`, `rank`, `signal_reason`, `decision`, `decision_reason`, `selected`), `fills[]`, `chains[]`, `alerts[]`, `reconciliation`, each list with its `capped` flag |
  | `/books/{book}/equity?from&to` | how am I doing, vs a benchmark | `journal.positions_daily_for` + `marks.equity_at`; `store.benchmarks` + prices for SPY and MTUM rebased to the window's start equity; `report.report` for the backtest's expected path per period | `series[]` of `{name, points[]: {session, value}}`, one for the book and one per benchmark, plus `periods[]` from the tracking comparison (`period_end`, `paper_return`, `backtest_return`, `gap`, `tolerance`, `within`) |
  | `/overview/equity?from&to` | how am I doing overall | the per-book series summed per session (every book is its own account, ADR 0017 B.4) | the same shape, `name: "all books"` |
  | `/books/{book}/positions` | what it holds vs what it meant to hold | the last marked session's `positions_daily` rows and the latest plan's targets (`journal.plans_for`, `report.compare_targets`) | `as_of_session`, `rows[]`: `security_id`, `ticker`, `quantity`, `mark_price`, `value`, `weight`, `target_weight`, `drift`, `tradable` |
  | `/books/{book}/orders?session` | what it did, and the proof | `journal.orders_for`, `fills_for`, `order_events_for`, `decisions_for` (the chain, as `OpsData.chains`) | `orders[]`: `client_order_id`, `session`, `side`, `security_id`, `ticker`, `quantity` or `notional`, `state`, `decision_reason`, `fills[]` (`at`, `quantity`, `price`), `chain[]` (`at`, `kind`, `detail`) |
  | `/books/{book}/runs` | did it run, and how | `journal.runs_for` | `runs[]`: `run_id`, `session`, `kind`, `invoked_by`, `started_at`, `status`, `notes` |
  | `/books/{book}/report` | is the machine tracking the backtest | `report.report`, `check.check` | `periods[]` as above, `check[]`: `name`, `passed`, `text` |
  | `/alerts?book&since` | is anything wrong or waiting on me | `journal.alerts_for`, `unconsumed_kill_switch_overrides` | `alerts[]`: `at`, `book_id`, `kind`, `detail`, `acknowledged`; `waiting_on_owner[]`: the open kill switches, unsettled orders and pending overrides, each with the CLI command that clears it |
  | `/strategies` | what each book runs, and why it trades what it trades | `store.registry`, the window's `frozen_json` | `strategies[]`: `hypothesis`, `family`, `cadence`, `frozen` (the frozen keys as a flat map), `books[]` |
  | `/health` | can I trust this screen | `health.health_report`'s summary, the store's `as_of`, schema version, lock states (`lock.is_held` per book) | `as_of`, `last_updated`, `schema_version`, `api_version`, `books[]: {book_id, run_in_progress}` |

  Every response carries `as_of` (the store's last `known_at` the reader saw) and `last_updated` (the last ingest run) in an envelope, as the design standard's header rule asks (principle 5), and `generated_at`. Timestamps are ISO 8601 with the UTC offset, sessions are ISO dates, money is a JSON number in USD, ids are strings, a missing value is `null`, never 0. Tickers are looked up as of the session (`store.master.securities_as_of`), never stored. The envelope and every field above are **the contract**: the committed `webapp/openapi.json` is generated from the models and a test fails when the two differ, and the front end's TypeScript types are generated from that file, so a shape change breaks both sides in CI, not on the phone.
- Nothing from an LLM is served or accepted: there is no memo field until ADR 0008's Phase 5 gate opens it, and then it is a string beside a signal, never an action.

### 2. Writes: stop and resume a book, through `paper kill` and `paper resume`, nothing else

**Options.** (a) The two handlers call the **same library functions `cli.py`'s `paper kill` and `paper resume` call** (`execution.window.kill`, `execution.resume.resume`), with the CLI's argument building (`paper_settings`, the book token check, `build_broker(settings, clock, book)` for resume, `utc_now`, the output scrubber) factored into one helper per command that both the CLI and the API call, so each write has one function and two callers, exactly as ADR 0011 point 2 did for the override writer. (b) The handler runs `tradepartner paper kill …` as a subprocess: byte-identical behaviour including exit codes, but a second process on every click, stdout parsing and a venv to find; it hides the write behind a shell. (c) Every `paper` command exposed (start, stop, abandon, override, settle): more screens, more review surface, none asked for. **Recommended: (a)**, two endpoints, under the order-path review rules (`safety-reviewer` on every PR that touches them, two passes; the `cli.py` refactor that extracts the helpers is itself an order-path PR).

**Rules.**
- `POST /api/v1/books/{book}/stop` with `{reason}` engages the book's kill switch through `window.kill` (owner source, the reason as the note, `paper kill`'s refusals as HTTP 4xx with the refusal name: blank reason 422, no open window 404, `KillWriteFailed` 500 **with the message that the switch is NOT engaged**, as the CLI prints). `POST /api/v1/books/{book}/resume` with `{reason, accept_broker_fills, accept_rejections}` runs `resume.resume`; a refusal is an outcome in the 200 body (as the CLI's exit code is), `LockHeld` is 409 `locked` (a run holds the book), `no_window` 404. Both take `reason` as typed, never defaulted or padded, so the journal row is the owner's words. The response body is the result plus the book's new summary, read **after** the writer returned.
- **No order placement from the UI, ever**, and no path to one: the API imports nothing from `execution.run`, `execution.phases`, `execution.wrapper`, `adapters.alpaca_broker` or `adapters.alpaca_trading_raw` except through the resume helper's broker factory, pinned by the same AST test as the no-SQL rule; `RiskGatedBroker` stays the only caller of `submit` (spec req 3) and the API is not among its callers. A screen that wants a "trade" button wants a new ADR.
- **The locks.** The store's single-writer rule: a write handler opens **no read-only connection** while it runs (an in-process read connection would make the writer's `open_for_write` fail at once with `StoreLockedError`, ADR 0011's same-process rule), and the API holds a process-wide write mutex so two clicks never run two writers at once; reads that arrive during a resume see `store_busy` for its write chunks and otherwise succeed, because the writer holds the file only per chunk. The paper run lock: `kill` takes none, so a stop works mid-run, which is its purpose; the run sees the engaged row at its next phase boundary, as it does for the CLI. `resume` takes the book's lock for its whole duration and is refused at once while a run holds it; the API never takes a run lock itself, and never holds one past the resume call. A running API therefore never blocks a scheduled `paper run`: its reads are short, its one long operation is a resume the owner asked for, under the run's own lock.
- **Confirmation and origin.** The front end asks for the reason and a typed confirmation before either call. The API accepts a write only with a same-origin `Origin` header and a custom request header (`X-TradePartner-Action`), so a cross-site form on the owner's browser cannot post it (a browser cannot add a custom header cross-origin without a preflight, and the API answers no preflight for another origin); on the tailnet path (section 4) it must also carry the owner's identity.
- The override form (spec req 9, `exclude_name` and the rest) is **not** an API write in this record; it stays on Streamlit (section 5, open question 3).

### 3. The front end: React + TypeScript on Vite, in `webapp/`, served by the API

**Options.** (a) **React + TypeScript via Vite**: the largest pool of headless components and charting bindings, TypeScript types generated from OpenAPI, the stack the owner's HTML/CSS design ports to as components with the same markup and CSS variables. (b) **SvelteKit**: less code per screen and a smaller bundle, but its router and server side are made for a Node host we do not want, and the headless and charting ecosystem is thinner. (c) **Server-rendered HTMX + Jinja from FastAPI**: no Node toolchain at all, one language, and the API could render HTML fragments; but crisp financial charts and dense sortable tables need client code anyway, the owner's design would become templates, and phone interactions (crosshairs, drill-down) are poor with partial page swaps. (d) Vue (FreqUI's choice): fine, but nothing in it beats (a) for this owner's design and the generated-types workflow. **Recommended: (a)**, unless the owner's design is already written in Svelte or Vue (open question 1).

**Where and how.**
- The front end lives in **`webapp/`** at the repo root (rotki's `frontend/` shape), with its own `package.json`, `pnpm-lock.yaml`, `tsconfig.json`, `vite.config.ts` and tests; nothing under `src/tradepartner/` imports it. `pnpm build` writes to `src/tradepartner/webapp/static/` (gitignored, never committed: a built bundle in a public repo is churn and an unreviewed binary), and `tradepartner web` serves it with FastAPI's `StaticFiles` **on the same port as the API** (freqtrade's shape): one origin, no CORS, one port for Tailscale Serve. With no build present the command serves the API and a one-line page saying how to build. `pnpm dev` runs Vite with a proxy to the API for hot reload.
- **Toolchain beside uv.** Node pinned in `.node-version` (the current LTS, 24, open question 6) and pnpm pinned in `package.json`'s `packageManager` field, as FreqUI does; `uv` stays the only Python tool (ADR 0001). CI gets **one extra job**, path-filtered to `webapp/**` and the lockfile: install from the lockfile, `pnpm lint`, `pnpm typecheck`, `pnpm test`, `pnpm build`, about two minutes; the Python shards are unchanged and the API's contract tests are pytest. Pre-commit runs the front end's formatter only on `webapp/` files. No Node is needed to run the tests of anything under `src/`.
- **Charting and component foundation.** Charts are built on **TradingView's `lightweight-charts`** (Apache-2.0; its NOTICE requires the attribution notice and a link to tradingview.com on the page, which the library's `attributionLogo` option draws on the chart), a canvas library made for financial time series (line, area, baseline, candlestick, histogram) with the crosshair and the time scale the design standard asks for, a few tens of kilobytes, no dependencies. A general-purpose library (Plotly, which the Streamlit pages use; ECharts, FreqUI's; Recharts) is rejected for the time series: each is five to twenty times the size, none draws a financial time scale or a crosshair that syncs across charts without work, and the terminal look the owner wants is lightweight-charts' default. Bars, gauges and sparklines are small SVG components over the tokens; a second charting library enters only when a chart needs one, by a plan line. Components are **headless primitives** (Radix Primitives or React Aria for menus, dialogs, tabs; TanStack Table for the dense tables), styled only by **design tokens** the owner's design defines as CSS custom properties in one file (`webapp/src/tokens.css`: colour per role, the type scale, a 4/8 px spacing scale, radii, the dark theme first and the light one from the same hues), so the polish comes from tokens the owner sets, not from a themed kit (no MUI, Ant, PrimeVue or Material) whose look would have to be fought. The design standard's token table moves to that file when the last Streamlit page retires; until then the three copies (`theme.py`, `.streamlit/config.toml`, `tokens.css`) are accepted, with a test that the shared roles agree.
- The screens are the owner's: this record fixes only that each screen is a function of one or two API resources, works at phone width (16 px gutters, no horizontal scroll, the standard's rule), and reads `as_of`, `last_updated` and `stale` from the envelope into the header.

### 4. Phone access and security: loopback by default, the owner's tailnet, identity from Tailscale, no secret in the browser

**Options.** (a) **Tailscale Serve** (`tailscale serve --bg --https=443 localhost:<port>`): tailscaled on the Mac terminates HTTPS with a tailnet certificate and proxies to the loopback port, reachable only from devices on the owner's tailnet, and adds `Tailscale-User-Login`, `Tailscale-User-Name` and `Tailscale-User-Profile-Pic` to every proxied request; Funnel (the public variant) is never enabled. (b) Bind the API to the Mac's Tailscale IP and reach it by IP: no HTTPS, no identity headers, and a bind address other than loopback, which rule 1 refuses. (c) A password or JWT like freqtrade: a credential that lives in the phone's browser and in `.env`, for an API that is never on a network a stranger can reach; it adds a secret to rotate and nothing the tailnet does not already prove. (d) Expose Streamlit over the tailnet: ADR 0011's reasons stand. **Recommended: (a)**, with (c) available later if the owner wants a second factor (open question 4).

**Rules.**
- The API binds **loopback only** (rule 1). The phone path is Tailscale Serve proxying to that port; the runbook records the two commands (`serve --bg …`, `serve status`) and that `tailscale funnel` is never run on this Mac. A test cannot see the tailnet, so the API's own checks are what make a mistake harmless: every request's `Host` must be `localhost`, `127.0.0.1` or the configured `webapp.tailnet_host` (the Mac's MagicDNS name, set only in `.env`, never in the repo), else 421; this also closes ADR 0011's accepted DNS-rebinding risk.
- **Identity.** A request with no `Tailscale-User-Login` header is accepted as the owner's own browser on the Mac (it reached loopback, which only a process on the Mac can). A request that carries the header must carry `webapp.owner_login` (set only in `.env`) exactly, else 403, **on reads and writes alike**; a write over the tailnet also needs the same-origin and custom-header checks of section 2. A proxied request cannot drop or forge the headers: tailscaled sets them, and a browser on the Mac cannot add a `Tailscale-*` header cross-origin. A request that reaches loopback with a forged header from a local process is a process already on the Mac, which is the charter's trust boundary.
- **No secret is ever served.** The API has no endpoint that returns `Settings`, and the error path runs every message through the CLI's scrubber before it is serialised, as the `paper` commands do; a test runs every endpoint, including the two writes' failure paths, with sentinel key values in the fixture settings and asserts no response, header or log line contains one. The browser holds no token, key or password; a lost phone is a device removed from the tailnet in the admin console, nothing to rotate in `.env`.
- Telemetry: none; the bundle calls no third-party host, pinned by a test over the built assets (no absolute `http` URL other than the attribution link).

### 5. Coexistence with Streamlit, and retirement page by page

Streamlit stays the dashboard until each screen reaches parity; the two run side by side on their own ports and both read the store through `open_read_only`, which neither holds. ADR 0011's page-purity rule stays in force for the Streamlit pages while they live, and its localhost bind stays.

**A Streamlit page is retired** (its module, its tests, its navigation entry deleted in one PR, class A unless it touches `cli.py` or config) when all four hold, written in that PR's body: (1) **parity**: every number and status the page shows is on the new screen, from the same reader, pinned by a test that the API response for the fixture store equals the page's data function's output field by field; (2) **used**: the owner has used the new screen for the page's purpose at least once on the real store and says so (a dated line on the PR); (3) **phone**: the screen passes the phone-width check in the front-end tests; (4) **no regression in review surface**: a page with a write (the override page) is retired only when its write has an API endpoint under section 2's rules, which this record does not grant (open question 3). The order follows the owner's four questions: the operations page and the book overview first (they are what he uses daily), then data health, then the trials, backtest and research pages last or never (they are agent and research tooling the cockpit already covers; open question 5). The Streamlit dependency, `dashboard/app.py`, `theme.py` and `.streamlit/` go with the last page, in a PR that marks ADR 0011 superseded in full and moves the design standard's token table to `tokens.css`.

### 6. Testing

- **Contract tests** (pytest, `tests/webapp/`): FastAPI's test client over the fixture store (`tests/execution/conftest.py`'s `journal_settings` on a temp-file copy, never the owner's store), one test per resource that validates the response against the models, compares it field by field to the reader's dataclass (the parity test of section 5), and pins the generated OpenAPI document to the committed `webapp/openapi.json`. The front end's unit tests (vitest) run over fixture JSON recorded from those same responses, so a screen is tested against the shape the API actually produced.
- **The no-write test.** Every `GET` is run against a fixture store, and the store file's bytes and every table's row count are the same before and after; the `tradepartner.webapp` package imports `open_for_write` nowhere and names the two writer helpers as its only write calls (the AST test of sections 1 and 2); the two write handlers are run against the fixture store with the fake broker and the rows they append are exactly those `paper kill`'s and `paper resume`'s own tests expect, no more; a request to any other method or path writes nothing.
- **Boundary tests.** A foreign `Host` is 421; a tailnet header with another login is 403; a cross-origin `POST` is refused; `store_busy` while another process holds the file for write (the lock tests' pattern); no sentinel secret in any response.
- **The locks.** A test that a write handler never has a read-only connection open (the same-process `StoreLockedError` would show it), and that `resume` during a held run lock returns 409 and writes nothing.
- The Streamlit pages' headless-render tests stay until their page retires; the retirement PR replaces them with the contract tests of the same cases.

### 7. Validate before building: the spike

Before any plan task starts, a `spike/webapp-probe` branch (no claim, no PR to merge, thrown away or mined for the first task) builds the smallest end-to-end slice: `GET /api/v1/books` and `GET /api/v1/books/{book}` over `ops.book_summaries` and `page_data` on a temp copy of the fixture store with an open window, and **one screen**, the owner's "how am I doing / books" design, fed by it, built with Vite + React + lightweight-charts over his tokens file, served by the one process on loopback and reached from his phone through Tailscale Serve.

It must show, in a comment on #1410 with numbers, before the plan's tasks are claimed: (1) the screen's numbers equal `paper status --all`'s line for the same fixture, by eye and by a test; (2) a request opens the read connection inside the handler and closes it before the response, logged, and a `GET` while another process holds the file for write returns `store_busy` and recovers on the next request; (3) the owner's design ported as components and tokens with no markup rewrite, counted (components written, tokens used, lines of CSS changed); (4) the phone reaches the screen over Serve with the identity header logged, `tailscale serve status` shows no Funnel, and a request from another device on the LAN or by the Mac's LAN address is refused; (5) `pnpm install && pnpm build` from clean in under two minutes on the Mac, with the bundle size; (6) a request on the fixture store finishes in under a second. If (2), (4) or (5) fails, the design changes before the plan is written, not after.

## Consequences

- Good: the owner gets the screens he designs, on the phone too, over numbers computed once in `execution` and `store`; the network boundary is explicit (loopback, tailnet identity, `Host` allowlist) and tested, which closes ADR 0011's accepted rebinding risk; the two writes have one function and two callers each, so `safety-reviewer` reviews one path per action; the contract is a committed file both sides generate from; the spike bounds the risk before a plan exists.
- Bad / accepted risks: a second language, lockfile and CI job (bounded to `webapp/` and about two minutes); a serialisation layer and the generated types to keep current; three copies of the tokens while Streamlit lives; a server process that, if it ever holds a connection, blocks the paper run (the per-request rule and its tests exist for this); lightweight-charts' attribution line on every chart page; Tailscale is a third party on the phone path (no data leaves the Mac through it except to the owner's own device, but its outage is a phone outage, and the desk path does not depend on it); the owner's design and this stack choice are made before a line of the front end exists, which the spike is for.
- Reversibility: cheap for the API (it is a thin layer over readers that already exist); moderate for the front end (a framework change is a rewrite of `webapp/`, not of anything under `src/`); the Streamlit pages are not deleted until parity, so the way back exists for as long as the retirement takes.
- Amendments this record implies, not in this PR (the plan's first task): the charter's Interface line and the roadmap's "User experience" paragraph ("no separate API" becomes "one local read API, two logged writes"), a dated pointer on ADR 0011 and on the design standard, `.env.example` with `WEBAPP_TAILNET_HOST` and `WEBAPP_OWNER_LOGIN` (names only), the scheduling runbook's Serve commands.
- Revisit if: the owner wants a write beyond stop and resume (a new ADR, under the order-path rules); the Phase 6 live book wants the same screens (ADR 0019 says whether a live book's stop and resume go through this API; nothing here lifts the `alpaca.paper` guard); the API's per-request reads prove too slow on a long journal (then the readers get bounded or cached in `execution`, never in a route); or the owner wants a second person on the tailnet (identity becomes a list, and an audit row per write).

## Open questions for the owner (one decision each, a recommendation beside it)

1. **Which front-end stack is the design in?** If the `spike/design-ui` work is HTML and CSS with sample data, or React, **recommend React + TypeScript on Vite** (section 3). If it is Svelte or Vue already, say so and that framework takes (a)'s place; the rest of the record is unchanged.
2. **Is the built bundle committed?** **Recommend no**: `pnpm build` locally and in CI, `src/tradepartner/webapp/static/` gitignored, `tradepartner web` says how to build when it is missing. Committing it (freqtrade downloads a release instead) would put a binary blob in every UI PR of a public repo.
3. **Does the override form move to the API now?** **Recommend no**: it stays on Streamlit until the operations screens have shipped and the owner has used stop and resume for real; adding it then is one more endpoint under section 2's rules, in a one-paragraph amendment, not a new ADR.
4. **Is Tailscale identity enough, or a passphrase too?** **Recommend identity only** (section 4): the tailnet already authenticates the device and the user, the API checks the login, and a passphrase would be a secret in the phone's browser. A second factor can be added later as a `webapp.require_passphrase` key if the owner wants it before the live book.
5. **Which Streamlit pages move at all?** **Recommend** the operations page, the book overview and data health move; the trials, backtest and research pages stay on Streamlit until the cockpit or a later decision takes them; they are research tooling, not the end-user app.
6. **Node version.** **Recommend the current LTS line (24)** pinned in `.node-version`, moved only on a plan line; pnpm pinned by `packageManager`.
7. **The overall benchmark on the first tile.** ADR 0005 names SPY and MTUM; **recommend SPY as the tile's comparison and both on the chart**, rebased to the window's start equity, total return, computed inside the system as ADR 0005 requires.
8. **How big is the spike?** **Recommend one team, one working day, Opus**, stopping at the first failed must-show; the spike's report is a comment on #1410, not a document.
