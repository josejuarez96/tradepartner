# 0018. The end-user app: a local read API and a web front end, replacing Streamlit page by page

**Status:** Proposed  ·  **Date:** 2026-10-09  ·  **Issue:** #1410  ·  **Supersedes:** [ADR 0011](0011-dashboard-technology.md)'s "no separate API" rule (its page-purity rule, point 1, stays and is what makes this change cheap)  ·  **Related:** [charter](../charter.md) (Interface, Constraints), [roadmap](../roadmap.md) ("User experience"), [ADR 0001](0001-python-uv-toolchain.md) (toolchain), [ADR 0004](0004-tooling-adopt-avoid.md) (adopt table), [ADR 0008](0008-llm-role.md) (LLM output never reaches orders), [ADR 0015](0015-expansion-seams.md) (seams), [ADR 0017](0017-fast-paper-and-machine-readiness-gate.md) (books), [design standard](../design/dashboard.md), [paper spec](../specs/paper-trading.md) reqs 3, 5, 9, 10, 12, 15 and 16, [paper plan](../plans/paper-trading.md) T156 and T163

**Numbering note.** This record takes 0018. The Phase 6 ADR (paper plan T163, "`0018-<slug>.md` or the next free number") takes **0019**, the number after this one.

## Context

In plain words: the owner wants an app he can use, at his desk and on his phone, that answers four questions. How am I doing, overall and per book, against a benchmark. What is each book holding and doing, and why. Is anything wrong or waiting on me. And can I stop or resume a book safely. He decided on 2026-10-09 that the answer is a proper web front end over a small local API ("option B"), replacing the Streamlit pages over time. Restyling Streamlit ("option A") was rejected: the polish he wants (a refined dark terminal look, crisp financial charts, dense but clean tables) and phone use are what ADR 0011 listed as the things Streamlit cannot draw and the reason it was bound to localhost. He is designing the UI himself, in his own window, on a `spike/design-ui` branch with sample data; this record has to choose a stack that design ports to without a rewrite.

What exists today. Six Streamlit pages in `src/tradepartner/dashboard/` (data health, backtest, trials, research, operations, override) under the [design standard](../design/dashboard.md), with 159 headless-render tests. ADR 0011 made every page a pure function of a read-only connection; the operations page draws `execution.ops.page_data(conn, settings, book)` and `ops.book_summaries`, which `paper status` prints too; the journal's rows (runs, orders, fills, marks, reconciliations, alerts, plans, kill-switch events) have readers in `store.journal`, keyed by the window the book's reader (`journal.open_window(conn, book)`, `latest_window`) resolves; since ADR 0017 (T156) every surface takes a book. So the numbers already live outside the renderer. That was ADR 0011's reversibility clause, and this record cashes it. Two CLI commands are **not** reads: `paper report` (`execution.report.report`) runs a tracking trial and appends a `paper_reports` row that names the trial only (`window_id`, `trial_id`, `through_session`; the per-period comparison `compare_periods` computes is **not persisted** today, and rebuilding it needs the whole window's journal, corporate actions and a price lookup per security and session), and `paper check` is pure but reads the whole window; neither may run per page view.

Three constraints shape the design. The store is DuckDB, single-writer, one connection mode per file per process: a read connection held by another process blocks the paper run's write chunks for `store.lock_retry_seconds` and then fails them (ADR 0011, Consequences), and a write opened in a process that already holds a read-only connection fails **at once**, with no retry (`store.db`'s same-process rule). So a web server that holds connections is a hazard to the run, and a web server that writes in-process is a hazard to its own writes. The paper run lock is per book and non-blocking (`execution.lock`): `paper kill` takes none, `paper resume` takes it and is refused at once while a run holds it; and `is_held`, which `page_data` and `book_summaries` call, takes a shared `flock` for an instant, during which a `run_lock` starting is refused as `locked`. And the charter's constraints stand: local, personal, secrets only in `.env`, LLM output never reaches an order, the dashboard's only writes are logged owner actions with a reason. The repo is public, so nothing in it may carry a credential, a tailnet name or the owner's login.

Prior art, read before deciding (owner rule). **freqtrade + FreqUI**: the bot serves a REST API with FastAPI and uvicorn (`freqtrade/rpc/api_server/webserver.py`), listening on `127.0.0.1:8080` by default; its docs recommend not exposing the API to the internet; auth is a username and password plus JWT for the SPA; FreqUI is a separate Vue 3 + TypeScript + Vite + pnpm repo (`packageManager: pnpm@…` pinned, ECharts for charts, GPL-3.0) whose built bundle the bot downloads with `freqtrade install-ui` into `api_server/ui/installed/` and serves as static files **on the same port** as the API, so one origin and no CORS in the common case. **Ghostfolio**: TypeScript end to end (NestJS, Angular, Prisma, Postgres, Redis, an Nx monorepo, Docker, AGPL-3.0), a multi-user SaaS shape; it shows what a full second stack costs and is the shape to avoid for one person with a Python core. **rotki**: a local-first, privacy-first portfolio tracker with a Python backend serving a REST API on localhost and a Vue + TypeScript frontend in a `frontend/` directory of the same monorepo, packaged with Electron (AGPL-3.0); the closest shape to ours, minus Electron. Hummingbot's dashboard went the other way (Streamlit over a FastAPI "backend-api") and is the option A we rejected. The pattern across the three that fit: Python owns the numbers and serves JSON on loopback; the UI is a TypeScript SPA in its own directory with its own lockfile, built to static files the Python server serves; auth is the network boundary plus one identity check.

## Options considered

Each numbered decision below lists its options; the summary of the rejected shapes is here.

1. **Restyle Streamlit (option A).** Pro: no new toolchain, the tests carry over. Con: no phone use without opening Streamlit's websocket to the network, which ADR 0011 refused for a reason that still holds (no identity check on it); interactions stay script re-runs; the look is Streamlit's. Rejected by the owner on 2026-10-09.
2. **A local read API plus a web front end (option B, this record).** Pro: any screen the owner designs can be built; one JSON contract serves the desk and the phone; the numbers stay in `execution` and `store`, computed once (ADR 0011 point 1 already made that so); the network boundary becomes explicit and testable. Con: a second language and toolchain beside uv (bounded below), a serialisation layer, a server process that must never hold the store.
3. **A desktop or native app** (Electron like rotki, SwiftUI for the phone). Con: two more toolchains and app distribution for one user; a browser over the tailnet gives the phone the same screens for free. Rejected.
4. **A hosted or cloud front end.** Con: the store and the keys leave the Mac; the charter says local and personal. Rejected without an option number.

## Decision

We will build the end-user app as **one local Python process that only ever reads the store**, serving a read API and a built web front end on loopback, reachable from the owner's phone only through his own Tailscale network with his identity required, writing nothing to the store except a book's kill switch engaged or released **by running the CLI's own `paper kill` and `paper resume` as subprocesses**, and retire the Streamlit pages one by one as each screen reaches parity.

### 1. The API: FastAPI, in this repo, over the CLI's read functions, one store read at a time

**Options.** (a) **FastAPI + uvicorn** in `src/tradepartner/webapp/` (freqtrade's choice; FastAPI and uvicorn are MIT and BSD-3): pydantic models, which the project already uses for `Settings`, generate the OpenAPI document the front end's types are built from; sync handlers in uvicorn's threadpool, because every reader is sync. (b) Flask or Litestar: no reason to prefer either over the one whose schema tooling we already depend on. (c) A GraphQL API: one endpoint, flexible queries, but the screens are known and few, and a flexible query over a single-writer store is a way to hold connections long. (d) No API, the SPA reads the DuckDB file through a WASM build in the browser: no second process, but it would ship the whole store to the phone, cannot hold a read lock politely, and leaves no place for the two writes. **Recommended: (a).**

**Rules.**
- The API is the package `tradepartner.webapp` (`api.py` routes, `models.py` response models, `serve.py` the server), started by `tradepartner web` (a `cli.py` command, so `safety-reviewer` reviews it like every command). One uvicorn worker. The command binds `127.0.0.1` on `webapp.port` (config, default 8788) and **refuses any other bind address**, checked on the bound socket at runtime, the way `render_app` checks the running Streamlit option (ADR 0011 point 3). No `CORSMiddleware` is ever added: an unanswered cross-origin preflight is part of the write defence (section 2).
- **The API process opens the store read-only, and only read-only.** `store.db.open_read_only(settings)` is the only store call in `tradepartner.webapp`; the package imports `open_for_write` nowhere, pinned by an AST test. Because it never writes in-process, the same-process mode conflict cannot arise inside it; the two writes are subprocesses (section 2).
- **One store read at a time, per request, short.** A process-wide gate (a semaphore of one) wraps every store access: a handler takes the gate, opens the connection, runs its readers, closes the connection, releases the gate, then serialises. A request that cannot take the gate within `webapp.gate_wait_seconds` (default 2) gets HTTP 503 `store_busy`, as does a `StoreLockedError` (another process holds the file for write); it is never retried in the handler, because a retry is a held lock by another name. Every per-row read is capped by `dashboard.page_row_limit` (renamed `webapp.row_limit` when the last Streamlit page goes; one key, two names until then) and every capped list says `capped: true`. **The contract for every read is ADR 0011's bound: it finishes within half of `store.lock_retry_seconds` on the fixture store with a full window** (a timing test per resource), and the spike measures it once on the real store, read-only, by the owner (section 7).
- **Every number comes from the functions the CLI uses or from a new pure function beside them**: `execution.ops.book_summaries` and `page_data`, `execution.marks.equity_at` over `store.journal.positions_daily_for`, `store.journal`'s readers (`runs_for`, `orders_for`, `fills_for`, `order_events_for`, `decisions_for`, `plans_for`, `reconciliations_for`, `kill_switch_events_for`, `paper_reports_for`, `unconsumed_kill_switch_overrides`), `store.registry` for the hypotheses, `store.benchmarks` for the benchmark ids, `store.master.securities_as_of` for tickers. **No SQL string in `tradepartner.webapp`**, pinned by the same AST test: a number the API needs and no reader provides is a new pure function in `execution` or `store`, with its own test, never a query in a route. The ones this record already knows it needs, each a plan task: an alerts-since-a-time reader (`journal.alerts_for` is a dedupe-key lookup, and `ops` uses a private per-window list), the last run's session beside `BookSummary.last_run_status`, the "waiting on me" list, the tracking periods **as `paper report` persists them** (today it persists none: the plan adds a `paper_report_periods` table, one additive journal schema version, that `report.report` appends beside its `paper_reports` row, and a reader of it; until that lands `/report` has no `periods[]`, and the API never computes a comparison itself and never runs a trial), a benchmark total-return series rebased to a window's start equity, and the per-session sum across books. `/health` reads what the dashboard header reads (the last ingest run and the store's `as_of`), **never `health.health_report`**, which is a full integrity scan.
- **Resources, in user terms**, under `/api/v1`, all `GET`. The fields below are the contract; the parity test (section 6) checks each against the reader through an explicit mapping, so a field may be renamed from its dataclass (as `switch` is from `switch_state`) without the contract following the code:

  | Resource | Answers | Behind it | Fields |
  |---|---|---|---|
  | `/books` | which books exist and how each is doing | `ops.book_summaries` + the last-run reader | `books[]`: `book_id`, `window` (`id`, `hypothesis`, `cadence`, `opened_on`, `state` open/stopped/abandoned), `positions_count`, `open_orders_count`, `switch` (`state`, `causes[]`, `run_in_progress`), `last_run` (`session`, `status`), `next_rebalance_session` |
  | `/books/{book}` | what this book is holding and doing now | `ops.page_data` | `positions_count`, `positions_value`, `open_orders_count`, `targets_count`, `switch`, `ranking[]` (`security_id`, `ticker`, `score`, `rank`, `signal_reason`, `decision`, `decision_reason`, `selected`), `fills[]`, `chains[]`, `alerts[]`, `reconciliation`, each list with its `capped` |
  | `/books/{book}/equity?from&to` | how am I doing, vs a benchmark | `positions_daily_for` + `equity_at`; the benchmark series reader | `series[]` of `{name, points[]: {session, value}}`, one for the book and one per benchmark (SPY, MTUM; ADR 0005) |
  | `/overview/equity?from&to` | how am I doing overall | the per-session sum across books (every book is its own account, ADR 0017 B.4) | the same shape, `name: "all books"` |
  | `/books/{book}/positions` | what it holds vs what it meant to hold | the last marked session's `positions_daily` rows and the latest plan's targets (`plans_for`) | `as_of_session`, `rows[]`: `security_id`, `ticker`, `quantity`, `mark_price`, `value`, `weight`, `target_weight`, `drift`, `tradable` |
  | `/books/{book}/orders?session` | what it did, and the proof | `orders_for`, `fills_for`, `order_events_for`, `decisions_for` (the chain, as `page_data` builds it) | `orders[]`: `client_order_id`, `session`, `side`, `security_id`, `ticker`, `quantity` or `notional`, `state`, `decision_reason`, `fills[]` (`at`, `quantity`, `price`), `chain[]` (`at`, `kind`, `detail`) |
  | `/books/{book}/runs` | did it run, and how | `runs_for` | `runs[]`: `run_id`, `session`, `kind`, `invoked_by`, `started_at`, `status`, `notes` |

  | `/alerts?book&since` | is anything wrong or waiting on me | the alerts-since reader; `unconsumed_kill_switch_overrides`; the waiting-on-me reader | `alerts[]`: `at`, `book_id`, `kind`, `detail`; `waiting_on_owner[]`: the engaged kill switches, unsettled orders and pending overrides, each with the CLI command that clears it |
  | `/strategies` | what each book runs, and why it trades what it trades | `store.registry`, the window's `frozen_json` | `strategies[]`: `hypothesis`, `family`, `cadence`, `frozen` (the frozen keys as a flat map), `books[]` |
  | `/health` | can I trust this screen | the header's reads; `lock.is_held` per book | `as_of`, `last_ingest`, `schema_version`, `api_version`, `books[]: {book_id, run_in_progress}` |

  Every response carries an envelope: `as_of` (the store's last `known_at` the reader saw), `last_ingest` (the last ingest run, the header's "last updated"), `last_run` for a book resource (the book's last paper run's `finished_at`, which is what `OpsData.last_updated` holds), `stale`, and `generated_at`. Timestamps are ISO 8601 with the UTC offset, sessions are ISO dates, money is a JSON number in USD, ids are strings, a missing value is `null`, never 0. Tickers are looked up as of the session, never stored. The committed `webapp/openapi.json` is generated from the models and a test fails when the two differ, and the front end's TypeScript types are generated from that file, so a shape change breaks both sides in CI, not on the phone.
- **Polling.** The front end polls no resource more often than `webapp.poll_seconds` (default 60) and only while a tab is visible. `is_held`'s instant shared lock is the same one the Streamlit page and `paper status` take today; the residual race with a `run_lock` starting in that instant is accepted here as ADR 0011 accepted it, and the scheduled job's `locked` exit is already the runbook's retry case.
- Nothing from an LLM is served or accepted: there is no memo field until ADR 0008's Phase 5 gate opens it, and then it is a string beside a signal, never an action.

### 2. Writes: kill and resume a book, by running `paper kill` and `paper resume`, nothing else

**Options.** (a) The handlers call the library functions `cli.py` calls (`execution.window.kill`, `execution.resume.resume`) in-process through shared helpers. Rejected: `kill`'s first step is a write-mode `connect()` and `switch.engage` opens `open_for_write` directly, so any read-only connection open in the API process at that instant (a polling tab) fails the write **at once** (the same-process rule), and a resume part-way through its chunks the same way; the in-process gate needed to prevent that would have to sit inside `store.db` under every write chunk, an order-path change, and a resume held in-process would make a kill wait behind minutes of broker calls. (b) **The handler runs the CLI command as a subprocess** of the same interpreter (`sys.executable`, the `tradepartner` entry point, `paper kill --book <b> --reason <r>` / `paper resume --book <b> --reason <r>` / `paper kill --all --reason <r>`): byte-for-byte the code path the owner uses at the desk, including `paper_settings`'s usage checks, the book-token check, `_paper_call`'s refusal exit codes and the scrubbed output; the API process never holds a write connection, so its reads can never break a write; a kill is a separate process from a resume, so it waits behind at most one write chunk (`open_for_write`'s cross-process retry), exactly as a CLI kill does during a run today. Cost: one interpreter start per click (seconds; the owner clicks these a few times a month), and the result is an exit code plus the command's scrubbed text. (c) Every `paper` command exposed (start, stop, abandon, override, settle): more screens, more review surface, none asked for. **Recommended: (b)**, three endpoints, under the order-path review rules (`safety-reviewer` on every PR that touches them, two passes).

**Rules.**
- **Endpoints**, all `POST`, each with `{reason}` in the body: `/api/v1/books/{book}/kill` runs `paper kill` (the screen's button says "Stop", the owner's word, and the record says here that it engages the kill switch and is **not** `paper stop`, which closes a window); `/api/v1/kill-all` runs `paper kill --all` and returns a result per book; `/api/v1/books/{book}/resume` runs `paper resume` **with neither accept flag**. `accept_broker_fills` and `accept_rejections` are the owner's CLI-only decisions (spec req 5, `resume.py`'s "only the owner's CLI flag sets it"); a resume that needs either is a desk action, and the API's refusal says so. The alternative, strict required booleans with their own confirmation on the screen, is open question 4; it is not granted here. `reason` is passed as typed, never defaulted, padded or retried; the front end asks for the reason and a typed confirmation before each call and never retries a write.
- **The call.** The subprocess is started with an argument list, never a shell (`shell=False`), the book token and the reason each as its own argument in `--book=<token>` / `--reason=<text>` form, the reason capped at `webapp.max_reason_chars` (default 500) and refused empty before anything runs; the CLI's own checks (the token grammar, the blank-reason usage error) run after, as they do at the desk.
- **Results.** Exit 0 is 200 with the command's text and the book's new summary, read after the subprocess exited; if that read meets `store_busy`, the answer is still 200 with the outcome and no summary, never a failure of a write that succeeded. The CLI's `PAPER_REFUSAL_EXIT` codes map one to one: `refused` (4; a resume refused by a verdict, or for want of an accept flag that only the desk may pass) is 409 with the refusal text; `locked` (5; a run holds the book, or the store is locked past the retry) is 409 `locked`; `no_window` (6) is 404; a usage error (exit 2: a bad book token, a blank reason) is 422; any other non-zero exit is 500 with the scrubbed text. **Every non-200 from `/kill` and `/kill-all` says on the screen, in the owner's words, that the kill switch is NOT engaged for that book**, whatever the cause (`KillWriteFailed`, a clock error, `multiple_open_windows`, a schema refusal); a `kill-all` result lists it per book. A client that disconnects mid-request does not stop the subprocess: it runs to its own end and its outcome is read from the journal on the next poll.
- **Concurrency and time.** A kill is **never refused, queued or made to wait** because a resume is running, on the same book or another: at the desk `paper kill` takes no lock and engages mid-resume (and `switch.release`'s `seen_event_id` check then stops that resume from releasing), and the web kill behaves the same. The one-slot-per-book rule covers resume only: a second resume on a book while one runs is 409 `busy` at once; a resume is never terminated by the API, whatever its length (its broker calls and its run lock are its own). A kill subprocess is waited for up to `webapp.kill_wait_seconds` (default `store.lock_retry_seconds` plus a margin, so one write-chunk retry fits); past that the API answers 504 and the screen says the kill is **NOT confirmed** and shows the switch state from the next poll, which is the journal's truth; the subprocess is still not terminated. A kill or a kill-all **never takes or waits on the API's read gate**: it is started at once, and a read that happens to overlap its write chunk sees `store_busy` for that moment instead, while the kill's chunk retries around the read as `open_for_write` does for any CLI kill. `kill-all` follows the kill rules for every book. The API process holds no run lock and no write connection, ever.
- **No order placement from the UI, ever**, and no path to one: `tradepartner.webapp` imports nothing from `tradepartner.cli`, `execution.run`, `execution.phases`, `execution.wrapper`, `execution.brokers` or any adapter, pinned by its own AST test; `tests/execution/test_boundaries.py` checks 1 to 3 (no broker import outside `execution/`, no `.submit(` call outside `execution/wrapper.py`, spec req 3) scan every module under `src/` and apply to the package unchanged, with no allowlist entry. The API process never constructs a broker and never uses a paper key: `Settings` loads them like every command's does, and the only process that touches Alpaca is the resume subprocess. A screen that wants a "trade" button wants a new ADR.
- **Origin.** A write is accepted only with a same-origin `Origin` header and the custom request header `X-TradePartner-Action`, so a cross-site page on the owner's browser cannot post it (a browser cannot add a custom header cross-origin without a preflight, and the API answers none); on the tailnet port (section 4) it must also carry the owner's identity.
- The override form (spec req 9, `exclude_name` and the rest) is **not** an API write in this record; it stays on Streamlit (section 5, open question 3).

### 3. The front end: React + TypeScript on Vite, in `webapp/`, served by the API

**Options.** (a) **React + TypeScript via Vite** (all MIT): the largest pool of headless components and charting bindings, TypeScript types generated from OpenAPI, the stack the owner's HTML/CSS design ports to as components with the same markup and CSS variables. (b) **SvelteKit**: less code per screen and a smaller bundle, but its router and server side are made for a Node host we do not want, and the headless and charting ecosystem is thinner. (c) **Server-rendered HTMX + Jinja from FastAPI**: no Node toolchain at all, one language, and the API could render HTML fragments; but crisp financial charts and dense sortable tables need client code anyway, the owner's design would become templates, and phone interactions (crosshairs, drill-down) are poor with partial page swaps. (d) Vue (FreqUI's choice): fine, but nothing in it beats (a) for this owner's design and the generated-types workflow. **Recommended: (a)**, unless the owner's design is already written in Svelte or Vue (open question 1).

**Where and how.**
- The front end lives in **`webapp/`** at the repo root (rotki's `frontend/` shape), with its own `package.json`, `pnpm-lock.yaml`, `tsconfig.json`, `vite.config.ts` and tests; nothing under `src/tradepartner/` imports it. `pnpm build` writes to `src/tradepartner/webapp/static/` (gitignored, never committed: a built bundle in a public repo is churn and an unreviewed binary), and `tradepartner web` serves it with FastAPI's `StaticFiles` **on the same port as the API** (freqtrade's shape): one origin, no CORS, one port per listener for Tailscale Serve. With no build present the command serves the API and a one-line page saying how to build. `pnpm dev` runs Vite with a proxy to the API for hot reload.
- **Toolchain beside uv.** Node pinned in `.node-version` (the LTS line current when the plan starts: 24, or 26 once it is LTS; open question 6) and pnpm pinned in `package.json`'s `packageManager` field, as FreqUI does; `uv` stays the only Python tool (ADR 0001). CI gets **one extra job**, path-filtered to `webapp/**` and the lockfile: install from the lockfile, `pnpm lint`, `pnpm typecheck`, `pnpm test`, `pnpm build`, about two minutes; the Python shards are unchanged and the API's contract tests are pytest. Pre-commit runs the front end's formatter only on `webapp/` files. No Node is needed to run the tests of anything under `src/`.
- **Charting and component foundation.** Charts are built on **TradingView's `lightweight-charts`** (Apache-2.0; its NOTICE requires the attribution notice and a link to tradingview.com on the page, which the library's `attributionLogo` option draws on the chart), a canvas library made for financial time series (line, area, baseline, candlestick, histogram) with a financial time scale and a crosshair, a few tens of kilobytes, no dependencies. A general-purpose library (Plotly, which the Streamlit pages use; ECharts, FreqUI's; Recharts) is rejected for the time series on size and on the financial time scale, not on features: each is several times the bundle, and the terminal look the owner wants is lightweight-charts' default. Linking crosshairs across charts is hand-wired (`subscribeCrosshairMove` to `setCrosshairPosition`), a few lines. Bars, gauges and sparklines are small SVG components over the tokens; a second charting library enters only when a chart needs one, by a plan line. Components are **headless primitives** (Radix Primitives, MIT, or React Aria, Apache-2.0, for menus, dialogs, tabs; TanStack Table, MIT, for the dense tables; vitest, MIT, for tests), styled only by **design tokens** the owner's design defines as CSS custom properties in one file (`webapp/src/tokens.css`: colour per role, the type scale, the standard's 8 px grid with 4 px half-steps, radii, the dark theme first and the light one from the same hues), so the polish comes from tokens the owner sets, not from a themed kit (no MUI, Ant, PrimeVue or Material) whose look would have to be fought. The design standard's token table moves to that file when the last Streamlit page retires; until then the three copies (`theme.py`, `.streamlit/config.toml`, `tokens.css`) are accepted, with a test that the shared roles agree. ADR 0004's adopt table gains these rows (Consequences).
- The screens are the owner's: this record fixes only that each screen is a function of one or two API resources, works at phone width (16 px gutters, no horizontal scroll, the standard's rule), and reads `as_of`, `last_ingest`, `last_run` and `stale` from the envelope into the header.

### 4. Phone access and security: loopback by default, the owner's tailnet on its own port, identity required there, no secret in the browser

**Options.** (a) **Tailscale Serve** (`tailscale serve --bg --https=443 localhost:<port>`): tailscaled on the Mac terminates HTTPS with a tailnet certificate and proxies to a loopback port, reachable only from devices on the owner's tailnet, and adds `Tailscale-User-Login`, `Tailscale-User-Name` and `Tailscale-User-Profile-Pic` to requests it proxies for a tailnet user (its docs; a tagged device's request carries none, and Funnel, the public variant, is never enabled). (b) Bind the API to the Mac's Tailscale IP and reach it by IP: no HTTPS, no identity headers, and a bind address other than loopback, which rule 1 refuses. (c) A password or JWT like freqtrade: a credential that lives in the phone's browser and in `.env`, for an API that is never on a network a stranger can reach; it adds a secret to rotate and nothing the tailnet does not already prove. (d) Expose Streamlit over the tailnet: ADR 0011's reasons stand. **Recommended: (a)**, with (c) available later as a second factor (open question 5).

**Rules.**
- **Two loopback listeners, one process.** The **desk port** (`webapp.port`) is for the browser on the Mac: a request that reaches it is a process on the Mac, the charter's trust boundary. The **tailnet port** (`webapp.serve_port`, off unless set) is the only target Serve ever proxies to, and on it **every request, read or write, must carry `Tailscale-User-Login` exactly equal to `webapp.owner_login`**, else 403; a missing header is 403; **an unset `webapp.owner_login` is 403 for every request on that port** (fail closed, never "check it if set"). A Funnel or a tagged-device request, which carries no identity, is refused on that port by that rule, so a wrong `tailscale funnel` by mistake exposes a 403. Both listeners check `Host` against `localhost`, `127.0.0.1` and the configured `webapp.tailnet_host` and answer 421 otherwise, which also closes ADR 0011's accepted DNS-rebinding risk. The identity rule rests on tailscaled setting the headers on what it proxies and overwriting any the client supplied; that is what its docs say and the spike verifies it (section 7), including which `Host` the proxied request carries. The keys `webapp.owner_login` and `webapp.tailnet_host` are set only in `.env` (`WEBAPP__OWNER_LOGIN`, `WEBAPP__TAILNET_HOST`, the `Settings` nesting delimiter), never in the repo, and both join the scrub set: no response body, 403, 421 or log line ever echoes them or any `Tailscale-*` value.
- **Reads from a hostile page.** Any request whose `Sec-Fetch-Site` header is present and not `same-origin` or `none` is refused before the store is touched, so a page in the owner's browser cannot loop `no-cors` reads against the store; the gate of section 1 bounds what it could hold in any case. The runbook records the Serve commands (`serve --bg …`, `serve status`) and that `tailscale funnel` is never run on this Mac.
- **No secret is ever served.** The API has no endpoint that returns `Settings`, and every error message runs through the CLI's scrubber (`_scrubbed`) before it is serialised, as the `paper` commands' do; a test runs every endpoint, including the writes' failure paths, with sentinel key values in the fixture settings and asserts no response, header or log line contains one. The browser holds no token, key or password; a lost phone is a device removed from the tailnet in the admin console, nothing to rotate in `.env`.
- Telemetry: none; the bundle calls no third-party host, pinned by a test over the built assets (an allowlist of the attribution link and framework namespace constants, every other absolute URL a failure).

### 5. Coexistence with Streamlit, and retirement page by page

**Options.** (a) **Page by page at parity** (this record): each Streamlit page lives until its screen passes four criteria, then goes in one PR. (b) One switch-over when the whole app is done: simpler bookkeeping, but months with the owner on the old pages while the new ones exist, and one large deletion to review. (c) Freeze Streamlit forever as the "research" dashboard: avoids the last deletions, but keeps a second server, port and theme copy for pages the cockpit already covers. **Recommended: (a)**, with (c)'s pages last or never (open question 7).

Streamlit stays the dashboard until each screen reaches parity; the two run side by side on their own ports and both read the store through `open_read_only`, which neither holds. ADR 0011's page-purity rule stays in force for the Streamlit pages while they live, and its localhost bind stays.

**A Streamlit page is retired** (its module, its tests, its navigation entry deleted in one PR, class A unless it touches `cli.py` or config) when all four hold, written in that PR's body: (1) **parity**: every number and status the page shows is on the new screen, from the same reader, pinned by the contract test's mapping (section 6); (2) **used**: the owner has used the new screen for the page's purpose at least once on the real store and says so (a dated line on the PR); (3) **phone**: the screen passes the phone-width check in the front-end tests; (4) **no new write surface**: a page with a write (the override page) is retired only when its write has an API endpoint under section 2's rules, which this record does not grant (open question 3). The order follows the owner's four questions: the operations page and the book overview first (they are what he uses daily), then data health, then the trials, backtest and research pages last or never. The Streamlit dependency, `dashboard/app.py`, `theme.py` and `.streamlit/` go with the last page, in a PR that marks ADR 0011 superseded in full and moves the design standard's token table to `tokens.css`.

### 6. Testing

**Options.** (a) **Contract tests in pytest over the fixture store plus a no-write test**, the front end tested over recorded fixture responses (this record). (b) End-to-end browser tests (Playwright) over a live API and store: closest to the owner's use, but a browser in CI, minutes per run, and the store's behaviour is what the pytest layer already pins; deferred until a screen regresses in a way the unit layers miss. (c) Snapshot tests of rendered HTML only: cheap and brittle, and they prove nothing about the store. **Recommended: (a)**.

- **Contract tests** (`tests/webapp/`): FastAPI's test client over the fixture store (`tests/execution/conftest.py`'s `journal_settings` on a temp-file copy, never the owner's store), one test per resource that validates the response against the models, compares it to the reader's output **through the explicit dataclass-to-model mapping** (the parity test of section 5), checks the read bound of section 1, and pins the generated OpenAPI document to the committed `webapp/openapi.json`. The front end's unit tests (vitest) run over fixture JSON recorded from those same responses, so a screen is tested against the shape the API actually produced.
- **The no-write test.** Every `GET` is run against a fixture store, and the store file's bytes and every table's row count are the same before and after; the `tradepartner.webapp` package imports `open_for_write`, `tradepartner.cli`, the order path and the adapters nowhere (the AST test of sections 1 and 2; `test_boundaries.py` unchanged); the write handlers are run with the subprocess call replaced by a fake that records the exact argv (list form, `--book=`, `--reason=`, the cap), and `/kill` and `/kill-all` once for real as subprocesses against the fixture store (a kill needs no broker), and the rows that appear are exactly those `paper kill`'s own tests expect, no more; `/resume` is not run as a real subprocess in tests, because a child process cannot reach the fake-broker seam (`make_app(broker=...)`), and that seam is never reachable from production argv; a request to any other method or path writes nothing.
- **Boundary tests.** On the tailnet port: no header 403, another login 403, `owner_login` unset 403; on either port a foreign `Host` 421, a cross-site `GET` (by `Sec-Fetch-Site`) refused, a cross-origin `POST` refused, no sentinel secret or `Tailscale-*` value in any response or log line.
- **The locks and the gate.** `store_busy` while another process holds the file for write (the lock tests' pattern) and while the gate is taken; a kill while another process holds a write chunk engages after the chunk or reports NOT engaged; a resume while a run holds the book's lock returns 409 and writes nothing; a second resume on the same book while one runs is 409 at once; **a kill on the same book while its resume subprocess runs is neither refused nor queued, engages, and that resume then does not release**; a kill-all during a resume engages every open book, the resumed one included, and is neither refused nor queued; a kill or kill-all while a read holds the gate is started at once, never 503; a kill past `webapp.kill_wait_seconds` answers 504 "NOT confirmed" and the next poll shows the journal's state.
- The Streamlit pages' headless-render tests stay until their page retires; the retirement PR replaces them with the contract tests of the same cases.

### 7. Validate before building: the spike

**Options.** (a) **One thin slice end to end** (this record): two read resources, one screen, the real phone path. (b) Write the plan from the design alone and let the first task find the problems: cheaper today, and the usual way a wrong stack or a broken phone path is found after three tasks are built. (c) A longer prototype with every screen: proves the design, not the risks. **Recommended: (a)**.

Before any plan task starts, a `spike/webapp-probe` branch (no claim, no PR to merge, thrown away or mined for the first task) builds the smallest slice: `GET /api/v1/books` and `GET /api/v1/books/{book}` over `ops.book_summaries` and `page_data` on a temp copy of the fixture store with an open window, and **one screen**, the owner's "how am I doing / books" design, fed by it, built with Vite + React + lightweight-charts over his tokens file, served by the one process on the desk port and the tailnet port, and reached from his phone through Tailscale Serve.

It must show, in a comment on #1410 with numbers **and with the login, the tailnet and MagicDNS names, every IP and every account id redacted** (the repo is public), before the plan's tasks are claimed: (1) the screen's numbers equal `paper status --all`'s line for the same fixture, by eye and by a test; (2) a request takes the gate, opens the read connection inside the handler and closes it before the response, logged; a `GET` while another process holds the file for write returns `store_busy` and recovers on the next request; (3) the owner's design ported as components and tokens with no markup rewrite, counted (components written, tokens used, lines of CSS changed); (4) the phone reaches the screen over Serve on the tailnet port; the comment records which `Host` and which `Tailscale-*` headers arrived (names, not values) and that a header the client supplied was overwritten; a request with no identity (from a tagged node, or a plain `curl` to the tailnet port on the Mac) is 403; `tailscale serve status` shows no Funnel; a request from another device on the LAN by the Mac's LAN address is refused; (5) `pnpm install && pnpm build` from clean in under two minutes on the Mac, with the bundle size; (6) every request finishes within half of `store.lock_retry_seconds` on the fixture store, and the owner runs the two reads once against the real store, read-only, with `paper run` idle, and records the time. If (2), (4) or (5) fails, the design changes before the plan is written, not after.

## Consequences

- Good: the owner gets the screens he designs, on the phone too, over numbers computed once in `execution` and `store`; the API process never writes, so its reads cannot break a write and the no-write test is a property of the process, not a promise; the two writes are the CLI commands themselves, so `safety-reviewer` reviews one path per action and the screen's kill behaves exactly as the desk's; the network boundary is explicit (loopback, a separate tailnet port that fails closed, `Host` and `Sec-Fetch-Site` checks) and tested, which closes ADR 0011's accepted rebinding risk; the contract is a committed file both sides generate from; the spike bounds the risk before a plan exists.
- Bad / accepted risks: a second language, lockfile and CI job (bounded to `webapp/` and about two minutes); a serialisation layer and the generated types to keep current; six new pure readers and one journal table (the persisted tracking periods) before the first screen is whole, and no tracking periods on the screen until that table exists; three copies of the tokens while Streamlit lives; a server process whose reads, though short and gated, still hold the file for moments the paper run's write chunks must retry around (bounded by the read contract, the poll floor and the gate; the `is_held` instant is accepted as ADR 0011 accepted it); an interpreter start per write click; lightweight-charts' attribution line on every chart page; Tailscale is a third party on the phone path (no data leaves the Mac through it except to the owner's own device, but its outage is a phone outage, and the desk path does not depend on it); the identity rule rests on Serve's documented header behaviour, verified in the spike, not in CI; the owner's design and this stack choice are made before a line of the front end exists, which the spike is for.
- Reversibility: cheap for the API (a thin layer over readers that already exist, plus the new pure ones, which the CLI can use too); moderate for the front end (a framework change is a rewrite of `webapp/`, not of anything under `src/`); the Streamlit pages are not deleted until parity, so the way back exists for as long as the retirement takes.
- **Amendments this record implies, which merge before any `tradepartner.webapp` task is claimed** (the plan's first task, the way ADR 0017's P0 went first): the charter's Interface line ("the only write action is a logged override" becomes "logged owner actions with a reason: the override form, and a book's kill switch engaged or released from the web app through the CLI's own commands"); the roadmap's "User experience" paragraph ("no separate API" becomes "one local read API, writes only through the CLI's commands"); paper spec req 5 ("released only by the owner with `paper resume --reason`" gains "from the desk or from the web app, which runs that command"), req 9 (the override form is the *Streamlit* dashboard's only write), req 10 (`paper report` persists its per-period comparison in a `paper_report_periods` table beside the `paper_reports` row, one additive journal schema version, `quant-auditor` and `safety-reviewer` on that task) and req 16 (the `web` command); a dated pointer on ADR 0011 and on the design standard; ADR 0004's adopt table (FastAPI, uvicorn, React, Vite, lightweight-charts, Radix or React Aria, TanStack Table, vitest, pnpm, with the licences named above); `.env.example` with `WEBAPP__OWNER_LOGIN` and `WEBAPP__TAILNET_HOST` (names only); the scheduling runbook's Serve commands.
- Revisit if: the owner wants a write beyond kill and resume (a new ADR, under the order-path rules); the Phase 6 live book wants the same screens (ADR 0019 says whether a live book's kill and resume go through this API; nothing here lifts the `alpaca.paper` guard); the read contract cannot be met on a long journal (then the readers get bounded or cached in `execution`, never in a route); or the owner wants a second person on the tailnet (identity becomes a list, and an audit row per write).

## Open questions for the owner (one decision each, a recommendation beside it)

1. **Which front-end stack is the design in?** If the `spike/design-ui` work is HTML and CSS with sample data, or React, **recommend React + TypeScript on Vite** (section 3). If it is Svelte or Vue already, say so and that framework takes (a)'s place; the rest of the record is unchanged.
2. **Is the built bundle committed?** **Recommend no**: `pnpm build` locally and in CI, `src/tradepartner/webapp/static/` gitignored, `tradepartner web` says how to build when it is missing. Committing it (freqtrade downloads a release instead) would put a binary blob in every UI PR of a public repo.
3. **Does the override form move to the API now?** **Recommend no**: it stays on Streamlit until the operations screens have shipped and the owner has used kill and resume for real; adding it then is one more subprocess endpoint under section 2's rules, in a one-paragraph amendment, not a new ADR.
4. **May the phone pass `--accept-broker-fills` or `--accept-rejections`?** **Recommend no** (section 2): both stay desk-only CLI flags, and the screen says so when a resume is refused for want of one. The alternative is two strict, required booleans each with its own typed confirmation; it can be added later as an amendment with a `safety-reviewer` pass.
5. **Is Tailscale identity enough, or a passphrase too?** **Recommend identity only** (section 4): the tailnet authenticates the device and the user, the tailnet port requires the owner's login and fails closed, and a passphrase would be a secret in the phone's browser. A second factor can be added later as a `webapp.require_passphrase` key if the owner wants it before the live book.
6. **Node version.** **Recommend the LTS line current when the plan starts** (24 today; 26 if it is LTS by then), pinned in `.node-version`, moved only on a plan line; pnpm pinned by `packageManager`.
7. **Which Streamlit pages move at all?** **Recommend** the operations page, the book overview and data health move; the trials, backtest and research pages stay on Streamlit until the cockpit or a later decision takes them; they are research tooling, not the end-user app.
8. **The overall benchmark on the first tile.** ADR 0005 names SPY and MTUM; **recommend SPY as the tile's comparison and both on the chart**, rebased to the window's start equity, total return, computed inside the system as ADR 0005 requires.
9. **How big is the spike?** **Recommend one team, one working day, Opus, plus about an hour of the owner's** (his design files, his phone, the two `tailscale serve` commands and the one read-only timing on the real store), stopping at the first failed must-show; the spike's report is a redacted comment on #1410, not a document.
