# 0027. An emergency stop that does not need the store: an out-of-store stop marker

**Status:** Proposed  ·  **Date:** 2026-10-28  ·  **Issue:** #2455  ·  **Related:** [#2194](https://github.com/josejuarez96/tradepartner/issues/2194), **Amends:** [ADR 0010](0010-phase-4-risk-rules.md) points 2 and 4 (check order; the switch's definition), [ADR 0018](0018-end-user-web-app.md) section 2 (the dashboard's Stop path)  ·  [ADR 0023](0023-break-first-fast-books-paper-exam.md), [ADR 0011](0011-dashboard-technology.md)

## Context

In plain words: the owner wants a stop that works even when the database is busy or broken. Today it may not.

`paper kill` (`execution/window.py` `kill`, ~1512-1560) engages the kill switch by appending an `engaged` row through `switch.engage`. The switch is derived only from store rows (`execution/switch.py`). Writers wait up to `writer_lock_retry_seconds` = 300 s (`cli.py` ~1625). On 2026-10-28 (#2194 comment) a Data health page render held a read connection for 19 s (47 s with the coverage button). The holds seen are 19-47 s; the 300 s case follows from the code and has not yet been reproduced, so the plan's first task is a drill that does (a held reader, `paper kill`, failing test first, per ADR 0023). Past 300 s of such a hold, `paper kill` prints "NOT engaged" and nothing is stopped. The dashboard Stop button runs the same command as a child (`dashboard/book_actions.py`), so it has the same gap. A run that cannot reach the store raises `StoreLockedError`; its `run_failed` alert write fails too, and only the heartbeat reaches the owner.

## Options considered

1. **Rely on the 300 s wait.** Pro: no change. Con: the failure is silent past 300 s and the wait is itself a delay in an emergency. Rejected.
2. **A second small database for the switch** (a second DuckDB file, or SQLite in WAL mode). Pro: transactional, queryable. Con: a second schema, migrations and backup path for one bit; a second DuckDB file still has DuckDB's single-writer lock and open-and-wait code, and SQLite adds an engine the repo does not use. Rejected.
3. **Raise the wait or hold fewer reads (the #2194 fixes).** Pro: removes the known cause. Con: a stop would still depend on the store whenever anything else holds it (backup, ingest, a crash). Kept as separate work, not a substitute.
4. **The broker's own cancel-all or account block.** Pro: store-independent. Con: needs the network and keys at the worst moment, does not stop our next run, and ADR 0010 keeps the broker behind the wrapper. Kept as a manual last resort, not the stop.
5. **A marker file outside the store, checked before the store** (this record). Pro: creating a file needs no lock; one syscall; works with the store down. Con: a second source of truth that must be reconciled (below).

## Decision

**1. The marker.** A stop marker is an empty-or-JSON file at a path from config (`execution.stop_marker_dir`, default beside the store, on the same volume). Two forms: `STOP.<book>` per book and `STOP.ALL` for all books. The JSON body holds `at` (tz-aware UTC), `source` (`cli`, `dashboard`), `reason`. Nothing in it is a secret.

**2. Engaging.** `paper kill` creates the marker FIRST, even for a book with no open window (see 7), atomically (`O_CREAT|O_EXCL` on a temp name in the same directory, then `rename`, then fsync the directory; already present counts as success), fsyncs, and only then tries the store row as today. It prints which of the two succeeded. If listing the open books outwaits the store wait, `kill --all` still exits 0 with `STOP.ALL` written (ADR 0018's exit 5 and the webapp's 409 mapping change accordingly). If the marker write fails (unwritable directory, full disk) it still tries the store row, and is "NOT engaged" (non-zero) only when both fail. Exit is zero if the marker exists, even when the store write failed ("STOPPED by marker; store row pending"). `paper kill --all` writes `STOP.ALL`.

**3. Checking, fail closed.** Every paper run and submit path checks the marker (its book's and `STOP.ALL`) BEFORE opening the store and BEFORE building a broker client or contacting the broker. A marker present means no order is created, amended or submitted, and the path exits with a new code `PAPER_STOPPED_BY_MARKER` (the next free code, 7; added to `PAPER_REFUSAL_EXIT`; the scheduler and runbook treat it as a stop, not a crash, and do not retry it; a mid-run stop ends `skipped_kill_switch`, exit 0, as today) and a `stopped_by_marker` message. **In a run already going**, every switch read (each phase boundary and each submit, ADR 0010 point 2's re-read) ORs the marker and ends the run `skipped_kill_switch`. **A marker refuses creates and submits, never a cancel or a halt's risk-reducing step**; `paper kill` itself cancels nothing today (it only appends the row), and that does not change. `paper resume` and read-only commands run with a marker present. A marker directory that cannot be read (permission, I/O error) is treated as a marker present. A missing directory is created at start-up; if it cannot be, the run refuses. The check is a pure function over a path, with the clock and filesystem passed in.

**4. Reconciling with the store.** The store row is still the record. Whenever the store is free, any run, `paper status`, or a small `paper sync-stop` step appends the missing `engaged` row (source `owner`, with `marker_id`; `at` is the marker's time, `known_at` the sync time). Exactly once: `paper kill` stamps the marker's id (its `at`) as `marker_id` on its own `owner` row when it writes one; the key is (`marker_id`, `window_id`) in a new nullable `kill_switch` column (`STOP.ALL` is one marker with one row per book), and sync skips a key already present. Synced rows use source `owner` with `marker_id` set, so the ADR 0017 E.1/E.4 shakedown counts, which read `owner` engagements, are unchanged; so that E.1/E.4 keep working, a scheduled run that finds a marker still tries the store with a short wait (`execution.stop_marker_store_wait_seconds`) and, if it connects, writes its `skipped_kill_switch` run row and syncs the marker; it never builds a broker client or sends an order. Only when the store cannot be reached does it refuse store-free, and that session carries a noted `missed_run` alert, which the plan checks against `execution/shakedown.py` (E.1 alerts only S-1 today). This is a schema change (new column) (the `marker_id` column only; no new `source` value), justified as a trading need (ADR 0023 freezes the schema otherwise) and left to the plan task. The marker is removed ONLY by `paper resume` (or release), and only after the store `released` row is committed and read back; a run, a reader or a sync step never removes it. If the release row fails, the marker stays. `paper resume` first runs the sync (before `resume_invocations`), so a marker-only stop has a row to release; then `paper resume <book>` removes `STOP.<book>`; `STOP.ALL` is removed only by a new `paper resume --all`, after every book's release row is committed or the book was already released after the marker's `at` (so a retry after a partial failure finishes) (`paper resume <book>` under `STOP.ALL` records that book's release and reports "still stopped by STOP.ALL; use resume --all", and leaves every other book stopped). Release keeps every existing gate in `switch.release` (reconciliation, `resume_id`); the marker adds a gate, it removes none. Derived state is "engaged" if the marker exists OR the store says engaged.

**5. Dashboard.** The Stop button calls the same `paper kill` child; it also writes the marker in-process first (same function), so a hung child cannot leave it unwritten. This amends ADR 0018's 2026-10-26 amendment on the Book page Stop (the source of `book_actions.py`'s no-write promise), and covers the future webapp `/kill` and `/kill-all` endpoints and their "NOT confirmed" text: the one exception is the marker file, resolved from `live_settings()` like `store_refusal` resolves the store. The dashboard stays read-only on the store.

**6. Reporting.** A marker with no store row is shown as "STOPPED (marker only)" on the Home and book pages, in `paper status`, and in the heartbeat payload, and raises a `stop_marker_unrecorded` alert through the non-store channels once it is older than a config minutes value (`execution.stop_marker_sync_minutes`). A run refused by a marker emits the heartbeat as stopped, not as failed.

**7. Tamper and stale cases.** The marker is a local file under the owner's account; anyone who can write it can stop trading, and anyone who can delete it can lift a stop. That is accepted: the same person can already edit `.env` and the store. A marker for a book with no open window cannot be recorded (rows need a `window_id`): it stays marker-only, blocks `paper start` for that book, shows as stopped, and does not raise the unrecorded alert; `paper resume --clear-marker` removes it. A deleted marker with an `engaged` store row still stops (derived state is the OR). A marker deleted before any store row exists is lost: mitigated by step 4's early sync and by a `STOP` log line in the run log. A stale marker (older than the store's last release) is not auto-removed; `paper status` flags it ("marker predates release") and `paper resume --clear-marker` removes it with the reason recorded. A marker with an unparseable body still stops (presence is what counts).

**8. What this does not change.** The risk rules in ADR 0010, the drawdown trigger, the release gates, and ADR 0023's break rules and exam are unchanged. No order path gains a way to place an order; the marker only adds a way to refuse one. ADR 0010 point 4's switch definition gains "or a marker" and point 2 gains the marker-first order; nothing else in ADR 0010 moves.

## Consequences

- Good: `paper kill` works with the store locked, absent or corrupt. The stop is one file check before anything else.
- Bad: two sources of truth, a new failure mode (a forgotten marker blocks every run), and a new config. The OR rule and the "marker only removed by resume" rule keep it fail-closed.
- Landing: the check order changes ADR 0010 point 2, so the build lands between windows, not mid-window (open question 5). Backup and restore copy the marker directory with the store.
- Reversibility: cheap; removing the check restores today's behavior.

- Tests: resume of a marker-only stop; partial `--all` retry; a run in progress stops at its next submit when the marker appears; resume works with a marker; `STOP.ALL` clear rule; no-window marker; sync idempotency by `marker_id`; kill with the store locked past the wait writes the marker; a run with the marker opens no store and builds no broker (spy); unreadable directory fails closed; atomic create under a race; sync appends exactly one row; release failure leaves the marker; a run never removes it; stale-marker flag; Stop button path; alert fires. A safety-reviewer pass is required.

## Open questions

1. Where does the default marker directory live? Recommend beside the store file, same volume, with a startup check that it is writable.
2. Should `STOP.ALL` also block read-only commands? Recommend no: only paths that can create, change or send an order, plus resume.
3. Does a marker also cancel open broker orders? Recommend no, in this record: stop first; cancellation stays the existing store-side step, revisited if it too proves store-dependent.
4. How old before `stop_marker_unrecorded` alerts? Recommend 10 minutes.
5. May this land mid-shakedown-span? Recommend no: at a window boundary, owner's call.
