# 0011. Dashboard technology: Streamlit under the design standard, no separate API

**Status:** Accepted (by merging; owner decision on #247 question 1, 2026-09-27)  ·  **Date:** 2026-09-27  ·  **Issue:** #268 (plan task T68)  ·  **Related:** [ADR 0004](0004-tooling-adopt-avoid.md), [ADR 0008](0008-llm-role.md) point 4, [design standard](../design/dashboard.md), [Phase 4 spec](../specs/paper-trading.md) reqs 9 and 12, [Phase 4 plan](../plans/paper-trading.md) T66, T69 and T69b

## Context

The [roadmap](../roadmap.md) fixes two things about the owner's interface: a CLI for jobs and a local dashboard that **reads the same database the system writes to**, with "no separate API, no duplicated logic"; and the dashboard is read-only with one exception, the override screen, whose write requires a reason and is logged. ADR 0004 adopted `streamlit` or `marimo` for the dashboard and left the choice to the Phase 2 plan, which chose Streamlit (T1 adds it, T21a built the shell). Three pages exist on it: data health (T21), backtest (T43) and the trial registry (T44).

The [design standard](../design/dashboard.md) (#165) fixed the look of every page and named one open decision: "whether Streamlit with this standard is enough, or a React front end behind a thin read-only API is warranted, is decided by an ADR at the start of Phase 4, when the operations page (the densest one) is specified". The Phase 4 spec now specifies that page (req 12: header with "as of" and "last updated", four KPI tiles with the kill-switch state as a status chip, the signal ranking as the hero, fills, a journal-chain detail view per order, alerts, reconciliation status) and the override page (req 9: the dashboard's only write, a form appending one `overrides` row through a short-lived write connection, "store busy" when the store is locked, never blocked by a memo). The spec's open question 1 put the choice to the owner with option (a), Streamlit, recommended; the owner accepted it on #247 on 2026-09-27.

Two facts shape the choice. The dashboard is used by one person on one machine, so there is no second client, no concurrent user and no network boundary to design for. And the page logic the spec requires is already specified as pure functions over a read-only connection (`execution.ops.page_data`, T66; `execution.check`, the same task), rendered by thin page modules, so what the page shows does not depend on what draws it.

## Options considered

1. **Streamlit under the design standard** (this ADR). Pages stay pure functions of a read-only connection and a date range rendered inside the shell's one connection per render (T21a); the operations page is `dashboard/ops_page.py` over `execution.ops.page_data`; the override page is a Streamlit form that calls T64b's `override` writer, which opens the store through `store.db.open_for_write` with the lock retry and shows the shell's "store busy" state when the store is held (spec req 9). Pro: no new dependency, no new process, no API to version or secure; the three existing pages, the theme tokens, the Plotly template and the headless-render tests carry over unchanged; the roadmap's "no separate API" rule stands; the one write goes through the same writer the CLI uses, so there is one code path for an override and one place `safety-reviewer` looks. Con: Streamlit re-runs a script per interaction and its widgets are coarse, so the chain detail view and the ranking are tables and cards rather than a bespoke interactive component; the standard's "…" card menu and crosshair tooltips are what Plotly and `st.dataframe` give, not custom controls; the page is only as responsive as a script re-run.
2. **A React front end behind a thin read-only API, plus one write endpoint for overrides.** Pro: any interaction the standard describes can be built exactly; a browser client could be opened from another machine. Con: it duplicates logic the roadmap forbids duplicating (every number would be computed once in `execution.ops` and serialised, validated and rendered again in a second language); it adds an API surface that must be authenticated, bound to localhost and reviewed, and a write endpoint that is a second code path into the override writer; it adds a build toolchain, a second test stack and a second design implementation of the same tokens; it amends the roadmap's rule and the charter's "local, read-only dashboard" wording for no requirement any page has; none of the Phase 4 pages needs an interaction Streamlit cannot draw. Rejected for the MVP.
3. **Marimo** (ADR 0004's other candidate). Pro: reactive notebooks with a dependency graph and no re-run-everything model. Con: the Phase 2 plan already chose Streamlit and three pages, the shell, the theme and the tests are built on it; switching the framework for the fourth page buys nothing the spec asks for and costs a rewrite. Not reopened.

## Decision

We will build the Phase 4 pages, and every later page, on **Streamlit under the design standard**, with **no separate API**.

1. **Pages stay pure.** Every page is a function of a read-only connection and a date range, as the design standard's Streamlit note says (T21a), rendered inside the shell's one connection per render. What the operations page shows comes from `execution.ops.page_data(conn, settings)` (T66), a pure function the CLI's `paper status` shares, so the page draws numbers it never computes. A React choice later would reuse `execution.ops` unchanged; that is why the logic lives there and not in the page module.
2. **The override form is the only write.** It is a Streamlit form on its own page (`dashboard/override_page.py`, T69b) that calls T64b's `override` writer, the same function `tradepartner paper` uses, which appends exactly one `overrides` row through `store.db.open_for_write` with the lock retry from `store.lock_retry_seconds` and returns the shell's "store busy" state when the store is held (spec req 9, acceptance "Overrides"). The form refuses an empty, whitespace-only or too-short reason (the window's frozen `paper.min_override_reason_chars`), refuses with `no_window` when no window is open, and is never blocked by the memo layer (ADR 0008 point 4: it renders with no memo table). No other page, widget or "…" menu writes anything; the design standard's "What stays out" list holds.
3. **The roadmap's rule stands.** "No separate API, no duplicated logic" is unchanged: the dashboard reads the store file directly through short-lived read-only connections, and its one write goes through the store's own writer. No HTTP service, no port and no client other than the browser Streamlit serves to.
4. **The design standard closes its open decision** with a pointer to this ADR; its tokens, layout, components and Streamlit implementation notes are the whole UI contract. Where Streamlit cannot draw a component the standard describes (a custom crosshair, a bespoke card menu), the page uses the nearest Plotly or Streamlit native (the Plotly template's hover layer, `st.dataframe` with its own table view) and the standard is amended by a dated note, not the page.

## Consequences

- Good: Phase 4 adds two page modules and no dependency, process, port or secret; `safety-reviewer` reviews one write path (the writer) whether the override comes from the form or the CLI; the headless-render tests and the no-colour-literal check extend to the new pages as they did to T43 and T44; the operations page's numbers are the same the CLI prints.
- Bad / accepted risks: Streamlit's per-interaction re-run makes the operations page only as quick as `page_data` over the journal, so a large journal may need `page_data` to bound its reads (the alerts list and the chain view are per order, not per window); interactions are limited to what Streamlit and Plotly offer; the dashboard is usable only on the machine running it, which is the charter's "runs locally" constraint, not a loss.
- Reversibility: cheap while pages stay pure. Replacing the renderer means rewriting the page modules, not `execution.ops`, the store or the writer; the override write would become an endpoint calling the same writer.
- Revisit if: a page needs an interaction Streamlit cannot draw and the standard cannot be amended around it; the owner wants to open the dashboard from a second machine (a network boundary appears, and an API with authentication becomes a real requirement rather than a duplication); `page_data` over a full paper window renders slower than a script re-run tolerates and bounding the reads is not enough; or Streamlit's licence or maintenance changes (ADR 0004's revisit rule).
