# 0007. Clock failures take the halt path, never the rejection path

**Status:** Accepted  ·  **Date:** 2026-09-25  ·  **Issue:** #64

## Context

Two different faults on the order path raise the same `ValueError` today ([adapters/broker.py](../../src/tradepartner/adapters/broker.py), T20):

- a **bad request**: quantity, price, side, symbol or `client_order_id` fails validation in `OrderRequest.__post_init__`. This is raised **when the caller builds the request**, before `Broker.submit` is called; a frozen `OrderRequest` that exists is valid.
- a **bad clock value**: the injected clock returns a naive `datetime`, or one that overflows once normalised to UTC. `FakeBroker` passes the raw value to `Order(submitted_at=...)` in `submit` and to `Fill(filled_at=...)` in `simulate_fill`, and `ensure_tz_aware_utc` ([timeutil.py](../../src/tradepartner/timeutil.py)) raises `ValueError` naming the field (#43; tests in #57 / PR #63). So the only `ValueError` that `submit` itself raises today comes from the clock.

Both are `ValueError` because `ensure_tz_aware_utc` validates a value without knowing where it came from, and #43 deliberately gave callers one exception type for an invalid value. That is correct for a validator. It is not enough for the layer that will sit above the broker.

[ADR 0003](0003-data-adapters-local-first.md) rule 7 puts every risk rule in a **risk-gated wrapper** around `Broker` (position limits, kill switch, idempotency), built in Phase 4 ([roadmap](../roadmap.md)). That wrapper has to decide, per exception, whether to **reject** one order and carry on with the rebalance, or **halt** the run. If it maps `ValueError` to "rejected", a broken clock is handled as a routine rejection, the rebalance continues, and every timestamp the run writes afterwards is wrong: `submitted_at` and `filled_at` on orders and fills, the `known_at` of anything journaled, the missed-rebalance detection of [ADR 0006](0006-universe-and-cadence.md), and the idempotency window a real adapter dedupes against. A clock that is **well-formed but wrong** (stuck, skewed, a frozen test clock left in, a 1970 value) does the same damage and raises nothing at all. A wrong clock is a fault in the **system**, not in one order. Development-process rule 7 ("rules before money") says the kill switch and its triggers are written down before paper trading; this is one of those triggers, and it was raised by `safety-reviewer` on PR #54 ([#57](https://github.com/josejuarez96/tradepartner/issues/57) item 2, split into #64).

This ADR decides **what enters the halt path** and the minimum a halt means. Everything else about halting (whether the kill switch persists across runs, cancelling or leaving open orders, alerting, how the owner resumes) belongs to the Phase 4 execution spec, and nothing here pre-empts it. No Phase 2 code changes.

## Options considered

1. **Keep one `ValueError`; the wrapper reads the message or field name to tell the causes apart.** Pro: no interface change. Con: string matching on an error message is exactly the kind of implicit contract that a later refactor breaks silently; a real broker adapter raises its own exception types anyway, so the wrapper would need a second mechanism for those.
2. **(a) A distinct exception type for clock faults**, not a `ValueError` subclass, raised by the broker and mapped by the wrapper to the halt path. Pro: explicit, typed, testable; survives adapter swaps because the type lives in shared code every adapter imports. Con: on its own it still lets a bad clock reach the broker, it catches only malformed values, and it still needs a rule for exceptions nobody anticipated.
3. **(b) Check clock health in the wrapper before `submit` is called**, so a bad clock never reaches the broker. Pro: catches the fault before the first order of a run, and is the one place that can check plausibility, because the wrapper has the calendar and the store. Con: a clock can go bad between the check and a `submit` (a run places many orders), and a real adapter may source timestamps from the broker, outside the pre-check's reach.
4. **Both (a) and (b), under a fail-closed default: rejection is an allowlist, everything else halts.** Pro: the pre-check catches the common case, including wrong-but-valid clocks, before any order; the typed exception names the fault when it happens anyway; the allowlist means an exception nobody classified cannot fall into the rejection path by accident. Con: slightly more interface surface; a run halts on faults that a more permissive design would skip past.

## Decision

We will take option 4.

1. **Two paths, and the rejection path is an allowlist.** The Phase 4 wrapper treats an exception from a `Broker` call as a per-order **rejection** (journal it, continue the run) only if it matches the allowlist. The rule, precisely:
   - The allowlist is **one frozen constant in code**, never config or anything changeable at runtime. A test asserts its exact contents, so any change shows up in review; adding a type to it is a `safety-reviewer` change.
   - Only `Exception` subclasses are classified. `BaseException` (`KeyboardInterrupt`, `SystemExit`) propagates untouched and is never a rejection.
   - `SystemFaultError` (point 4) is checked **first** and always halts, even if a class also inherits from an allowlisted type. Then the exception is matched by `isinstance` against the constant. **Everything else halts**: `ValueError`, adapter transport errors, anything not on the list.
   - The rule covers **every** `Broker` method, not only `submit`. Each method has its own allowlist, **empty by default**; `cancel`'s `UnknownOrderError` and `OrderNotOpenError` are classified by the Phase 4 spec like any other candidate.
   - The allowlist starts **empty**. The per-order outcomes a real adapter reports (not tradable, insufficient buying power, market closed) are **candidates the Phase 4 spec evaluates one by one**, each admitted through a reviewed edit. Some are systemic in disguise: "market closed" on a scheduled run is a calendar or scheduling fault; "insufficient buying power" can mean local and broker state have drifted, or that buys depended on a sell that was itself rejected.
   - **Many rejections are a fault.** A run halts when its rejections exceed a per-run cap from config (proposed key `exec.max_rejections_per_run`), and always when every order in the run was rejected. A systemic fault that shows up as a string of per-order rejections must not become a silent missed rebalance.
2. **What a halt is, at minimum.** After the exception the wrapper makes **no further `submit` call in this run**, the exception **propagates to the caller** (never swallowed or converted into a rejection), and the fault is journaled with its type. The Phase 4 spec owns everything beyond that: whether the kill switch persists across runs, cancelling versus leaving open orders, alerts, and resume. One constraint on the spec: for a real adapter, an order whose `submit` raised a non-allowlisted exception is in an **unknown state, not absent** (the broker may have accepted it before the failure), so the halt path reconciles it before any resume.
3. **A duplicate `client_order_id` is a third outcome, idempotent replay, not a rejection.** On `DuplicateClientOrderIdError` the wrapper fetches the existing order. If **every** field matches the request, it adopts that order as this order's outcome and journals it as a replay. If any field differs, or the fetch fails, it **halts**: a duplicate id with different fields is an id-generation bug, and an unfetchable duplicate is an unknown state. This needs either a `Broker.get_order(client_order_id)` method or the existing `Order` attached to the exception; the Phase 4 spec chooses. Crash recovery through replay assumes `client_order_id` is **derived deterministically** (for example from the rebalance session, symbol and side), never a fresh random id per run; the spec owns that derivation.
4. **Clock faults get their own type.** `class SystemFaultError(Exception)` and `class ClockError(SystemFaultError)`, neither a `ValueError` subclass. `ClockError` is importable by every adapter; the base class may live in a neutral module (for example `tradepartner/errors.py`) if the Phase 4 spec adds non-broker members (reconciliation mismatch, stale data), so every fault shares one halt mapping. The Phase 4 plan fixes the module. Every adapter **wraps its clock call**: it calls the clock, immediately passes the result through `ensure_tz_aware_utc(..., field_name="clock")`, and turns **any** exception from the call or the validation (the clock raising, a non-`datetime` return, a naive value, a UTC overflow) into `ClockError` chained from the original, **before** any `Order` or `Fill` is built and before any state changes. `ensure_tz_aware_utc` is unchanged and keeps raising `ValueError`: it validates values, and #43's "one exception type for an invalid value" still holds for it. The distinction is made at the call site that knows the value came from a clock.
5. **Clock health is checked before the first `submit` of a run, and plausibility is part of it.** The wrapper and the adapter are built with the **same clock callable** at composition time (a test checks they hold the same object; the `Broker` ABC exposes no clock). Before any order the wrapper reads that clock and raises `ClockError` unless the reading is (a) well-formed per `ensure_tz_aware_utc`, and (b) **inside a bounded window around the scheduled session**: not earlier than the last committed ingestion run and not later than the end of the next XNYS session are the proposed bounds; the Phase 4 spec fixes them and their config keys per CLAUDE.md. During the run, (c) every further reading the wrapper takes must be **no earlier than the previous one**, or it halts with `ClockError`. Well-formedness is checked in both places; plausibility and monotonicity live in the wrapper, because it is the layer with the calendar and the store.
6. **A `ValueError` from building an `OrderRequest` also halts.** The wrapper builds and validates every request of a run **before it submits the first one**; a request our own code cannot construct is a bug or a data fault, not a broker rejection. This is narrower than #64's framing of a bad request as a "normal rejection": that framing describes the broker's view, and the allowlist in point 1 is what keeps the two views from being confused.
7. **Where it lands.** Two Phase 4 plan tasks, the second depending on the first:
   - **Task A, broker types:** `SystemFaultError`, `ClockError`, the clock wrap in `fake_broker.py`, and tests extending #63's: a clock that returns a naive value, an overflowing value, a non-`datetime`, or raises, makes **`submit`** raise `ClockError` (not `ValueError`) with no order recorded and the `client_order_id` reusable; and makes **`simulate_fill`** raise `ClockError` with the order unchanged and still `OPEN`, no fill recorded and positions unchanged.
   - **The wrapper task** carries, as acceptance criteria: `ClockError` takes the halt path; an exception of an unknown type takes the halt path; the allowlist constant's exact contents are pinned; an identical duplicate is a replay and a differing one halts; the per-run rejection cap halts; the pre-check (a)–(c) halts; wrapper and adapter share one clock object.
   Until Task A merges, `FakeBroker` keeps raising `ValueError`, and nothing consumes it as a rejection because no wrapper exists.

## Consequences

- Good: a broken clock cannot be mistaken for an order rejection; the classification is a type, not a string; an exception nobody thought of halts instead of slipping through; a systemic fault disguised as many rejections halts too; the same contract binds the fake broker and the real adapter, so the paper-to-live swap cannot lose it (ADR 0003 rule 7).
- Bad / accepted risks: the wrapper halts on more conditions than a permissive design would, so some runs stop where a skip might have been fine; that is the intended trade at this scale (monthly rebalance, one owner, a logged missed rebalance is already an accepted event per ADR 0006). A halt mid-run on a real adapter leaves orders in an unknown state until reconciled, which the Phase 4 spec must design before paper trading. The plausibility bounds can produce false halts if ingestion and trading drift apart in time; the bounds are config so they can be widened with a reviewed change.
- Reversibility: cheap before Phase 4 (this is a contract with no implementation yet); moderate after, because the wrapper's tests encode it.
- Revisit if: the Phase 4 spec chooses to source order timestamps from the broker rather than a local clock (the pre-check then covers less and the typed exception carries the load); paper trading shows halts from clock or rejection-cap rules that were in fact benign; or a real adapter cannot distinguish a clock fault from a transport error.
